# PR-1 准入门槛验证 · 结果

spec：`docs/specs/core/tool-catalog-proxy.md`（用户已批准）
问题：**模型仅凭紧凑签名（目录条目）构造的参数，能否被真实 MCP 服务器接受？**

- 模型：`deepseek-flash`（网关 `WAVE_MODEL`）
- 判定方：**严格 MCP server**（`server.mjs`），只有它接受才算成功
- 每次运行 = 独立 Agent 会话 + 隔离 `HOME`；180s 超时；并发 6
- 原始产物：`/tmp/cpp-run1/{runs,server-calls}-<tag>.jsonl`（每轮/每次叶子调用）、`analysis-<tag>.json`；本目录 `results/` 存了 4 份 `analysis-*.json` + `catalog-size.json`

---

## 一、结论：**达标（通过准入门槛）**

| 组                       | 工具暴露                                                               | 首次成功       | 重试后  | 叶子调用次数   |
| ------------------------ | ---------------------------------------------------------------------- | -------------- | ------- | -------------- |
| `flat`（对照，完整链路） | 3 个工具**逐条声明**（完整 JSON Schema）                               | 120/120 = 100% | 120/120 | 120            |
| `catalog`（实验，转发）  | 同样 3 个工具只作目录条目，挂在**一个 `ToolInvoke`** 的 description 里 | 120/120 = 100% | 120/120 | 120（1.00/轮） |

规模：3 档复杂度 × 20 次 × 2 轮 × 2 组 = **240 轮**，`infraErrors=0`、`timeouts=0`、`retried=0`、**全部 5 个失败分类均为 0**。

| 达标线（用户给定）     | 实测  | 结果 |
| ---------------------- | ----- | ---- |
| 转发组首次成功率 ≥ 90% | 100%  | ✅   |
| 与对照组差 ≤ 5pp       | 0.0pp | ✅   |
| 缺必填类 ≤ 5%          | 0%    | ✅   |

三档逐档（`analysis-r1-en.json` 的 `byTool`）也都是 40/40 = 100%，`delta=0`：简单（2–3 个必填标量）、中等（嵌套对象 + 枚举 + 默认值 + 可选/必填混合）、复杂（2128 字符长描述 + 嵌套数组 + 多枚举 + 默认值）。**结论对复杂度不敏感。**

**没有触发任何退化/扩量分支**：结论远离 85%–92% 的模糊带（100%），因此按「接近达标线才扩量/换模型」的规则不再加量、不换模型。

## 二、判别力证明（消融实验：`--signature none`）

100% vs 100% 本身**证不了**目录签名有用（可能是任务太简单）。因此加了消融臂：`catalog` 组但目录条目**只留工具名 + 描述、删掉签名**（`--signature none`，30 轮）。

| 指标         | 有签名（r1-en catalog） | 无签名（ablate-nosig）                            |
| ------------ | ----------------------- | ------------------------------------------------- |
| 首次成功率   | 100%                    | **33.3%**（simple 100% / medium 0% / complex 0%） |
| 失败分类     | 全 0                    | `MISSING_REQUIRED = 20`                           |
| 重试后成功率 | 100%                    | 100%（靠 server 报错反馈逐步补齐）                |
| 每轮叶子调用 | 1.00                    | **4.07**（中位 4，最多 8）                        |
| 中位耗时     | 12.0s                   | 30.8s                                             |
| 叶子调用总数 | 120                     | 122（30 轮）                                      |

失败样例原始参数（`results/analysis-ablate-nosig.json` 的 `samples`，12 条）显示两类错法：①**猜字段名**——`compose_config` 传 `{"service":"web-gateway","platform":"macos-arm64"}`（真名是 `name` / `target{os,arch}`）；②**猜结构**——先把 `target` 传成字符串 `"??"`，再补成 `{}`，再被枚举打回。

⇒ 两点可写进 spec 的口径修订建议：

1. **签名确实在承载信息**，不是装饰。
2. **验收指标必须是「首次成功率」**：server 的报错信息足够详细，模型总能靠重试补上（`eventuallyRate` 100%），所以「重试后成功率」区分不出两组，只有首次成功率 + 叶子调用次数能。

## 三、退化形态（`args` 改 JSON 字符串）· 不用上第二跳

用户给定的第一顺位退化验证，作为附加臂跑了 30 轮（`--argsMode json-string`，`args` 声明为 string，模型自行序列化）：

| 形态                        | 首次成功率   | 重试后 | 每轮叶子调用 | 中位耗时 |
| --------------------------- | ------------ | ------ | ------------ | -------- |
| `args: object`（主臂）      | 100%         | 100%   | 1.00         | 12.0s    |
| `args: JSON 字符串`（退化） | 30/30 = 100% | 100%   | 1.00         | 11.8s    |

该模型两种携带形态等价，**不需要第二跳**（`args` 保持对象即可；字符串形态作为备选保留）。

## 五、目录体积实测（`estimateTokens`，非 chars/4）

`measure-tokens.mjs` 起真 Agent、从容器里取**真实内置工具 config**（25 个）。

### 5.1 内置工具全量逐条声明

| 口径                                   | tokens     |
| -------------------------------------- | ---------- |
| 静态 description                       | 11,511     |
| 经 `prompt()` 动态覆盖后的 description | **28,235** |

`prompt()` 覆盖使声明体积膨胀 **2.45×**——这是目录设计与预算必须知道的（见 spec 缺口 ③）。

### 5.2 典型池（25 内置 + 3–5 MCP）

| 池                | flat（ext=json） | flat（plain） | 目录  | 压缩比（json / plain） |
| ----------------- | ---------------- | ------------- | ----- | ---------------------- |
| en，+5 MCP（30）  | 14,300           | 7,150         | 3,266 | **4.38× / 2.19×**      |
| en，+10 MCP（35） | 15,690           | 7,845         | 3,621 | 4.33× / 2.17×          |
| zh，+5 MCP（30）  | 13,749           | 7,182         | 3,298 | **4.17× / 2.18×**      |
| zh，+10 MCP（35） | 14,966           | 7,870         | 3,646 | 4.10× / 2.16×          |

MCP 部分单独看（en，5 个）：2,790 → 888 tokens（3.14×，558.0 → 177.6 tokens/tool）。

**中文 vs 英文**：中文池目录 3,298 vs 英文 3,266（**+1.0%**，因为 CJK 约 1 token/字，英文约 0.25），压缩比 4.17× vs 4.38×——中文略差但同量级。描述字符数：en `{82, 86, 2128}` vs zh `{27, 23, 731}`。

**只算内置工具（不含 MCP）的目录 = 2,383 tokens。**

### 5.3 截断触发点（按预算找「第一个 MCP 工具开始 PARTIAL」）

| 预算      | en 密排 | en 分片命名空间 | zh 密排 |
| --------- | ------- | --------------- | ------- |
| 2,000     | **1**   | 1               | 1       |
| 3,000     | 9       | 9               | 9       |
| 4,000     | 23      | 23              | 23      |
| **6,000** | **50**  | **50**          | 51      |
| 8,000     | >60     | >60             | >60     |

（「密排 vs 分片命名空间」两种工具分组形状的曲线几乎重合，说明截断点由条目体积决定，不由命名空间结构决定。）

### 5.4 描述裁剪的效果（弱杠杆）

en 典型池目录 3,266 → 200 tokens 上限 2,793（−14.5%）→ 120 上限 2,713 → 60 上限 2,653。zh 同样量级（3,298 → 2,796 / 2,716 / 2,657）。

**裁剪规则应按 token，不按字符**：预算本身是 token 计价的；同一信息量的中文描述约 1 token/字、英文约 0.25 token/字，按字符裁会让中文实际被砍掉 4 倍的信息。且裁剪只是 13%–15% 量级的杠杆，不值得为它引入第二套单位。

## 六、预算默认值建议：**6,000 tokens**（替换借来的「8000 字符 / 2000 est token」）

推导：

1. **2,000 不可用**：光内置工具的目录就是 2,383 tokens，2,000 会让目录在**第一个 MCP 工具处就 PARTIAL**——用户一挂 MCP 就看到 `PARTIAL - X of Y shown`，等于把「有界」做成了「默认残缺」。
2. **3,000 太紧**：PARTIAL 起于 9 个 MCP 工具（真实 MCP server 很容易超过，如 github 单个 server 就 20+ 工具）。
3. **6,000 覆盖典型部署且留余量**：内置 2,383（2.5× 余量）、典型 5 MCP 池 3,266（**1.84× 余量**）、10 MCP 池 3,621（1.66×）；PARTIAL 起于 ~50 个 MCP 工具。
4. **它始终比被替换的东西便宜**：6,000 < 该池的 plain flat 声明 7,150（2.2×），更远低于 ext=json flat 14,300（4.4×）与内置工具裸声明 11,511。
5. 超过 6,000 才截断的场景（>50 MCP 工具）正是 `ToolSearch` 存在的理由，符合 spec「常驻有界 + 超出可搜 + 截断显式」。

（3,000 可作为「省 token 优先」的备选档，代价是 PARTIAL 提前到 9 个 MCP 工具。）

## 九、保真度欠账（结论必须连同这些一起读）

1. **`catalog` 组的叶子调用不走 `mcpManager.executeMcpTool`**（叶子在该组被 `disallowedTools` deny 以模拟「已连接但未声明」，deny 会连带拒绝执行路径），改由探针自己的极简客户端发到**同一个严格 server**。参数校验语义完全一致，「参数能否被接受」的结论不受影响；受影响的是**生产派发路径**，由后续 PR 的集成测试覆盖。
2. **`flat` 组走完整生产链路**（SDK 循环 + SDK MCP 客户端），是真对照。
3. **目录渲染器是本目录的一次性实现**（PR-2 用正式模块替换）：签名规则 = 类型 + 必填/可选 + 枚举值 + 默认值 + 两级嵌套展开。渲染越保守结论越强，`maxDepth` 是可调旋钮。
4. **`prompt()` 动态描述不参与目录条目**（见缺口 ③）。

## 十、本次验证暴露的 spec 缺口（**未改 spec，仅列出**）

| #   | 缺口                                                                                                                        | 证据                                               |
| --- | --------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| ①   | **常驻预算默认值（现写 ≈2000 est token / 8000 字符）不可行**：内置工具目录本身 2,383 tokens 即超                            | `results/catalog-size.json`；本文 §5.3             |
| ②   | **验收指标未定义**：「成功率」需明确是**首次成功率**（server 报错反馈能让模型重试成功，`eventuallyRate` 恒 100%，无区分力） | §2 消融臂：首次 33.3% vs 重试后 100%               |
| ③   | **目录条目用静态 description 还是 `prompt()` 动态 description 未定**；两者体积差 **2.45×**（11,511 → 28,235）               | §5.1；README 保真度欠账 4                          |
| ④   | **`--tools` 今天不过滤 MCP 工具**（只作用于内置工具注册），而 tools-selection spec 场景 4 要求白名单同时限制 MCP            | 技术方案 §风险；`toolManager.ts:176` vs `:380-419` |
| ⑤   | **`ToolSearch` 的返回形状未定义**（返回目录条目文本？返回展开签名？是否影响后续调用）                                       | spec「目录内搜索」一节缺少结果契约                 |
| ⑥   | **`namespace` 与保留名 `builtin` 的冲突规则未定**（MCP server 若叫 `builtin` 怎么办）                                       | spec §命名只规定保留字，未定冲突行为               |
| ⑦   | **MCP 工具池经根容器单例共享给子代理**，转发是否对子代理可见/可调用未定                                                     | `containerSetup.ts:186`                            |
| ⑧   | **截断与预算的关系未写成可验收的数值契约**（多少工具起 PARTIAL、PARTIAL 文案的确切格式）                                    | §5.3、§6 给出建议值，spec 无数字                   |
