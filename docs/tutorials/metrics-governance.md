# 研发效能度量与治理

客户在采购前几乎一定会问两件事：**用了之后我怎么知道谁在用、花了多少、交付有没有变好**，以及**会不会把我们的代码和提问拿到别处**。这一节把度量的口径、可用的数据通道与治理边界一次讲清。

## 效能度量分三层看 {#metrics-layers}

度量数据只能回答一部分问题，通常分三层看：**前两层我们直接供数，第三层里 AI 参与的那部分我们也供数，剩下的要和企业自己的研发平台打通**。

| 层次       | 回答的问题         | 数据来源                                                                                                                          |
| ---------- | ------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| 采用度     | 谁在用、用得多深   | 企业端「研发效能」页面（按用户 / 按仓库的排行与产出贡献、会话与事件明细）+ 管控台的积分用量趋势与企业用量统计                     |
| 用量与成本 | 消耗了多少         | 企业端「用量统计」页的 API 调用明细 + 管控台的企业用量统计 + SDK 用量回调 / 遥测导出                                              |
| 交付结果   | 交付变快、变稳了吗 | AI 参与的活动量（提交数 / PR-MR 数 / 变更行数）由客户端本地识别后上报；交付周期与稳定性需与企业自己的 Git / CI / 项目管理平台打通 |

- **采用度看的是趋势和阻力，不是考核**：用的人少，先去找原因（缺文档、缺权限、场景不匹配），而不是拿来做排名。
- **交付结果这一层分两半**：AI 参与的活动量我们直接供数——客户端在本地识别「经由工具成功创建的提交」「经由工具发起的 PR / MR」与编辑类工具写入的增删行数，是纯命令行行为检测，不依赖任何托管平台（私有化 GitLab 与公有 GitHub 同等成立）。但**交付变快、变稳最终要看企业自己的数据**：周期时间、吞吐、稳定性这类指标来自企业自己的 Git / CI / 项目管理数据，需要与用量数据打通后一起看——这也是业界一致做法。

业界共识也支持这个口径：SPACE 框架指出**没有单一指标能刻画生产力**，建议至少跨 3 个维度测量；Google DORA 报告显示 AI 采用与交付吞吐可能正相关，但与**交付稳定性仍呈负相关**——所以 AI 使用指标必须和交付指标一起看。

> 免责一句：代码行数是活动量指标而非质量指标——业界（含 Anthropic 自己的研究）都指出用它衡量生产力会高估，重构反而会减少行数。我们把它定位成参考，不作为绩效。

## 企业端「研发效能」页面 {#efficiency-board}

前两层里客户端能供的那部分，在企业端运营平台的「研发效能」页面直接可看。这个页面**只讲研发效能**，指标面就是四族：**活跃会话、提交、PR / MR、代码行变更**。

- **概览卡**：活跃会话、提交、Pull Request、代码行变更（代码行变更同时给新增与删除行数）。
- **时间趋势**：选一个指标看走势（会话 / 提交 / PR / 新增行 / 删除行），按自然日分桶，窗口跨度不超过一天时改用小时；图下方是同一批数值的等值表（列全这五个指标），便于核对与复制。
- **维度排行 / 产出贡献**：两张卡能力相同，都支持「用户 / 仓库」两个维度与上面那五个指标，按所选指标降序并给出**该指标的**占比（超出前 10 名的取值聚合成「其他」，相加仍等于合计）。默认组合分别是「用户 × 提交」（谁在产出）与「仓库 × 新增行」（改动落到哪些仓库）。
- **事件计数与两张明细表**：事件按「会话开始 / 结束、用户输入、工具决策、上下文压缩、错误」分别计数；会话明细逐会话列出提交、PR 与增删行数，事件明细逐条列出事件内容及其用户 / 会话 / 模型 / 仓库归属，两张表都可搜索、排序、分页。
- **导出入口随卡片**：时间趋势、维度排行、产出贡献各自带一个导出入口，导出恒等于该块**当前呈现**的数据（当前窗口、该块的维度与指标，含「其他」聚合项）。

**Token、缓存命中与调用明细不在这个页面**：它们归「用量与成本」，在同一个运营平台的「用量统计」页（见第 3 节）；本页筛选行右侧也有一条「用量与成本见『用量统计』」的入口。请求数、错误数与平均请求耗时同样不在本页——它们不属于研发效能口径，也不参与本页的任何数字（后端取数按四族指标的白名单走）。

![企业端「研发效能」页面](/guide/efficiency.webp)

- **数据来自成员客户端上报**，不是网关侧推断——所以看得见「本机提交了多少次」「改了多少行」这类只在客户端发生的事实。页面顶部标注数据覆盖窗口、分桶粒度（自然日 / 小时）与最后一次上报时间；数据是客户端周期上报后落库的，**最新时段可能还不完整**，别把「还没上报完」读成「用量下降」。
- **「活跃会话」是「窗口内有上报活动的会话数」**，不是「窗口内新开的会话数」：客户端的增量上报没有心跳，窗口内没有活动的会话不出现在明细里——那是正常现象，不是丢数据。
- 该页面由**内置上报通道**供数（见第 4 节），不需要企业自建收集器；入口只对企业端管理员可见。

## 用量与成本 {#usage-cost}

token 明细本身在企业端运营平台的「用量统计」页看：「API 调用明细」按用户与模型展示输入 / 输出 / 显式与隐式缓存命中 / 缓存创建，另有「套餐调用明细」，两种明细都能按调用次数 / 用户 / 模型 / 日期分组并给出计费。**「研发效能」页面不再重复呈现这些**，只在上方给一个跳转入口。需要接进企业自建平台、或要做到逐次可追溯时，用 Agent 侧的两条通道：

- **按交互追溯**：SDK 中每条助手消息带各自的用量元数据，可追溯到具体一次交互。
- **单次会话核对**：CLI 会话退出时按模型打印 token 总量摘要。

## 遥测导出：三条通道 {#telemetry-export}

CodeWave IDE 的遥测走 OpenTelemetry 标准，客户端侧有**三条互不顶替的通道**，按「谁来消费」选：

- **内置上报**：直达**部署方的 CodeWave 服务端**，企业端「研发效能」页面据此供数，不需要企业自建收集器、也不需要逐台配置（默认开启，退出开关见[第 6 节](/sdk/telemetry#otel-privacy)）。
- **自建 OTLP**：导出到企业自己的 OTLP 收集器（Grafana Tempo、Jaeger、Datadog 等兼容后端均可），纳入既有的监控与告警体系。
- **Console 打印**：把遥测以可读形式直接打印到终端（对齐 Claude Code 的 `console` 导出器），零配置本地观察；只在交互模式生效，`--stdio` / `--print` 宿主会自动剥除以免污染输出通道。

三条通道的关键区别是**数据的落点**：内置上报到的是部署方自己的服务端（私有化部署时数据不出企业环境），自建 OTLP 到企业指定的收集器，console 只在成员本机终端呈现、不出机器。三者互不顶替——配了自建 OTLP 不会关掉内置上报，反之亦然。自建通道需要显式配置导出器才会产生流量。

可导出的内容：

| 类别    | 内容                                                                                                                                                                                                                                                                                                                |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Metrics | 按类型拆分的 token 用量（`wave.tokens`）、会话数（`wave.sessions`）、编辑类工具的增删行数（`wave.lines.changed`）、经由工具成功创建的提交数与 PR / MR 数（`wave.commits` / `wave.pull_requests`）、按 `user` / `cli` 拆分的活跃时长（`wave.active_time`）、编辑类工具的权限决策数（`wave.code_edit_tool.decision`） |
| Logs    | `session_start` / `session_end` 等会话生命周期事件，以及工具权限决策、压缩等结构化事件                                                                                                                                                                                                                              |

其中提交数与 PR / MR 数**只认「经由工具、且成功」的创建动作**（`git commit`、`gh pr create` / `glab mr create` 等），不看结果是否被合并，也不依赖任何托管平台的 API 或凭据——私有化 GitLab 与公有 GitHub 场景行为一致。

两个较新的口径值得说清：**活跃时长不是在线时长**——`type=cli` 只计 agent 实际在跑的时间（模型调用、工具执行），弹窗等你批准的那几分钟不算，多会话在同一进程里并发时各记各的；`type=user` 只把相邻两次输入间隔小于 5 秒的那段算作在场，长间隔视为挂机。**权限决策数**只覆盖 `Edit` / `Write` 两个编辑类工具的决定（允许与拒绝都计），`source` 区分这次决定来自配置规则、hook、还是你在弹窗里的选择。

指标与事件都带同一组**标准归属属性**：会话 id、账号 id 与（已认证时的）邮箱、终端类型；部署方还可以用 `OTEL_RESOURCE_ATTRIBUTES` 给自己的车队打团队 / 部门标签（例如 `department.name=infra`），该标签既进遥测资源也会投影到指标数据点上，按团队过滤在各类收集器里都成立。**仓库维度（`vcs.repository.*`）默认关闭**，需要按仓库归因时用 `OTEL_METRICS_INCLUDE_REPOSITORY=1` 打开（远端 URL 里的凭据会被剥离，本地路径不出现在遥测里）。**入口标识（`app.entrypoint`）默认也关闭**：需要按「CLI / 桌面端 / VS Code / JetBrains / 远控通道」拆用量时用 `OTEL_METRICS_INCLUDE_ENTRYPOINT=1` 打开（事件面恒带）。

导出器选择与完整配置项见[功能规格说明：OpenTelemetry 集成](/specs/enterprise/opentelemetry)。

## 用量回调（SDK 集成） {#usage-callback}

如果企业自建了度量平台或看板，也可以不走管控台页面，直接通过 SDK 取用量数据：

- **`onUsagesChange` 回调**：每次 AI 调用与消息压缩完成后触发，推送当前会话累计的用量数组，适合实时同步到自建平台。
- **`get usages()` 方法**：随时按需读取同一份数据，适合定时取数、生成报表或与外部监控系统对接。

接口定义与用法见 [SDK 文档 - 回调系统](/sdk/messaging#agent-callbacks-interface)，数据范围与边界见[功能规格说明：用量追踪](/specs/enterprise/usage-tracking-callback)。

## 隐私与治理 {#telemetry-privacy}

三点先说清楚：

- **默认不采集提示内容**：遥测**默认不记录**用户提示文本与工具调用内容，只有显式开启 `OTEL_LOG_USER_PROMPTS=1` / `OTEL_LOG_TOOL_CONTENT=1` 时才会包含。默认配置下 `user_prompt` 事件不含提示原文。
- **归属属性是身份、不是内容**：每条遥测记录带账号 id 与邮箱（已认证时）、会话 id、终端类型；未登录时用本机持久匿名 id（不含 PII）。仓库归属默认关闭、本地路径不出现；`session.id` 若不需要可从指标侧关掉（`OTEL_METRICS_INCLUDE_SESSION_ID=0`）。
- **按团队聚合呈现，不做个人排行**：用量数据用于容量与成本规划、定位使用阻力，不做个人产出排名。
- **管理员可统一下发配置**：管理员可通过服务端托管配置统一下发遥测参数（托管配置的 `env` 键按同名覆盖成员本机值），无需逐台机器配置。

**自建通道默认关闭**：不配置导出器时，数据不会流向企业自建的收集器；console 输出只在成员本机终端呈现、不出机器。**内置上报的落点是部署方自己的 CodeWave 服务端**——私有化部署时即企业自己的服务器，不流向第三方；它**默认开启**，管理员可以用托管配置为整个车队下发开关（托管配置优先于成员本机配置）。关掉全部遥测出站（内置上报与企业自建导出器一起）用总闸 `DISABLE_TELEMETRY=1`；只想停自建导出器，把 `OTEL_METRICS_EXPORTER` / `OTEL_LOGS_EXPORTER` 设为 `none`。依据见[功能规格说明：OpenTelemetry 集成](/specs/enterprise/opentelemetry)。
