# 功能规格说明：桌面端系统通知

**创建日期**：2026-11-26

> 本规格描述桌面应用在窗口不可见（被其他应用遮挡、最小化、隐藏到托盘）或失焦时，如何通过操作系统级通知提醒用户。应用内提醒通道（侧边栏状态点、应用内 toast、确认对话框）见 [desktop-sessions.md](./desktop-sessions.md)「后台会话确认提醒」，两者是互补关系而非替代。
>
> **本规格取代以下既有约束**：`desktop-remote.md`「SSH 远程后台会话」场景 7、`desktop-sessions.md`「后台会话确认提醒」场景 6 中「应用不得发送系统级通知，仅通过应用内呈现」的表述。取代后的口径是——应用内通道保持不变，系统通知作为**窗口不可见时的补充通道**新增；`desktop-shell.md`「无干扰通知」故事保留（版本更新、plan 提示仍走消息流，不弹系统通知）。

## 用户场景与测试

### 用户故事：窗口不可见时收到确认请求的系统通知（优先级：P1）

作为 CodeWave IDE 桌面端用户，我希望在切到其他应用、把窗口最小化或隐藏到托盘期间，一旦某个会话需要我确认（执行命令、修改文件、确认计划、回答问题），系统通知能直接把我叫回来，以便我不会让一个会话白白挂在那里等我一整天。

**为什么是这个优先级**：这是本规格存在的根本理由。现有应用内通道（侧边栏琥珀色状态点、应用内 toast、分屏内的确认对话框）全部要求窗口在用户眼前；用户切走后这三条通道同时失效，后台会话会无限期挂起。同理 Claude Code 桌面端把「需要用户介入」的通知设为最高优先级。

**独立测试**：在桌面端发起一个会触发命令确认的会话，把窗口切到别的应用（或最小化、或 Windows 下关闭到托盘），等待确认请求产生，验证系统通知在 macOS 通知中心 / Windows 操作中心出现，标题与正文分别指向会话与待确认内容；点击通知验证窗口回到前台并定位到该会话的确认对话框。同一场景下让窗口保持可见且聚焦，验证**不**出现系统通知（应用内通道已覆盖）。

**验收场景**：

1. **假设** 桌面端窗口处于不可见（被完全遮挡、最小化、或 Windows 下关闭到托盘）或不是系统焦点窗口，**当**某会话产生权限审批请求（命令执行、文件编辑、计划确认等任一类型），**则**必须发出操作系统级通知，标题指向该会话（优先会话标题，缺失时回退为项目名），正文说明待确认的类别与关键内容（如待执行的命令、待修改的文件路径）；窗口可见且聚焦时不得发出系统通知。
2. **假设** 会话通过 AskUserQuestion 向用户提问，**当**问题产生且窗口不可见或失焦，**则**必须发出系统通知，正文包含第一个问题的原文；问题文本过长时截断为单行可读的长度，不得整段倾泻。
3. **假设** 某会话正在等待确认、窗口不可见，**当**用户在通知上点击，**则**窗口必须被唤起至前台并获得焦点，界面定位到该会话（会话不在任何分屏时按既有「历史会话即时进入」逻辑在新分屏打开），对应的确认对话框直接可见。
4. **假设** 用户在别处已经处理了该确认请求（例如通过远控页、或在通知到达前已回到应用里点掉），**当**请求被解决，**则**对应的系统通知必须被主动关闭，不得留下一条指向已消失对话框的僵尸通知。
5. **假设** 同一会话在等待确认期间连续发起多个确认请求，**当**窗口持续不可见，**则**同一会话的通知必须合并为一条（后到者更新内容，不叠加多条）；该会话所有待确认请求全部清除后再有新请求，视为新一轮，可再次提醒。
6. **假设** 多个会话同时等待确认，**当**通知发出，**则**各会话的通知互相独立、互不覆盖，点击任一条都定位到它自己的会话。
7. **假设** 某个会话被归档、删除或在通知到达时已不存在，**当**通知即将发出，**则**必须跳过该通知，不得出现指向不存在会话的通知。
8. **假设** 会话是由系统自行续跑（例如上下文恢复、循环唤醒）而非用户发起的一轮，**当**该轮结束或产生确认，**则**必须照常按前述规则提醒——这类续跑正是用户不在场时才发生的场景，不得因为「不是用户发起的」而被静音。

### 用户故事：窗口不可见时收到回合完成的通知（优先级：P2）

作为 CodeWave IDE 桌面端用户，我希望切走之后某个会话把活干完了（或反过来停下来等我输入）时能收到系统通知，以便我不必每隔几分钟切回来检查一次。

**为什么是这个优先级**：与确认请求相比，回合完成不阻塞任何人、晚知道几分钟没有实质损失，因此排在 P1 之后；但它是用户切走期间最频繁发生、也最想知道的事，缺了它会让「切走」变成「不敢切走」。

**独立测试**：在桌面端发起一个耗时较长的会话，切到别的应用，等待该轮结束，验证系统通知出现，标题为会话标题、正文为「已完成」；另起一轮让其以错误收尾，验证正文改为体现失败；点「停止」中断一轮，验证不发通知。点击通知验证回到该会话。同时验证窗口可见时不发系统通知、侧边栏「已完成未读」绿点行为不变。

**验收场景**：

1. **假设** 某会话的一轮对话正常结束（模型不再调用工具，且该轮没有以错误收尾），**当**结束时窗口不可见或失焦，**则**必须发出系统通知，正文表明「已完成」。
2. **假设** 该轮由用户主动中断（点「停止」），**当**轮次结束，**则**不得发出「已完成」通知——用户已经亲手结束，再提醒一次是噪音。
3. **假设** 该轮以错误收尾（判据是 SDK 的 `noticeAdded` 通知带 `level: "error"` 且 `scope: "turn"`——`scope` 由 SDK 在写入通知时标注：`"turn"` 表示该错误结束了本回合，含模型调用失败、输出超限停止、技能执行失败、UserPromptSubmit hook 拒绝提示词；`"event"` 或缺省表示回合仍在继续的非阻塞错误，如 PreToolUse / PostToolUse / PermissionRequest hook 失败、上下文压缩失败，这类错误不得把正常收尾的回合标成出错），**当**轮次结束，**则**必须发出通知并在正文中体现失败，不得与成功情形同样表述为「已完成」；错误通知与「已完成」通知同样受场景 4（窗口可见时不发）约束。
4. **假设** 窗口可见且聚焦，**当**任意会话的一轮结束，**则**不发出系统通知；后台会话的提醒继续由侧边栏「已完成未读」绿点承载（沿用 2026-09-10「已完成不弹应用内 toast」的既有拍板，本条只新增窗口不可见时的系统通知通道）。
5. **假设** 一个会话在一轮中同时产生了确认请求与回合结束，**当**通知发出，**则**确认请求的通知优先，回合完成的通知不得覆盖或顶掉尚未处理的确认通知。
6. **假设** 用户点击回合完成的通知，**当**点击生效，**则**窗口唤起至前台并定位到该会话，侧边栏该会话的「已完成未读」标记按既有规则清除。

### 用户故事：通知等级与声音可调（优先级：P2）

作为 CodeWave IDE 桌面端用户，我希望在设置页按类别决定每类通知是「弹窗提醒」「只在任务栏/Dock 上标记」还是「完全不提醒」，并且能关掉提示音，以便我可以让确认请求打断我、但让回合完成安静待着（「仅标记」在下一个故事落地前与「关闭」表现相同：都不弹窗）。

**为什么是这个优先级**：通知一旦上线，默认值必然有人嫌吵、有人嫌不够。分级开关是让它可被接受的前提；但它不改核心行为，所以排在触发逻辑之后。

**独立测试**：在设置页「桌面端设置」区块分别把「权限请求」「回合完成」调到三个等级，在窗口不可见时触发对应事件，验证弹窗/仅标记/完全静默三种表现；切换提示音开关验证系统通知的声音变化；重启应用验证设置保持。

**验收场景**：

1. **假设** 用户打开设置页「全局设置」的「桌面端设置」区块（仅桌面端显示），**则**必须存在「系统通知」分组，包含三个类别——权限请求提醒（Bash / Edit 等工具权限）、回答提问提醒（AskUserQuestion）、回合完成提醒，**三类默认均为「弹窗提醒」**（开箱即生效，无需任何配置）；每类可选「弹窗提醒」「仅标记（不弹窗，仅在任务栏/Dock 标记）」「关闭」三档。
2. **假设** 某类别被设为「弹窗提醒」，**当**该类事件在窗口不可见时发生，**则**必须弹出系统通知并同时产生任务栏/Dock 标记。
3. **假设** 某类别被设为「仅标记」，**当**该类事件在窗口不可见时发生，**则**必须**不**弹出系统通知，但仍产生任务栏/Dock 标记（见下一个故事）与既有的应用内通道。
4. **假设** 某类别被设为「关闭」，**当**该类事件发生，**则**不得发出系统通知、不得产生该类别的任务栏/Dock 标记；应用内通道（侧边栏状态点、确认对话框）不受影响，照常工作。
5. **假设** 存在「提示音」开关（默认开启），**当**关闭，**则**此后发出的系统通知必须静音，行为上与系统级的「静音通知」一致；重启后保持。
6. **假设** 用户修改了任一项通知设置，**则**必须即时生效（无需重启应用），且持久化在桌面端本地偏好中——与「主题」「接收 Beta 版更新」同档，不写入用户级 `settings.json`、不影响插件端与 CLI。
7. **假设** 插件端（VS Code / JetBrains）打开设置页，**则**不得显示该系统通知分组（与「桌面端设置」区块现有的端侧限定一致）。

### 用户故事：任务栏闪烁 / Dock 弹跳与角标（优先级：P3）

作为 CodeWave IDE 桌面端用户，我希望应用图标本身能反映「有几个会话在等我」，并在需要我介入时轻推一下（Windows 任务栏闪烁、macOS Dock 弹跳），以便我不需要读通知内容，扫一眼图标就知道有没有事。

**为什么是这个优先级**：角标与弹跳是通知的补充提示，缺少它们通知依然可用；而且在「仅标记」等级下它们是唯一可见信号，因此仍需实现，只是排在最后。

**独立测试**：在窗口不可见时制造 1 个、2 个、多个等待确认的会话，验证应用图标角标数字与待确认会话数一致；处理完所有确认后验证角标消失；把「权限与问题提醒」设为「仅标记」后触发请求，验证任务栏闪烁（Windows）/ Dock 弹跳（macOS）出现，且进入应用后停止。

**验收场景**：

1. **假设** 有 N 个会话正在等待用户确认（且对应类别的等级不是「关闭」），**当**窗口不可见或失焦，**则**应用图标必须显示角标且数字等于等待确认的会话数；N 变为 0 时角标必须消失，不得残留。
2. **假设** 某类提醒的等级为「弹窗提醒」或「仅标记」，**当**该类事件在窗口不可见时发生，**则**必须触发一次任务栏闪烁（Windows/Linux）或 Dock 弹跳（macOS）。
3. **假设** 闪烁或弹跳已触发，**当**用户把窗口切回前台，**则**必须立即停止闪烁/弹跳，不得继续干扰。
4. **假设** 所有等待确认的请求都已处理，**当**最后一个请求解决，**则**必须停止闪烁/弹跳并清空角标。
5. **假设** 该类提醒等级为「关闭」，**当**该类事件发生，**则**不得触发闪烁、弹跳或计入角标；等级从「弹窗」或「仅标记」改为「关闭」只约束此后发生的事件，此前已计入角标的等待会话不追溯撤销，处理完最后一个请求即清空。
6. **假设** 操作系统不支持角标或闪烁（例如某些 Linux 桌面环境、或未签名/未注册的 Windows 安装），**当**触发这些补充提示失败，**则**必须静默降级——系统通知本身照常可用，不得因为标记失败而影响主流程或抛出可见错误。

### 边界情况

- **操作系统未授予通知权限**：macOS 首次发出通知时系统会请求授权，用户拒绝后所有系统通知静默失效。此时应用不得反复弹窗骚扰，也不得崩溃——通知发出失败只静默，不影响应用内通道与角标 / 闪烁。Electron 43 没有查询通知授权状态的 API（`Notification.isSupported()` 只判平台不判授权），所以设置页不显示「未授权」状态行、也不提供跳转入口；待 Electron 提供查询能力后再补。
- **Windows 通知发不出的已知原因**：应用未设置 AppUserModelID、或安装方式导致开始菜单快捷方式缺失，都会让 toast 注册失败。这属于打包与安装层面的前提，必须在正式安装包上验证，不能只在开发模式（`electron .`）验证通过就算完。
- **应用正在全屏（含演示/共享屏幕）**：窗口可见且聚焦，按场景 1 不发系统通知，避免在共享屏幕上弹出私人内容。
- **多个窗口**：当前只有一个主窗口；若未来新增窗口（如预览独立窗口），「窗口不可见/失焦」按**主窗口**判定，不因某个附属窗口获得焦点就判定用户在场。
- **远程主机会话（SSH / WSL）**：与本地会话同等对待。远端会话跑在远端机器上，窗口隐藏时更容易被遗忘，反而是最该提醒的场景。
- **应用正在退出过程中**：不再发出新通知；已发出的通知随进程退出自然消失。
- **通知延迟与否**：确认类请求不人为延迟；但若请求在通知真正发出之前就被解决（例如用户已经回到应用点掉了），必须撤销该通知而不是照发。
- **禁止打扰的场景**：用户正在该会话所在的分屏里看、且窗口在前台时，一律不发系统通知，即使该会话在别的分屏。
