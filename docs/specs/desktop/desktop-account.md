# 功能规格说明：桌面端账户卡片

> 本规格描述侧边栏底部的账户卡片：登录态、用量展示、功能菜单与更新按钮。设置页见 [desktop-settings.md](./desktop-settings.md)；更新源、feed 与下载链路的宿主侧语义见 [desktop-distribution.md](./desktop-distribution.md)「桌面端自动更新」。

## 用户场景与测试

### 用户故事：账户卡片 · 用量浮层内容（套餐用量 / API 余额 两个维度切换）（优先级：P1）

作为桌面端用户，我希望登录后从账户卡片**行尾用量按钮**弹出的浮层里看到用量信息（**2026-11 交互改版起收在浮层里**，浮层内的内容按本故事展示；开合与预警点见下一故事），且**两个维度互斥切换**：默认停在**套餐用量**（本周条 + 本月条 + 套餐到期日 + 计费结论行；某一维正在报警时默认改停到那一维，见下一故事场景 11），要看余额时切到 **API 余额**（已用 / 剩余 + 预警文案），以便我随时知道：套餐能用到什么时候、当前是哪个限额不足、以及现在的请求到底在扣套餐积分还是扣 API 余额——入口恒在行尾、不必去别处找，也不会被「套餐没耗尽时并不消耗」的 API 余额干扰。

**为什么是这个优先级**：账户卡片是桌面端侧边栏核心运营入口；把用量从「hover ⓘ 才出明细」升级为「一个能装下完整两维、可随时打开的视图」是账户卡片的核心变化（P1）。**2026-10-09 交互定稿**把原「套餐两根条 + API 余额行平铺」收敛为**维度切换**：套餐未用尽时 API 余额不参与计费、余额为 0 也不影响使用，故默认不占版面，维度切换取代原来的 hover ⓘ 明细气泡（气泡内容即余额维度本体）。

**独立测试**：desktop 登录态下发含 billing/apiQuota 的 `desktopAccountInfo`，**点行尾用量按钮弹出浮层后**验证默认停在**套餐维度**（**本周**在上、**本月**在下两根条 + 各维余量百分比 + `progressbar` role + 到期日），且**不渲染** API 余额块；点页签切到**余额维度**渲染「已用 ¥n / 剩余 ¥N」、套餐块与到期日让位；两维只有一维可用时**不渲染页签**、直接展示那一维（单维保留块内标题行）；切换「不限制（`limit = null`）/ 不可用（`limit = 0`）/ 触顶（`reason = month` / `week`）/ 已到期（`reason = no_plan`）/ 阻断（`mode = blocked`，三个 code）」各态验证条与结论行；table-driven 遍历每个已知 `reason` / `code` 断言结论行文案**非空**，再各给一个**规格外**取值（`reason` 与 `blocked` 的 `code`）断言渲染兜底文案 + 色调、且不再是「什么都不画 / 空文案红框」（见场景 23）；余额维度 ⓘ 的 tooltip 说明余额用途。

**验收场景**：

1. **假设**当前请求判定走套餐（`billing.mode = "plan"`）且两维限额均为正数，**当**打开账户卡片的用量浮层，**则**浮层顶部渲染维度页签「套餐用量 / API 余额」（`role="tablist"`，默认选中**套餐用量**）与两根额度条（**本周** = 自然周、**本月** = 滚动月，**本周在上**——自然周窗口更短、更容易触顶，优先关注），每根条按自己那维的窗口量显示余量百分比 `max(0, round((1 − used / limit) × 100))`（分母为该维限额、分子为该维窗口内用量，均由宿主下发，客户端不自行推算窗口）；每根条带 `progressbar` role、`aria-valuenow` = 该维余量百分比；**无结论行**。页签选中态用 `aria-selected` 标记；有页签时「套餐用量」这一称呼由页签承担，块内不再重复一行标题。
2. **假设**某维 `limit = null`（管理员未设置 = 不限制），**当**查看该维，**则**该维**不画条**、显示「无额度限制」；另一维照常。（不得把 `null` 当 `0` —— 会把不限额的企业误报成「不可用」。）
3. **假设**某维 `limit = 0`（显式 0 = 该维度不可用）且 `billing.reason = "dimension_unavailable"`，**当**查看该维，**则**该维**不画条**、置灰显示「不可用」（**不是**「已用尽」，也不是「无额度限制」），并出现结论行「套餐额度不可用（限额为 0），当前按 API 余额计费」。
4. **假设**本人本滚动月用量触顶（`billing.reason = "month"`），**当**查看月条，**则**月条显示空条 +「0%」（**2026-10-09 交互定稿**：触顶与其余百分比同样读数字、同样常规色，条只表达余量、超用封底到 0；「哪个窗口用完、现在按什么计费」由结论行承担，不在条上重复表达「已用尽」+ 琥珀），周条照常，结论行「本月额度已用尽，当前按 API 余额计费」。
5. **假设**本人本自然周用量触顶（`billing.reason = "week"`，月未触顶），**当**查看周条，**则**周条显示空条 +「0%」，月条照常，结论行「本周额度已用尽，当前按 API 余额计费」。
6. **假设**`billing.reason = "no_plan"` 且 `billing.plan` 带 `expireDate`（存在已到期的套餐订单），**当**查看套餐块，**则**套餐块**保留**并显示到期日与结论行「套餐已到期（`<expireDate>` 到期），当前按 API 余额计费」（不再整块消失）。「已到期订单」的判据以服务端为准：`type='plan'` **且 `status='active'`**（**未作废**）且 `end_date <` 今日，与生效分支同谓词——**已作废订单不参与**，全部套餐订单已作废时视同「无套餐」（`plan = null`，落到场景 10 的兜底）。
7. **假设**`billing.reason = "enterprise"`（企业维度本期额度触顶），**当**查看套餐块，**则**本人两根条照常显示个人读数（企业池触顶不改个人数字），并渲染结论行「企业本期额度已用尽，当前按 API 余额计费」，色调为**琥珀预警**（与月/周同族：下个窗口自动恢复，不属「需人工干预」的错误色）。**2026-09-22 口径变更**：原先（2026-09-21）此原因**不渲染**结论行，理由是「漏提示优于误提示」——该理由已判定站不住：说「企业本期额度已用尽」是事实，且与个人两根条不冲突（条 = 个人读数，结论行 = 计费结论）；真正有误读风险的是把企业池的数字画成个人的条，不是这句话本身。当时（不渲染时）成员看到的是「个人两根条健康 + API 余额在掉」而毫无解释（缺陷单 3479183306383616 据此报障）。本次只补呈现层，**不动计费口径**（企业池与个人条之和的折算摩擦属产品口径、不在本场景范围）。
8. **假设**`billing.mode = "blocked"`（套餐与 API 均不可用；`code ∈ EXPIRED_NO_API / USER_QUOTA_ZERO / TEAM_QUOTA_ZERO`），**当**查看账户卡片，**则**结论行**复用 proxy 402 的同一句文案**（按 code 三选一：`EXPIRED_NO_API` =「您订购的套餐已过期，无法使用本产品！」/ `USER_QUOTA_ZERO` =「您的 API 额度已用完，请联系公司管理员分配额度后使用！」/ `TEAM_QUOTA_ZERO` =「团队 API 额度已用完，请联系公司管理员充值后使用！」）；`blocked` 不下发 `plan` 四数，故此时套餐块只有该结论行。
9. **假设**套餐块渲染且 `billing.plan` 带 `expireDate`，**当**查看**套餐维度**，**则**维度页签行右侧显示套餐到期日（`YYYY-MM-DD 到期`）；到期日属套餐信息，切到**余额维度**时不再展示（该位置改由余额的 ⓘ 占用，见场景 16）。
10. **假设**`billing.plan` 为 `null`（无生效套餐、也**没有**未作废的已到期订单），**当**查看账户卡片，**则**不渲染套餐块（未购买的企业无法登录桌面端，实际不出现；**全部套餐订单已作废**同样落在这里——作废不是到期，不得拿作废单的截止日渲染「套餐已到期」；仅作契约兜底）。
11. **假设**宿主下发了 `apiQuota` 且套餐维度也有数据，**当**点页签切到**余额维度**，**则**面板渲染两行「已用 ¥n」「剩余 ¥N」；金额格式 = ¥ 前缀 + 两位小数 + 千位分隔；两行金额**右对齐且等宽数字**（`font-variant-numeric: tabular-nums`，便于比较），随账户消息实时刷新。
12. **假设**API 余额充足（剩余 ≥ 限额 20%），**当**查看余额维度，**则**「剩余」金额以正常色展示，无预警文案。
13. **假设**API 余额不足（剩余 < 限额 20% 且 > 0），**当**查看余额维度，**则**「剩余」金额以预警色展示，并附同色提示「余额不足20%，建议及时充值」；「已用」行不套用预警色。
14. **假设**API 余额用完（剩余 ≤ 0），**当**查看余额维度，**则**「剩余」以错误警示色（主题变量，如 `--vscode-errorForeground`）显示「已用完」（**不显示负数**），并附红色提示「额度已用完，请联系管理员充值」。
15. **假设**API 不限额（`apiQuota.limit = null`），**当**查看余额维度，**则**「剩余」行显示「不限额」（正常色）、不显示金额，也不参与 20% 预警；「已用」行照常显示金额。
16. **假设**用户 hover 或键盘 Tab 聚焦余额维度的 ⓘ 图标（`data-testid="api-quota-info"`，独立按钮，`aria-label="API 余额说明"`，排在**余额维度的右上角**），**则**弹出 tooltip「将在套餐用量耗尽时使用API余额」——说明这笔余额只在套餐不可用时才参与计费。该图标与套餐维度的**到期日**处于同一类位置：两个维度各自承载自己的说明性信息，切换时互不干扰。
17. **假设**两维只有一维可用（`billing` 为空 ⇒ 只有余额；或 `apiQuota` 为空 ⇒ 只有套餐），**当**打开用量浮层，**则不渲染页签**、直接展示那一维，并在块内保留自己的标题行（「套餐用量」/「API 余额」）替代页签（仅余额这一维时，ⓘ 落到该标题行右侧——页签行没了，但 ⓘ 属余额信息，仍在该维度右上角）。
18. **假设**用户切到余额维度后在同一会话内继续操作，**当**卡片因宿主推送重新渲染，**则**停留的维度被记住（不会自动跳回套餐维度）；而**只剩一维**时自动落到仅存的那一维（不停留在已消失的维度上，避免空白面板）。
19. **假设**用户点击余额维度的**金额文本**，**当**点击发生，**则**不触发任何行为（金额非热区，仅 ⓘ 为热区，且 ⓘ 只出 tooltip、不再弹出明细气泡）。
20. **假设**用户把指针移开 ⓘ，**当**指针离开，**则**tooltip 自动消失（无需点击），不残留任何悬浮面板——原「hover ⓘ 弹出明细气泡 + 移出延迟 150ms 收起 + `Esc`/外部点击强制收起」的整套机制**随气泡一并删除**，在 `Esc` / 外部点击上不再有任何待收起的浮层。
21. **假设**余额维度处于预警态（不足 20% / 已用完），**当**切回套餐维度，**则**套餐维度不受余额预警影响（预警文案与色调只属于余额维度，不跨维度残留）。
22. **假设**宿主下发 `billing` 与 `apiQuota` 均为空/未下发，**当**查看账户卡片，**则**浮层无内容可展示，个人信息行尾部的用量按钮不渲染。
23. **假设**宿主下发的 `billing.reason` 是**规格外取值**（服务端先于客户端发版新增的枚举值），**当**渲染账户卡片，**则**结论行照常渲染「套餐额度当前不可用，按 API 余额计费」（**琥珀预警**）——**不得静默不渲染**（原先 `switch` 无 `default`，未识别的 `reason` 会隐式返回、结论行整块消失，用户只看到「本人两根条健康 + API 余额在掉」而零解释，与场景 7 的缺陷单 3479183306383616 同款失效）；**假设**宿主下发的 `billing.code` 是规格外取值（`mode = "blocked"`），**当**渲染账户卡片，**则**渲染兜底阻断文案「当前用量受限，请联系公司管理员」（**错误色**）——**不得渲染一条没有文案的结论行**（空红框：查表得 `undefined` 但元素照挂）；两处均按客户端既有约定 `console.warn` 记一条未知枚举日志（不新建日志/打点基建）。**2026-09-22 追加**：兜底文案「说少而准」——结论行要回答的是「为什么在扣 API」，而这件事只需 `mode = "api"` 就能确定，故不猜是哪一池（月/周/企业）用完；色调沿用本规格既有的「会不会自愈」分档（见场景 3–7 的说明）：未知原因不预设「需人工干预」（那是错误色那档的语义），给琥珀，避免无谓制造焦虑。**起因**：客户端遇到不认识的枚举就静默是同一类失效——09-22 修掉 `enterprise`（场景 7）后复核发现同类还有这两处，本次一并收口；根因是**两端不同机发布**（服务端先加枚举、客户端旧版本不认识），故除运行期兜底外，`reason` 的 `switch` 另加 `default` 分支做**编译期穷尽性检查**（`const _exhaustive: never = billing.reason`，仓内新增 `AccountBillingDegradeReason` 却忘了处理时直接编译失败——但它拦不住跨仓先发，两者都要有）。

### 用户故事：账户卡片 · 用量浮层与预警点（优先级：P2）

作为桌面端用户，我希望账户卡片**默认只显示个人信息一行**，用量信息收进一层浮层——点个人信息行尾部的**用量按钮**就在卡片上方弹出与卡片等宽的浮层，看完点浮层外或按 Esc 即收起；同时**用量出问题时不能在收起态彻底沉默**，用按钮右上角的一颗小圆点告诉我「这里有事」，以便卡片保持清爽但不会漏掉余额不足、额度耗尽这类预警。

**为什么是这个优先级**：空间收纳是浮层的辅助能力，先保证浮层里的展示正确（P1 故事）后再谈收纳。**2026-11 交互改版**：原「默认展开 + 显隐按钮就地收起/展开」改为「默认收起 + 点击弹出浮层」——就地展开会把卡片顶高、把侧边栏下方的会话列表往下推，弹层则不改变卡片高度；收起态下预警不可见，故保留一颗点透出（用户否掉了「不提示」与「有预警自动展开一次」两个方案）。**入口限定在行尾用量按钮**：个人信息行热区仍然只开纯功能菜单，一颗入口做一件事。

**独立测试**：登录态进入卡片验证无浮层、卡片仅剩个人信息一行、按钮 icon 为仪表盘（dashboard）且 `aria-label="查看用量"`、`aria-haspopup="dialog"`；点按钮验证浮层出现且内容按 P1 故事展示（默认停在**套餐维度**）、与卡片等宽、底边贴个人信息行顶向上弹；再点按钮 / 点浮层外 / 按 Esc 验证收起（打开后焦点进入浮层；**键盘打开的**按 Esc 或再点一次按钮收起后焦点回到按钮，鼠标打开的焦点不抢）；打桩 `getBoundingClientRect` 后改窗口高度并派发 `resize`，验证浮层 `bottom` 随锚点重算（不跟卡片分家）；重新挂载验证**仍回到收起态**（不记忆）；分别用「套餐正常 / 周月耗尽 / 余额不足 20% / 余额耗尽 / 套餐已到期 / 被阻断」场景验证圆点有无与颜色；浮层开着时点热区验证菜单打开、浮层收起（互斥）；`billing`+`apiQuota` 均未下发时验证用量按钮不渲染。

**验收场景**：

1. **假设**用户进入桌面端（组件挂载，含重新打开客户端、切换会话后重新挂载），**当**查看账户卡片，**则**卡片只渲染个人信息行（无用量块、无页签、无浮层），个人信息行尾部用量按钮 icon 为仪表盘（dashboard，`aria-label="查看用量"`、`aria-haspopup="dialog"`、`aria-expanded="false"`）；收起状态**不做持久化**，每次挂载都回到收起态（**2026-11-05 交互定稿**：用户明确选「每次都收起」，不记住上次的开合选择）。
2. **假设**当前**没有任何用量预警**，**当**查看用量按钮，**则**按钮上**不出现任何角标**（保持干净）；圆点只在真有预警时挂上。
3. **假设**当前**存在用量预警**，**当**查看用量按钮，**则**按钮右上角出现一颗 **6px 实心圆点**（距按钮上边缘、右边缘各 2px，`pointer-events: none` 不参与点击）；读屏 `aria-label` 为「**查看用量（有预警）**」。
4. **假设**预警点的**严重度**判定：**红** = 结论行 `tone = "error"`（`blocked` / 维度不可用 / 套餐已到期）或 API 余额耗尽（剩余 ≤ 0）；**琥珀** = 结论行 `tone = "warning"`（本周/本月/企业池触顶）或 API 余额不足 20%；**当**两种情况同时成立，**则**取**红**（高严重度优先）。色调复用既有主题变量：`--vscode-errorForeground`（错误）/ `--vscode-editorWarning-foreground`（预警），不新造色值；新增预警来源时并入同一判定，不另起一套颜色/图标。
5. **假设**用户点击用量按钮，**当**浮层弹出，**则**浮层在**卡片上方**出现：宽度与卡片一致（约 235px，右缘对齐）、底边贴个人信息行顶部向上展开、盖住卡片上方内容（不改变卡片自身高度、不推动侧边栏其它区域）；浮层内容按 P1 故事渲染（默认停在**套餐用量**维度，页签可切到 **API 余额**；若某一维正在报警，默认改停到那一维，见场景 11）；浮层的定位用 fixed（侧边栏 `overflow: hidden` 会裁掉 absolute 后代）；向上空间不足时浮层内部滚动，不越过视口顶部。按钮 `aria-expanded="true"`，icon 恒为仪表盘（开合不换图标）。
6. **假设**浮层已打开，**当**再次点击用量按钮 / 点击浮层外任意位置 / 按 Esc，**则**浮层收起、卡片恢复为个人信息行；三种路径都关闭浮层（打开时焦点进入浮层，符合 dialog 语义；点外部关闭时焦点留给用户点中的位置，不抢）。**键盘关闭的两条路径——Esc、再按一次用量按钮（Enter/空格 toggle）——都把焦点交还用量按钮**；**鼠标关闭的焦点落空**——鼠标用户此刻指针多半已离开按钮，把焦点塞回去会让按钮进入 `:focus` 态、顺带弹出「查看用量」气泡，这条气泡再没有 `mouseleave` 能收掉，会一直挂在空中（2026-11-05 修的「鼠标移开后仍显示提示文案」）。**2026-11-05 补**：按钮 toggle 关闭同样要交还焦点——`Tooltip` 的 `disabled` 在开合间把 wrapper 摘掉再装回，按钮 DOM 节点随之重建，不同步补 focus 的话键盘用户的焦点会落到 `body`、Tab 顺序回卷到页首。
7. **假设**浮层处于打开态且宿主/用户改变了窗口尺寸，**当**窗口 resize，**则**浮层**重新测量锚点**、继续贴住个人信息行顶与卡片右缘（`fixed` 坐标是打开那一刻的快照，卡片贴侧栏底部、随窗口高度移动，不重测就与卡片分家）。
8. **假设**当前有预警，**当**浮层打开或关闭，**则**按钮上的圆点**始终保留**（不闪烁、不随开合切换）——浮层默认只展示套餐维度，预警可能落在余额维度（如余额耗尽），圆点是唯一的常驻出口。
9. **假设**浮层处于打开态，**当**点击个人信息热区，**则**纯功能菜单打开、用量浮层收起；**假设**纯功能菜单处于打开态，**当**点击用量按钮，**则**浮层打开、菜单收起——两个弹层互斥，同一位置不叠两层。
10. **假设**宿主下发 `billing` 与 `apiQuota` 均为空/未下发，**当**查看账户卡片，**则**没有用量可看，用量按钮不渲染（卡片只剩个人信息行 + 有更新时的更新按钮）。
11. **假设**浮层打开时**某一维正在报警**（结论行 `tone` 为 warning/error，或余额不足 20% / 已耗尽），**当**浮层弹出，**则**默认**停到报警的那一维**——免得「打开只看到健康的套餐条、预警藏在另一页签里」（**2026-11-05 定稿**：用户在有预警时选「停在报警的那一维」，而不是「总是套餐」）；两维同时报警时取**更严重**的那档（错误 > 预警），同档回到套餐维度；两维都没有预警时保持套餐维度，也不覆盖用户在本次打开期间的切换。

### 用户故事：账户卡片 · 个人信息行与纯功能菜单（优先级：P1）

作为桌面端用户，我希望点击头像/姓名热区弹出**纯功能菜单**（设置/企业控制台/帮助文档/退出登录），菜单贴着个人信息行向上弹出、与卡片等宽，再次点击热区或失焦/Esc 可收起，以便操作账户相关功能且不被用量信息干扰。

**为什么是这个优先级**：这是账户卡片新模型对既有「更多按钮 + 用量浮层」双入口的**结构性替换**（已登录不再有独立「…」更多按钮），是账户卡片的核心差异，必须最先明确（P1）。

**独立测试**：登录态验证热区点击开/关菜单、菜单含 4 项且无用量块、贴行弹出、与卡片等宽（右缘对齐）；点击外部与 Esc 收起；方向键/Enter/Space 键盘操作；未登录态验证整条登录按钮 + 更多按钮仍保留；远程主机标注。

**验收场景**：

1. **假设**用户未登录，**当**查看账户卡片，**则**显示整条「登录」按钮（占满卡片宽度）+ 右侧「更多」（…）按钮；点登录走现有 SSO 流程；「更多」菜单含登录项。
2. **假设**用户已登录，**当**查看个人信息行，**则**显示头像（邮箱前缀首字母圆形占位）+ 姓名（邮箱前缀；无邮箱显示「已登录」），行尾部为更新按钮（有更新时）+ 用量按钮（打开用量浮层）；**不显示独立「…」更多按钮**。
3. **假设**已登录用户点击头像/姓名热区（`data-testid="account-card-hotzone"`，热区 `aria-expanded` 反映菜单开合，支持 Enter/空格开合），**当**菜单展开，**则**菜单**纯功能、仅 4 项**：「设置 / 企业控制台（↗）/ 帮助文档（↗）/ 退出登录」（退出登录为危险色 + 上方分隔线），**不含任何用量信息**。
4. **假设**菜单打开，**当**查看菜单，**则**菜单**向上弹出**、盖住卡片上方内容（不遮挡个人信息行）；内容自动换行、不超出面板。
5. **假设**菜单已打开，**当**再次点击个人信息热区，**则**菜单收起（toggle）；若用量浮层同时开着，则按下一故事的互斥规则先收起浮层。
6. **假设**菜单已打开，**当**点击菜单外部任意区域或按 `Esc`，**则**菜单收起（焦点回到触发热区）。
7. **假设**菜单已打开，**当**使用键盘（方向键在菜单项间移动焦点、Enter/Space 激活、Esc 关闭——roving tabindex），**则**焦点按方向键循环移动，激活项执行对应行为。
8. **假设**用户选择菜单项，**当**点击「设置」，**则**打开设置页面；点击「企业控制台（↗）」则打开对应网址（新标签页/外部）；点击「帮助文档（↗）」则浏览器新标签页打开 `serverUrl + /docs`；点击「退出登录」则执行登出并回到未登录卡片态。
9. **假设**账户卡片处于远程主机会话（host 非 local），**当**查看菜单，**则**「设置 / 退出登录」项旁标注主机名（如「设置（prod）」），本地主机不标注；用量与菜单登录项跟随聚焦分屏所属主机。

### 用户故事：账户卡片 · 更新按钮状态机 S0–S6（优先级：P2）

作为桌面端用户，我希望有新版本时在个人信息行右侧出现「更新」按钮，走「下载二次确认 → 下载中禁用 → 就绪自动弹重启确认」状态机，由我决定重启时机，以便在知情的前提下更新应用而不被自动重启打断。

**为什么是这个优先级**：按钮状态机依赖宿主下发 `update.status` 并响应下载/重启命令，涉及 desktop 主进程改动（宿主须把 electron-updater 事件映射为 `update.status` 推送并响应 `desktopUpdateDownload`/`desktopUpdateRestart` 命令）；宿主侧就绪前按钮无数据可渲染，故整体排 P2（在 P1 的用量常驻/菜单稳定后接线）。webview 侧状态机与宿主接线均属本规格验收范围。

**独立测试**：webview 侧下发 `update: { available: true, version: "1.2.0", status: "idle" }`，验证 S1 按钮「更新」→ 点击弹 S2 确认框 → 确认后发 `desktopUpdateDownload` 且按钮进入「正在下载更新…」disabled；模拟宿主把 status 改为 ready，验证自动弹 S4 重启确认（仅一次）、[稍后] 转「重启」按钮、[立即重启] 发 `desktopUpdateRestart`；Esc 关闭 S2 后不下载；status 回退 idle 时按钮恢复「更新」。

**验收场景**：

1. **假设**无更新（`update.available: false` 或不带 `update`），**当**查看个人信息行，**则**不显示更新按钮（S0）。
2. **假设**检测到新版本（`available: true` 且 `status: "idle"`），**当**查看个人信息行，**则**更新按钮显示「更新」（S1），点击进入 S2。
3. **假设**用户点击「更新」，**当** S2 下载二次确认对话框弹出，**则**标题「更新到新版本」，正文含版本号 `vX.Y.Z` 与「安装完成后由你选择重启时机，不会自动重启客户端」语义，按钮「取消 / 下载更新」；**仅 `Esc` 可关闭**（点对话框外部不关闭）。
4. **假设**用户在 S2 点击「下载更新」，**当**确认下载，**则** webview 向宿主发送 `desktopUpdateDownload` 命令，更新按钮变为「正在下载更新…」并 **disabled**（防重复下载，点击无反应，S3）。
5. **假设**宿主将 `update.status` 推送为 `"ready"`，**当** webview 收到新快照，**则**自动弹出「重启以完成更新」确认框（S4），按钮「稍后 / 立即重启」，正文提示「重启会中断正在运行的任务，建议先保存工作」；**不自动重启**；该弹框每轮就绪只自动弹一次（防重复弹窗）。
6. **假设**用户在 S4 点击「稍后」，**当**对话框关闭，**则**更新按钮文案变为「重启」（S5），期间应用可正常使用；再次点击按钮重新弹出 S4 确认框。
7. **假设**用户在 S4/S5 点击「立即重启」，**当**确认重启，**则** webview 向宿主发送 `desktopUpdateRestart` 命令，更新状态复位、按钮消失（S6）；是否实际退出安装由宿主处理。
8. **假设**下载过程中宿主推送 `status: "idle"`（下载失败/取消），**当**按钮状态刷新，**则**按钮恢复「更新」文案与可点状态；重新点击回到 S2 确认流程。
9. **假设**更新按钮处于下载中（disabled），**当**用户点击它，**则**无任何反应，不弹对话框、不发命令。

## 边界情况

- **未登录**：账户卡片仅登录按钮 + 更多按钮；无用量浮层、无个人信息行、无更新提示（没有用量时用量按钮也不显示）。

- **未配置套餐 / 均未下发**：`billing.plan` 为 `null`（无生效套餐、且没有未作废的已到期订单——从未购买、或订单已全部作废）时套餐块不渲染；`billing` 与 `apiQuota` 均未下发时用量浮层没有内容、用量按钮不渲染。

- **套餐三态别混**：`limit = null`（不限制）与 `limit = 0`（不可用）是两种状态，**都不画条**，但文案与视觉必须区分；触顶（该维 `used ≥ limit`）读「0%」（空条 + 常规色，2026-10-09 起）——条只表达余量、超用封底到 0，「哪个窗口用完 / 现在按什么计费」由结论行回答。旧「整单大池子」口径（`monthlyQuota × months`）随旧 `plan` 字段一并退出卡片：后端仍保留旧字段兼容已发布客户端，新卡片不再取数。

- **用量浮层内 = 两个互斥维度**（2026-10-09 交互定稿）：套餐用量与 API 余额不并列展示，用页签切换，默认套餐维度。理由是二者地位不对等——套餐没耗尽时 API 余额不参与计费、余额为 0 也不影响使用，故默认不占版面；两维**只有一维有数据**时不渲染页签、直接展示那一维。维度选择是卡片内的视图状态（不落盘、不跨会话）。

- **结论行优先级**：`blocked` > 不可用（`dimension_unavailable`）> 已用尽（月优先于周）> 无结论行；`enterprise` **照渲染**（企业本期额度触顶 ⇒ 琥珀预警，与月/周同档；2026-09-22 起，原先刻意不渲染）。

- **枚举是开放集合（服务端可能先于客户端发版）**：`billing.reason` / `billing.code` 的新取值由服务端先上线、已发布的客户端不认识（两端不同机发布）。客户端**必须**对未识别取值给兜底结论行（文案与色调见场景 23），**不得静默**；兜底文案**不含对具体原因的猜测**（不点名月/周/企业哪一池用完）。**spec 背书、因此维持不渲染**的三种情形（本次不碰、也不是缺陷）：`mode = "plan"`（套餐可用，无话可说）、`reason = "no_plan"` 且 `plan = null`（从未购买或订单已全部作废，无到期日可讲）、`billing` 与 `apiQuota` 双缺（用量区整体不渲染）。

- **API 余额**（余额维度）：面板两行「已用 / 剩余」，金额右对齐 + 等宽数字；剩余 < 限额 20% 金额预警色 + 琥珀提示；剩余 ≤ 0 显示「已用完」错误色 + 红色提示；`limit = null` 显示「不限额」。ⓘ 排在**余额维度的右上角**（与套餐维度的到期日同一处，不回金额行，见场景 16），只出 tooltip 说明用途。

- **下载中**：更新按钮 disabled，点击无反应。

- **对话框**：S2 仅 Esc 关闭；S4 稍后后可再次弹确认；均不自动关闭/不自动重启。

- **远程主机**：个人信息菜单「设置 / 退出登录」标注主机名；用量与登录态跟随聚焦分屏所属主机。

- **用量轮询失败**：保留上次成功显示。

## 数据契约与命令

### desktopAccountInfo（窗口级推送，无 paneId）

`update?` 字段承载更新按钮状态机输入（S0–S6），完整契约如下：

```ts
export interface AccountUpdateInfo {
  available: boolean; // 有新版本
  version?: string; // 新版本号（对话框/按钮 tooltip 文案使用）
  status?: "idle" | "downloading" | "ready"; // 更新过程状态
}
/** 套餐两根额度条的四个数 + 到期日（codechat `GET /api/v1/account` → `billing.plan`）. */
export interface AccountBillingPlanUsage {
  monthUsed: number;
  monthLimit: number | null; // 滚动月限额；null = 不限制，0 = 该维度不可用
  weekUsed: number;
  weekLimit: number | null; // 自然周限额；null = 不限制，0 = 该维度不可用
  expireDate: string; // 套餐到期日（YYYY-MM-DD）
}
/**
 * 降级原因（客户端据此选结论行文案；枚举由后端定义，见 codechat spec 场景 5–11）.
 * 五个原因**各有结论行**（`enterprise` 自 2026-09-22 起也渲染，见场景 7）；唯一
 * 「不渲染」的组合是 `no_plan` 且 `plan = null`（从未购买）。
 * 该类型只是**客户端侧的枚举快照**：服务端可能先发版新增取值，客户端必须对规格外
 * 取值渲染兜底结论行（见场景 23），不得静默。
 */
export type AccountBillingDegradeReason =
  | "month"
  | "week"
  | "enterprise"
  | "no_plan"
  | "dimension_unavailable";
/** 阻断码（客户端按 code 复用 proxy 402 文案；同样只是枚举快照，规格外取值走场景 23 的兜底文案）. */
export type AccountBillingCode =
  | "EXPIRED_NO_API"
  | "USER_QUOTA_ZERO"
  | "TEAM_QUOTA_ZERO";
/**
 * 计费结论（codechat 形态甲：闸口镜像）。判定出自后端 `getBillingVerdict`——与 proxy 扣费
 * **同一份代码**；客户端只渲染、**不自行判断「走套餐还是走 API」**（旧方案由客户端比较数字，
 * 已因限额「0」语义翻转发生过一次静默失效）。`plan` 子对象：有生效套餐 = 四数 + 到期日；
 * 无生效套餐但有**未作废**的已到期订单 = 仅 `{ expireDate }`；从未购买、或订单已全部作废 = null。
 */
export type AccountBillingInfo =
  | { mode: "plan"; plan: AccountBillingPlanUsage }
  | {
      mode: "api";
      reason: AccountBillingDegradeReason;
      plan: AccountBillingPlanUsage | { expireDate: string } | null;
    }
  | { mode: "blocked"; code: AccountBillingCode };
export interface DesktopAccountInfoMessage {
  command: "desktopAccountInfo";
  isAuthenticated: boolean;
  user?: { id: string; email?: string } | null;
  billing?: AccountBillingInfo | null; // 套餐两根条 + 到期日 + 计费结论
  apiQuota?: AccountApiQuotaInfo | null; // { limit: number|null, used }
  update?: AccountUpdateInfo | null; // 应用更新状态（S0–S6 输入）
}
```

**下发规则**：

- 未登录：`isAuthenticated: false`，`billing`/`apiQuota`/`update` 可不带。
- 无生效套餐、且没有未作废的已到期订单（从未购买，或订单已全部作废）：`billing.plan: null`（套餐块不渲染）；`billing` 与 `apiQuota` 均未下发时用量浮层没有内容、用量按钮不渲染。
- API 不限额：`apiQuota.limit: null`（共用团队余额）。
- 无更新：不带 `update` 或 `update.available: false`。
- 账户/用量/结论/更新状态变化时宿主主动推送新快照；轮询失败保留上次成功数据。

## 数据契约与命令

### desktopAccountInfo（窗口级推送，无 paneId）

`update?` 字段承载更新按钮状态机输入（S0–S6），完整契约如下：

```ts
export interface AccountUpdateInfo {
  available: boolean; // 有新版本
  version?: string; // 新版本号（对话框/按钮 tooltip 文案使用）
  status?: "idle" | "downloading" | "ready"; // 更新过程状态
}

/** 套餐两根额度条的四个数 + 到期日（codechat `GET /api/v1/account` → `billing.plan`）. */
export interface AccountBillingPlanUsage {
  monthUsed: number;
  monthLimit: number | null; // 滚动月限额；null = 不限制，0 = 该维度不可用
  weekUsed: number;
  weekLimit: number | null; // 自然周限额；null = 不限制，0 = 该维度不可用
  expireDate: string; // 套餐到期日（YYYY-MM-DD）
}

/**
 * 降级原因（客户端据此选结论行文案；枚举由后端定义，见 codechat spec 场景 5–11）.
 * 五个原因**各有结论行**（`enterprise` 自 2026-09-22 起也渲染，见场景 7）；唯一
 * 「不渲染」的组合是 `no_plan` 且 `plan = null`（从未购买）。
 * 该类型只是**客户端侧的枚举快照**：服务端可能先发版新增取值，客户端必须对规格外
 * 取值渲染兜底结论行（见场景 23），不得静默。
 */
export type AccountBillingDegradeReason =
  | "month"
  | "week"
  | "enterprise"
  | "no_plan"
  | "dimension_unavailable";

/** 阻断码（客户端按 code 复用 proxy 402 文案；同样只是枚举快照，规格外取值走场景 23 的兜底文案）. */
export type AccountBillingCode =
  | "EXPIRED_NO_API"
  | "USER_QUOTA_ZERO"
  | "TEAM_QUOTA_ZERO";

/**
 * 计费结论（codechat 形态甲：闸口镜像）。判定出自后端 `getBillingVerdict`——与 proxy 扣费
 * **同一份代码**；客户端只渲染、**不自行判断「走套餐还是走 API」**（旧方案由客户端比较数字，
 * 已因限额「0」语义翻转发生过一次静默失效）。`plan` 子对象：有生效套餐 = 四数 + 到期日；
 * 无生效套餐但有**未作废**的已到期订单 = 仅 `{ expireDate }`；从未购买、或订单已全部作废 = null。
 */
export type AccountBillingInfo =
  | { mode: "plan"; plan: AccountBillingPlanUsage }
  | {
      mode: "api";
      reason: AccountBillingDegradeReason;
      plan: AccountBillingPlanUsage | { expireDate: string } | null;
    }
  | { mode: "blocked"; code: AccountBillingCode };

export interface DesktopAccountInfoMessage {
  command: "desktopAccountInfo";
  isAuthenticated: boolean;
  user?: { id: string; email?: string } | null;
  billing?: AccountBillingInfo | null; // 套餐两根条 + 到期日 + 计费结论
  apiQuota?: AccountApiQuotaInfo | null; // { limit: number|null, used }
  update?: AccountUpdateInfo | null; // 应用更新状态（S0–S6 输入）
}
```

**下发规则**：

- 未登录：`isAuthenticated: false`，`billing`/`apiQuota`/`update` 可不带。
- 无生效套餐、且没有未作废的已到期订单（从未购买，或订单已全部作废）：`billing.plan: null`（套餐块不渲染）；`billing` 与 `apiQuota` 均未下发时用量浮层没有内容、用量按钮不渲染。
- API 不限额：`apiQuota.limit: null`（共用团队余额）。
- 无更新：不带 `update` 或 `update.available: false`。
- 账户/用量/结论/更新状态变化时宿主主动推送新快照；轮询失败保留上次成功数据。
- **宿主只做透传**：`billing` 由 codechat `GET /api/v1/account` 下发，经 CLI `getAccountInfo` → desktopHost `accountCache` 原样带到卡片；宿主**不重算**任何判定或窗口（窗口起点、限额聚合口径都在服务端，客户端一无所知）。

### 套餐额度条计算（按余量计）

```
barPercent(used, limit) = max(0, round((1 − used / limit) × 100))    // limit > 0
```

- 每根条用**自己那维**的数（月条 = monthUsed/monthLimit，周条 = weekUsed/weekLimit）；`limit = null` 或 `0` 时不画条（分别显示「无额度限制」「不可用」）。
- 100% = 满（未使用）；触顶时该条显示**空条 +「0%」**（常规色，2026-10-09 起）。

### 命令契约

- `desktopUpdateDownload`（webview → host）：用户确认 S2 后通知宿主开始下载。
- `desktopUpdateRestart`（webview → host）：用户在 S4/S5 选择立即重启后通知宿主安装并重启。
- **宿主接线**：webview 侧 S0–S6 状态机调用上述两个命令；宿主（desktopHost.ts）把 electron-updater 事件映射为 `update.status` 随 `desktopAccountInfo` 推送并响应两命令；toast 更新链路不提供（`autoDownload=false`，下载仅在 S2 确认后启动）。触发检查的时机（启动自动 / 手动 / 运行期固定间隔轮询，见 [desktop-distribution.md](./desktop-distribution.md)「桌面端自动更新」场景 11）不改变状态机语义——任一时机发现新版本都只置 idle（S1）。降级边界见 [desktop-distribution.md](./desktop-distribution.md)「桌面端自动更新」故事场景 5。

## 非目标（明确排除）

- **账户卡片的通知语义**：账户卡片不含 toast/通知语义（信息类 toast 自动消失、带操作按钮 toast 不自动消失等通知行为由会话/后台通知故事承载，桌面端更新提醒由「更新按钮状态机」全权接管）。

- **不猜未识别的降级原因、也不扩张「静默」的范围**：对规格外的 `billing.reason`，卡片只说明「套餐额度当前不可用，按 API 余额计费」，不猜测哪一池（月/周/企业）用完、也不据此推断恢复时间或提示用户找谁（见场景 23）。同时明确：**spec 背书的静默仍是静默**——`mode = 'plan'`（无话可说）、`no_plan` 且 `plan = null`（无到期日可讲）、`billing`/`apiQuota` 双缺（用量区整体不渲染）这三种**维持不渲染**，本次兜底只针对「客户端不认识服务端下发的取值」这一类失效（2026-09-22）。
