# 功能规格说明：桌面端账户卡片

> 本规格描述侧边栏底部的账户卡片：登录态、用量展示、功能菜单与更新按钮。设置页见 [desktop-settings.md](./desktop-settings.md)；更新源、feed 与下载链路的宿主侧语义见 [desktop-distribution.md](./desktop-distribution.md)「桌面端自动更新」。

## 用户场景与测试

### 用户故事：账户卡片 · 用量浮层内容（套餐用量 / API 余额 两个维度切换）（优先级：P1）

作为桌面端用户，我希望登录后从账户卡片**行尾用量按钮**弹出的浮层里看到用量信息（**2026-11 交互改版起收在浮层里**，浮层内的内容按本故事展示；开合与预警点见下一故事），且**两个维度互斥切换**：默认停在**套餐用量**（本周条 + 本月条 + 套餐到期日 + 计费结论行；某一维正在报警时默认改停到那一维，见下一故事场景 11），要看余额时切到 **API 余额**（已用 / 剩余 + 预警文案），以便我随时知道：套餐能用到什么时候、当前是哪个限额不足、以及现在的请求到底在扣套餐积分还是扣 API 余额——入口恒在行尾、不必去别处找，也不会被「套餐没耗尽时并不消耗」的 API 余额干扰。

**为什么是这个优先级**：账户卡片是桌面端侧边栏核心运营入口；把用量从「hover ⓘ 才出明细」升级为「一个能装下完整两维、可随时打开的视图」是账户卡片的核心变化（P1）。**2026-10-09 交互定稿**把原「套餐两根条 + API 余额行平铺」收敛为**维度切换**：套餐未用尽时 API 余额不参与计费、余额为 0 也不影响使用，故默认不占版面，维度切换取代原来的 hover ⓘ 明细气泡（气泡内容即余额维度本体）。

**独立测试**：desktop 登录态下发含 billing/apiQuota 的 `desktopAccountInfo`，**点行尾用量按钮弹出浮层后**验证默认停在**套餐维度**（**本周**在上、**本月**在下两根条 + 各维余量百分比 + `progressbar` role + 到期日），且**不渲染** API 余额块；点页签切到**余额维度**渲染「已用 ¥n / 剩余 ¥N」、套餐块与到期日让位；两维只有一维可用时**不渲染页签**、直接展示那一维（单维保留块内标题行）；切换「不限制（`limit = null`）/ 不可用（`limit = 0`）/ 触顶（`reason = month` / `week`）/ 已到期（`reason = no_plan`）/ 阻断（`mode = blocked`，三个 code）」各态验证条与结论行；table-driven 遍历每个已知 `reason` / `code` 断言结论行文案**非空**，再各给一个**规格外**取值（`reason` 与 `blocked` 的 `code`）断言渲染兜底文案 + 色调、且不再是「什么都不画 / 空文案红框」（见场景 23）；余额维度 ⓘ 的 tooltip 说明余额用途；再单独走一遍「`billing.mode` × `apiQuota.limit`」交叉矩阵：`plan` + `limit = 0` 静默（不出现「已用完」）、`api` + `limit = 0` 读「已用完」、`blocked` + 耗尽复用 402 文案、`billing` 缺省 + `limit = 0` 仍读「已用完」（见场景 14 / 24）。

**验收场景**：

1. **假设**当前请求判定走套餐（`billing.mode = "plan"`）且两维限额均为正数，**当**打开账户卡片的用量浮层，**则**浮层顶部渲染维度页签「套餐用量 / API 余额」（`role="tablist"`，默认选中**套餐用量**）与两根额度条（**本周** = 自然周、**本月** = 滚动月，**本周在上**——自然周窗口更短、更容易触顶，优先关注），每根条按自己那维的窗口量显示余量百分比 `max(0, round((1 − used / limit) × 100))`（分母为该维限额、分子为该维窗口内用量，均由宿主下发，客户端不自行推算窗口）；每根条带 `progressbar` role、`aria-valuenow` = 该维余量百分比；**无结论行**。页签选中态用 `aria-selected` 标记；有页签时「套餐用量」这一称呼由页签承担，块内不再重复一行标题。
2. **假设**某维 `limit = null`（管理员未设置 = 不限制），**当**查看该维，**则**该维**不画条**、显示「无额度限制」；另一维照常。（不得把 `null` 当 `0` —— 会把不限额的企业误报成「不可用」。）
3. **假设**某维 `limit = 0`（显式 0 = 该维度不可用）且 `billing.reason = "dimension_unavailable"`，**当**查看该维，**则**该维**不画条**、置灰显示「不可用」（**不是**「已用尽」，也不是「无额度限制」），并出现结论行「套餐额度不可用（限额为 0），当前按 API 余额计费」。
4. **假设**本人本滚动月用量触顶（`billing.reason = "month"`），**当**查看月条，**则**月条显示空条 +「0%」（**2026-10-09 交互定稿**：触顶与其余百分比同样读数字、同样常规色，条只表达余量、超用封底到 0；「哪个窗口用完、现在按什么计费」由结论行承担，不在条上重复表达「已用尽」+ 琥珀），周条照常，结论行「本月额度已用尽，当前按 API 余额计费」。
5. **假设**本人本自然周用量触顶（`billing.reason = "week"`，月未触顶），**当**查看周条，**则**周条显示空条 +「0%」，月条照常，结论行「本周额度已用尽，当前按 API 余额计费」。
6. **假设**`billing.reason = "no_plan"` 且 `billing.plan` 带 `expireDate`（存在已到期的套餐订单），**当**查看套餐块，**则**套餐块**保留**并显示到期日与结论行「套餐已到期（`<expireDate>` 到期），当前按 API 余额计费」（不再整块消失）。「已到期订单」的判据以服务端为准：`type='plan'` **且 `status='active'`**（**未作废**）且 `end_date <` 今日，与生效分支同谓词——**已作废订单不参与**，全部套餐订单已作废时视同「无套餐」（`plan = null`，落到场景 10 的兜底）。
7. **假设**`billing.reason = "enterprise"`（企业维度本期额度触顶），**当**查看套餐块，**则**本人两根条照常显示个人读数（企业池触顶不改个人数字），并渲染结论行「企业本期额度已用尽，当前按 API 余额计费」，色调为**琥珀预警**（与月/周同族：下个窗口自动恢复，不属「需人工干预」的错误色）。**2026-09-22 口径变更**：原先（2026-09-21）此原因**不渲染**结论行，理由是「漏提示优于误提示」——该理由已判定站不住：说「企业本期额度已用尽」是事实，且与个人两根条不冲突（条 = 个人读数，结论行 = 计费结论）；真正有误读风险的是把企业池的数字画成个人的条，不是这句话本身。当时（不渲染时）成员看到的是「个人两根条健康 + API 余额在掉」而毫无解释（缺陷单 3479183306383616 据此报障）。本次只补呈现层，**不动计费口径**（企业池与个人条之和的折算摩擦属产品口径、不在本场景范围）。
8. **假设**`billing.mode = "blocked"`（套餐与 API 均不可用；`code ∈ EXPIRED_NO_API / USER_QUOTA_ZERO / TEAM_QUOTA_ZERO`），**当**查看账户卡片，**则**结论行**复用 proxy 402 的同一句文案**（按 code 三选一：`EXPIRED_NO_API` =「您订购的套餐已过期，无法使用本产品！」/ `USER_QUOTA_ZERO` =「您的 API 额度已用完，请联系公司管理员分配额度后使用！」/ `TEAM_QUOTA_ZERO` =「团队 API 额度已用完，请联系公司管理员充值后使用！」）；`blocked` 不下发 `plan` 四数，故此时套餐块只有该结论行。
9. **假设**套餐块渲染且 `billing.plan` 带 `expireDate`，**当**查看**套餐维度**，**则**维度页签行右侧显示套餐到期日（`YYYY-MM-DD 到期`）；到期日属套餐信息，切到**余额维度**时不再展示（该位置改由余额的 ⓘ 占用，见场景 16）。
10. **假设**`billing.plan` 为 `null`（无生效套餐、也**没有**未作废的已到期订单），**当**查看账户卡片，**则**不渲染套餐块（未购买的企业无法登录桌面端，实际不出现；**全部套餐订单已作废**同样落在这里——作废不是到期，不得拿作废单的截止日渲染「套餐已到期」；仅作契约兜底）。
11. **假设**宿主下发了 `apiQuota` 且套餐维度也有数据，**当**点页签切到**余额维度**，**则**面板渲染两行「已用 ¥n」「剩余 ¥N」；金额格式 = ¥ 前缀 + 两位小数 + 千位分隔；两行金额**右对齐且等宽数字**（`font-variant-numeric: tabular-nums`，便于比较），随账户消息实时刷新。
12. **假设**API 余额充足（剩余 ≥ 限额 20%），**当**查看余额维度，**则**「剩余」金额以正常色展示，无预警文案。
13. **假设**API 余额不足（剩余 < 限额 20% 且 > 0），**当**查看余额维度，**则**「剩余」金额以预警色展示，并附同色提示「余额不足20%，建议及时充值」；「已用」行不套用预警色。
14. **假设**当前请求**确实按 API 余额计费**（`billing.mode = "api"`，或宿主未下发 `billing`、只下发了余额维度）且 API 余额用完（剩余 ≤ 0），**当**查看余额维度，**则**「剩余」以错误警示色（主题变量，如 `--vscode-errorForeground`）显示「已用完」（**不显示负数**），并附红色提示「额度已用完，请联系管理员充值」。**2026-11-05 修正**：`apiQuota.limit` 不得用于反推「当前是否可用」——后端 `checkApiAvailable → TEAM_QUOTA_ZERO` 下发的 `limit = 0` 语义是「此刻若降级到 API 计费会被 402」，不是「当前额度已用完」；只买试用套餐、从未充值 API 的企业该值恒为 0，照旧渲染会给「套餐还剩 99%」的账号报「额度已用完」（线上实例见 issue #2776）。**`billing.mode` 是唯一判据**，见场景 24。
15. **假设**API 不限额（`apiQuota.limit = null`），**当**查看余额维度，**则**「剩余」行显示「不限额」（正常色）、不显示金额，也不参与 20% 预警；「已用」行照常显示金额。
16. **假设**用户 hover 或键盘 Tab 聚焦余额维度的 ⓘ 图标（`data-testid="api-quota-info"`，独立按钮，`aria-label="API 余额说明"`，排在**余额维度的右上角**），**则**弹出 tooltip「将在套餐用量耗尽时使用API余额」——说明这笔余额只在套餐不可用时才参与计费。该图标与套餐维度的**到期日**处于同一类位置：两个维度各自承载自己的说明性信息，切换时互不干扰。
17. **假设**两维只有一维可用（`billing` 为空 ⇒ 只有余额；或 `apiQuota` 为空 ⇒ 只有套餐；**私有化不会被归到这一条**——它连 `apiQuota` 也不下发，落场景 22），**当**打开用量浮层，**则不渲染页签**、直接展示那一维，并在块内保留自己的标题行（「套餐用量」/「API 余额」）替代页签（仅余额这一维时，ⓘ 落到该标题行右侧——页签行没了，但 ⓘ 属余额信息，仍在该维度右上角）。
18. **假设**用户切到余额维度后在同一会话内继续操作，**当**卡片因宿主推送重新渲染，**则**停留的维度被记住（不会自动跳回套餐维度）；而**只剩一维**时自动落到仅存的那一维（不停留在已消失的维度上，避免空白面板）。
19. **假设**用户点击余额维度的**金额文本**，**当**点击发生，**则**不触发任何行为（金额非热区，仅 ⓘ 为热区，且 ⓘ 只出 tooltip、不再弹出明细气泡）。
20. **假设**用户把指针移开 ⓘ，**当**指针离开，**则**tooltip 自动消失（无需点击），不残留任何悬浮面板——原「hover ⓘ 弹出明细气泡 + 移出延迟 150ms 收起 + `Esc`/外部点击强制收起」的整套机制**随气泡一并删除**，在 `Esc` / 外部点击上不再有任何待收起的浮层。
21. **假设**余额维度处于预警态（不足 20% / 已用完），**当**切回套餐维度，**则**套餐维度不受余额预警影响（预警文案与色调只属于余额维度，不跨维度残留）。
22. **假设**宿主下发 `billing` 与 `apiQuota` 均为空/未下发（**私有化部署的常态**：codechat `GET /api/v1/account` 在 `SAAS_MODE` 非 `true` 时恒返回 `{}`——`billing` / `plan` / `apiQuota` 一个都不给，见 codechat spec `wave-desktop-account-card.md` 场景 13），**当**查看账户卡片，**则**浮层无内容可展示，个人信息行尾部的用量按钮不渲染；且**不得**把缺字段解释成「0 额度 / blocked / 不限额」——它表达的是「本部署没有额度体系」。
23. **假设**宿主下发的 `billing.reason` 是**规格外取值**（服务端先于客户端发版新增的枚举值），**当**渲染账户卡片，**则**结论行照常渲染「套餐额度当前不可用，按 API 余额计费」（**琥珀预警**）——**不得静默不渲染**（原先 `switch` 无 `default`，未识别的 `reason` 会隐式返回、结论行整块消失，用户只看到「本人两根条健康 + API 余额在掉」而零解释，与场景 7 的缺陷单 3479183306383616 同款失效）；**假设**宿主下发的 `billing.code` 是规格外取值（`mode = "blocked"`），**当**渲染账户卡片，**则**渲染兜底阻断文案「当前用量受限，请联系公司管理员」（**错误色**）——**不得渲染一条没有文案的结论行**（空红框：查表得 `undefined` 但元素照挂）；两处均按客户端既有约定 `console.warn` 记一条未知枚举日志（不新建日志/打点基建）。**2026-09-22 追加**：兜底文案「说少而准」——结论行要回答的是「为什么在扣 API」，而这件事只需 `mode = "api"` 就能确定，故不猜是哪一池（月/周/企业）用完；色调沿用本规格既有的「会不会自愈」分档（见场景 3–7 的说明）：未知原因不预设「需人工干预」（那是错误色那档的语义），给琥珀，避免无谓制造焦虑。**起因**：客户端遇到不认识的枚举就静默是同一类失效——09-22 修掉 `enterprise`（场景 7）后复核发现同类还有这两处，本次一并收口；根因是**两端不同机发布**（服务端先加枚举、客户端旧版本不认识），故除运行期兜底外，`reason` 的 `switch` 另加 `default` 分支做**编译期穷尽性检查**（`const _exhaustive: never = billing.reason`，仓内新增 `AccountBillingDegradeReason` 却忘了处理时直接编译失败——但它拦不住跨仓先发，两者都要有）。
24. **假设**`billing.mode = "plan"`（套餐可用、请求按套餐计费）而 `apiQuota.limit = 0`（只买试用套餐、从未充值 API 的企业，团队余额恒为 0；线上实例见 issue #2776），**当**切到**余额维度**，**则**该维度**不得**出现「已用完」、错误警示色或「额度已用完，请联系管理员充值」提示——剩余按数值渲染、「已用完」一侧的金额**封底到 0**（读「¥0.00」），无任何 API 侧预警/拦截结论。**假设**`billing.mode = "blocked"`（此时 API 侧是否可用已由 402 结论判定）且余额耗尽，**当**查看余额维度，**则**同样不自行下「已用完」结论，改由**余额面板内**复用 proxy 402 的同一句文案（按 `code` 三选一，与场景 8 同源；`data-testid="account-api-conclusion"`）。只有 `billing.mode = "api"`（`reason ∈ month | week | enterprise | no_plan | dimension_unavailable`）或宿主未下发 `billing`、只下发了余额维度时，`limit = 0` / 剩余 ≤ 0 才等于「当前真的用完」（降级后无套餐兜底），按场景 14 渲染。**判据只有 `billing.mode`**：客户端不得用 `apiQuota.limit` 反推可用性。

### 用户故事：账户卡片 · 用量浮层与预警点（优先级：P2）

作为桌面端用户，我希望账户卡片**默认只显示个人信息一行**，用量信息收进一层浮层——点个人信息行尾部的**用量按钮**就在卡片上方弹出与卡片等宽的浮层，看完点浮层外或按 Esc 即收起；同时**用量出问题时不能在收起态彻底沉默**，用按钮右上角的一颗小圆点告诉我「这里有事」，以便卡片保持清爽但不会漏掉余额不足、额度耗尽这类预警。

**为什么是这个优先级**：空间收纳是浮层的辅助能力，先保证浮层里的展示正确（P1 故事）后再谈收纳。**2026-11 交互改版**：原「默认展开 + 显隐按钮就地收起/展开」改为「默认收起 + 点击弹出浮层」——就地展开会把卡片顶高、把侧边栏下方的会话列表往下推，弹层则不改变卡片高度；收起态下预警不可见，故保留一颗点透出（用户否掉了「不提示」与「有预警自动展开一次」两个方案）。**入口限定在行尾用量按钮**：个人信息行热区仍然只开纯功能菜单，一颗入口做一件事。

**独立测试**：登录态进入卡片验证无浮层、卡片仅剩个人信息一行、按钮 icon 为仪表盘（dashboard）且 `aria-label="查看用量"`、`aria-haspopup="dialog"`；点按钮验证浮层出现且内容按 P1 故事展示（默认停在**套餐维度**）、与卡片等宽、底边贴个人信息行顶向上弹；再点按钮 / 点浮层外 / 按 Esc 验证收起（打开后焦点进入浮层；**键盘打开的**按 Esc 或再点一次按钮收起后焦点回到按钮，鼠标打开的焦点不抢）；打桩 `getBoundingClientRect` 后改窗口高度并派发 `resize`，验证浮层**与菜单**的 `bottom` 都随锚点重算（不跟卡片分家）；同一套桩把个人信息行顶压到视口顶部附近，验证浮层 `maxHeight` 跟着收缩、不越过视口顶；把 `documentElement.clientWidth/clientHeight` 打桩成小于 `innerWidth/innerHeight`（模拟滚动条），验证浮层右缘按前者算；重新挂载验证**仍回到收起态**（不记忆）；分别用「套餐正常 / 周月耗尽 / 余额不足 20% / 余额耗尽 / 套餐已到期 / 被阻断」场景验证圆点有无与颜色，并验证读屏文案分「有预警」「有预警，需处理」两档；浮层开着时点热区验证菜单打开、浮层收起（互斥）；`billing`+`apiQuota` 均未下发时验证用量按钮不渲染。

**验收场景**：

1. **假设**用户进入桌面端（组件挂载，含重新打开客户端、切换会话后重新挂载），**当**查看账户卡片，**则**卡片只渲染个人信息行（无用量块、无页签、无浮层），个人信息行尾部用量按钮 icon 为仪表盘（dashboard，`aria-label="查看用量"`、`aria-haspopup="dialog"`、`aria-expanded="false"`）；收起状态**不做持久化**，每次挂载都回到收起态（**2026-11-05 交互定稿**：用户明确选「每次都收起」，不记住上次的开合选择）。
2. **假设**当前**没有任何用量预警**，**当**查看用量按钮，**则**按钮上**不出现任何角标**（保持干净）；圆点只在真有预警时挂上。
3. **假设**当前**存在用量预警**，**当**查看用量按钮，**则**按钮右上角出现一颗 **6px 实心圆点**（距按钮上边缘、右边缘各 2px，`pointer-events: none` 不参与点击）；严重度**不能只靠颜色**表达（圆点本身 `aria-hidden`），读屏 `aria-label` 按档区分：「**查看用量（有预警）**」= 琥珀档（会自愈），「**查看用量（有预警，需处理）**」= 红档（需人工干预）；无预警时只用「查看用量」。

### 用户故事：账户卡片 · 用量刷新时机（响应头驱动 + 打开浮层时核对）（优先级：P2）

作为桌面端用户，我希望**用量数字在我真正消耗额度的时刻刷新**——每次模型调用的响应里就带着当时的额度读数，卡片（含收起态的预警点）因此当场变色；我点开用量浮层时，客户端再向账户接口核对一次全量状态（套餐到期日、企业池、余额），以便我不必等一分钟的定时轮询、也不会在私有化部署下被客户端每分钟白打一次恒返回空对象的接口。

**为什么是这个优先级**：这是**数据刷新链路**的改造（配额仍然由既有故事渲染，本故事不改任何展示口径），排在展示与交互定稿之后。**2026-11-06 定稿（A 形态）**：服务端（codechat issue #51）已在 proxy 每次模型调用上发出 `x-codechat-quota-*` 头（数值就是闸口那一次 `getBillingVerdict` 的结果，**零额外查询**），故「每次调用都在变」的读数改由响应头搭载；`GET /api/v1/account` 保留但**降频到「点开用量浮层时核对一次」**，**60 秒定时轮询删除**——它在私有化下每分钟打一次恒返回 `{}` 的接口，而真正的变化时刻本来就有响应可搭载。已接受的代价：共享 API 余额被同事消耗时，最长到下次打开浮层才发现（预警点在本人发起调用时立即跟上）。

**独立测试**：给宿主喂一组带 `x-codechat-quota-*` 的响应头，验证 `desktopAccountInfo` 随之推送且 `billing` / `apiQuota` 按映射表（见「额度响应头」小节）更新——table-driven 覆盖 plan / api（含 `no_plan` 只有到期日）/ blocked / 只有 `api-*`（只更新余额维度）/ 一个头都没有五类，以及 `limit` 三态解码（`unlimited` → `null`、`unavailable` → `0`、数字原样）与 `api-limit` 的两态（`unlimited` → `null`、`0` → 已用完）；喂一组头缺失或数值不可解析的响应，验证**不推送、不请求、不错写成 0**；模拟 402（`code` + 头）与上游 429/5xx（错误响应同样带头）两条错误路径，验证读数照常刷新；用 fake timers 断言登录后**不再有**任何周期性 `getAccountInfo` 请求（删轮询）；webview 侧点开浮层验证发出**一次** `desktopRefreshAccountUsage`、且收起再打开会再发一次。

**验收场景**：

1. **假设**用户在会话里发起一次模型调用，**当**该次调用的响应带 `x-codechat-quota-*` 头，**则**宿主把头顶层的读数映射成新的 `billing` / `apiQuota` 并推送 `desktopAccountInfo`——卡片收起态下预警点立刻跟上（用的还是既有判定：结论行 tone / 余额不足 20% / 已用完），浮层开着时两根条与结论行当场更新；用户无需任何额外操作。
2. **假设**响应是**非 2xx**（proxy 402 阻断、上游 429 被限流、5xx），**当**错误响应同样带头，**则**读数**照常刷新**（402 当场变「被阻断」结论行 + 红档预警点；429/5xx 也刷新余量）——错误路径的头与成功路径**同等对待**，不能只看成功响应。
3. **假设**头里的读数是「本次调用**前**」的快照（流式响应在首字节前就把头发完、扣费在流结束后），**当**客户端渲染，**则**不得据此反推本次消耗、不得把「读数与上次相同」当成「这次没计费」，也不得自行 +1 或做任何补偿；下一次调用会用新的快照把差异补上。
4. **假设**用户在浮层收起态点开用量按钮，**当**浮层打开，**则** webview 向宿主发**一次** `desktopRefreshAccountUsage`，宿主调 `getAccountInfo` 做一次全量核对（套餐两根条、到期日、结论行、企业池、API 余额）并推送；**一次打开只发一次**（不随渲染反复发、不因页签切换再发）；核对失败时**保留上次成功显示**，不弹错、不清空（与既有「失败保留」口径一致）。
5. **假设**登录态发生变化（登录 / 登出 / 切换主机）或宿主首次拿到账户数据，**当**状态变化，**则**照旧推送 `desktopAccountInfo`；**此后没有任何周期性请求**——刷新的触发源只有三个：**账户状态变化的推送**、**每次带额度头的响应**、**打开浮层时的那一次核对**（60 秒定时轮询删除，见边界情况）。
6. **假设**响应里**没有任何** `x-codechat-quota-*` 头（私有化部署、自定义网关、中间层剥掉了不认识的响应头、或对端根本不是 codechat），**当**收到该响应，**则**不更新**任何**用量数据、**不触发**任何额外查询，已有数据保持不变；用量区仍按「有没有用量数据」渲染（`billing` / `apiQuota` 双缺 = 不渲染，见上一故事场景 22）——客户端**不判部署模式**，「没有头」就是「这次没有新信息」，不等于「0 额度 / 不限额 / 被阻断」。
7. **假设**头解析：`limit` 三态解码为 `unlimited → null`（不限制）、`unavailable → 0`（该维度不可用）、数字原样；`api-limit` **只有两态**（`unlimited → null`、数字原样 —— API 余额是充值制，`0` 就是「已用完」，与套餐侧的 `0` 语义不同）；**数值不可解析（非数字、负数、空串）时该项按「没给」处理**（不更新、不错写成 0，避免把健康的账号渲染成「已用尽」）。
8. **假设**头里**没有** `api-*` 三个字段（`ok_plan` 路径故意不发：套餐可用时不查 `api_quotas`，没有数字可发），**当**映射 `apiQuota`，**则**保留上次已知的 `apiQuota`、不清空——否则正停在余额维度的用户会被下一次套餐计费调用的响应把余额行挤掉（`apiQuota` 从此只在「打开浮层核对」与「头里确实给了 `api-*`」两种时机变化）。
9. **假设**同一份 `billing` 既来自响应头也来自账户接口，**当**两者先后写入，**则**后到的覆盖先到的、不做新旧比较也不打时间戳——两者数值同源（服务端 proxy 闸口与账户卡片共用 `getBillingVerdict` 同一份判定），差异只可能是「一次调用的时间差」；客户端**不得**为了对齐两者而额外请求。
10. **假设**该响应同时带 `x-codechat-quota-utilization` / `-surpassed-threshold` / `x-codechat-quota-status`，**当**渲染预警，**则**仍按浮层既有的「剩余 < 限额 20%」自算，**不**改用头里的阈值——同一件事只有一套阈值，避免头（0.8）与浮层（20%）两处算法给出不同档位；`claim` / `reset` / `weekly-reset` / `monthly-reset` 当前**只解析、不渲染**（重置时刻与「哪个窗口用完」由到期日与结论行承担，见故事一场景 4–7）。

### 用户故事：账户卡片 · 个人信息行与纯功能菜单（优先级：P1）

作为桌面端用户，我希望点击头像/姓名热区弹出**纯功能菜单**（设置/企业控制台/帮助文档/退出登录），菜单贴着个人信息行向上弹出、与卡片等宽，再次点击热区或失焦/Esc 可收起，以便操作账户相关功能且不被用量信息干扰。

**为什么是这个优先级**：这是账户卡片新模型对既有「更多按钮 + 用量浮层」双入口的**结构性替换**（已登录不再有独立「…」更多按钮），是账户卡片的核心差异，必须最先明确（P1）。

**独立测试**：登录态验证热区点击开/关菜单、菜单含 4 项且无用量块、贴行弹出、与卡片等宽（右缘对齐）；点击外部与 Esc 收起；方向键/Enter/Space 键盘操作；未登录态验证整条登录按钮 + 更多按钮仍保留；远程主机标注。

**验收场景**：

1. **假设**用户未登录，**当**查看账户卡片，**则**显示整条「登录」按钮（占满卡片宽度）+ 右侧「更多」（…）按钮；点登录走现有 SSO 流程；「更多」菜单含登录项。
2. **假设**用户已登录，**当**查看个人信息行，**则**显示头像（邮箱前缀首字母圆形占位）+ 姓名（邮箱前缀；无邮箱显示「已登录」），行尾部为更新按钮（有更新时）+ 用量按钮（打开用量浮层）；**不显示独立「…」更多按钮**。
3. **假设**已登录用户点击头像/姓名热区（`data-testid="account-card-hotzone"`，热区 `aria-expanded` 反映菜单开合，支持 Enter/空格开合），**当**菜单展开，**则**菜单**纯功能、仅 4 项**：「设置 / 企业控制台（↗）/ 帮助文档（↗）/ 退出登录」（退出登录为危险色 + 上方分隔线），**不含任何用量信息**。
4. **假设**菜单打开，**当**查看菜单，**则**菜单**向上弹出**、盖住卡片上方内容（不遮挡个人信息行）；内容自动换行、不超出面板。
5. **假设**菜单已打开，**当**再次点击个人信息热区，**则**菜单收起（toggle）；若用量浮层同时开着，则按下一故事的互斥规则先收起浮层。
6. **假设**菜单已打开，**当**点击菜单外部任意区域或按 `Esc`，**则**菜单收起（焦点回到触发热区）。
7. **假设**菜单已打开，**当**使用键盘（方向键在菜单项间移动焦点、Enter/Space 激活、Esc 关闭——roving tabindex），**则**焦点按方向键循环移动，激活项执行对应行为。
8. **假设**用户选择菜单项，**当**点击「设置」，**则**打开设置页面；点击「企业控制台（↗）」则打开对应网址（新标签页/外部）；点击「帮助文档（↗）」则浏览器新标签页打开 `serverUrl + /docs`；点击「退出登录」则执行登出并回到未登录卡片态。
9. **假设**账户卡片处于远程主机会话（host 非 local），**当**查看菜单，**则**「设置 / 退出登录」项旁标注主机名（如「设置（prod）」），本地主机不标注；用量与菜单登录项跟随聚焦分屏所属主机。

### 用户故事：账户卡片 · 更新按钮状态机 S0–S3（优先级：P2）

作为桌面端用户，我希望新版本在后台安静下载好，等我想升级时点开「更新」，先看清这一版改了什么，再决定什么时候重启，以便升级既不打断当前工作，也不用为一次升级多做无谓的点击或看一屏自动弹出的窗口。

**为什么是这个优先级**：按钮状态机依赖宿主下发 `update` 快照并响应重启命令，涉及 desktop 主进程改动（宿主须把 electron-updater 事件映射为快照并响应 `desktopUpdateRestart` 命令）；宿主侧就绪前按钮无数据可渲染，故整体排 P2（在 P1 的用量常驻/菜单稳定后接线）。webview 侧状态机与宿主接线均属本规格验收范围。

**产品口径：后台下载完全静默、重启前保留一次知情与确认（2026-11-06 定稿）**。这一版把更新收成两下：**宿主检查命中即在后台下载，下载中与下载失败都不显示任何按钮**（不转圈、不占位、不弹窗）；**下载完成才出现「更新」按钮**，点开是「重启以完成更新」确认框——正文下面是本次更新内容（release notes），底部「稍后 / 立即重启」，由用户看完再点一下「立即重启」。**不自动弹框、不自动重启**：下载可能在用户专注工作时完成，弹窗会打断；而重启一定要由用户按下。演进：更早的版本要求下载前再确认一次（旧「更新到新版本」对话框），一次更新最少点三下（更新 → 下载更新 → 立即重启）；同日早先的版本改为「下载中显示『正在下载』disabled + 就绪自动弹一次确认框」（一次点击，但会主动打断），最终按本节口径定稿。代价（已接受）：下载中用户看不到任何进度，弱网下也看不到「正在下」的状态，只能等按钮出现；发现即下载，计量网络下会主动吃流量，且没有「先别下」的入口。

**独立测试**：webview 侧（1）`update` 为 `null` / `available: false` 时不渲染按钮；下发 `{ available: true, version, releaseNotes }` 时按钮呈现「更新」且**不自动弹出任何对话框**、不发任何命令；（2）点击按钮弹出「重启以完成更新」确认框（按钮「稍后 / 立即重启」），[稍后] 关闭后按钮仍在并可再次打开，[立即重启] 发 `desktopUpdateRestart`；（3）快照带 `releaseNotes`（数组，含两个版本）时确认框按版本分段渲染「本次更新内容」块（段标题 `vX.Y.Z`、新 → 旧、块内滚动、不撑破按钮区），空数组/缺失时不渲染该块、确认框其余部分逐字不变；宿主侧用例覆盖：`update-available` **不推送**快照（按钮不出现）、`update-downloaded` 才推 `available: true` + 过滤后的 `releaseNotes`、归一化（字符串 → 单元素数组、数组按已装版本过滤 + 坏版本号丢弃 + 倒序、过滤后为空不下发）、下载失败只记日志不推可点状态。

**验收场景**：

1. **假设**无更新、或宿主仍在后台下载、或下载失败，**当**查看个人信息行，**则**不显示更新按钮（S0）：下载中不出现「正在下载」之类的进行中态，也不提供取消入口；下载失败静默，等下一次检查（运行期轮询 / 下次启动）自动重试。
2. **假设**宿主完成下载（`update.available: true`），**当**查看个人信息行，**则**显示「更新」按钮（S1）——品牌红实底的主行动样式；**不自动弹任何对话框、不抢焦点、不发命令**。
3. **假设**用户点击「更新」，**当**点击，**则**弹出居中的「重启以完成更新」确认框（S2）：标题「重启以完成更新」，正文提示「新版本已就绪，重启后生效。重启会中断正在运行的任务，建议先保存工作。是否立即重启？」，按钮「稍后 / 立即重启」；**不自动重启**。**当**快照还带 `releaseNotes`（宿主**已按已装版本过滤、按版本倒序**的数组，来源与口径见 [desktop-distribution.md](./desktop-distribution.md)「更新内容（Release Notes）」），**则**在正文下方渲染「本次更新内容」块：**每一项一段**，段标题为版本号 `vX.Y.Z`，其下是该版本的平铺变更条目（即使只有一项也保留版本号段标题——渲染形态只有一种）；段落之间按数组顺序（新 → 旧）排列，块整体限高滚动（超出对话框可视高度时块内滚动，不得撑高对话框挤坏按钮区）。条目是该版本的 markdown 文本，用仓库已有的 `marked` + `DOMPurify` 渲染，仅允许段落/列表/加粗等轻量语法，**不得渲染可点击链接**（生成的记录本身不含链接与作者）——记录块是纯展示，无可交互元素、无折叠、无「查看全部」。`releaseNotes` 缺失 / 空数组 / 所有项 `note` 为空或仅空白时**不渲染该块**，确认框标题、正文、按钮与交互与无记录时逐字一致。这一屏对齐 Electron 官方的 auto-updater 最佳实践（`update-downloaded` 时把 `releaseNotes` 放进取舍框），不新增状态机步骤。
4. **假设**用户在确认框点击「稍后」（或按 `Esc`、点对话框外部——与「稍后」等价），**当**对话框关闭，**则**按钮保持「更新」，期间应用可正常使用；再次点击按钮重新弹出同一确认框。
5. **假设**用户点击「立即重启」，**当**确认重启，**则** webview 向宿主发送 `desktopUpdateRestart` 命令，更新状态复位、按钮消失（S3）；是否实际退出安装由宿主处理。这是用户在这次更新里唯一的「执行」点击（连同打开确认框的那一下，共两下）。

## 边界情况

- **未登录**：账户卡片仅登录按钮 + 更多按钮；无用量浮层、无个人信息行、无更新提示（没有用量时用量按钮也不显示）。

- **未配置套餐 / 均未下发**：`billing.plan` 为 `null`（无生效套餐、且没有未作废的已到期订单——从未购买、或订单已全部作废）时套餐块不渲染；`billing` 与 `apiQuota` 均未下发（私有化部署的常态，见下条「私有化部署」）时用量浮层没有内容、用量按钮不渲染。

- **套餐三态别混**：`limit = null`（不限制）与 `limit = 0`（不可用）是两种状态，**都不画条**，但文案与视觉必须区分；触顶（该维 `used ≥ limit`）读「0%」（空条 + 常规色，2026-10-09 起）——条只表达余量、超用封底到 0，「哪个窗口用完 / 现在按什么计费」由结论行回答。旧「整单大池子」口径（`monthlyQuota × months`）随旧 `plan` 字段一并退出卡片：后端仍保留旧字段兼容已发布客户端，新卡片不再取数。

- **用量浮层内 = 两个互斥维度**（2026-10-09 交互定稿）：套餐用量与 API 余额不并列展示，用页签切换，默认套餐维度。理由是二者地位不对等——套餐没耗尽时 API 余额不参与计费、余额为 0 也不影响使用，故默认不占版面；两维**只有一维有数据**时不渲染页签、直接展示那一维。维度选择是卡片内的视图状态（不落盘、不跨会话）。

- **结论行优先级**：`blocked` > 不可用（`dimension_unavailable`）> 已用尽（月优先于周）> 无结论行；`enterprise` **照渲染**（企业本期额度触顶 ⇒ 琥珀预警，与月/周同档；2026-09-22 起，原先刻意不渲染）。

- **枚举是开放集合（服务端可能先于客户端发版）**：`billing.reason` / `billing.code` 的新取值由服务端先上线、已发布的客户端不认识（两端不同机发布）。客户端**必须**对未识别取值给兜底结论行（文案与色调见场景 23），**不得静默**；兜底文案**不含对具体原因的猜测**（不点名月/周/企业哪一池用完）。**spec 背书、因此维持不渲染**的三种情形（本次不碰、也不是缺陷）：`mode = "plan"`（套餐可用，无话可说）、`reason = "no_plan"` 且 `plan = null`（从未购买或订单已全部作废，无到期日可讲）、`billing` 与 `apiQuota` 双缺（用量区整体不渲染，= 私有化部署，见「边界情况」的私有化条）。

- **API 余额**（余额维度）：面板两行「已用 / 剩余」，金额右对齐 + 等宽数字；剩余 < 限额 20% 金额预警色 + 琥珀提示；剩余 ≤ 0 显示「已用完」错误色 + 红色提示；`limit = null` 显示「不限额」。ⓘ 排在**余额维度的右上角**（与套餐维度的到期日同一处，不回金额行，见场景 16），只出 tooltip 说明用途。

- **`apiQuota.limit` ≠ 可用性**（2026-11-05）：`limit` 只是「此刻若降级到 API 计费还能用多少」，不是「当前能不能用」——`TEAM_QUOTA_ZERO` 下未充值企业恒得 `limit = 0`，而套餐可能还剩大半。故余额维度的「已用完 / 预警色 / 红色充值提示」只在 `billing.mode = "api"` 或 `billing` 缺省（宿主只下发了余额维度）时出现；`mode = "plan"` 一律按数值渲染（封底 0，「¥0.00」），`mode = "blocked"` 改用 proxy 402 文案（面板内 `account-api-conclusion`）。客户端**不得**用 `apiQuota.limit` 反推计费结论（issue #2776）。

- **下载中**：更新按钮 disabled，点击无反应；不提供取消入口。

- **对话框**：重启确认框（S2）点对话框外部不关闭，`Esc` / 「稍后」等价；不自动关闭、不自动重启。

- **远程主机**：个人信息菜单「设置 / 退出登录」标注主机名；用量与登录态跟随聚焦分屏所属主机。

- **用量数据刷新失败**：打开浮层时的核对请求失败（网络错误 / 超时 / 服务端 5xx）或推送写不进去时，**保留上次成功显示**——不清空、不弹错、不把卡片降级成「没有用量」；下一次带头的响应或下一次开浮层再补上。

- **60 秒轮询已删除**（2026-11-06，A 形态）：不再有任何周期性的 `GET /api/v1/account`。刷新只剩三个触发源——账户状态变化的推送、每次带 `x-codechat-quota-*` 的响应、打开用量浮层时的一次核对（场景 5）。收益：私有化部署不再每分钟打一次恒返回 `{}` 的接口；代价（已接受）：共享 API 余额被同事消耗时，最长到下次打开浮层才发现。

- **额度头是热路径上的免费输出**：头里的数字全部来自 proxy 那一次 `getBillingVerdict`（零额外 DB 查询），故客户端**不得**因为「头不全」就去补一次账户接口请求——头缺什么就只更新它给了的那几个字段（场景 7、8），也不得为解析头新增任何定时器或后台任务。

- **头的值一律纯 ASCII 英文标识**（`month` / `unlimited` / `EXPIRED_NO_API` 等），中文文案由客户端映射；服务端新增的未知 `reason` / `code` 取值仍走上一故事场景 23 的兜底文案，不得静默（两端不同机发布，头与会话接口同一个风险面）。

- **私有化部署整块不下发**（2026-11-06 对齐 codechat 定稿）：codechat `GET /api/v1/account` 在私有化（`SAAS_MODE` 非 `true`，**未设置即私有化**，判定入口是 codechat 的 `deploymentMode.ts`）下**恒返回空对象 `{}`**——`billing` / `plan` / `apiQuota` 一个都不给（三块数据全由套餐订单 / API 充值订单 / `api_quotas` 派生，私有化不部署运营端、这些数据不存在）。客户端以「**`billing` 与 `apiQuota` 双缺**」为「本部署没有额度体系」的信号：用量按钮整颗不渲染、不出现任何额度结论行，且**不得**解释成 0 额度 / blocked / 不限额三者中的任何一个。判据为什么是「双缺」而不是 codechat spec 措辞里的「缺 `billing` 为唯一信号」：本规格的场景 14 / 17 / 24 明确支持「宿主只下发余额维度」这一契约形态（`billing` 缺、`apiQuota` 在 ⇒ 只展示余额），而私有化两者**都**缺，两条口径在私有化下结论一致、不冲突。桌面端**拿不到部署模式字段**（`saasMode` 只随企业端登录响应与权限目录下发，wave 的 `getAuthStatus` 只回 `isAuthenticated` / `user`），因此客户端**不做**任何「是不是私有化」的判断，只按「有没有用量数据」渲染；SaaS 下非 active 成员（待审核 / 已拒绝 / 已禁用 / ops_admin）同样是空对象，走同一条路径。

## 数据契约与命令

### desktopAccountInfo（窗口级推送，无 paneId）

`update?` 字段承载更新按钮状态机输入（S0–S3），完整契约如下：

```ts
export interface AccountUpdateInfo {
  available: boolean; // 新版本已下载完成、可重启（下载中宿主不推快照）
  version?: string; // 新版本号（宿主从 UpdateInfo.version 带回，随快照下发）
  /** 变更记录，宿主已按「已装版本」过滤并按版本倒序（每项一段，见场景 3）。
   *  取自 electron-updater 的 `UpdateInfo.releaseNotes`，来源与生成口径见
   *  desktop-distribution.md「更新内容（Release Notes）」。
   *  缺失 / 空数组 = 没有可展示的记录，确认框不渲染记录块。 */
  releaseNotes?: Array<{ version: string; note: string }>;
}

/** 套餐两根额度条的四个数 + 到期日（codechat `GET /api/v1/account` → `billing.plan`）. */
export interface AccountBillingPlanUsage {
  monthUsed: number;
  monthLimit: number | null; // 滚动月限额；null = 不限制，0 = 该维度不可用
  weekUsed: number;
  weekLimit: number | null; // 自然周限额；null = 不限制，0 = 该维度不可用
  expireDate: string; // 套餐到期日（YYYY-MM-DD）
}

/**
 * 降级原因（客户端据此选结论行文案；枚举由后端定义，见 codechat spec 场景 5–11）.
 * 五个原因**各有结论行**（`enterprise` 自 2026-09-22 起也渲染，见场景 7）；唯一
 * 「不渲染」的组合是 `no_plan` 且 `plan = null`（从未购买）。
 * 该类型只是**客户端侧的枚举快照**：服务端可能先发版新增取值，客户端必须对规格外
 * 取值渲染兜底结论行（见场景 23），不得静默。
 */
export type AccountBillingDegradeReason =
  | "month"
  | "week"
  | "enterprise"
  | "no_plan"
  | "dimension_unavailable";

/** 阻断码（客户端按 code 复用 proxy 402 文案；同样只是枚举快照，规格外取值走场景 23 的兜底文案）. */
export type AccountBillingCode =
  | "EXPIRED_NO_API"
  | "USER_QUOTA_ZERO"
  | "TEAM_QUOTA_ZERO";

/**
 * 计费结论（codechat 形态甲：闸口镜像）。判定出自后端 `getBillingVerdict`——与 proxy 扣费
 * **同一份代码**；客户端只渲染、**不自行判断「走套餐还是走 API」**（旧方案由客户端比较数字，
 * 已因限额「0」语义翻转发生过一次静默失效）。`plan` 子对象：有生效套餐 = 四数 + 到期日；
 * 无生效套餐但有**未作废**的已到期订单 = 仅 `{ expireDate }`；从未购买、或订单已全部作废 = null。
 */
export type AccountBillingInfo =
  | { mode: "plan"; plan: AccountBillingPlanUsage }
  | {
      mode: "api";
      reason: AccountBillingDegradeReason;
      plan: AccountBillingPlanUsage | { expireDate: string } | null;
    }
  | { mode: "blocked"; code: AccountBillingCode };

export interface DesktopAccountInfoMessage {
  command: "desktopAccountInfo";
  isAuthenticated: boolean;
  user?: { id: string; email?: string } | null;
  billing?: AccountBillingInfo | null; // 套餐两根条 + 到期日 + 计费结论
  apiQuota?: AccountApiQuotaInfo | null; // { limit: number|null, used }
  update?: AccountUpdateInfo | null; // 应用更新状态（非 null = 就绪可重启，S1 起）
}
```

**下发规则**：

- 未登录：`isAuthenticated: false`，`billing`/`apiQuota`/`update` 可不带。
- 无生效套餐、且没有未作废的已到期订单（从未购买，或订单已全部作废）：`billing.plan: null`（套餐块不渲染）；`billing` 与 `apiQuota` 均未下发时用量浮层没有内容、用量按钮不渲染。
- API 不限额：`apiQuota.limit: null`（共用团队余额）。
- 无更新：不带 `update` 或 `update.available: false`。
- `releaseNotes` 由宿主从 electron-updater 的 `UpdateInfo.releaseNotes` **归一化并按已装版本过滤**后下发（generic provider 把 feed `latest*.yml` 里的同名字段原样透传上来）：**数组**形态逐项保留 `compareVersions(parseVersion(item.version), parseVersion(app.getVersion())) > 0` 的项、版本号不可解析的项丢弃、结果按版本倒序；**字符串**形态包装成单元素数组 `[{ version: info.version, note }]`；过滤后为空、缺字段、空串/仅空白一律不下发（webview 按 S2 场景 4 不渲染记录块）。**版本比较只在宿主做**——webview 不认识版本比较，只渲染收到的数组，也不做任何过滤或排序。
- 账户/用量/结论/更新状态变化时宿主主动推送新快照；轮询失败保留上次成功数据。
- **宿主只做透传**：`billing` 有两个来源，都是服务端同一份判定（proxy 闸口与账户卡片共用 `getBillingVerdict`）——① codechat `GET /api/v1/account` 下发，经 CLI `getAccountInfo` → desktopHost `accountCache` 原样带到卡片（只在打开浮层时核对一次）；② 模型响应头 `x-codechat-quota-*`，由宿主按下方「额度响应头」小节映射成同一份契约。宿主**不重算**任何判定或窗口（窗口起点、限额聚合口径都在服务端，客户端一无所知）。

### 额度响应头 `x-codechat-quota-*`（模型调用响应 → 宿主输入）

模型调用的响应（proxy 转发）在**每次调用**上带一组额度头，数值即该次闸口判定的结果。19 个字段（缺失 = 本维度没有数据，不得用 `0` 或 `rejected` 表达）：

| 头                                             | 取值                                                                  | 说明                                                                                |
| ---------------------------------------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `x-codechat-quota-status`                      | `allowed` / `allowed_warning` / `rejected`                            | 有快照即恒发。本规格只用来判断「这次带了额度头」；预警档位仍按浮层自算（场景 10）   |
| `x-codechat-quota-claim`                       | `weekly` / `monthly` / `enterprise` / `api` / `none`                  | 代表性限额（哪一池最可能先触顶）。只解析、不渲染                                    |
| `x-codechat-quota-reset`                       | unix 秒                                                               | 代表限额的重置时刻；`claim` 为 `api` / `enterprise` / `none` 时省略。只解析、不渲染 |
| `x-codechat-quota-weekly-used`                 | 数字                                                                  | 本自然周已用积分                                                                    |
| `x-codechat-quota-weekly-limit`                | 数字 / `unlimited` / `unavailable`                                    | 三态：`null`→不限制、`0`→该维度不可用、正数→限额                                    |
| `x-codechat-quota-weekly-reset`                | unix 秒                                                               | 本窗口重置时刻（下周一 00:00，北京时间）。只解析、不渲染                            |
| `x-codechat-quota-weekly-utilization`          | `0`–`1`（4 位小数）                                                   | 该维限额为正数时才发。只解析、不渲染                                                |
| `x-codechat-quota-weekly-surpassed-threshold`  | `0.8`                                                                 | 越过 80% 才发。只解析、不渲染                                                       |
| `x-codechat-quota-monthly-used`                | 数字                                                                  | 本滚动月已用积分                                                                    |
| `x-codechat-quota-monthly-limit`               | 数字 / `unlimited` / `unavailable`                                    | 同周三态                                                                            |
| `x-codechat-quota-monthly-reset`               | unix 秒                                                               | 本窗口重置时刻。只解析、不渲染                                                      |
| `x-codechat-quota-monthly-utilization`         | `0`–`1`（4 位小数）                                                   | 限额为正数时才发。只解析、不渲染                                                    |
| `x-codechat-quota-monthly-surpassed-threshold` | `0.8`                                                                 | 越过 80% 才发。只解析、不渲染                                                       |
| `x-codechat-quota-plan-expire`                 | `YYYY-MM-DD`                                                          | 有生效套餐（或仅剩已到期订单）时才发                                                |
| `x-codechat-quota-reason`                      | `month` / `week` / `enterprise` / `no_plan` / `dimension_unavailable` | 降级原因，只在判定走 API 时下发                                                     |
| `x-codechat-quota-code`                        | `EXPIRED_NO_API` / `USER_QUOTA_ZERO` / `TEAM_QUOTA_ZERO`              | 402 阻断码                                                                          |
| `x-codechat-quota-api-status`                  | `allowed` / `rejected`                                                | 只在判定走 API 时下发（`ok_plan` 路径不查 `api_quotas`，三个 `api-*` 一个都不发）   |
| `x-codechat-quota-api-used`                    | 数字                                                                  | 同上                                                                                |
| `x-codechat-quota-api-limit`                   | 数字 / `unlimited`                                                    | 充值制：`0` 就是「已用完」（与套餐侧 `0` 语义不同）                                 |

**映射（只在宿主做一次，webview 认原契约）**：

| 头里有什么                                       | → `billing`                                                                                                         | → `apiQuota`                         |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| `-code`（或 `status = rejected`）                | `{ mode: "blocked", code }`（`code` 未知时原样透传，webview 走上一故事场景 23 的兜底文案）                          | 有 `api-*` 则按右边更新              |
| `-reason`                                        | `{ mode: "api", reason, plan }`：两根条四数齐 ⇒ 四数 + 到期日；只有 `plan-expire` ⇒ `{ expireDate }`；都缺 ⇒ `null` | 同上                                 |
| 无 `-reason`、无 `-code`，两根条在               | `{ mode: "plan", plan: 四数 + 到期日 }`                                                                             | 通常不下发（`ok_plan` 不发 `api-*`） |
| 无 `-reason`、无 `-code`、无两根条，只有 `api-*` | **不下发**（webview 走「只下发余额维度」形态，见上一故事场景 17 / 24）                                              | 按 `api-*` 更新                      |
| 一个头都没有                                     | 不动                                                                                                                | 不动                                 |

- `apiQuota` 由 `api-limit`（`unlimited`→`null`）+ `api-used` 组装；`-api-*` 缺省时**保留上次值**（场景 8）。
- `blocked` 快照在服务端结构上**可能仍带两根条四数**（`quotaFromVerdict` 的 `base` 对 blocked 也生效），但 webview 的 `blocked` 分支本来不画条（故事一场景 8），故映射时**丢弃**——不为此扩张契约。
- **时序**：流式响应在首字节前设头 ⇒ 头里是「本次调用前」的读数；非流式与 402 / 上游错误路径同值。客户端不得据此反推本次消耗（场景 3）。
- **私有化不发任何头**：服务端私有化短路路径根本不生成快照，因此一个 `x-codechat-quota-*` 都不发（不是发 0、也不发 `rejected`）——与 `GET /api/v1/account` 恒返回 `{}` 同源。客户端以「这次没有头」处理（场景 6），**不判部署模式**。
- **传递链（实现约束）**：agent-sdk 在每次请求返回后从响应头筛出这批字段（成功响应取 `response.headers`；错误响应取 **SDK 自己抛出的 HTTP 错误对象上的 `.headers`** —— 这一层必须把响应头挂到错误上，否则 402/429 的读数会在热路径上丢掉），经 CLI → stdio 通知送到 desktopHost，由宿主一处映射。VS Code / JetBrains 宿主当前不消费该通知（它们没有本规格的账户卡片）。

### 套餐额度条计算（按余量计）

```
barPercent(used, limit) = max(0, round((1 − used / limit) × 100))    // limit > 0
```

- 每根条用**自己那维**的数（月条 = monthUsed/monthLimit，周条 = weekUsed/weekLimit）；`limit = null` 或 `0` 时不画条（分别显示「无额度限制」「不可用」）。
- 100% = 满（未使用）；触顶时该条显示**空条 +「0%」**（常规色，2026-10-09 起）。

### 命令契约

- `desktopUpdateRestart`（webview → host）：用户在重启确认框选择「立即重启」后通知宿主安装并重启（S3）。这是更新流程里唯一由 webview 发出的命令——下载由宿主自己开始，不需要 webview 参与。
- `desktopRefreshAccountUsage`（webview → host）：**打开用量浮层时发一次**，宿主据此调 `getAccountInfo` 核对全量用量（套餐两根条 + 到期日 + 结论行 + 企业池 + API 余额）并推送新的 `desktopAccountInfo`；失败保留上次成功数据。这是取代 60 秒轮询的主动核对时机（见「用量刷新时机」故事场景 4）。桌面端专属命令（`desktop` 前缀），只需注册桌面端路由。
- **宿主接线**：宿主（desktopHost.ts）把 electron-updater 事件映射为 `update` 快照随 `desktopAccountInfo` 推送，并响应 `desktopUpdateRestart`。**`autoDownload` 必须保持 electron-updater 的默认开启态**（不得显式置 false）：`update-available` 到达即开始后台下载，但**不推快照**——webview 因此看不到任何「下载中」形态（S0）；`update-downloaded` 才推 `{ available: true, … }`（S1，按钮出现）；下载失败只记日志、不推任何可点状态（S0），等下一次检查自动重试；已就绪后的安装阶段错误不降级。toast 更新链路仍然不提供。触发检查的时机（启动自动 / 手动 / 运行期固定间隔轮询，见 [desktop-distribution.md](./desktop-distribution.md)「桌面端自动更新」场景 11）不改变状态机语义——任一时机发现新版本都在后台自动下载。降级边界见 [desktop-distribution.md](./desktop-distribution.md)「桌面端自动更新」故事场景 5。

- **用量侧接线**：`desktopHost` 消费 stdio 的额度头通知（映射成 `billing` / `apiQuota`，见「额度响应头」小节）、响应 `desktopRefreshAccountUsage`，并**删除**原有的 `accountPollIntervalMs` / `accountPollTimer` / `startAccountPolling` 及其在 `webviewReady` 时的启动分支（2026-11-06）。账户状态变化时（登录 / 登出 / 切换主机）仍主动推送快照。

## 非目标（明确排除）

- **不做本地用量推算**：不从响应头反推本次调用的消耗、不在客户端记账或做「+1 / −1」补偿，也不引入「读数没变 = 没计费」这类推断（场景 3）。额度变化一律以服务端下一次给数为准。

- **不改预警阈值口径**：头里的 `utilization` / `surpassed-threshold` / `status` 不接管渲染判据，预警档位仍按浮层既有的「剩余 < 限额 20%」一套算法（场景 10）——同一件事不能有两套阈值。

- **不新增推送通道**：不引入 WebSocket / SSE 之类的额度推送，也不把 60 秒轮询换个名字装回来；刷新靠「带头的响应 + 打开浮层时核对」两条既有链路（场景 5）。

- **账户卡片的通知语义**：账户卡片不含 toast/通知语义（信息类 toast 自动消失、带操作按钮 toast 不自动消失等通知行为由会话/后台通知故事承载，桌面端更新提醒由「更新按钮状态机」全权接管）。

- **不猜未识别的降级原因、也不扩张「静默」的范围**：对规格外的 `billing.reason`，卡片只说明「套餐额度当前不可用，按 API 余额计费」，不猜测哪一池（月/周/企业）用完、也不据此推断恢复时间或提示用户找谁（见场景 23）。同时明确：**spec 背书的静默仍是静默**——`mode = 'plan'`（无话可说）、`no_plan` 且 `plan = null`（无到期日可讲）、`billing`/`apiQuota` 双缺（用量区整体不渲染）这三种**维持不渲染**，本次兜底只针对「客户端不认识服务端下发的取值」这一类失效（2026-09-22）。
