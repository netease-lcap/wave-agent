# 功能规格说明：Context 命令

**创建日期**：2026-11-17

> 参照 Claude Code 的 `/context`（CLI 侧 `analyzeContextUsage` + `ContextVisualization`，图形界面侧 `get_context_usage` 控制请求 + 以输入框旁用量环为锚点的 `ChatContextRingPopoverBody` 浮层——与 `/permissions`、`/effort` 同属 composer 菜单，不是居中对话框）。压缩本身见 [message-compact.md](../core/message-compact.md)，输入框旁的用量环见 [context-usage-indicator.md](../ui/context-usage-indicator.md)。

## 用户场景与测试 _（必填）_

### 用户故事：在 CLI 里查「这 62% 是谁占的」（优先级：P1）

作为在终端里长时间对话的用户，我希望运行 `/context` 就能看到当前上下文窗口按来源拆开（系统提示词、内置工具、MCP 工具、记忆文件、技能清单、子代理清单、对话消息、压缩保留区、可用空间），以便判断是哪个 MCP 服务或哪份记忆文件把窗口吃掉了。

**为什么是这个优先级**：这是请求的核心。今天 CLI 只有一层合成数——输入框旁的用量环（一个百分比）与退出时才打印的 token 汇总；「装了一堆 MCP 之后又慢又笨」这种真实高频痛点，界面上无法判断是哪个来源吃的。

**独立测试**：在一个装了 ≥1 个 MCP 服务的会话里运行 `/context`，报告里的分类合计与可用空间、压缩保留区三者之和等于上下文窗口；`MCP tools` 一节按 `服务名 · 工具名` 列出每个工具的体积。

**验收场景**：

1. **假设** agent 处于交互状态，**当**用户输入 `/context`，**则**对话流里追加一条只读报告（**不是**覆盖层、不隐藏输入框、不阻塞下一轮输入），报告自上而下依次为：标题 `Context Usage`、网格、`模型 · 已用/窗口 tokens (百分比)` 一行、`Auto-compact at N tokens` 一行、`Estimated usage by category` 分类列表、以及各来源的明细分组；用户可像读普通消息一样滚动回看，报告不进模型上下文、不落盘为对话历史。
2. **假设**报告已渲染，**则**分类列表按固定顺序给出（`System prompt`、`System tools`、`MCP tools`、`Memory files`、`Skills`、`Custom agents`、`Messages`、`Autocompact buffer`、`Free space`），每条形如 `⛁ <名称>: <tokens> tokens (<百分比>)`；`tokens` 为 0 的分类整行省略；`Autocompact buffer` 与 `Free space` 恒在末尾两行。
3. **假设**报告已渲染，**则**网格恒为 10 行 × 10 个方块：每个方块代表窗口的 1%（200k 窗口 2k 一格、1M 窗口 10k 一格），按分类顺序填 `⛁`（已占）/ `⛝`（压缩保留区）/ `⛶`（可用）；**CLI 不逐块着色** —— 消息流里的文本块走 Markdown 渲染，没有逐字符着色能力，靠字符本身区分三档。
4. **假设**存在 MCP 工具，**则**报告在分类列表之后给出 `MCP tools · /mcp` 分组，每行 `└ 服务名 · 工具名: N tokens`，按体积降序；同理给出 `Memory files · /memory`（路径 + tokens）、`Skills · /skills`（技能名 + tokens）、`Custom agents · /agents`（子代理名 + tokens）与 `System tools`（工具名 + tokens）的分组。
5. **假设**会话尚未产生任何带 usage 的响应（新会话第一条消息之前），**当**用户运行 `/context`，**则**仍然出报告：总量退化为分类估值之和，`模型` 一行与网格照常渲染，且不出现 `NaN`／空百分比。
6. **假设**某个来源的读取失败（MCP 服务在列目录时断开、记忆文件读不到），**则**该分类按 0 处理、报告照常输出，并在报告末尾追加一行错误说明（对齐「宁可当场失败也不要静默自愈」：失败必须可见，但不该让整条命令失败）。

### 用户故事：在图形界面里查同一份构成（优先级：P1）

作为桌面端 / IDE / 手机页的用户，我希望点输入框旁的用量环（或运行 `/context`）就在环旁边看到同样的构成明细，而不是去终端里敲命令，也不用离开当前对话。

**为什么是这个优先级**：四个前端与 CLI 共用同一个 agent（图形界面经 stdio 驱动 CLI，手机页经中继 RPC），能力不该几端不一致；CC 的图形界面也是同一个锚点（用量环 popover），用户已经习惯「点那个百分比看构成」。

**独立测试**：在任一图形界面点用量环（或输入 `/context`），环旁边弹出浮层；把其中某个 MCP 服务摘掉后重开浮层，`MCP tools` 分类与明细同步变化。

**验收场景**：

1. **假设**用户在桌面端 / IDE / 远控页输入框输入 `/context` 并确认，**或**直接点击输入框旁那个百分比用量环，**则**在输入框上方弹出「Context window」浮层（两种入口形态完全一致）：浮层**非模态** —— 不遮对话内容、**不压住输入框本身**（底边贴在输入框上沿）、输入框照常可输入、不把 `/context` 作为消息发给模型；**横向左对齐输入框左缘**（与输入框上方的 `/rewind`、`/btw`、模型选择器、权限模式菜单同一族：`bottom: 100%` + 靠左，不做右对齐、不居中），纵向向上展开，上方空间不够时翻到下方，两向都不够时收到可用高度并在浮层内部滚动；Esc、关闭按钮（`×`）或点击浮层外部关闭；浮层开着时**再点一次用量环即收起**（点环不算「点外部」，收起只能靠这条或 Esc / `×`）；打开时先显示加载态 `Loading context breakdown…`，数据到达后替换为内容。
2. **假设**用量环尚未渲染（新会话首轮之前宿主还没推送用量），**当**用户运行 `/context`，**则**浮层仍然打开，锚点回退到输入框底栏右侧，不因缺环而不响应或飘到视口角落。
3. **假设**浮层已渲染，**则**内容自上而下为：一条分段占用条（按分类着色，悬停显示各段名称与 token 数）、`已用 / 窗口 (百分比)` 一行、分类行列表（与 CLI 同一套分类与顺序，每行 `色块 + 名称 + tokens + 百分比`；`Free space` 与 `Autocompact buffer` 的百分比列显示 `—`，因为它们不占对话可用量）、以及可折叠的明细分组（`MCP tools`、`System tools`、`Memory files`、`Skills`、`Custom agents`，默认折叠、标出行数与合计 tokens）。
4. **假设**分类超过 6 条，**则**明细列表只列出体积最大的 5 条，其余合并为一行 `Other`（对齐 CC 桌面端 `C = 6` 的截断规则），保证浮层高度可控。
5. **假设**会话还没有任何用户消息，**则**浮层显示空态文案 `Send a message to see context usage.`，而不是空白或 0% 的分段条。
6. **假设**浮层打开期间没有新的响应到达，**则**底部给出 `Last updated {time}. Send a message to refresh.`；本轮正在运行则改为 `Last updated {time}. Refreshes when this turn ends.`——浮层不自动轮询。
7. **假设**服务端（旧版本 CLI）没有这条 RPC 方法，**则**宿主回一条错误、浮层显示失败提示并允许重试，不静默展示空浮层。

### 用户故事：分项口径写着「估算」两个字（优先级：P2）

作为用户，我希望知道哪些数字是实测、哪些是估出来的，以免把 `Memory files: 1.2k` 当成上游账单上的准确值。

**为什么是这个优先级**：上游 usage 只给总量（`total_tokens`），分项必然是本进程里按字符估算（`estimateTokens`，CJK 1 字≈1 token、其他 4 字≈1 token、JSON 2 字≈1 token）。不说清楚，用户会把两套数字放一起对账，然后怀疑其中一个是 bug。

**验收场景**：

1. **假设**上一次响应带有 usage，**则**报告顶部总量取该响应的 `total_tokens`（与用量环同源，环的 100% = 自动压缩阈值）；分项各自为本地估值，二者不保证相加等于总量。
2. **假设**用户看分类百分比，**则**百分比分母一律是**上下文窗口**（不是压缩阈值）；`Autocompact buffer` 一行表示「压缩阈值到窗口」的保留量、`Free space` 表示「到压缩阈值为止的余量」，因此「分类合计 + buffer + free = 窗口」恒成立。
3. **假设**用户想知道用量环的 100% 落在报告的哪一行，**则**报告必须显式给出自动压缩阈值（`Auto-compact at N tokens`）——环的百分比与分类百分比分母不同，这一行是两者之间的换算依据。
4. **假设**看 `Skills` 与 `Custom agents` 两行，**则**它们量的是**对话里下发的那份清单正文**（`utils/skillListing.ts` / `utils/agentListing.ts` 渲染出的文本），并且这部分体积已从 `Messages` 里扣除——同一段文字只能在报告里出现一次；清单没下发过（新会话）时两行省略。

### 边界情况

- **窗口未知**：`getContextWindow()` 返回非正数时，百分比一律显示 `—`，网格画成空格而不是除零崩溃。
- **会话被切换**：报告在生成期间会话被切走，则丢弃本次结果（与既有「会话被切走时不写入」口径一致），不把旧会话的数字贴到新会话上。
- **明细过长**：`MCP tools` 有 40 个工具时，CLI 报告照实全列（它是滚动区里的一条消息，不是固定高度的覆盖层）；图形界面浮层的明细分组各自滚动，浮层总高受视口限制（见场景 1 的三段定位），不出现滚不到的低半截。
- **未启用的来源**：知识库 / 任务工具 / Exec 等按开关决定是否在工具表里的，未启用时对应 tokens 自然为 0，不显示该分类（不写「未启用」占位）。
- **同时多处打开**：同一时刻只允许一个 `/context` 浮层（单实例）；已打开时再次点环或运行命令不叠加第二个。

## 非目标（明确排除）

- **不调用上游 token-count 接口**：CC 的 `/context` 会为每个分类额外发 token 计数请求（`detail: 'full'`）；我们只做本地估值（对应 CC `detail: 'summary'` 的思路，但比它更细，因为各部分文本都在进程内）。
- **不做自动刷新与后台推送**：浮层按需打开、不常驻、不轮询；常驻展示属于输入框旁用量环的职责。
- **不做浪费诊断**：CC 的 `ContextSuggestions`（「Bash 结果占了 18%，用 head/grep 收敛」之类）不在本次范围内。
- **不改动压缩策略与阈值公式**：`getAutoCompactThreshold` 与圆环百分比语义保持现状，本命令只读取它们。
- **不做成本 / cache 明细**：`/cost`、`/usage` 另论（cache 命中与计费口径见 `core/` 下相关规格）。
