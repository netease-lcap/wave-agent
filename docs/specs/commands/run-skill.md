# 功能规格说明：Run Skill

**创建日期**：2026-11-27

## 用户场景与测试 _（必填）_

### 用户故事：一句话把应用跑起来并看到效果（优先级：P1）

作为开发者，我希望说「跑一下」「截个图」，agent 就真的把应用启动、驱动到用户能看到的地步，而不是跑测试或 import 一个内部函数了事，以便确认改动在真实应用里成立。

**为什么是这个优先级**：这是 `/run` 唯一的用途，也是 `/verify` 在拿到 handle 时最先找的东西。没有它，「改动能用吗」只能靠推断。

**独立测试**：在一个 CLI 项目里运行 `/run`，验证 agent 真的执行了该命令、检查了退出码与输出，而不是只跑测试套件。

**验收场景**：

1. **假设**项目有可驱动的应用表面，**当**用户运行 `/run` 时，**则**技能启动真实应用（CLI 在命令行、服务在 socket、GUI 在窗口）并驱动它，而不是跑测试或对内部函数做 `import` 调用。
2. **假设**应用已启动，**当**技能驱动时，**则**它把应用推到用户能看到结果的状态：CLI 打一条代表性命令并看退出码，服务 `curl` diff 触及的路由并读响应体，TUI 发一次导航并抓 pane，GUI 点按钮并截图后**看那张截图**。
3. **假设**用户运行 `/run <额外要求>`，**当**技能执行时，**则**附加要求进入本轮上下文，与技能正文一起生效。

---

### 用户故事：优先复用项目已有的启动技能（优先级：P1）

作为开发者，我希望 `/run` 先找仓库里已经写好的启动/驱动技能（作者已经踩过一遍的结论），而不是每次重新摸索，以便在 monorepo 里也能一次跑对。

**为什么是这个优先级**：冷启动一个项目常常要十几分钟，且每次都重来；仓库里已有的 `run-*` / `verifier-*` 技能就是上一轮的结论。

**独立测试**：在 `packages/<pkg>/.wave/skills/run-<pkg>/SKILL.md` 放一个启动技能，运行 `/run`，验证 agent 找到它并按它的配方执行。

**验收场景**：

1. **假设**当前目录或其祖先目录下存在 `.wave/skills/` 或 `.claude/skills/`，**当**技能开始时，**则**它沿目录树向上（到仓库根为止）收集各技能的 `description:`，找出描述启动/驱动本应用的技能。
2. **假设**找到匹配的启动技能，**当**技能执行时，**则**它按该技能逐行执行（不改写、不跳过其中的补丁步骤），并在报告里说明用的是哪一个。
3. **假设**找到多个都像、无法判断该跑哪个单元，**当**技能执行时，**则**它问用户要跑哪个单元，不猜。
4. **假设**匹配的启动技能已过期（与本次任务无关的机制性失败），**当**技能执行时，**则**它告知用户并建议用 `/run-skill-generator` 刷新，而不是默默改写它。
5. **假设**没有任何技能描述启动本应用，**当**技能执行时，**则**它回落到按项目类型的通用配方。

### 用户故事：按项目类型拿到对的配方与示例（优先级：P2）

作为开发者，我希望技能按我的项目类型（CLI、Web 服务、TUI、Electron、浏览器应用、库）给出对应的启动与驱动形状，并能打开一份可照抄的示例，以便我不必从零设计交互手段。

**为什么是这个优先级**：六类项目的驱动手段差别很大；有示例能显著缩短第一次跑通的时间，但没有它也能靠通用配方完成。

**独立测试**：在一个 Web 服务项目里运行 `/run`，验证技能给出的启动方式是后台启动 + 健康检查，而不是前台阻塞；并能打开 `examples/server.md`。

**验收场景**：

1. **假设**目标是 Web 服务 / API，**当**技能驱动时，**则**它后台启动、等端口真的在服务、用 `curl` 打路由、读响应体，并在结束时清理进程。
2. **假设**目标是 TUI 或交互式终端程序，**当**技能驱动时，**则**它用终端复用发按键并抓帧；没有 tmux 的平台（Windows）用 node-pty 的真 ConPTY。
3. **假设**目标是 Electron / 桌面 GUI 或浏览器应用，**当**技能驱动时，**则**它用 Playwright 驱动（桌面用 `_electron`，浏览器用真 Chromium）并产出截图。
4. **假设**目标是库 / SDK（没有进程可跑），**当**技能驱动时，**则**它在包边界写导入调用的冒烟脚本，而不是试图启动进程。
5. **假设**技能正文链接到 `examples/*.md`，**当**用户打开链接时，**则**该文件随内置技能一起落盘（6 份示例都真实存在，不是死链）。

### 用户故事：这次摸索值得留下来时转给生成器（优先级：P2）

作为开发者，当这次启动需要装包、改配置或写驱动脚本才跑通时，我希望 `/run` 建议把这套做法沉淀成项目技能，以便下个会话不用重来。

**为什么是这个优先级**：它决定的是「经验要不要留下来」，不影响这一次能不能跑通。

**独立测试**：在一个需要 `apt-get` 装依赖才跑通的项目里运行 `/run`，验证报告里建议了 `/run-skill-generator`；在开箱即用的项目里运行，验证没有这条建议。

**验收场景**：

1. **假设**跑通需要额外装包、设环境变量、打补丁或写驱动，**当**技能收尾时，**则**它建议用户用 `/run-skill-generator` 把过程固化成项目技能。
2. **假设**应用开箱即用地跑起来了，**当**技能收尾时，**则**它不建议生成技能。

### 边界情况

- **只启动不驱动**：不算跑过。启动只证明入口能解析；技能必须驱动到用户能看到结果的状态。
- **启动失败**：报告失败点与试过的命令，不把「编译通过」当作已跑过。
- **共享进程状态**（端口、锁文件、临时目录）：隔离使用（独立端口、`mktemp -d`）；没有 tmux 的平台用 node-pty 真 ConPTY。
- **示例里的 `chromium-cli`**：那是示例假定 PATH 上存在的一个 headless Chromium REPL，不属于 wave——CC 的 npm 包里也没有它，CC 原文自带 `If `chromium-cli` isn't available` 的兜底。命令保留原文，文件顶部有注记说明改用项目已有的无头浏览器驱动。

## 范围之外

- **`chromium-cli` 这套内建工具**：见上，保留原文 + 注记，不伪造替代命令。
- **与 `/run-skill-generator` 的示例去重**：CC 的生成器注册时是 `files = { "template.md": TEMPLATE_MD, ...RUN_EXAMPLE_FILES }`，两个技能共用同一批示例；本项目把内容只存一份（`run-examples.ts`），按各自目录前缀展开，规格见 `commands/run-skill-generator-skill.md`。
- **自动触发**：`/run` 是用户显式调用的命令（`userInvocable`），不在每轮自动注入。
