# 功能规格说明：Verify Skill

**创建日期**：2026-11-27

## 用户场景与测试 _（必填）_

### 用户故事：提交前把改动真的跑一遍（优先级：P1）

作为开发者，我希望在提交非平凡改动前让 agent 真正驱动这段改动并观察它的运行时行为，而不是只看测试和类型检查，以便在提交前发现「测试全绿但东西不能用」的问题。

**为什么是这个优先级**：这是技能存在的唯一理由。测试、构建、类型检查都是对源码的间接推断；`/verify` 的判据是运行时观察到的行为。它也是与 `/code-review`（读 diff 的静态审查）、`/simplify`（改质量）的分工边界。

**独立测试**：在一条有运行时表面的改动上（例如改了某个 CLI 命令的输出）运行 `/verify`，验证 agent 实际驱动了该命令、贴出捕获到的输出，并给出判定。

**验收场景**：

1. **假设**当前分支相对 `main` 有含运行时表面的改动，**当**用户运行 `/verify` 时，**则**技能读取完整范围的 diff、判定改动落在哪类 surface（CLI/TUI、Server/API、GUI、Library、Prompt、CI），并在该 surface 上驱动改动。
2. **假设**技能正在驱动改动，**当**它收集证据时，**则**它不把「测试通过 / 构建干净 / 类型检查通过 / 导入源码函数调用过」当作证据。
3. **假设**改动只涉及测试、文档或没有运行时表面的代码，**当**技能执行时，**则**判定为 SKIP，并用一行说明没有可驱动的表面。
4. **假设**用户运行 `/verify <额外要求>`，**当**技能执行时，**则**附加要求进入本轮上下文，与技能正文一起生效。

### 用户故事：复用仓库既有的驱动配方（优先级：P1）

作为开发者，我希望 `/verify` 优先复用仓库里已经写好的构建/启动/驱动配方（尤其是针对某个包或子系统的验证器），而不是每次从零摸索，以便验证在大型 / monorepo 仓库里也能落得下来。

**为什么是这个优先级**：冷启动摸清一个包怎么跑起来常常要十几分钟，且每次都重来。仓库里已有的配方是「上一轮会话的结论」，优先读它是最省成本的一步。

**独立测试**：在 `packages/<pkg>/.wave/skills/` 下放一个 `verifier-*` 技能，运行 `/verify`，验证 agent 找到并使用了它，且在报告的 Method 里点名。

**验收场景**：

1. **假设**工作目录（仓库根或 diff 触及的包目录）下存在 `.wave/skills/` 或 `.claude/skills/`，**当**技能开始拿「handle」时，**则**它先列出这些目录并检查其中是否有匹配当前 surface 的 `verifier-*` / `run-*` 技能。
2. **假设**找到与 surface 匹配的 `verifier-*` 技能，**当**技能执行时，**则**它按该技能的配方驱动改动，并在报告的 Method 里写明用的是哪一个。
3. **假设**只找到 `run-*` 技能而没有匹配的验证器，**当**技能执行时，**则**它把该技能里的构建/启动原语当作 handle 使用。
4. **假设**两者都没有，**当**技能执行时，**则**它从 README / package.json / Makefile 冷启动，并把时间盒子放在约 15 分钟；超时则报告 BLOCKED 并写明卡在哪一步、试过哪些命令。

### 用户故事：沉淀验证配方供下次复用（优先级：P2）

作为开发者，我希望这次摸出来的可行配方被写进仓库，以便下次（以及别的 agent 会话）跳过冷启动。

**为什么是这个优先级**：没有沉淀时这套流程每次都要重付冷启动成本；但它是锦上添花，不阻塞「这次验证能不能给出判定」。

**独立测试**：在一个没有验证器技能的仓库里跑通一次 `/verify`，验证它的引导落成一个 `verifier-*` 技能文件，且下次运行会读到它。

**验收场景**：

1. **假设**技能冷启动成功跑通了改动，**当**它收尾时，**则**它把「能跑起来的命令 + 值得驱动的流程 + 踩到的坑」落成一个简短的 `verifier-*` 技能文件，放在它探测过的目录层级（单包仓库放仓库根，monorepo 放被改动的包目录）。
2. **假设**已经存在对应的验证器技能文件，**当**技能执行时，**则**它只在被该文件误导过时才编辑（里面记录的命令跑不通或确实记错了），不做风格重写或重排。
3. **假设**技能要把配方落盘，**当**它选择文件名时，**则**它使用 `verifier-*` 命名而不是与内置 `verify` 同名，避免项目技能整篇顶掉内置技能的方法论。

### 用户故事：报告能被别人复现（优先级：P2）

作为 reviewer，我希望 `/verify` 的结论带着能打开的原始证据（pane 抓帧、响应体、截图），以便我不必重跑就能判断这次 PASS 是否可信。

**为什么是这个优先级**：没有证据的 PASS 与没有 PASS 等价；但判定本身（PASS/FAIL）才是主产出。

**独立测试**：在远端 surface 上运行 `/verify`，验证报告里点名了通过 `SendUserFile` 送出的证据文件。

**验收场景**：

1. **假设**技能给出判定，**当**它渲染报告时，**则**报告含一行改动摘要、Verdict（PASS/FAIL/BLOCKED/SKIP）、Claim、Method、Steps、Findings 各段。
2. **假设** `SendUserFile` 工具可用（远端 surface，读者打不开本地路径），**当**技能收尾时，**则**它把截图/录制发出去并在报告里点名发了什么。
3. **假设**拿不准某次观察是改动导致还是环境问题，**当**技能判定时，**则**它给 FAIL 并附上原始捕获，而不是解释成「看起来没问题」。
4. **假设**多个检查点里只有部分通过，**当**技能判定时，**则**它不给「部分通过」，整体按 FAIL 处理，直到全部通过或某个失败被解释清楚。

### 边界情况

- **改动没有运行时表面**（纯文档、纯类型、纯测试）：SKIP，一行说明；不跑测试、不跑构建来「验证」。
- **改动内部函数**：内部函数不是 surface。技能沿调用链追到上面某类 surface（CLI 提示、socket 响应、像素、包边界）再观察。
- **描述与 diff 不一致**：diff 是事实，描述是主张；不一致本身就是一条 finding。
- **verifier 技能自身失效**（与本次改动无关的机制性失败）：不因此给改动 FAIL，而是问用户是否修验证器。
- **共享进程状态**（端口、锁文件、临时目录）：隔离使用（独立端口、`mktemp -d`、`tmux -L <name>`；没有 tmux 的平台用 node-pty 真 ConPTY）。
- **平台差异**：GUI 面用 Playwright 驱动并截图；CLI/TUI 面在 macOS/Linux 用 tmux 抓 pane，在 Windows 用 node-pty 抓帧。
- **项目侧与内置 `verify` 同名**：内置技能由产品注册，项目同名技能在 wave 的合并顺序里会覆盖它；因此沉淀配方用 `verifier-*` 命名，两者并存。

## 范围之外

- **斜杠菜单独立短描述**：CC 的 `menuDescription` 只能代码注册、markdown 写不了，且 CC 未向用户开放该字段；本项目同样不加。
- **提交前自动催促**：CC 在准备 commit 时会提示先跑 `/verify` 和 `/code-review`；本项目没有内置 commit / PR 技能，该提示没有宿主，本轮不做。
- **`run-skill-generator` 的能力细节**：由独立技能 `/run-skill-generator` 提供，规格见 `commands/run-skill-generator-skill.md`；本技能只是调用它。
