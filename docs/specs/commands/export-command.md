# 功能规格说明：Export 命令

**创建日期**：2026-12-01

> 参照 Claude Code 的 `/export`（`commands/export/` + `components/ExportDialog.tsx` + `utils/exportRenderer.tsx`）：它不另写一套文本格式，而是把 CLI 自己的消息组件渲染成 ANSI、再剥掉转义序列。
>
> 相关：转录的落盘与读取见 [session-management.md](../ui/session-management.md)；清理策略（`cleanupPeriodDays`）决定「转录还在不在」；消息渲染见 [message-rendering-system.md](../ui/message-rendering-system.md)。

## 用户场景与测试 _（必填）_

### 用户故事：把这段对话带走（优先级：P1）

作为在终端里跟 agent 排障的用户，我希望 `/export` 之后能把刚才这整段对话粘到工单、周报或聊天窗口里，以便别人能看到我问了什么、agent 改了什么，而不用我手抄。

**为什么是这个优先级**：这是命令的唯一目的。此前唯一的出口是滚屏选中复制，超过一屏就不可行，工具调用的参数与结果更是折不进来。

**独立测试**：在一个已经聊过几轮（含至少一次工具调用）的会话里输入 `/export`，选「Copy to clipboard」，验证剪贴板里是一份完整的纯文本对话；再选一次「Save to file」，用默认文件名回车，验证当前目录下多出一个 `.txt`，内容与剪贴板一致。

**验收场景**：

1. **假设** agent 已产生至少一条消息，**当**用户输入 `/export`，**则**输入框上方弹出选择浮层（标题 `Export Conversation`、副标题 `Select export method:`），两个选项为 `Copy to clipboard` / `Save to file`（各自带一行说明），底部一行 `↑/↓ to select · Enter to confirm · Esc to cancel`；选项文字、副标题与 CC 逐字一致。
2. **假设**浮层的高亮停在第一项，**当**用户按 `Enter`，**则**正文写入系统剪贴板、浮层关闭，对话流里追加一条 `Conversation copied to clipboard`。
3. **假设**用户选了 `Save to file`，**则**浮层进入文件名这一步：一行 `Enter filename:`、一行 `> ` 前缀的输入框，名字**预填**为 `<yyyy-MM-dd-HHmmss>-<首条输入的 slug>.txt`，光标停在末尾，底部提示换成 `Enter to save · Esc to go back`。
4. **假设**处于文件名这一步，**当**用户按 `Enter`，**则**文件写进**会话的当前工作目录**，对话流里追加 `Conversation exported to: <绝对路径>`；**当**用户按 `Esc`，**则**退回选项那一步（不关浮层）；在选项那一步按 `Esc` 才关闭浮层，并追加 `Export cancelled`。
5. **假设**用户直接带文件名（`/export notes.txt`），**当**命令执行完，**则**跳过浮层、直接写文件并给出同一句 `Conversation exported to: …` —— 与 CC 的 `/export <filename>` 同一行为。
6. **假设**用户输入的文件名没有后缀或后缀不是 `.txt`，**则**落盘时后缀被强制改成 `.txt`（已有 `.txt` 则原样保留）；文件名里的空串不能被提交（清空后按 `Enter` 无反应）。
7. **假设**浮层打开，**则**输入框让出键盘（`↑`/`↓`/`Enter`/`Esc` 归浮层），浮层期间不出现第二个同类入口；浮层关闭后输入框照常可用。

### 用户故事：导出的内容就是屏幕上看到的那一份（优先级：P1）

作为用户，我希望 `.txt` 里的样子与我在终端里看到的对话一致（同样的工具调用点线结构、同样的错误行、同样的 Markdown 原文），以便我核对时不用在两套排版之间来回对照。

**为什么是这个优先级**：一旦导出另写一套格式，同一条消息在界面与文件里就会分叉；用户拿到文件后无法判断「屏幕上有的东西文件里为什么没有」。

**独立测试**：让 agent 跑一次会失败的命令（比如在不存在的目录里 `pnpm install`），`/export` 之后打开文件，验证工具块的 `● Bash`、`Parameters:`、`Result:` 与错误行都在，顺序与终端一致。

**验收场景**：

1. **假设**会话里有工具调用，**则**导出内容按终端的样子给出工具块（`● <工具名>` + `Parameters:` + `Result:`），工具入参与结果都是**完整**的（不按折叠态的「最后 5 行」截断、不换成参数摘要）。
2. **假设**会话里有中文内容，**则**导出文件是 UTF-8，中文正常显示、没有乱码，也没有残留的 ANSI 转义序列。
3. **假设**会话里含图片块，**则**导出内容出现占位行 `# Image (N)`，不导出行内 base64。
4. **假设**这条会话从未压缩过，**则**导出的是整条线程；**假设**压缩过，**则**导出仍然是**整条线程**（压缩之前的轮次都在），不是屏幕上「最近一次压缩之后」的那几十条。
5. **假设**老转录（append-only 修复之前写的）里同一个消息 id 出现两次，**则**导出只出现一次，内容取文件中最后一次出现的那份。

### 用户故事：导出失败时能看懂为什么（优先级：P2）

作为用户，我希望在转录已经不在、或写文件失败时，看到一句能据以行动的话，而不是一条命令「什么也没发生」。

**为什么是这个优先级**：`cleanupPeriodDays` 默认 30 天会清掉旧转录，「导出老会话时悄悄没反应」会让用户以为是自己按错了。

**独立测试**：用 `cleanupPeriodDays` 之外的旧会话（或删掉转录文件）运行 `/export`，验证给出的说明里点名了转录路径与清理策略；把当前目录设成不可写再选「Save to file」，验证给出的是写失败的原始错误。

**验收场景**：

1. **假设**这份会话的转录文件不存在，**当**用户运行 `/export`，**则**不打开浮层，只在对话流里追加一条说明：点名转录路径，并说明它可能已被 `cleanupPeriodDays`（默认 30 天）清理。
2. **假设**转录存在但读失败（权限不足、JSON 坏行），**则**追加 `Failed to export conversation: <原始错误>`，不做静默重试。
3. **假设**这次会话一条消息都没有，**则**给出「没有可导出的内容」的说明，不写空文件、不开浮层。
4. **假设**写文件失败（目录不可写、磁盘满），**则**追加 `Failed to export conversation: <原始错误>`，并保留用户在文件名输入框里敲的名字（读者不需要重新猜）。
5. **假设**剪贴板这一步失败（终端不接受 OSC 52 序列），**则**明确说复制失败，并指出 `/export <filename>` 是可行的替代路径 —— 不谎报成功。

### 用户故事：桌面端把整段对话打包发给别人（优先级：P1）

作为在桌面端排障的用户，我希望 `/export` 直接落成一份可以贴到工单里的归档，里面既有我能读的可读版、也有能交给支持人员复现问题的原始转录，以便我不用再单独去 `~/.wave/projects/` 里翻那份 JSONL。

**为什么是这个优先级**：桌面端的报障场景里，单文件 `.txt` 不够——别人要复现就得看原始转录，而用户自己要看的是可读版；两者装在同一个归档里，一次保存就齐了。

**独立测试**：在一个聊过几轮（含工具调用）的会话里输入 `/export`，在系统「保存」对话框里直接回车，验证目标目录下多出 `wave-session-<yyyyMMdd-HHmmss>-<会话 id 前 8 位>.tar.gz`；解包后三样文件都在，`transcript.jsonl` 与会话主机上那份转录逐字节相同，`transcript.md` 里没有 base64。

**验收场景**：

1. **假设**桌面端当前分屏里有会话，**当**用户输入 `/export`，**则**弹出系统「保存」对话框：标题 `导出会话「<会话标题>」`、默认位置是桌面、默认文件名 `wave-session-<yyyyMMdd-HHmmss>-<会话 id 前 8 位>.tar.gz`、筛选器只有「会话归档（`tar.gz`）」。
2. **假设**用户确认了保存路径，**则**先出现一条带 spinner 的「正在导出会话…」，完成后**用同一条**提示换成成功态「会话已导出：<绝对路径>」，并在文件管理器里选中该文件。
3. **假设**用户在对话框里取消，**则**什么都不发生：不取内容、不打包、不弹提示（取消是他自己摁的）。
4. **假设**归档里有 `transcript.jsonl`，**则**它与会话主机上那份转录**逐字节相同**：原样拷贝，不重新序列化、不裁剪。
5. **假设**会话跑在远端（ssh / WSL）主机上，**则**导出照样可用：内容由拥有转录的那台机器上的 CLI 读出来再回传，宿主不去本地磁盘找转录（远端会话的转录根本不在本机）。
6. **假设**原始转录超过 50 MB，**则**归档里只有 `transcript.md` 与 `manifest.json`，提示写明「原始转录 X MB，超过导出上限，归档里没有 transcript.jsonl」——宁可少一样东西，也不静默截断。
7. **假设**同一个会话的导出还在进行（对话框已确认、正在取内容或打包），**当**用户再次 `/export`，**则**第二次被拒绝并提示「这个会话正在导出，请稍候」：不再开一次对话框，也不并发写同一个文件。
8. **假设**这份会话的转录已被 `cleanupPeriodDays` 清理，**则**提示点名清理策略（与 CLI 同一句话，见下面第 3 个故事），不写成笼统的「导出失败」。
9. **假设**打开归档里的 `transcript.md`，**则**它按块给出可读内容：`text` 按 `## 用户` / `## 助手` 分节、压缩摘要自成 `## 上下文压缩`、工具调用一行摘要 + 结果（前 30 行）、图片只写 `[图片：宽x高 / 格式]`（**绝不写 base64**）、`reasoning` 一律跳过、`isMeta` 消息**整条不写**（不留包裹标记，与 CLI 的纯文本导出同口径）。
10. **假设**会话改过名（`custom-title` 条目），**则**可读版与清单的标题都用**最后一条**改名的结果；`manifest.json` 里同时有工作目录、Git 分支、创建时间、导出时间、规模（消息 / 注入消息 / 工具调用 / 图片）、应用版本与平台。
11. **假设**转录里跳过了注入消息，**则**可读版的规模行尾部带一句「（另跳过 N 条注入消息）」，`manifest.json` 的 `injectedMessages` 记同一个数；两者的条数都**不含**注入消息 —— 读者看到的规模就是 `messages`，拿两份数相加才对得上 `transcript.jsonl` 的消息条数。

### 边界情况

- **默认文件名的首条输入取不到**（首条是纯图片、或被 slug 化后为空）：退化成 `conversation-<yyyy-MM-dd-HHmmss>.txt`。
- **中文 / 非 ASCII 的首条输入**：文件名净化只保留 `a-z0-9` 与连字符，中文会被清空，因此走上面的回退名（与 CC 同一个判据，不改成保留中文，避免 Windows/macOS 之间的文件名差异）。
- **首条输入很长**：只取首行，超过 50 字符截断并加 `…`。
- **`isMeta` 消息**（注入的 `<system-reminder>`、技能清单之类）：**两个形态都整条跳过**（CLI 的纯文本、桌面端归档里的 `transcript.md`），与屏幕上一致地不导出；跳过多少条记在规模行与 `manifest.json` 的 `injectedMessages` 里，免得别人拿对话条数去核对转录行数时以为缺了几条。
- **写到哪里**：会话的**当前工作目录**（`agent.currentWorkdir`，即 Bash 工具 spawn 用的那个目录），不是进程启动目录 —— agent 在会话里 `cd` 过之后，两者会不同。
- **`wave -p`（非交互）会话**：命令不在那一套里存在（没有输入框），不涉及。
- **子会话（subagent）的转录不进桌面端归档**：`manifest.json` 里用 `subagentTranscripts: "unlinked"` 明写这一句 —— 支持人员看到它就不必再问「是不是漏打包了」。
- **桌面端归档的大小上限只看原始转录**：可读版与清单总是写全（它们的大小由转录内容决定，不会单独失控）。

## 实现说明（终端）

**正文怎么来**：`renderTranscriptPlainText` 把每条的每个块用**屏幕上同一个组件**（`MessageBlockItem`）渲染一遍，取第一帧的 ANSI 再剥掉转义序列。为了导出完整内容，渲染时固定展开态、不套用消息列表的「最近 30 条」上限、不画欢迎横幅。渲染用 `RenderOnceAndExit` + `PassThrough` 当 stdout（非 TTY 下 Ink 输出完整帧），没有新增依赖。

**读哪一份转录**：SDK 的 `loadTranscriptForExport()` 直接读会话自己的 JSONL（`forEachTranscriptEntry`），**不**复用 `loadFullMessageThread()` —— 后者读不到文件时返回空数组，无法区分「已被清理」与「读失败」。去重口径与分页读一致：同 id 取最后一次的内容、位置留在首次出现处。

**宿主侧**：`Agent.exportTranscript()` 把 `{ messages, stats }` 交给宿主；CLI 在 `useChat` 里渲染正文并按选择复制/落盘，结果以一条只读的助手消息追进对话流（与 `/rename`、`/context` 同一个落点，不进模型上下文、不落盘）。

**统计行**：浮层顶部多一行 `<N> messages · <N> tool calls · <N> images`（CC 没有这一行）。加它是因为 CC 的选项列表里除了标题没有任何「这次要导出多少内容」的线索，而我们的转录可能很大；它只影响观感，不改变选项与话术。数字取 `countTranscriptStats()`，**不含注入消息**（正文本来就不写它们，数字得跟正文对得上）；注入的条数在桌面端归档的规模行与 `manifest.json` 里交代，CLI 这一行不提。

## 实现说明（桌面端）

**入口只有桌面端**：`/export` 落的是一个 `tar.gz` 归档，要靠主进程的原生「保存」对话框和 `shell.showItemInFolder`；插件端能落盘的地方是编辑器工作区，远控页没有磁盘写权限。所以宿主命令表里它标 `surfaces: ["desktop"]`，webview 里那条字面量分支只在桌面端生效。

**内容一律从会话主机取**：主进程不知道转录在哪（远端会话在另一台机器的 `~/.wave/projects/…`），所以可读版、清单、原始字节都由拥有转录的那个 `wave --stdio` 进程算好，经一条会话级 RPC（`exportTranscript`）回传；主进程只做「写文件 + 打包」。本地会话也走同一条路，不额外开一条本地分支。

**清单为什么在 CLI 侧拼**：主进程只准 import `wave-agent-sdk/host`（`check:sdk-surface`），把整个 SDK barrel 拖进宿主 bundle 曾经把桌面端崩在 `whenReady` 之前。因此 `manifest.json` 在 CLI 进程里序列化成字符串再过线，应用版本与平台作为 RPC 参数传下去。

**打包形态**：暂存目录 → `tar` 一次 → `finally` 里清场，与导出诊断日志同一条路子；`.tar.gz` 而不是 `.zip` 是因为仓库里没有 zip 依赖，`tar` 本来就是桌面端运行时依赖，Finder 与 Windows 10+ 都能直接打开。

**中间态**：对话框关掉之后还有「取回 + 打包」两段可能好几秒的等待，所以先挂一条带 spinner 的提示，再用**同一个提示 id** 换成结果 —— webview 按 id 原地覆盖，不叠两条。

**与 Claude Code 的差别**（CC 只有终端形态，桌面端没有对照物）：

- 可读版用 Markdown 而不是「屏幕渲染 + 剥 ANSI」，因为归档要能被别的编辑器打开。
- 原始转录**进归档**且逐字节保留，因为报障场景里它是唯一的取证依据。
- 落点**只有保存对话框**，**没有**「写进会话当前目录」这条路 —— 这是有意为之，不是缺口：桌面端同时开着多个 pane、每个 pane 可以有自己的 workdir，界面上没有一个能无歧义解释的「当前目录」，对话框是唯一说得清的落点。因此也**不解析** `/export <路径>` 的参数（与「绝对路径缺口不修」同一条拍板）。
- 文件名与默认目录按桌面端自己的习惯定（`wave-session-<yyyyMMdd-HHmmss>-<会话 id 前 8 位>.tar.gz`、默认落在桌面），与 `exportDiagnostics` 对齐，不像 CC 那样从首条输入生成 slug。

## 已知边界（本轮没验 / 结构性保证覆盖不到的地方）

- **远端与 WSL 会话没有真机验证过**。结构上是硬的：内容（可读版、清单、原始字节）全部由拥有转录的那个 `wave --stdio` 进程算好再经一条会话级 RPC 回传，主进程不碰本地路径（约束写在 `packages/desktop/src/main/exportSessionArchive.ts` 顶部注释里），本地会话走的也是同一条路、没有本地分支。但「ssh 主机上的会话导成 tar.gz」目前只有单测覆盖 —— 真机验证需要一台可达的 ssh 主机，本机没有。
- **大文件过线只压到 20.3 MB**。实测 20.3 MB 的转录（base64 后约 27 MB）能完整过 stdio 的 JSON-RPC 行协议并打出归档；50 MB 上限那一点没有实测，那时单条 JSON 行约 67 MB，CLI 子进程与主进程各持一份。上限、超限话术与「拒 jsonl 但照出可读版」的逻辑由单测覆盖。
- **`shell.showItemInFolder` 在没有文件管理器的 Linux 桌面上静默无事发生**：不报错也不提示，文件仍然写好了。未在 Linux 真机验证。

## 非目标（明确排除）

- **不导出 JSONL 原文（CLI 形态）**：`/export jsonl` 之类的参数不存在（CC 也没有）；原始转录只以 `transcript.jsonl` 的形式出现在桌面端归档里。
- **不落 `~/.wave/exports`**：CLI 把文件写到当前工作目录，桌面端写到用户在对话框里选的位置。
- **不做 Markdown 渲染（CLI 形态）**：终端的正文是「终端看到的纯文本」，不是重新排版的 Markdown（与 CC 一致）；Markdown 只用于桌面端归档里的 `transcript.md`。
- **IDE（VS Code / JetBrains）与远控页不做 `/export`**：前者没有「交给系统保存」的落点，后者没有磁盘写权限；把这一行列给它们就是点了没反应的行。
