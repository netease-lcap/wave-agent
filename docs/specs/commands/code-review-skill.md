# 功能规格说明：Code Review Skill

**创建日期**：2026-06-29

## 用户场景与测试 _（必填）_

### 用户故事：审查当前 diff 的正确性错误（优先级：P1）

作为开发者，我希望审查当前分支更改的正确性错误，以便在合并前发现问题，而不依赖外部 CI 或托管的 git 平台。

**为什么是这个优先级**：错误检测是代码审查的主要价值。使用 `git diff`（而非 `gh`）使 skill 适用于任何 git 主机——GitLab、自托管或仅本地仓库。

**独立测试**：在特性分支上进行带有明显错误的更改，运行 `/code-review`，并验证错误以文件和行范围报告。

**验收场景**：

1. **假设**当前分支有未提交或已提交但未合并的更改，**当**用户运行 `/code-review` 时，**则** skill 先跑 `git diff origin/HEAD...HEAD` 取整条分支对默认分支的 diff（默认分支不叫 `main` 就换名，认不出基准就退回 `git diff HEAD~1`），再报告更改中发现的正确性错误。
2. **假设** skill 要自己写一条 git 命令去取 diff 而不是用正文给的那几行，**当**它写命令时，**则**不使用 `@{upstream}` / `@{u}` 配 `..` / `...`、括号分组的命令、`$?` 这类 shell 变量——这三种写法在 bash 与 PowerShell 下行为不一致，而且各自都要一次权限。
3. **假设**当前分支没有更改，**当**用户运行 `/code-review` 时，**则** skill 停止并告知用户没有可审查的内容。
4. **假设**发现正确性错误，**当**渲染报告时，**则**每个发现包含简要描述和 `<file>:<line range>` 引用。

### 用户故事：审查发现以结构化清单交付（优先级：P1）

作为开发者，我希望审查结果以一份字段固定的清单交给界面渲染，而不是让我从 agent 的正文里再读一遍，以便每条发现都能逐条看到文件、行号、严重程度与核实结论，并在修复之后看到每条各自的处理结果。

**为什么是这个优先级**：清单是这项功能全部结果的交付通道。正文里的自由排版无法被界面逐条跟踪（哪条已修、哪条被跳过），也无法在修复前后对齐同一条发现。

**独立测试**：在一份有两处可确认错误的改动上运行 `/code-review`，验证 agent 的回复里不再重复罗列发现，界面显示两条带文件与行号的条目；再以 `--fix` 运行，验证每条发现带上「已修 / 跳过 / 无需改动」的处理结果。

**验收场景**：

1. **假设**审查结束且经核实的发现非空，**当** agent 交付结果时，**则** 这些发现以一份结构化清单交付，每条含文件路径、摘要、失效场景，以及可选的（行号、短标签、类别、严重程度、核实结论）。
2. **假设**没有任何发现通过核实，**当** agent 交付结果时，**则** 交付的是一份空清单，界面显示「没有发现」，而不是一份空报告。
3. **假设**清单已交付，**当** agent 撰写回复时，**则** 回复不再重复清单内容，只说明发现已交付。
4. **假设**本次审查以某个努力级别运行，**当**交付结果时，**则** 清单带上该级别（`low` / `medium` / `high` / `xhigh` / `max`）供界面展示。
5. **假设**用户带 `--fix` 运行，**当**修复阶段结束、重新交付清单时，**则** 每条发现带上它自己的处理结果（已修 / 跳过 / 无需改动）；没有被处理过的条目不显示处理结果。
6. **假设**一次审查得出超过 32 条发现，**当**交付结果时，**则** 交付被拒绝并提示条数超限——清单不会被悄悄截断成 32 条。
7. **假设**当前会话没有可用的清单工具，**当** agent 交付结果时，**则** 它按同一份字段定义在正文里写一遍 JSON 清单（`level` 与 `findings`），而不是改回报自由排版。
8. **假设**发现被判了严重程度，**当**交付时，**则**只有三档——🔴 **Important**（这次改动引入、合并前必须修）、🟣 **Pre-existing**（问题在，但不是这次带来的）、🟡 **Nit**（小瑕疵）——按这个顺序排列；严重程度只用来标注与排序，**不因为它低就丢弃任何一条**。
9. **假设**某条发现只是「机制成立但触发不确定」（`PLAUSIBLE`），**当**标注严重程度时，**则**它低于同类的 `CONFIRMED` 条目，不能因为描述听起来更严重就排在前面。

### 用户故事：可配置的努力级别（优先级：P2）

作为开发者，我希望控制审查的彻底程度——从快速的浅扫到详尽的最大努力扫描——以便根据更改大小和风险在审查成本和覆盖率之间权衡。

**为什么是这个优先级**：不同的更改需要不同的审查深度。单行拼写修复需要快速扫描；大型重构受益于更广泛的覆盖，即使以更多噪音为代价。

**独立测试**：在同一 diff 上运行 `/code-review low` 和 `/code-review max`，验证 `max` 启动更多 agent，并覆盖 `low` 不跑的角度。

**验收场景**：

1. **假设**用户运行 `/code-review low`，**当** skill 执行时，**则**它只跑两个角度（Angle A 与 Conventions），只报几乎确定的发现。
2. **假设**用户运行不带参数的 `/code-review`，**当** skill 执行时，**则**它默认为 `medium` 努力，跑六个角度（Angle A–E 与 Conventions）。
3. **假设**用户运行 `/code-review high`，**当** skill 执行时，**则**它跑全部十个角度。
4. **假设**用户运行 `/code-review max`，**当** skill 执行时，**则**它同样跑全部十个角度，但把低置信度的候选也报出来。

### 用户故事：并行多维审查与逐条核实（优先级：P2）

作为开发者，我希望审查并行覆盖多个独立维度（错误、AGENTS.md 合规性、git 历史、代码重用、效率），每条候选都由一个独立 agent 核实过，以便我可以专注于高信号问题。

**为什么是这个优先级**：并行审查减少延迟并扩大覆盖。核实阶段逐条判定候选是真问题、机制成立但触发不确定、还是事实有误，以过滤单次审查会暴露的误报。

**独立测试**：在带有重用问题和效率问题的 diff 上运行 `/code-review max`，验证两个维度都产生候选，且每条候选都拿到一份核实结论。

**验收场景**：

1. **假设**努力级别选出 N 个角度，**当** Phase 1 执行时，**则**每个角度一个 agent，全部在同一条消息里并发启动，每个接收完整 diff。
2. **假设**任何角度产生了候选，**当** Phase 2 执行时，**则**先去重指向同一处机制的候选，再为每条候选单独派一个核实 agent，它返回 `CONFIRMED`、`PLAUSIBLE`、`REFUTED` 之一。
3. **假设**候选已完成核实，**当** Phase 4 执行时，**则**只保留结论为 `CONFIRMED` 或 `PLAUSIBLE` 的候选，`REFUTED` 的一律丢弃。
4. **假设** Phase 1 要跑的角度，**则**它们覆盖「怎么找」的十个方向：逐行 diff、被删行为、跨文件调用点、语言陷阱、包装器转发、复用、简化、效率、改动位置是否在正确的一层、AGENTS.md 合规——而不是按「谁来看」分角色。
5. **假设**没有候选存活，**当**渲染报告时，**则** skill 如此说明并停止。

### 用户故事：核实之后再补扫一轮盲区（优先级：P2）

作为开发者，我希望在所有候选核实完之后再派一个 agent 带着已确认的清单回头扫一遍 diff 的盲区，以便抓住前面那些角度都没覆盖到、但阅读时一眼能看出来的问题。

**为什么是这个优先级**：角度是并发的，彼此看不到对方的结论；一轮补扫能让「已经确认了什么」变成线索，也用一次额外调用兜住并发拆分留下的缝。但它只是补漏，价值低于逐个角度的正面审查。

**独立测试**：在一份每个角度都能给出候选的 diff 上运行 `/code-review max`，验证核实结束后确实还派了一个补扫 agent，并且它给出的每条候选都又过了一次核实才进报告。

**验收场景**：

1. **假设** Phase 2 已跑完，**当** Phase 3 执行时，**则** skill 再派一个 agent，把已核实的发现清单一并交给它，让它在 diff 上补扫盲区。
2. **假设**补扫 agent 给出候选，**当**交付前，**则**最多收 8 条，且每条都要过 Phase 2 的核实；没通过核实的一样丢弃。
3. **假设**补扫没有发现新东西，**当**执行时，**则**它就这么说——正文明确禁止为了凑数而补充发现（Do not pad）。
4. **假设**补扫出来的候选与已核实的某条指向同一处机制，**当**交付时，**则**合并成一条，不重复报。

### 用户故事：AGENTS.md 合规审计（优先级：P2）

作为项目维护者，我希望审查检查更改是否遵守仓库的 `AGENTS.md` 文件（根目录和目录级），以便 AI 编写的代码遵循项目约定。

**为什么是这个优先级**：AGENTS.md 编码项目特定指导；审计合规性保持 AI 生成的更改与团队标准一致。

**独立测试**：添加禁止某种模式的 `AGENTS.md` 规则，在更改中引入该模式，运行 `/code-review`，并验证发现引用 AGENTS.md 规则。

**验收场景**：

1. **假设**根 `AGENTS.md` 存在，**当** AGENTS.md 合规 agent 运行时，**则**它根据根 AGENTS.md 指导检查 diff。
2. **假设**被修改文件所在目录存在 AGENTS.md 文件，**当**合规 agent 运行时，**则**它还检查那些目录级 AGENTS.md 文件。
3. **假设**发现违反了 AGENTS.md 规则，**当**发现被报告时，**则**它点名违反的是哪一份 AGENTS.md（根目录就给路径，目录级就写明是哪个目录），并引用被违反的那条规则原文。
4. **假设**某条候选只是「文档精神」上不太合、指不出具体的规则原文与违规行，**当**审查时，**则**它不进入报告——不做风格偏好推断。

### 用户故事：向 PR/MR 发布审查评论（优先级：P2）

作为开发者，我希望当平台 CLI（`gh` 或 `glab`）可用时将审查发现作为评论发布在 pull/merge request 上，以便我的团队可以在代码旁边看到审查，而无需从终端复制粘贴。

**为什么是这个优先级**：发布到 PR/MR 使发现对整个团队可见，并与代码更改一起持久化。当没有 CLI 或 PR/MR 时，发现回退到直接终端输出。

**独立测试**：在安装了 `gh` 且有 PR 的 GitHub 仓库上运行 `/code-review`，验证评论出现在 PR 上且无终端输出。在没有 `gh` 的仓库上，验证发现直接输出到终端。

**验收场景**：

1. **假设**仓库托管在 GitHub.com 且安装了 `gh` 且当前分支有 PR，**当**Phase 4执行时，**则**审查通过 `gh api repos/{owner}/{repo}/pulls/{pr}/comments` 作为 PR 评论发布，不输出到终端。
2. **假设**仓库托管在 GitLab.com 且安装了 `glab` 且当前分支有 MR，**当**Phase 4执行时，**则**审查通过 `glab mr note` 作为 MR 注释发布，不输出到终端。
3. **假设**没有安装平台 CLI，**当**Phase 4执行时，**则**发现直接输出到终端。
4. **假设**安装了 CLI 但当前分支没有 PR/MR，**当**Phase 4执行时，**则**发现直接输出到终端。
5. **假设**没有发现通过核实，**当**Phase 4执行时，**则** skill 显示"no issues"并停止——不发布评论也不输出发现。
6. **假设**仓库托管在自建 GitLab（主机名不是 `gitlab.com`）且安装了 `glab` 且当前分支有 MR，**当**Phase 4执行时，**则**审查通过 `glab mr note` 作为 MR 注释发布，不输出到终端。
7. **假设**评审目标只给出 MR 编号（`!12` 或裸数字 `12`）而命令里没有项目路径，**当**发布到 GitLab 时，**则**命令是 `glab mr note 12 -m "<body>"`、不带 `-R`，并注明这条命令要在那个项目自己的 checkout 里执行——`glab` 只会拿当前目录所属的项目当目标，`cd` 到别处就会发错仓库。给出整条 MR 链接时项目路径已经写进命令（`-R group/proj`），不需要这句。

### 用户故事：裸数字按仓库托管方解析评审目标（优先级：P2）

作为使用 GitLab 仓库的开发者，我希望 `/code-review 12` 直接指向本仓库的合并请求，而不是非得写成 `!12` 或贴整条链接，以便不管仓库托管在哪，指 PR/MR 都只敲一个数字。

**为什么是这个优先级**：`!12` 已经能精确表达 MR，所以这一条只是省事；但它决定「12 到底是哪个对象」，写错就是评错了 diff，因此不能靠猜。识别不出托管方时也不留空——国内的私有化部署基本都是自建 GitLab，所以**非公网域名的远端一律按私有化部署的 GitLab 处理**（已知取舍：自建 GitHub Enterprise 会被同样当成 GitLab）。

**独立测试**：把远端分别指到 github.com 与 gitlab.com 的同名仓库，各自跑一次 `/code-review 12`，验证读到的 diff 命令分别是 `gh pr diff 12` 与 `glab mr diff 12`；再把远端换成一个自建 GitLab 地址（例如 `ssh://git@g.example.com:22222/o/r.git`）跑一次，验证同样是 `glab mr diff 12`；最后在一个没有配远端的仓库里跑一次，验证不注入任何目标。

**验收场景**：

1. **假设**远端指向 `gitlab.com` 且执行 `/code-review 12`，**当** skill 选评审目标时，**则**目标是本仓库的合并请求 `!12`，读 diff 用 `glab mr diff 12`。
2. **假设**远端指向 `github.com` 且执行 `/code-review 12`，**当** skill 选评审目标时，**则**目标是本仓库的 pull request `12`，读 diff 用 `gh pr diff 12`。
3. **假设**远端指向 `bitbucket.org` 且执行 `/code-review 12`，**当** skill 选评审目标时，**则**不注入任何目标，行为与不带目标完全一致（评审当前分支）。
4. **假设**远端指向自建实例（主机名既不是 `github.com` 也不是 `gitlab.com`，例如私有化部署的 GitLab），**当** skill 选评审目标时，**则**按私有化部署的 GitLab 处理，目标是本仓库的合并请求 `!12`，读 diff 用 `glab mr diff 12`。
5. **假设**没配远端、或远端地址认不出主机名，**当** skill 选评审目标时，**则**不注入任何目标，行为与不带目标完全一致——既没有远端也没有 PR/MR 可评，猜一个只会评错东西。
6. **假设**显式写出 `!12` 或整条 GitLab MR 链接，**当** skill 选评审目标时，**则**无论远端指向哪里都按合并请求处理。
7. **假设**远端是 `gitlab.com` 或自建实例，**当**执行 `/code-review --comment` 且未给目标时，**则**选 GitLab 的那一段（`glab mr note`），不发 GitHub 评论。
8. **假设**显式给出整条 PR 链接（`https://<任意主机>/o/r/pull/9`），**当** skill 选评审目标时，**则**按 URL 形状判为 pull request，与远端的托管方默认值无关——自建的 GitHub Enterprise 链接仍然交给 `gh pr diff`。

### 边界情况

- **如果 diff 非常大怎么办？** skill 将完整 diff 传递给每个 agent；skill 本身不进行截断。大型 diff 可能达到模型上下文限制——这是可接受的，表现为 agent 错误。
- **如果 `main` 分支在本地不存在怎么办？** 先走 `git diff origin/HEAD...HEAD`（默认分支叫别的名字就换名），它给不出东西时退回 `git diff main...HEAD`，连基准都认不出时才退回 `git diff HEAD~1`，仅审查最后一次提交。
- **如果分支 diff 是空的、但工作区有改动怎么办？** 把工作区算进来（`git diff HEAD`），不要因为拿不到提交区间就告诉用户「没有可审查的内容」。
- **如果发现是误报怎么办？** 核实阶段把事实有误、或已在别处被守卫的候选判为 `REFUTED` 并丢弃；skill 还列出显式排除的误报类别（预先存在的问题、linter 级别的挑剔、有意更改等）。
- **如果 AI 尝试自动触发 skill 怎么办？** frontmatter 中的 `disable-model-invocation: true` 阻止 AI 自动调用 skill；它仅通过 `/code-review` 由用户调用。
- **如果 `--fix` 之后再次交付清单怎么办？** 那是同一份清单的更新，不是追加的第二份：交付的条目与第一次同一批，只是每条多了处理结果，界面据此更新已有条目的状态。
- **如果核实 agent 与审查 agent 意见不一致怎么办？** 核实 agent 的结论对保留与否具有权威性；审查 agent 自己的评估不参与该判定。
- **如果 PR 链接指向自建实例（GitHub Enterprise）怎么办？** 只有主机名认得出是 `github.com` 时才敢拼 `-R owner/repo` 与 `gh api repos/…`（那是 github.com 的端点拼法）；自建实例上整条 URL 交给 `gh pr diff`，连 `pr diff` 的替代命令也不给。这条与「非公网一律当 GitLab」**不冲突**：默认值只作用于裸数字，链接一律按 URL 形状（`/pull/` 还是 `/-/merge_requests/`）判定。
- **如果远程是自托管 GitLab（不是 gitlab.com）怎么办？** 平台检测按远端地址的主机名精确匹配（`github.com` / `gitlab.com` / `bitbucket.org` 及三个 SSH 别名），不做子串匹配；自定义域的自托管实例归入「其它」，**按私有化部署的 GitLab 处理**——裸数字走 `glab mr diff`，`--comment` 走 `glab mr note`。代价是自建 GitHub Enterprise 被同样当成 GitLab，裸数字会走 `glab`：国内 GHES 部署极少，这个误判可以接受；而显式写 `!12` 或整条链接的人完全不受影响。
- **如果远端地址认不出主机名、或者根本没配远端怎么办？** 不注入任何目标，也不猜托管方——没有远端就没有 PR/MR 可评，宁可让 skill 去评当前分支，也不要拼一条可能指向别处的命令。
- **如果评审目标只有 MR 编号、没有项目路径怎么办？** `glab mr note` 不带 `-R`，正文要说明这条命令得在那个项目自己的 checkout 里执行——这是 `glab` 的定位方式（当前目录所属项目），不是可省略的客套话。给出整条链接时项目路径已在命令里，不出现这句。
- **如果 `gh` 或 `glab` 已安装但未认证怎么办？** 发布评论的 CLI 命令将失败；skill 将其视为"PR/MR 不存在"并静默跳过。
- **如果发布评论失败怎么办？** skill 回退到直接终端输出，确保不丢失信息。
