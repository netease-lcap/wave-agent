# 功能规格说明：OpenTelemetry 集成

**规格文件**：`docs/specs/enterprise/opentelemetry.md`
**创建日期**：2026-05-09

## 用户场景与测试 _（必填）_

### 用户故事：指标与日志的 OTLP 远程导出（优先级：P1）

作为开发者，我希望将 Wave 的指标与事件日志发送到企业自己的 OTLP 收集器，以便统一度量会话成本、容量与使用模式，并把关键生命周期事件纳入既有的审计与检索体系。

**为什么是这个优先级**：这是企业接入的主要用例——把结构化的指标与事件交给外部后端，才能在不解析日志的前提下做成本与容量规划、定位使用阻力。

**独立测试**：通过 `OTEL_EXPORTER_OTLP_ENDPOINT` 将 Wave 指向一个 OTLP 收集器，运行会话，并验证指标与事件出现在收集器的查询界面中。

**验收场景**：

1. **假设** `OTEL_LOGS_EXPORTER=otlp` 且有收集器端点，**当**会话开始和结束时，**则**收集器收到 `session_start` 和 `session_end` 的结构化日志事件。
2. **假设** `OTEL_METRICS_EXPORTER=otlp` 且有收集器端点，**当**用户完成一轮消息交互时，**则**收集器收到按模型与类型标注的 token 用量、请求计数与请求耗时、以及会话计数指标。
3. **假设** 同一进程内已经有会话结束过（长驻宿主可承载多个会话，如桌面端远程主机连的 daemon），**当**新会话开始、完成一轮并记录事件时，**则**收集器仍收到该会话的事件与指标——导出器是进程级的，单个会话结束不得停止采集。

### 用户故事：运营指标（对齐 Claude Code 的指标面，优先级：P1）

作为把 Wave 接入企业度量平台的接入方，我希望有稳定命名的运营指标，覆盖成本（token 用量）、效率（请求耗时、错误率）与产出（代码行数、会话数、提交数与 PR/MR 数），以便直接填进既有看板做容量规划与成本分摊，而不是靠解析事件日志自行聚合。

**为什么是这个优先级**：metrics 是 fleet 级问题的答案（哪个模型贵、错误率是否上升、用量是否回落），也是企业侧唯一能低成本长期保留的信号；事件日志适合审计、解析成本高。

**独立测试**：配置 OTLP 或 console 导出器，跑一轮包含多模型调用、一次被拒绝的工具调用、一次文件编辑与一次成功提交的会话，观察指标齐全且归属属性正确。

**指标族（API 契约，命名 `wave.*`）**：

- 请求类：`wave.api.requests`（计数，按 `model`）、`wave.api.errors`（计数，按 `model`）、`wave.api.duration`（直方图，按 `model`）
- 用量类：`wave.tokens`（计数，按 `model` + `type`：input / output / cache_read / cache_creation）
- 会话类：`wave.sessions`（计数）
- 产出类：`wave.lines.changed`（计数，按 `direction`：added / removed，来源为编辑类工具的执行结果）、`wave.commits`（计数，来源为经由工具成功创建提交的动作）、`wave.pull_requests`（计数，PR 与 MR 合入同一计数，来源为经由 shell 命令或 MCP 工具成功发起创建 PR/MR 的动作）

其中 `wave.commits` / `wave.pull_requests` 对齐 Claude Code 的 `commit.count` / `pull_request.count` 口径：**只认「经由工具、且成功」的创建动作**，不看结果是否被合并、不依赖任何托管平台（私有化 GitLab 与 GitHub 同等成立），也不携带归属属性。

**验收场景**：

1. **假设** OTEL 指标已启用，**当** agent 完成一次模型调用时，**则** `wave.api.requests` 与 `wave.api.duration` 各记录一次，且 `wave.tokens` 按 input / output / cache 类型分别累加，归属属性为当次请求的模型。
2. **假设** OTEL 指标已启用，**当**模型调用失败或工具权限被拒绝时，**则** `wave.api.errors` 递增（模型调用失败计入该指标；工具决策拒绝走事件日志，不重复计入指标）。
3. **假设** OTEL 指标已启用，**当**编辑类工具写入了文件变更时，**则** `wave.lines.changed` 按 added / removed 分别累加编辑结果中的行数。
4. **假设** 未配置 `metricsExporter`，**当**会话进行时，**则**不产生任何指标（默认关闭，与另外两类信号一致）。
5. **假设** 一轮会话里发生自动压缩，**当**压缩完成后，**则**压缩后的 token 计数继续累计在同一会话的 `wave.tokens` 上（压缩不重置指标、不产生负值）。
6. **假设** 指标导出所需的耗时与错误信息（如失败原因字符串）存在，**则** 指标不携带提示词、文件内容或其它内容级数据，只带低基数归属属性。
7. **假设** OTEL 指标已启用，**当** agent 经由 Bash 工具成功创建了一个提交（含 `git -C <dir> commit`、前导环境变量赋值、`--amend`、以及 `git add -A && git commit -m x` 这类复合命令）时，**则** `wave.commits` 递增一次；一次工具调用无论涉及多少个提交动作，最多只计一次。
8. **假设** 创建提交的命令执行失败（非 0 退出），**则** `wave.commits` 不递增；由脚本内部或非提交类命令（如 `git merge`）间接产生的提交也不计——口径与 Claude Code 一致，只认「经由工具、且成功」的建提交动作。
9. **假设** OTEL 指标已启用，**当** agent 经由 shell 命令（如 `gh pr create`、`glab mr create`）或 MCP 的建 PR/MR 工具成功创建了一个 PR 或 MR 时，**则** `wave.pull_requests` 递增一次；创建失败的调用不计；PR 与 MR 不作区分，同一个计数。
10. **假设** 这两个指标已启用，**则** 它们不携带归属属性（不按模型、仓库或人拆分），也不依赖任何 Git 托管平台的 API 或凭据——私有化 GitLab 与公有 GitHub 场景下行为一致。

### 用户故事：通过事件日志的会话诊断（优先级：P2）

作为开发者，我希望关键会话生命周期事件（开始、结束、压缩、工具决策、错误）有结构化事件日志，以便无需解析原始 JSONL 文件即可重建会话期间发生的事情。

**为什么是这个优先级**：这提供了可搜索的结构化审计跟踪，补充原始消息历史。事件通过配置的 logs 导出器导出（OTLP 用于远程，console 用于本地观察）。

**独立测试**：使用 `OTEL_LOGS_EXPORTER=otlp` 运行 Wave，完成包含多轮包括压缩和被拒绝工具调用的会话，并验证所有生命周期事件出现在收集器中。或将导出器设为 `console`，直接观察事件以可读形式打印。

**验收场景**：

1. **假设** OTEL 日志已启用，**当**会话开始时，**则**记录 `session_start` 事件，包含 sessionId、model 和 workdir。
2. **假设** OTEL 日志已启用，**当** agent 自动压缩对话时，**则**记录 `compaction` 事件，包含压缩前后的 token 计数。
3. **假设** OTEL 日志已启用，**当**工具权限被拒绝时，**则**记录 `tool_decision` 事件，包含工具名称和决策。
4. **假设** `OTEL_LOG_USER_PROMPTS=1`，**当**用户发送消息时，**则** `user_prompt` 事件包含实际提示文本。**假设** `OTEL_LOG_USER_PROMPTS` 未设置，**则**排除提示文本。

### 用户故事：console 导出器（零依赖本地观察，优先级：P2）

作为开发者，我希望把事件与指标直接以可读形式打印到终端来观察遥测内容，以便不配置任何收集器就能当场调试（对齐 Claude Code 的 `console` 导出器）。

**为什么是这个优先级**：交互 TUI 默认接管 console 输出（Ink patchConsole），打印内容呈现在当前帧上方、不打碎界面；但 stdout 在结构化输出宿主里是协议通道（`--stdio` 的 JSON-RPC、`--print` 的结果流），console 打印会直接破坏协议——所以该选项必须与「非交互宿主自动剥除」配套，与 Claude Code 在 stream-json 模式下的处理同构。

**独立测试**：交互模式下把导出器设为 `console`，运行一轮会话，观察终端出现结构化输出且交互不受阻；再以 `--print` 或 `--stdio` 运行同样配置，确认输出通道没有 console 打印的内容、协议报文完好。

**验收场景**：

1. **假设** 某类信号的导出器为 `console` 且处于交互 TUI，**当** agent 处理消息时，**则** 结构化输出呈现在界面上方，交互正常继续。
2. **假设** 同一配置在 `--stdio` / `--print` 模式下运行，**当** 会话进行时，**则** stdout 上没有 console 打印的内容，协议通道保持纯净。

### 用户故事：出站凭据由命令动态提供（优先级：P2）

作为把遥测接到企业内部收集器的接入方，我希望 OTLP 出站头由一条命令在发送前提供，而不是写死成配置里的字符串，以便凭据轮换或吊销后不需要重新下发配置、也不需要重启长驻宿主（桌面端 / VS Code）里的会话。

**为什么是这个优先级**：不配动态头时一切照旧，因此不阻塞；但只要上报目标要求「凭据按设备签发、有生命周期、可吊销」，静态头就是硬伤——要么把 token 烧进分发包，要么每次轮换让全员改配置重启。

**独立测试**：在 `~/.wave/settings.json` 里把 `monitoring.telemetry.headersHelper` 指向一个打印固定 JSON 头的脚本，把导出目标指向一个记录请求头的本地收集器，运行一次会话；再把脚本改成打印另一组头、等过一个刷新间隔，观察收集器收到的是新头。

**验收场景**：

1. **假设** 用户级配置里给了 `monitoring.telemetry.headersHelper` 且同时存在静态 `headers`，**当** 导出器发送一批数据时，**则** 该批次带两组头，**同名键取命令给出的值**。
2. **假设** helper 上一次成功返回过头，**当** 刷新间隔到达后 helper 失败（非 0 退出 / 超时 / stdout 不是合法 JSON 对象）时，**则** 导出沿用上一次成功取到的头继续发送，agent 会话不受影响，并记录一条限流警告（只在失败种类变化时重复）。
3. **假设** helper 从未成功过，**当** 导出时，**则** 只带静态头发送，批次不被丢弃、会话不中断。
4. **假设** 同一刷新间隔内有多次导出（多个信号、多个批次），**则** 命令在该间隔内只被执行一次（并发调用共享同一次运行，导出器之间共享同一份缓存）。
5. **假设** 间隔已过且 helper 恢复正常，**当** 下一次导出时，**则** 使用新取到的头（无需重启进程）。
6. **假设** 宿主在进程内注入了取头函数（`AgentOptions.telemetry.headersProvider`），**当** 导出时，**则** 使用注入函数的返回值，配置里的 helper 命令不执行。
7. **假设** `monitoring.telemetry.headersHelper` 只出现在项目 `.wave/settings.json` / `settings.local.json`（随仓库分发）里，**当** 配置加载时，**则** 该键被忽略（同块其它遥测设置照常生效）并记录警告。
8. **假设** helper 失败，**则** 失败信息只包含失败种类与退出码；命令的 stdout 不进入日志与审计。
9. **假设** `monitoring.telemetry` 写在 `settings.json` 或由服务端托管配置下发，**当** 会话启动时，**则** 该配置到达 SDK 并参与导出配置解析（含 `headersHelper`）；托管层与本地层按字段合并，同名键以托管层为准。

### 边界情况

- **如果导出端点（OTLP 收集器 / 转发层入口）不可达会怎样？** 遥测导出应优雅失败并记录警告；agent 会话必须正常继续而不阻塞。
- **如果出站头由命令提供、而该命令失败会怎样？** 遥测链路保持可用（沿用上次成功的头，否则只发静态头），失败以限流警告呈现；agent 会话必须不受影响，命令 stdout（即凭据）不得进入任何日志面。
- **如果出站头命令来自仓库内的配置文件会怎样？** 该键被忽略（随仓库分发的配置不得指定本机要执行的命令），其它遥测设置仍生效。
- **如果 OTEL 已启用但未配置导出器会怎样？** 不设置默认导出器。用户必须显式配置至少一个导出器。这避免在交互模式中意外的 stdout 污染。
- **如果 console 导出器跑在结构化输出宿主（`--stdio` / `--print`）里会怎样？** console 在遥测初始化处被自动剥除（对齐 Claude Code 的 stream-json 处理），stdout 协议通道保持纯净；console 只在交互 TUI 下生效。
- **如果配置里还留着早期版本的导出器值（`jsonl`、`tracesExporter` 整键）会怎样？** 认不出或已下架的取值被忽略并记录告警，其余遥测设置照常生效——不因为遗留配置使整个遥测初始化失败。
- **如果遥测初始化失败会怎样？** agent 必须在没有遥测的情况下正常启动；记录警告但不崩溃。
