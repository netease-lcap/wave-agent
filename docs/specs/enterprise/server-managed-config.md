# 功能规格说明：服务器托管配置下载

**创建日期**：2026-05-25

## 用户场景与测试 _（必填）_

### 用户故事：启动时下载托管设置（优先级：P1）

作为组织管理员，我希望将托管设置（允许的工具、模型限制、环境变量）推送到团队的 Wave agent，以便在不要求每个用户手动配置设置的情况下执行组织策略。

**为什么是这个优先级**：这是核心价值主张——团队和企业的集中配置管理。

**独立测试**：使用在 Wave AI 上配置了托管设置的账户通过 SSO 认证，启动 Wave，并验证托管设置已应用。

**验收场景**：

1. **假设**用户通过 SSO 认证且服务器有托管设置，**当** Wave 初始化时，**则**它从 `WAVE_SERVER_URL/api/v1/managed-settings` 下载托管设置并应用。
2. **假设**用户未通过 SSO 认证，**当** Wave 初始化时，**则**不下载托管设置，使用仅本地设置。
3. **假设**托管设置包含 `model` 标量字段，**当**解析设置时，**则**托管模型优先于本地 `settings.json` 模型（管理员强制）。**假设**托管设置包含 `env.WAVE_MODEL` 但没有 `model` 字段，**当**用户在 `settings.json` 中有 `model` 字段时，**则**用户的模型优先（用户覆盖管理员的默认值）。

---

### 用户故事：基于校验和的缓存（优先级：P2）

作为慢速网络上的用户，我希望 Wave 在托管设置未更改时跳过重新下载，以便启动快速且节省带宽。

**为什么是这个优先级**：性能优化——大多数启动会发现设置未更改，因此避免下载是有意义的改进。

**独立测试**：在服务器上托管设置未更改的情况下启动 Wave 两次；验证第二次启动不进行下载请求。

**验收场景**：

1. **假设**托管设置之前使用校验和下载过，**当** Wave 初始化且服务器返回相同校验和时，**则**使用缓存的设置而无需重新解析。
2. **假设**托管设置之前已下载，**当**服务器返回不同的校验和时，**则**新设置被下载、解析和缓存。

---

### 用户故事：设置合并优先级（优先级：P1）

作为组织管理员，我希望我的托管设置对特定键覆盖本地用户设置，以便安全策略（例如，不允许的工具）不能被本地配置规避。

**为什么是这个优先级**：没有正确的合并优先级，托管设置可能被本地设置覆盖，使集中管理失去意义。

**独立测试**：配置不允许 Bash 工具的托管设置，验证本地 `allowedTools` 设置不能重新启用 Bash。

**验收场景**：

1. **假设**托管设置包含 `disallowedTools: ["Bash"]`，**当**设置被合并时，**则** Bash 工具被禁用，无论本地 `allowedTools` 设置。
2. **假设**托管设置不包含 `model` 字段，**当**设置被合并时，**则**使用 `settings.json` 中的本地 `model` 设置。
3. **假设**托管和本地设置都包含 `env` 字段，**当**设置被合并时，**则**托管环境变量覆盖同键的本地变量，非重叠的本地环境变量被保留。

### 用户故事：在设置页查看服务端下发的配置（优先级：P1）

作为使用企业托管配置的用户，我希望在设置页「全局设置」视图里直接看到服务端下发的配置原文，以便不去翻本机的 `~/.wave/remote-settings.json` 也能确认服务端到底管控了哪些项。

**为什么是这个优先级**：托管配置的价值是「组织集中管控」，但在本故事之前，用户只能从「由组织配置管理」这类逐键标注间接猜测被管了什么，看不到完整清单——这是托管配置可解释性的基础能力（P1）。展示是只读的，不改变任何生效配置，因此风险低、可独立交付。

**独立测试**：在已登录且服务端已下发托管配置的环境中打开设置页「全局设置」视图，验证出现「服务端配置」区块并以只读 JSON 展示服务端下发的配置内容；在服务端未下发（未登录 / 服务端未为该组织配置 / 下发已被撤销）的环境中验证该区块显示空态说明；反复进出该视图验证内容随服务端最新下发刷新。

**验收场景**：

1. **假设**服务端已下发托管配置，**当**用户打开设置页「全局设置」视图，**则**该视图内（其它区块之后）必须渲染「服务端配置」区块，以**只读**的 JSON 文本展示服务端下发的完整配置——格式化缩进、等宽字体、内容可选中复制；展示内容 = 服务端最近一次成功下发的配置原文，**不做字段筛选**（不挑「重要项」展示，用户要看到的是全量清单）。
2. **假设**服务端未下发托管配置（未登录、服务端未为该组织配置托管设置、或此前下发的配置已被撤销），**当**用户打开「全局设置」视图，**则**「服务端配置」区块显示空态说明（如「当前没有服务端下发的配置」），**不得**渲染空 JSON 块（`{}`）、也不得渲染一个空白文本框让用户以为是加载失败。
3. **假设**「服务端配置」区块已展示，**当**用户查看它，**则**该区块**纯只读**——不提供任何编辑控件、不提供保存/应用按钮、不因它的存在改变任何生效配置；它只回答「服务端下发了什么」（修改组织策略的入口在服务端，不在本机）。
4. **假设**用户反复进入/离开「全局设置」视图，**当**视图重新打开，**则**展示的是**当前**的下发内容（以进程内最近一次成功下发的配置为准；托管配置在本次应用运行期间被服务端更新过时，重入视图必须看到新内容），**不得**只在应用启动时读取一次后长期沿用旧值。
5. **假设**服务端下发的配置里包含某个键，而该键同时也在本机可配（如自动记忆开关、上下文长度），**当**该键的生效值确实来自服务端下发，**则**「服务端配置」区块展示的内容与其它区块「由组织配置管理」的标注必须出自**同一份下发配置**——不得出现「区块里没有这个键、别处却标着由组织配置管理」的矛盾。
6. **假设**用户处于 VS Code 扩展 / JetBrains 插件 / 桌面端任一宿主，**当**打开设置页「全局设置」视图，**则**三端都必须展示该区块、行为与内容一致；读取的是**会话所在进程**的下发配置（IDE 远端连接时读远端机器上的下发内容），并按各宿主既有设置页形态承载（桌面端为全页设置、IDE 为编辑器区域设置标签页）。

### 边界情况

- **如果托管设置端点不可达会怎样？** Wave 必须在缓存可用时使用缓存设置，否则使用仅本地设置。记录警告但不阻止启动。
- **如果托管设置包含无效 JSON 会怎样？** Wave 必须记录错误并回退到仅本地设置。
- **如果用户退出 SSO 会怎样？** 后续启动不再下载托管设置，但之前缓存的托管设置保持有效，直到被本地更改覆盖。
- **如果托管设置与环境变量冲突会怎样？** 用户的 `settings.json` `model` 字段覆盖管理员的 `env.WAVE_MODEL` 默认值。如果管理员想要强制执行，他们使用 `model` 标量字段，在合并期间覆盖本地值。Shell 环境变量（在 Wave 启动前设置）是最低优先级的回退。
- **设置重新加载期间（文件监视器）会怎样？** 托管设置在文件更改时不会重新下载——它们仅在初始化期间下载。
- **设置页「服务端配置」区块展示的是缓存的下发内容，不是实时请求：** 它读的是本进程最近一次成功下发并缓存的托管设置（与服务端端点的定时刷新同源），因此展示失败（端点不可达但缓存可用）时显示的仍是上次成功下发的内容；端点从不可达恢复后，区块随下一次刷新更新。打开视图不额外发起网络请求，避免把「查看配置」变成一次网络等待。
- **下发内容含敏感值（如 `env` 里的密钥类变量）时不脱敏：** 区块展示的是服务端下发的**完整原文**——客户要看的就是服务端究竟管控了什么，逐字段脱敏会直接违背该能力的目的；该内容本就以 `0600` 落盘在用户本人的 `~/.wave/remote-settings.json`，展示不等于新增暴露面。若将来需要「对外截图友好」的形态，须另立需求（例如显式折叠敏感项），不在本故事范围内。
- **本机缓存文件损坏/无法解析时：** 与「服务端未下发」同处理（区块显示空态），不得让设置页渲染报错或阻塞其它区块。
- **如果 `WAVE_SERVER_URL` 配置在 `settings.json` 的 `env` 中而非 shell 环境变量会怎样？** 启动时本地 `settings.json` 的 `env` 在 `loadMergedConfiguration` 内才写入 `process.env`，而远程设置的网络请求通过 `getServerUrl()` 读取 `process.env.WAVE_SERVER_URL` 来决定目标端点。因此网络请求必须在 `loadMergedConfiguration` **之后**启动；否则 `WAVE_SERVER_URL` 尚未写入 `process.env`，`getServerUrl()` 回落到 `DEFAULT_SERVER_URL`（生产），用测试环境签发的 token 命中生产端点，必然 401 且无法恢复。磁盘缓存加载（`loadCacheFromDisk`）仍须在 `loadMergedConfiguration` **之前**完成，以便合并时 `getRemoteSettingsSync()` 返回缓存的托管设置。两者职责分离：缓存加载在前，网络刷新在后。
