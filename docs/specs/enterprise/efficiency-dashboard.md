# 功能规格说明：研发效能看板

**规格文件**：`docs/specs/enterprise/efficiency-dashboard.md`
**创建日期**：2026-10-16

数据来源见 [OpenTelemetry 集成](./opentelemetry.md) 的「默认上报到 Wave 服务端」——本规格只管**收到数据之后怎么呈现**，不管采集与上报。

## 用户场景与测试 _（必填）_

### 用户故事：用时间趋势看研发效能的走向（优先级：P1）

作为企业管理员，我希望研发效能页面在明细数据之外还有按天的时间趋势，以便一眼看出用量与产出是在涨还是在跌、哪天异常，而不是逐格读数字再自己比对。

**为什么是这个优先级**：明细表回答的是"某一项数值是多少"，回答不了"在变好吗"。研发效能的核心问题恰恰是走向——用量是否失控、产出是否下降、某天上线的改动是否立刻反映到了数据上。没有时间序列，看板就只是把数据库摆出来。

**独立测试**：在一个跨越数天、每天都有会话数据的窗口上打开页面，确认趋势的每一天取值与该天单独查询的窗口聚合一致；再收窄到只有一天，确认趋势退化为单个点而不是空白或报错。

**验收场景**：

1. **假设** 所选窗口跨越多个自然日，**当** 管理员打开研发效能页面，**则** 呈现按自然日分桶的时间趋势，横轴为日期、覆盖窗口内每一天（没有数据的日期按 0 呈现，不跳过，避免走向被误读）。
2. **假设** 窗口内某一天没有数据，**则** 该天在趋势上取值为 0 而非缺口——不跳过日期、不插值。
3. **假设** 窗口跨度不超过一天，**当** 页面呈现趋势时，**则** 改用小时粒度分桶，而不是退化成只有一个点的趋势。
4. **假设** 趋势已呈现，**当** 管理员核对任一日的数值时，**则** 该日取值与把窗口收窄到该日后查询得到的聚合值一致——趋势与明细来自同一份口径，不存在两套算法。
5. **假设** 趋势图已渲染，**则** 同样的数值同时以表格形式提供（图不是唯一的数值载体，便于核对、复制与无障碍访问）。
6. **假设** 指标是累积量（计数器），**当** 按桶折算某一天的量时，**则** 取该桶与相邻桶的差值，且跨桶重置、重复上报（重试）不产生虚高或重复计数。
7. **假设** 某一指标族不携带某归属维度（如会话数、提交数、PR 数不携带模型），**则** 该维度的趋势不呈现这一指标族，而不是画一条恒为 0 的线。
8. **假设** 窗口内没有任何数据，**当** 打开页面时，**则** 呈现空状态说明，而不是空白坐标轴或错误提示。
9. **假设** 所选窗口超过服务端允许的上限，**当** 请求到达服务端时，**则** 明确回报"窗口过大"并保持页面可用（现状同此，见 [OpenTelemetry 集成](./opentelemetry.md) 的查询面）。

### 用户故事：按维度看谁在贡献、用量花在哪（优先级：P2）

作为企业管理员，我希望在趋势之外还能按人、按仓库、按模型查看排名与产出贡献，以便回答"谁在产出""这个仓库值不值得继续投入""成本被哪个模型吃掉了"。

**为什么是这个优先级**：趋势回答"整体在变好吗"，回答不了"是谁造成的"。但它是同一个看板的延伸而非独立能力——没有趋势时它退化成一个静态报表，价值有限，所以排在趋势之后。

**独立测试**：构造两个用户、两个仓库、两个模型的数据，确认排名按量降序且各自占比之和为 100%（含"其他"聚合项），并确认产出类指标（提交、PR、变更行数）只出现在人与仓库维度、不出现在模型维度。

**验收场景**：

1. **假设** 窗口内有多个用户、仓库或模型，**当** 呈现任一维度排行时，**则** 按该维度的数值降序排列，并给出各项占该维度总量的比例。
2. **假设** 某个维度的取值数超过页面呈现上限，**则** 超出部分聚合为一项"其他"，其数值为其余各项之和——聚合项不是丢弃项，各层级相加仍等于总计。
3. **假设** 查看模型维度，**则** 只呈现用量类指标（请求、错误、耗时、token）——会话数、提交数、PR 数、变更行数按口径不携带模型归属，不在该维度出现（沿用 [OpenTelemetry 集成](./opentelemetry.md) 的归属口径）。
4. **假设** 查看用户或仓库维度，**则** 同时呈现用量类与产出类指标（会话、提交、PR、变更行数）。
5. **假设** 仓库归属默认关闭、数据未携带 `vcs.repository.*`，**则** 仓库维度呈现为空状态并说明原因，而不是显示成"(未知仓库)"这类会被误读为真实取值的占位。
6. **假设** 某条数据缺少人/模型归属，**则** 归入明确的"未知"分类并照常计入总计——不静默丢弃，否则各维度之和会对不上总量。
7. **假设** 管理员从趋势图上看到某天异常，**当** 他想定位到具体会话时，**则** 能从该日下钻到会话明细（会话维度已带人、仓库、模型归属）。

### 用户故事：把看板数据导出用于汇报（优先级：P2）

作为企业管理员，我希望把当前窗口与维度的数据原样导出为表格文件，以便贴进汇报材料、或交给财务做成本分摊，而不必逐屏截图或手工抄数。

**为什么是这个优先级**：汇报是看板的真实下游用途，但导出不会改变数据本身，只是换个承载形式，所以在呈现能力之后。

**独立测试**：在任一窗口点击导出，确认导出的行数与各列数值与页面上看到的一致（含"其他"聚合项），且导出内容与管理员当前的窗口筛选一致、不是全量数据。

**验收场景**：

1. **假设** 管理员已选定窗口与维度，**当** 触发导出时，**则** 导出内容为**当前筛选条件下的聚合结果**（与页面所见一致），而不是全量原始数据。
2. **假设** 导出已生成，**则** 内容为可直接打开的表格形式，含列名，且累积量给出的是折算后的量而非原始计数器读数。
3. **假设** 窗口内无数据，**当** 触发导出时，**则** 导出仅含表头的空表或明确提示无数据，不产生一份会被误读为"零用量"的表格。

### 边界情况

- **如果客户端导出的批次有周期延迟会怎样？** 页面呈现的是**已落库**的数据，不承诺实时；最近时间段可能还不完整。看板需要标注数据的时间覆盖范围，避免把"还没上报完"读成"用量下降"。
- **如果同一条数据被重复上报会怎样？** 入端按数据点幂等去重（现状同此）；按桶做差时也要保证重试不产生重复计数——两处都错才会计出虚高的趋势。
- **如果窗口很长（跨月）会怎样？** 服务端有窗口上限并会拒绝过大的请求；看板应给出可操作的提示而不是静默失败或空白。
- **如果模型维度里出现历史遗留的无归属数据会怎样？** 与"未知"分类同理——计入总量，不因缺归属而消失；但模型维度不呈现产出类指标这一条不因此放宽。
- **如果某项指标在窗口内没有任何数据点会怎样？** 该指标不出现在趋势中（或呈现为明确的空状态），不渲染出一条"看起来恒为 0 的真实趋势"。
- **如果页面同时呈现趋势与明细会怎样？** 两者必须来自同一次查询窗口与同一套折算规则，任何一处口径变化都需同步——图与表对不上比只有表更糟。
- **如果企业里存在没有数据的新成员会怎样？** 他不出现在排行里（排行基于有数据的人），而不是以 0 值占据一行。
