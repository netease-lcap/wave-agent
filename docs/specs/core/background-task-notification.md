# 功能规格说明：后台任务完成通知

**创建日期**：2026-08-21

> 对齐 Claude Code 的后台任务完成通知行为：Bash 后台任务与 Agent 子代理（fork 子代理、后台化 subagent、后台 workflow）完成时，其完成通知作为 `task-notification` 消息注入主对话——该消息对 UI 消息流隐藏（`isMeta: true`），对模型上下文可见（包装为 "A background agent completed a task:" + XML），并照常持久化到会话 jsonl。用户感知路径为模型主动汇报、`/tasks` 面板与后台任务面板，不经消息流。
>
> **注入时机**：通知一产生即入队，与当前是否正在应答无关。注入点取「请求边界」——每次向模型发请求之前检查队列并注入，因此同一轮内工具执行完、模型还会被再次请求时，通知搭下一次请求一起到达模型，不必等本轮收尾。模型不再发起工具调用（本轮结束）时，退化为轮末注入并开启新一轮。两个时机都不在流式输出中途插入消息。

## 用户场景与测试 _（必填）_

### 用户故事：后台任务完成通知（优先级：P1）

作为用户，我希望后台任务（Bash 后台命令、后台子代理、后台 workflow）完成时，其完成通知注入主对话供模型感知并汇报，但不在 UI 消息流中打扰我，以便消息流只呈现真实对话，任务结果由模型归纳后呈现。

**验收场景**：

1. **假设** 后台任务完成，**当** 完成通知注入主对话时，**则** 通知成为 role:user 的 meta 消息（`isMeta: true`），在 CLI 与 Webview 消息流中均不显示。
2. **假设** 后台任务完成通知已注入，**当** 模型读取消息上下文时，**则** 模型看到包装文本 "A background agent completed a task:" 加 `<task-notification>` XML（含 task-id、task-type、status、summary、output-file）。
3. **假设** 完成的是 workflow 任务，**当** 模型读取通知正文时，**则** 正文除公共标签外还带逐 agent 的用量计数（`agent_count` / `agents_done` / `agents_error` / `agents_skipped` / `agents_empty_result` / `subagent_tokens` / `tool_uses` / `duration_ms`）与失败明细，失败时给出逐 agent 结果文件位置与恢复指引；计数不写进说明结局的那一行标题；这些标签只有 SDK 内的解析点读取，消息流的隐藏渲染不受标签增减影响。
4. **假设** 后台任务完成通知已注入并触发新一轮 AI 应答，**当** 会话保存时，**则** 通知消息（isMeta）与随后的 assistant 消息一同写入会话 jsonl，恢复会话后模型上下文与通知行为不变。
5. **假设** 后台任务被手动终止（killed），**当** 任务结束时，**则** 不注入完成通知。
6. **假设** 多个后台任务同时完成，**当** 通知注入时，**则** 所有通知合并进同一轮 AI 应答（批量处理）。
7. **假设** 通知消息被注入（role:user + `isMeta: true`），**当** 宿主收到 `notificationMessageAdded` 时，**则** 除按 `appendMessage` 增量下发给 webview 外，还必须把该消息按到达顺序写入宿主自己的消息缓存——通知虽不在消息流中显示，却仍占据"最后一条消息"这个位置：只推不写会让宿主缓存与 webview 对 `noticeAdded` 的落位判定（末条为 assistant 则合并进该条，否则新建一条）读到不同的末条，于 `setInitialState` 从缓存重放时（桌面端会话/分栏切换、界面重载）把同一轮的错误块画到与 webview 不同的气泡里。此约束只针对 **`setInitialState` 直接取自宿主缓存、不重新拉取**的宿主（桌面端）；读缓存前必先 `getMessages` 的纯拉取型宿主（VS Code / JetBrains 插件）由拉取自愈，无需增量镜像。
8. **假设** 某一轮应答返回了工具调用，**当** 这批工具执行完毕、模型即将被再次请求时队列里已有后台任务完成通知，**则** 通知在本次请求发出前注入（role:user + `isMeta`，排在工具结果之后），模型在同一轮内读到它并据此继续，本轮不会因为等待通知而空转收尾。
9. **假设** 模型本轮不再发起工具调用（本轮结束），**当** 队列里有通知，**则** 沿用轮末注入并开启新一轮；通知自身不单独延长本轮：只有本来就要继续请求时才会在轮中注入。
10. **假设** 轮中已注入过通知，**当** 本轮随后收尾，**则** 不再重复注入同一条通知（注入即消费），轮末注入也不会因为轮中注入过而跳过其它待注入通知。

### 边界情况

- **旧会话恢复**：历史会话 jsonl 中的通知消息若不含 `isMeta` 标记（本变更前写入），恢复后可能短暂可见——不做迁移，新写入的消息均带标记。
- **/clear 与 abort**：`MessageQueue.clear()` 保留 pending 通知（不丢弃后台结果）；abort 期间不注入通知（折叠进下一轮，防止孤儿循环）。
- **注入粒度**：通知只能在请求边界落地，因此流式输出中途、以及一批工具仍在执行时都不会插入；一个耗时很长的前台工具会把期间完成的后台通知一并压到它结束之后。
