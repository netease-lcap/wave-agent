# 功能规格说明：工具延迟加载

**规格文件**：`docs/specs/core/tool-deferred-loading.md`
**创建日期**：2026-09-13

## 设计背景

工具以完整 JSON Schema（描述、参数、枚举、必填）逐条声明进请求 `tools`。工具越多——MCP 服务器带来的一批，加上内置工具本身——固定开销越大，而其中绝大多数在一次会话中从未被调用。工具延迟加载的目标是：**默认不把「可延迟的工具」逐条声明，而是把它们的紧凑目录挂在唯一一个「转发工具」的说明里；模型需要某个工具时，调用转发工具按目录点名，由 host 转发到真正的叶子工具执行。**

**范围 = 任意已注册工具，不是 MCP 专属。** 机制内核只认「工具池里有哪些已注册工具」，MCP 工具与内置工具走同一条链路；某类工具是否纳入，由**逐个工具的标注**决定（对齐 Claude Code 内置工具的 `shouldDefer: true` 与逃生口 `alwaysLoad`）。

**命名与寻址（通用名，不含 `mcp`）**：与 wave 既有的「名词+动词」命名族一致（`TaskCreate` / `CronList` / `WebFetch`），搜索工具与 Claude Code 的 `ToolSearch` 同名。

- 转发工具 = **`ToolInvoke`**；搜索工具 = **`ToolSearch`**
- 转发工具的寻址字段 = **`namespace`**（语义：MCP 服务器的服务器名，或内置工具保留的命名空间 `builtin`）、**`tool`**、**`args`**：
  - `ToolInvoke({ namespace: "github", tool: "create_issue", args: {...} })`
  - `ToolInvoke({ namespace: "builtin", tool: "Read", args: {...} })`
- 目录条目记法 = **`<namespace>.<tool>(签名) // 描述`**：
  - `github.create_issue(owner: string, repo: string, title: string)`
  - `builtin.Read(file_path: string, offset?: number, limit?: number)`

目录本身也必须有界：**常驻部分**受体积上限约束，超出上限的工具不写进常驻目录、改为「可搜索够到」（见「目录预算与显式截断」「目录内搜索」）。这才让「挂更多工具」成为可能——若目录只能整放，工具数一多就退化回逐条声明，等于没做；若截断隐式进行，模型不知道有未显示的工具，也不会去搜。因此「常驻有界 + 超出可搜 + 截断显式」是本机制的核心价值，不是可选优化。

三点设计前提：

1. **能力边界不变**：转发只是「声明形态」的变化，不是权限或能力的放宽——叶子的审批、规则持久化、拒绝语义全部仍以**叶子**为单位（MCP 叶子 = `mcp__server__tool`，内置叶子 = 工具名本身，如 `Read` / `Bash`），与今天逐条声明时完全一致（见 [`core/tool-permission-system.md`](./tool-permission-system.md)）。
2. **机制内核覆盖任意已注册工具；内置工具是否纳入由逐个标注决定**：defer 粒度 = **逐个工具标注**（不按类别），并支持**逐工具 opt-out = 始终扁平声明**（等价 Claude Code 的 `alwaysLoad`）。热工具（`Read` / `Edit` / `Write` / `Bash` / `Grep` / `Glob` 等每轮都可能用到的）默认**不 defer**，冷工具优先；首批名单待定，评估维度 = schema 体积 + 使用频率。工具的显式选择语义见 [`ui/tools-selection.md`](../ui/tools-selection.md)。
3. **不依赖任何服务端协作**：本机制不要求上游提供「工具检索」能力（OpenAI 协议没有 Anthropic 式的服务端工具检索），也不要求模型调用未声明的工具——目录与转发工具本身都是**已声明**的工具。上游对未声明工具调用的实际返回形状与客户端处理边界见 [`core/ai-error-handling.md`](./ai-error-handling.md) 的边界情况。

**收益差异（诚实写明，别让实现者以为 defer 越多越好）**：对 MCP 工具，本机制省掉的是「逐条声明」这件事本身；**对内置工具，省掉的只是「完整 schema → 紧凑签名」（实测约 3.6×，547 → 151 字符/工具），不是 Claude Code 那种「完全不发、发现后才进 `tools[]`」**——而且代价是多一层调用形态。所以**热工具做 defer 反而亏**（省下的字符抵不过多一跳与出错面），本机制的内置侧价值集中在冷工具长尾。

**P1 准入条件（开工第一步的验收，不是另行排队的实验）**：在**真实复杂 schema**（多参数、嵌套对象、枚举、带默认值、长描述；MCP 工具与内置工具都要覆盖）上验证目录保真度——即「模型仅凭目录中的紧凑签名，能构造出被目标工具接受的参数」的**首次成功率（first-try success rate）**与失败类型分布。**验收指标必须是首次成功率，不得用「最终成功率」**：叶子返回的错误足够详细，模型据其重试后总能补齐参数（实测最终成功率恒为 100%，对「有签名」与「无签名」两组都无区分力），只有首次成功率反映目录签名本身承载了多少信息。可验收阈值 = 转发组首次成功率 ≥ 90%、与逐条声明组的差值 ≤ 5pp、缺必填类失败 ≤ 5%（指标定义、消融臂证据与实测数字见「目录保真度边界」）。若该验证不达标，则先补齐目录保真（例如对复杂工具退化为可获取完整 schema 的第二跳），通过后才能继续 P1 其余部分。

## 用户场景与测试 _（必填）_

### 用户故事：已注册工具经延迟加载按需转发（优先级：P1）

作为用户，我希望可延迟的工具（MCP 工具与标注了 defer 的内置工具）默认不逐条占用请求的工具声明，而是在需要时由模型按目录点名调用，以便在不损失能力的前提下减少每轮的固定开销。

**为什么是这个优先级**：这是本功能的核心机制。它决定了工具声明形态、调用链路与结果呈现，其余故事都建立在它之上。

**独立测试**：在含 MCP 工具与内置冷工具的会话中，检查请求的工具列表不含逐条的可延迟工具、而含 `ToolInvoke` 且其说明包含目录；让模型通过 `ToolInvoke` 调用其中一个工具（分别取 MCP 叶子与内置叶子），验证结果来自正确的叶子。

**验收场景**：

1. **假设** 延迟加载生效（见「阈值门控与默认生效」），**当** agent 构建请求的工具列表时，**则** 可延迟工具不作为逐条独立工具声明，其能力改由 `ToolInvoke` 的说明承载，且 `ToolInvoke` 本身是已声明的工具
2. **假设** 目录已挂载在 `ToolInvoke` 的说明中，**当** 模型需要使用某个工具时，**则** 它调用 `ToolInvoke` 并给出目标 `namespace` 与 `tool`（以及该工具的参数；`ToolInvoke` 自身的声明形状与 `args` 承载方式见「转发工具声明契约」）
3. **假设** 模型调用了 `ToolInvoke` 并指名 `namespace` 与 `tool`，**当** host 处理该调用时，**则** 它必须把 `args` 原样交给该叶子工具执行（MCP 叶子经其服务器、内置叶子走其原有执行路径），并把执行结果作为该次调用的工具结果回给模型
4. **假设** 模型给出的 `namespace` 或 `tool` 不在当前目录（服务器未连接、工具不存在、该工具未纳入延迟加载，或该 agent 无权使用），**当** host 处理该调用时，**则** 它必须返回可诊断的失败结果（说明目标不存在/不可用并列出可用的 `namespace` 与工具名），不得执行该叶子
5. **假设** 一次转发调用完成，**当** 结果在对话中渲染时，**则** 用户必须能看到该次调用实际命中哪个叶子工具及其结果（P1 允许以通用工具块呈现并标明叶子工具名；呈现美化属后续优先级）
6. **假设** 某 MCP 服务器的服务器名等于内置工具保留的命名空间 `builtin`，**当** 该服务器被连接时，**则** 连接必须**照常建立**，但该服务器的全部工具必须被**排除出延迟加载**（等价强制逐条扁平声明，效果同逐工具 `alwaysLoad`）——它们仍以 `mcp__builtin__tool` 全名逐条声明、可正常调用，只是不进入目录。不得因此让连接失败，也不得静默改名：改叶子的 `namespace` 会让目录里的名字与该叶子的权限全名、与用户的 `.mcp.json` 配置不一致；而「不进目录」已使寻址歧义自然消失（这些工具根本不出现在目录里）。系统应给出一条可操作的日志/提示，说明该服务器因命名空间与保留名冲突而未纳入延迟加载

### 用户故事：目录内容契约（优先级：P1）

作为依赖目录来判断「有哪些能力、参数怎么填」的模型，我希望目录条目稳定、完整且可确定，以便我能在不额外探查的情况下构造出正确的调用。

**为什么是这个优先级**：目录是模型对该批工具唯一的信息来源；条目缺失或不确定会直接表现为调用失败或能力「消失」。

**独立测试**：对同一工具池连续渲染两次目录，验证文本逐字节相同；检查条目是否覆盖 `namespace`、工具名、参数签名、必填参数与枚举取值，且记法为 `<namespace>.<tool>(签名) // 描述`。

**验收场景**：

1. **假设** 目录被渲染，**当** 检查任一条目时，**则** 它必须采用统一的 `<namespace>.<tool>(签名) // 描述` 记法——命名空间与工具名都是可独立取用的字段（用于填 `ToolInvoke` 的 `namespace` / `tool`），不得合并成一个不可拆分的长名
2. **假设** 某工具的输入 schema 声明了参数，**当** 该工具的条目录入目录时，**则** 条目必须给出参数签名（如 `(file_path: string, offset?: number)`），且**必填参数必须被明确标出**（可选参数须带可选标记）
3. **假设** 某参数只接受枚举取值，**当** 该工具的条目录入目录时，**则** 条目必须列出允许的取值（取值不得省略为「枚举类型」这类无信息描述）
4. **假设** 同一工具池（同一组已连接服务器、同一批已注册工具、同一组 defer 标注）连续渲染两次，**当** 比较两次目录文本时，**则** 必须逐字节相同——目录内容只依赖工具池，不依赖时间、会话轮次或近期的调用历史
5. **假设** 某 MCP 服务器未连接或其工具列表为空，**当** 目录被渲染时，**则** 该服务器的工具不得出现在目录中（目录只描述当前真正可调用的能力）
6. **假设** 某工具的说明文本可由上下文动态生成（如按当前可用子代理、技能或工作目录变化的 `prompt()` 结果），**当** 其条目录入目录时，**则** 目录条目必须以该工具的**静态 description** 作为描述来源，动态生成的说明结果**不得**进入目录（同一个工具池的声明体积会因此从 11,511 tokens 膨胀到 28,235 tokens，2.45×）；若某工具只有动态说明而没有静态 description，**则** 它仍必须出现在目录中（不得因此不出现），其**描述留空**（记法中省略 `// 描述` 段，不得回退去取动态说明的任何部分），参数签名、必填与枚举照常渲染——确定性优先：目录文本只依赖工具池与预算配置
7. **假设** 某工具的条目录入目录，**当** 检查其描述长度时，**则** 过长的描述必须被裁剪，且裁剪必须**按 token**（与预算同口径）而不是按字符数——同一信息量的中文描述约 1 token/字、英文约 0.25 token/字，按字符裁剪会让中文被砍掉的信息量是英文的数倍

### 用户故事：转发工具声明契约（优先级：P1）

作为依赖上游校验来构造调用的使用者，我希望 `ToolInvoke` 自身的参数声明是固定不变的三项（目标命名空间、目标工具、参数），而不是随工具池逐工具展开，以便请求的工具列表在各种工具池下保持恒定、目录内容的变化不会牵动调用形状。

**为什么是这个优先级**：这是本机制**唯一随工具池变化的东西是说明文本、而不是声明结构**这一前提的落点。声明若随工具池变化，则「请求前缀稳定」不成立；`args` 的承载方式若不写死，实现时各写各的，模型行为与退化路径都会失控。

**独立测试**：在三种不同工具池（不同服务器数量、不同工具数量、不同内置 defer 标注）下构建工具列表，验证 `ToolInvoke` 的参数声明逐字段相同；分别以省略 `args`、`args: {}`、`args: null` 调用 `ToolInvoke`，验证均按无参数处理；用错误的 `args` 调用，验证错误来自叶子工具而非客户端。

**验收场景**：

1. **假设** 延迟加载生效，**当** `ToolInvoke` 被声明给上游时，**则** 其参数声明必须恒为 `namespace`（string，必填）、`tool`（string，必填）、`args`（开放对象，可选）三项，且该声明**不随工具池变化**——连接/断开服务器、工具增删、defer 标注变化都不得改变这三个字段的名字、类型与必填性（变的只有它的说明文本，即目录）
2. **假设** 上游查看 `ToolInvoke` 的声明，**当** 它构造 `args` 时，**则** `args` 必须是**开放对象**（不声明 properties、允许任意键），内层参数形状由目录签名承载，而不是在 `ToolInvoke` 的声明里逐工具展开参数结构
3. **假设** 模型调用 `ToolInvoke` 时省略 `args`、传入 `{}`、或传入 `null`，**当** 该调用被处理时，**则** 一律按「无参数」处理，不得因此报错，也不得要求模型必须提供 `args`
4. **假设** `ToolInvoke` 的 `args` 内层参数不正确，**当** 该调用被交给叶子工具时，**则** 客户端不得对 `args` 做内层参数校验——错误必须由叶子（MCP 服务器或内置工具）返回并原样回给模型（与今天逐条声明时一致，边界见「目录保真度边界」，本条不重复定义）
5. **假设** 模型调用的是 `ToolInvoke`（一个**已声明**的工具），**当** 上游返回该调用时，**则** 它必须是与逐条声明工具相同的常规调用形状——「未声明工具被返回成非 function 形状并被流式解析静默丢弃」那条边界**不适用于**本机制的调用，两者不得混为一谈：本机制真正的风险是「已声明工具的**嵌套参数**产出不正确」，不是「工具未声明」
6. **假设** P1 准入验证显示模型直接产出嵌套对象的质量不达标，**当** 需要退化时，**则** 第一顺位退化必须是把 `args` 改为 **JSON 字符串**承载（模型输出字符串、由 host 解析），不得跳过该顺位直接引入第二跳；这条退化改变的是**参数承载形态**（进得去、但换记法），与「目录保真度边界」中的**目录条目显式退化**（参数结构不进目录）是两件事，互不替代

### 用户故事：逐工具 defer 标注与 alwaysLoad 逃生口（优先级：P1）

作为用户，我希望 defer 的粒度是**逐个工具**、并能把某个工具固定为逐条声明，以便我对频繁使用、或对参数保真度敏感的工具保留与今天完全一致的调用方式，而不是被迫在整类工具上做选择。

**为什么是这个优先级**：粒度决定收益与风险的分配——按类别（例如「所有内置工具」「整台 MCP 服务器」）做 defer 必然把热工具一起卷进去，而热工具 defer 是净亏（见「设计背景」的收益差异）。逐工具标注是「只 defer 冷工具」得以成立的前提。

**独立测试**：对工具池中的工具做不同标注（默认 / defer / `alwaysLoad`），验证被标记 `alwaysLoad` 的工具始终以独立工具形式出现且不出现在目录条目中、未标注的工具按默认策略处理；对同一台 MCP 服务器只标注其中一个工具，验证只影响该工具。

**验收场景**：

1. **假设** 某工具被标注 `alwaysLoad`，**当** agent 构建请求的工具列表时，**则** 该工具必须作为逐条独立工具声明（与引入延迟加载之前一致），并且不得出现在目录条目中
2. **假设** 某工具未被标注 `alwaysLoad` 且按默认策略参与延迟加载，**当** 延迟加载生效时，**则** 其能力进入目录（由 `ToolInvoke` 承载），不作为独立工具声明
3. **假设** 某 MCP 服务器只有其中一个工具被标注 `alwaysLoad`，**当** 工具列表构建时，**则** 只有该工具被逐条声明，该服务器其余工具仍按默认策略进入目录
4. **假设** 某冷门内置工具被标注为其参与延迟加载（等价 `shouldDefer: true`），**当** 工具列表构建时，**则** 该内置工具不再逐条声明，其能力进入目录（与 MCP 工具走同一条链路）
5. **假设** 某工具所在服务器已断开连接（或该工具因 `--tools` 白名单被排除），**当** 工具列表构建时，**则** `alwaysLoad` 不得使其凭空出现（延迟加载与 `alwaysLoad` 都只描述当前真正可调用的工具）
6. **假设** 延迟加载因阈值门控未生效，**当** 工具列表构建时，**则** 所有工具照今天的方式逐条声明，`alwaysLoad` 不产生额外差异

### 用户故事：阈值门控与默认生效（优先级：P1）

作为用户，我希望延迟加载在默认情况下开启，但只在「确实有可省内容」时才介入，以便没有 MCP、也没有标注 defer 的内置工具的会话完全不受影响。

**为什么是这个优先级**：默认开让绝大多数会话自动受益；阈值止损则避免在无收益场景引入一层间接（以及一层额外的失败面）。

**独立测试**：在「可 defer 工具数为 0、3、5」三种工具池（分别由 MCP 工具、内置 defer 工具、两者混合构成）下构建工具列表，验证门控在阈值边界处的切换；在显式开启/关闭下验证覆盖阈值。

**验收场景**：

1. **假设** 用户未对延迟加载做任何显式配置，**当** 可 defer 的工具数量达到阈值（5 个）时，**则** 延迟加载生效——计数口径为**当前工具池中所有参与延迟加载的已注册工具**（MCP 工具与标注了 defer 的内置工具合计）
2. **假设** 用户未对延迟加载做任何显式配置，**当** 可 defer 的工具数量低于阈值（含 0 个）时，**则** 延迟加载不生效——工具照今天的方式逐条声明，不产生目录文本，也不额外引入 `ToolInvoke`
3. **假设** 用户显式关闭延迟加载，**当** 工具列表构建时，**则** 无论可 defer 工具数量多少都不生效（逐条声明）
4. **假设** 用户显式开启延迟加载，**当** 工具列表构建时，**则** 即使可 defer 工具数量低于阈值也必须生效（显式意愿优先于阈值默认）
5. **假设** 一次会话内工具池未变化，**当** 连续多轮构建工具列表时，**则** 门控判定结果必须保持一致（不因单轮请求或近期调用历史而反复开关）

---

### 用户故事：目录必须反映当前 agent 的工具池（优先级：P1）

作为用户，我希望目录只包含**当前这个 agent 真正有权使用**的工具，以便转发工具不会变成权限提升通道（子代理本无 `Write`，却能经 `ToolInvoke` 调 `Write`）。

**为什么是这个优先级**：这是本机制的安全边界。目录一旦是「全局工具表」而不是「当前工具池」，`ToolInvoke` 就成了绕过子代理工具限制、绕过 `--tools` 白名单的统一入口。

**独立测试**：构造一个工具池受限的 agent（如子代理或 `--tools` 白名单会话），验证目录中不出现其无权使用的工具、且经 `ToolInvoke` 指名这些工具时失败；验证主代理与子代理的目录各自反映自己的工具池。

**验收场景**：

1. **假设** 某 agent 的工具池不含某工具（子代理未派生该工具、`--tools` 未允许、或该工具因权限模式不可用），**当** 它的目录被渲染时，**则** 目录中不得出现该工具的条目——目录的输入必须是**该 agent 的工具池**，而不是全局工具表
2. **假设** 子代理本无某工具（如内置 `Write`），**当** 它调用 `ToolInvoke({ namespace: "builtin", tool: "Write", ... })` 时，**则** 必须按「工具不存在/不可用」失败，不得执行该叶子——`ToolInvoke` **不得**成为权限提升通道
3. **假设** 主代理与子代理的工具池不同（子代理是受限子集），**当** 两者各自构建目录时，**则** 两个目录必须各自反映自己的工具池（不得共用一份全量目录，也不得因缓存而复用另一方的目录）
4. **假设** 某工具出现在目录中（因为该 agent 有权使用它），**当** 它经 `ToolInvoke` 被调用时，**则** 仍必须通过该叶子原有的权限检查（「在目录中」不等于「免审批」）
5. **假设** agent 的工具池在会话中发生变化（连接/断开服务器、`--tools` 变更、派生子代理、defer 标注变化），**当** 目录重新渲染时，**则** 目录必须随之收缩或扩张，不得保留已无权使用的工具的条目
6. **假设** 存在主代理与其子代理（两者工具池不同），**当** 任一 agent 构建工具列表时，**则** 目录必须是**按该 agent 重新生成**的——工具池的内容沿用现状（含 MCP 工具池经根容器单例共享的现状），本机制**不改变**既有的可见性：某 agent 的池里有某 MCP 工具，它才进该 agent 的目录。`ToolInvoke` 随该 agent「有目录」而被声明，不得为所有 agent 声明一份由根容器一次性生成的全量目录（否则转发即成为权限提升路径）

---

### 用户故事：权限规则按叶子匹配（优先级：P1）

作为配置了细粒度规则（如 `Bash(npm test)`）的用户，我希望规则评估用的是**叶子的名字与叶子自己的参数**，而不是转发工具的入参，以便规则语义不因引入延迟加载而漂移或失效。

**为什么是这个优先级**：规则是用户表达安全意图的方式；若评估对象变成 `ToolInvoke` 的字段，那么既有的全部规则（含 `Bash(...)` 这类带参数模式）都会失效或误命中，等于静默放宽权限。

**独立测试**：对一个需要参数匹配的叶子（如 `Bash`）经 `ToolInvoke` 发起调用，验证规则匹配用的是叶子的名字与其 `args` 内的参数（而非 `namespace` / `tool` 字段）；验证既有允许/拒绝规则照旧命中。

**验收场景**：

1. **假设** 模型经 `ToolInvoke` 调用某叶子，**当** 评估权限规则时，**则** 必须用**叶子的名字**匹配——MCP 叶子 = `mcp__server__tool`，内置叶子 = 工具名本身（如 `Bash`）；不得用 `namespace` / `tool` 字段或 `ToolInvoke` 这个名字去匹配叶子规则
2. **假设** 模型调用 `ToolInvoke({ namespace: "builtin", tool: "Bash", args: { command: "npm test" } })`，**当** 评估带参数的模式（如 `Bash(npm test)`）时，**则** 必须使用**叶子自己的参数**（`args` 内该叶子的参数，即 `command`）进行匹配，不得拿 `ToolInvoke` 的入参结构去匹配
3. **假设** 已存在允许规则 `Bash(npm test)`，**当** 参数为 `npm test` 的 `Bash` 叶子经 `ToolInvoke` 被调用时，**则** 必须命中并立即执行（规则命中的语义与逐条声明时完全一致）
4. **假设** 已存在拒绝规则 `Bash(rm *)`，**当** 参数为 `rm -rf /` 的 `Bash` 叶子经 `ToolInvoke` 被调用时，**则** 必须被拒绝（拒绝规则仍优先）
5. **假设** 转发调用的 `args` 缺省或为空，**当** 评估一个依赖参数的模式规则时，**则** 必须按「该叶子无参数」的语义判定，不得因取不到叶子参数而默认放行（fail-closed）
6. **假设** 存在针对 `ToolInvoke` 本身的拒绝规则，**当** 模型尝试任意转发调用时，**则** 该调用必须被整体拒绝；反之，针对 `ToolInvoke` 的允许规则**不得**被当作任意叶子的放行依据（与「叶子审批语义不变」一致）

---

### 用户故事：叶子审批语义不变（优先级：P1）

作为用户，我希望经 `ToolInvoke` 发起的调用——无论叶子是 MCP 工具还是内置工具——在权限确认、规则持久化、拒绝判定、错误返回与结果渲染上，与今天逐条声明时逐项一致，以便延迟加载不成为绕过权限的通道。

**为什么是这个优先级**：MCP 叶子是受限工具，内置叶子也各有既有的审批流程（如 `Edit` / `Write` / `Bash`），其持久化的「不再询问」规则都以叶子为单位；这条被削弱等同于权限语义被静默改变。

**独立测试**：在无匹配规则下经 `ToolInvoke` 分别调用一个 MCP 叶子与一个需确认的内置叶子，验证确认提示均以**叶子**标识该调用；选择「不再询问」后检查持久化规则为叶子规则；在 `dontAsk` 模式下验证未预批准的叶子被拒绝。

**验收场景**：

1. **假设** 模型经 `ToolInvoke` 调用某 MCP 叶子且没有任何匹配的权限规则，**当** 权限检查发生时，**则** 系统必须提示确认，且该确认以**叶子工具全名** `mcp__server__tool` 标识这次调用（不是 `ToolInvoke` 的名字）
2. **假设** 显示了该确认提示，**当** 用户选择「是，不再询问」时，**则** 持久化的规则必须是叶子全名 `mcp__server__tool`（与逐条声明时写入的规则完全同形）
3. **假设** 已存在针对叶子全名 `mcp__server__tool` 的允许规则，**当** 该叶子经 `ToolInvoke` 被调用时，**则** 必须立即执行而不提示（持久化规则的命中不因外层是 `ToolInvoke` 而失效）
4. **假设** 权限模式为 `dontAsk` 且该叶子未被预批准，**当** 它经 `ToolInvoke` 被调用时，**则** 必须被拒绝（`ToolInvoke` 本身不构成对该叶子的放行）
5. **假设** 某**内置**叶子本身需要确认（如 `Edit` / `Write` / `Bash`），**当** 它经 `ToolInvoke` 被调用时，**则** 必须照常弹出该叶子既有的确认流程，「不再询问」写入的同样是该叶子的规则形式（如 `Bash(npm test)`），与逐条声明时完全一致
6. **假设** 叶子执行失败或返回错误，**当** 结果回到模型与用户时，**则** 错误的形状与渲染必须与逐条声明时一致（转发不得吞掉错误、改变错误文案或伪造成功）

### 用户故事：目录保真度边界（优先级：P1）

作为用户，我希望目录在参数信息上「宁可显式退化，也不静默失真」，以便复杂工具不会因为目录写法而出现难以解释的调用失败。

**为什么是这个优先级**：紧凑签名是本机制唯一的实质质量风险；退化的边界必须写死，否则复杂工具的失败会表现为「AI 用不对这个工具」这类不可归因的问题。

**独立测试**：用声明了嵌套对象、枚举、默认值与长描述的工具（MCP 工具与内置工具各一）渲染目录，检查必填与枚举是否完整保留、超复杂 schema 的行为是否显式退化。

**验收场景**：

1. **假设** 某工具的输入 schema 复杂到无法在目录条目中完整表达，**当** 其条目录入目录时，**则** 必须采用**显式退化**形式（保留 `namespace`、工具名与简短用途说明，并标明参数需以完整 schema 为准），不得以省略号或截断产生看起来完整、实际错误的签名
2. **假设** 任一工具的条目录入目录（无论是否退化），**当** 检查该条目时，**则** **必填参数（required）与枚举取值必须始终出现**——这两类信息是构造合法调用的最低要求，不因退化而丢失
3. **假设** 某工具声明为无需参数，**当** 其条目录入目录时，**则** 该条目仍必须出现并明确标为无参数（不得因无签名而不列出该工具）
4. **假设** 模型按目录签名构造的参数被叶子拒绝（保真度不足），**当** 执行结果返回时，**则** 叶子返回的错误必须作为该次调用的工具结果回给模型，使模型能据此纠正并重试；系统不得吞掉错误或伪造成功
5. **假设** 需要在真实工具上验证保真度，**当** P1 开工时，**则** 必须先完成「真实复杂 schema 下模型仅凭目录签名构造出被叶子接受参数」的**首次成功率**验证（覆盖面须包含 MCP 工具与内置工具，见本 spec「设计背景」的 P1 准入条件），该验证通过是继续 P1 其余部分的前置条件
6. **假设** 需要判定目录保真度是否达标，**当** 选择验收指标时，**则** 指标必须是**首次成功率（first-try success rate）**，不得用「最终成功率」：叶子返回的错误足够详细（缺字段、类型不符、枚举越界均带出错路径），模型据其重试后总能补齐参数，最终成功率对「有目录签名」与「无目录签名」两组都接近 100%、无区分力。可验收阈值为：转发组首次成功率 ≥ 90%、与同一批工具逐条声明组的差值 ≤ 5pp、缺必填类失败 ≤ 5%
7. **假设** 需要证明该指标确实由目录签名承载，**当** 做对照时，**则** 必须包含**消融臂**（目录条目只保留 `namespace`、工具名与描述，**去掉参数签名**）：该臂首次成功率降至 33.3%（简单工具 100%，含嵌套对象/枚举的中等与复杂工具均为 0%），失败全部落在缺必填类（20/30 次），模型据错误重试后回到 100%——即重试率与叶子调用次数才是签名信息量的度量（消融臂平均 4.07 次叶子调用/轮，带完整签名的转发组为 1.00 次/轮）；带完整签名的转发组与逐条声明组则首次成功率均为 100%、差值为 0pp、缺必填类为 0%

### 用户故事：目录外能力必须拒绝（优先级：P1）

作为用户，我希望模型只能调用目录中真实存在的能力，以便不会出现「看起来调用了某工具、实际什么都没发生」或凭空编造结果的情况。

**为什么是这个优先级**：目录是能力的唯一清单；一旦模型可以凭想象调用目录外的名字，失败将变得不可追踪，且会掩盖目录本身的缺失。

**独立测试**：让模型请求一个不在工具池中的能力（如未连接的服务器、不存在的工具名、未被该 agent 允许的工具），验证它如实说明不可用并列出可用能力，而不是发起调用或编造结果。

**验收场景**：

1. **假设** 模型请求的能力对应的 `namespace` 或 `tool` 不在**完整目录**中（完整目录 = 常驻部分加上被截断、需经搜索才能看到的条目），**当** 系统处理该请求时，**则** 必须如实说明该能力当前不可用，并列出可用的 `namespace`（以及可用的工具名或获取方式），不得编造调用，也不得伪造执行结果
2. **假设** 目标 `namespace` 存在但所点名的 `tool` 不在该命名空间的完整目录中，**当** 系统处理该请求时，**则** 不得转发这次猜测性调用（按「工具不存在」处理）
3. **假设** 模型需要的能力确实不在完整目录中，**当** 它请求该能力时，**则** 系统不得为此临时扩大工具集或加载目录外的工具——能力清单只能由工具池变化（连接/断开服务器、改配置、改 defer 标注）改变
4. **假设** 完整目录中列有某工具但该工具在调用时已不可用（服务器断开、执行环境失效），**当** 转发调用执行时，**则** 必须返回可诊断的失败结果，模型应据此报告失败，不得表现为成功

### 用户故事：目录预算与显式截断（优先级：P1）

作为连接了很多 MCP 服务器、又想让冷门内置工具也进目录的用户，我希望常驻目录的体积有明确上限、超出部分被**显式**标注并可用搜索够到，以便工具数量增长时不会把目录撑成新的固定开销，也不会让模型误以为「目录里没有 = 世界上没有」。

**为什么是这个优先级**：本机制存在的意义就是「能挂更多工具」。目录若只能整放，工具一多就退化回逐条声明（等于白做）；截断若隐式进行，则与「目录外能力必须拒绝」直接冲突——模型不知道存在被截断的工具，就不会去搜，「挂更多工具」随之落空。因此「常驻有界 + 截断显式」是硬约束，不是呈现细节。

**独立测试**：构造工具池使其完整目录明显超出常驻预算，验证常驻部分不超预算且首行标为 `PARTIAL — X of Y tools shown`；构造小工具池，验证首行标为 `COMPLETE — all Y tools shown`；构造多个 `namespace` 竞争的目录，验证每个 `namespace` 至少出现一行且分配按 `namespace` 轮转摊平；对同一工具池连续渲染两次，验证文本逐字节相同。

**验收场景**：

1. **假设** 工具池规模使完整目录超出常驻预算，**当** 目录被渲染时，**则** 常驻部分必须不超过预算，且该预算只约束**常驻部分**——超出部分不写进常驻目录，但仍属于完整目录、可由搜索获取。**预算单位是 token（按 `estimateTokens` 计价），不是字符数**；默认 **6000 tokens**，可配置
2. **假设** 需要审视默认预算值，**当** 检查默认值时，**则** 默认值必须覆盖典型部署（内置工具全量 + 3～5 台 MCP 服务器）并仍明显低于它所替换的逐条声明体积：6000 tokens 覆盖「内置工具全量 + 5 台 MCP 服务器」，且只在约 50 个以上 MCP 工具时才触发 PARTIAL；`3000 tokens` 记为「省 token 优先」的备选档（一个可选的配置值，不是与 6000 并列的默认值）
3. **假设** 完整目录的全部条目都已在预算内渲染完成，**当** 检查目录首行时，**则** 它必须为固定文案 `COMPLETE — all <Y> tools shown`（Y = 完整目录的条目总数）
4. **假设** 完整目录的全部条目渲染后超出预算，**当** 目录被渲染时，**则** 触发截断，首行固定文案为 `PARTIAL — <X> of <Y> tools shown`（X = 已常驻的条目数，Y = 完整目录的条目总数），且紧随其后必须给出一行指向 `ToolSearch` 的指引（如 `Not shown: <Y-X> tools — call ToolSearch to find them.`）；文案语言与工具声明语言一致。**预算数值不进模型可见文本**（它只用于观测，不参与模型决策），只进 host 侧日志
5. **假设** 目录处于 PARTIAL 状态，**当** 模型需要判断某能力是否存在时，**则** 它不得把「不在常驻目录中」当作「不存在」——首行与指引必须让模型知道存在未显示的工具并据此去搜索（该提示缺失即与「目录外能力必须拒绝」冲突）
6. **假设** 任意一个 `namespace` 已连接/有可调用工具，**当** 目录被渲染（无论是否截断）时，**则** 该 `namespace` 必须至少出现一行代表行，内容为 `namespace` 名 + 该 `namespace` 的工具总数（如 `github: 24 tools`），即使它的工具全部被截断——模型必须知道有哪些 `namespace` 存在
7. **假设** 多个 `namespace` 竞争同一份预算，**当** 预算被分配时，**则** 必须按 `namespace` **轮转**摊平（不得让排在前面的 `namespace` 吃光预算），且每个 `namespace` 至少保住其代表行
8. **假设** 工具池与预算配置相同（含截断状态相同），**当** 连续渲染两次目录时，**则** 两次文本必须逐字节相同——截断与预算分配结果只依赖工具池与预算配置，不依赖轮次或调用历史
9. **假设** 一个池由内置工具全量（25 个）加 60 个 MCP 工具组成，**当** 它在默认预算（6000 tokens）下渲染时，**则** 必须为 PARTIAL，且每个已连接的 `namespace` 至少有一行代表行；同一池在内置工具之外只有 5 个 MCP 工具时，**则** 必须为 COMPLETE

### 用户故事：目录内搜索（优先级：P1）

作为需要用到某个未被常驻显示的工具的用户，我希望模型能用一个只读的搜索工具在**完整目录**里翻找（包括被截断的部分），以便常驻目录保持有界的同时，全部工具仍然够得到。

**为什么是这个优先级**：搜索是「常驻有界」得以成立的对价——没有它，截断就等于丢能力。它与本机制的能力边界直接相关：只翻找已有工具池，绝不加载新工具。

**独立测试**：让模型以某工具名/参数名/描述关键词调用 `ToolSearch`，验证返回条目与常驻目录同一记法、结果有界并标注是否还有更多；验证 `ToolSearch` 不需要审批、不触发任何叶子执行；验证在延迟加载未生效时该工具不被声明。

**验收场景**：

1. **假设** 延迟加载生效，**当** 工具列表构建时，**则** `ToolSearch` 必须作为一个**只读**的已声明工具出现，接受必填 `query` 与可选 `limit` / `offset`（默认 `limit` = 10，`offset` 用于翻页），且**不需要权限审批**（与现有只读工具一致，不得为此引入审批摩擦）
2. **假设** 模型以某关键词调用 `ToolSearch`，**当** 搜索执行时，**则** 它必须在 **host 侧本地**、在**完整目录（常驻部分 + 被截断部分）**上做大小写不敏感的子串匹配，匹配范围覆盖 `namespace`、工具名、工具描述与参数名；不得联网、不得执行任何叶子工具、不得调用模型
3. **假设** 搜索命中若干条目，**当** 结果返回给模型时，**则** 结果必须是**文本**：命中项一行一条，每条与常驻目录**同一记法**（`<namespace>.<tool>(签名) // 描述`），并在文本中给出总数与是否还有更多——总数为 `X of Y` 形式（X = 本条结果返回的条数，Y = 完整目录中的匹配总数），还有更多时必须给出下一页入口（即下一步应使用的 `offset`）
4. **假设** 匹配数量超过默认上限（默认 10 条），**当** 结果返回时，**则** 只返回有界的条目数并标注还有更多——结果体积不得随匹配总数增长（不得一次把整个目录搬进上下文）
5. **假设** 搜索没有任何匹配，**当** 结果返回时，**则** 必须明确说明「无匹配」并给出可操作的回落提示（换用更短或更通用的关键词、注意搜索范围仅限当前工具池），不得返回空响应、不得编造工具名
6. **假设** 一次搜索完成，**当** 检查随后的请求内容时，**则** 搜索结果只落在**对话历史**中（作为工具结果文本），**不产生任何可调用声明、不改变 `tools[]`**——这是本设计的前提，也是与「把搜索结果回填进工具声明」这类做法（会打断请求前缀缓存）的结构性差别
7. **假设** 模型通过搜索找到了某个工具，**当** 它随后要使用该工具时，**则** 调用仍必须经 `ToolInvoke` 发出——搜索只翻找已有工具池，不改变能力清单，也不加载目录外的工具
8. **假设** 延迟加载未生效（可 defer 工具数不足阈值、可 defer 工具全部 `alwaysLoad`、或按工具选择走扁平声明），**当** 工具列表构建时，**则** `ToolSearch` 也**不得**被声明（没有目录可搜，不得留一个悬空工具）

## 关键实体

- **工具目录**：当前 agent 可调用的、参与延迟加载的工具的紧凑清单，每条采用 `<namespace>.<tool>(签名) // 描述` 记法（含必填与枚举）。
- **完整目录**：工具池中全部参与延迟加载的工具的目录（常驻部分 + 被截断、只能经搜索看到的条目）。「目录外能力必须拒绝」判据用的是完整目录，不是常驻部分。
- **常驻目录（常驻部分）**：写进 `ToolInvoke` 说明、每轮随请求发出的那部分目录，受预算上限约束。
- **目录预算（常驻上限）**：常驻目录的体积上限，**单位为 token（按 `estimateTokens` 计价，不是字符数）**，默认 **6000 tokens**（「省 token 优先」的备选档 = 3000 tokens），可配置；只约束常驻部分，不约束完整目录或搜索结果。默认值的推导：6000 tokens 覆盖典型部署（内置工具全量 + 3～5 台 MCP 服务器）且仍低于它所替换的逐条声明体积，只在约 50 个以上 MCP 工具时才触发 PARTIAL。
- **目录完整性首行（COMPLETE / PARTIAL）**：目录首行的完整性标注，文案固定。COMPLETE = `COMPLETE — all <Y> tools shown`（全部条目已常驻）；PARTIAL = `PARTIAL — <X> of <Y> tools shown`（仅显示 X 个、共 Y 个），且 PARTIAL 必须紧随一行指向 `ToolSearch` 的指引（如 `Not shown: <Y-X> tools — call ToolSearch to find them.`）。该标注是硬契约（模型据此决定是否搜索）。预算数值不出现在这段文案里（它只用于观测，不参与模型决策），只进 host 侧日志。
- **描述来源（静态 description）**：目录条目的描述一律取自工具的**静态 description**；可随上下文变化的动态说明结果（如 `prompt()` 的输出）不进目录（两者体积差 2.45×：同一批内置工具的声明体积 11,511 → 28,235 tokens）。只有动态说明而没有静态 description 的工具仍进目录，其**描述留空**（记法中省略 `// 描述` 段）——同一处不引入任何动态来源。
- **`namespace`**：转发工具的寻址字段。MCP 工具 = 其服务器名；内置工具 = 保留命名空间 `builtin`。它只是**寻址与展示**用的命名空间，不是权限标识。**`builtin` 是保留名**：MCP 服务器名与保留名相同时，连接照常建立，但该服务器的工具**全部排除出延迟加载**（强制逐条扁平声明），并给出一条可操作的日志/提示——不静默改名、不让连接失败、也不引入歧义。
- **`ToolInvoke`**：唯一一个承载目录说明的已声明**转发工具**；接受目标 `namespace`、目标 `tool` 与 `args`，由 host 交给真正的叶子工具执行。
- **`ToolInvoke` 声明**：`ToolInvoke` 对上游的参数声明，恒为 `namespace`（string，必填）、`tool`（string，必填）、`args`（开放对象，可选）三项，不随工具池变化；`args` 不声明内层 properties，内层形状由目录签名承载。
- **`args` 承载形态**：`args` 的表达方式。默认 = 开放对象；第一顺位退化为 **JSON 字符串**（模型输出字符串、host 解析），仅在 P1 准入验证显示嵌套对象产出质量不达标时启用。
- **`ToolSearch`**：与 `ToolInvoke` 同批声明的**只读**工具（无需审批），接受必填 `query` 与可选 `limit`（默认 10）/ `offset`，在 host 侧对完整目录做本地子串匹配；它翻找工具池，不改变能力清单。**返回形状契约**：结果是**文本**，命中项一行一条、每条与常驻目录同一记法（`<namespace>.<tool>(签名) // 描述`），并带上总数 `X of Y`（X = 本次返回条数，Y = 完整目录中的匹配总数）与是否还有更多（还有更多时给出下一页应使用的 `offset`）；无命中时说明「无匹配」并给可操作的回落提示。
- **搜索结果的落点**：搜索结果作为工具结果文本进入**对话历史**，**不产生任何可调用声明、不改变 `tools[]`**——这是本设计的前提（搜索之后仍必须经 `ToolInvoke` 调用），也是与「把搜索结果回填进工具声明」做法的结构性差别（后者会打断请求前缀缓存）。
- **叶子**：最终被执行的工具。MCP 叶子 = `mcp__server__tool`；内置叶子 = 工具名本身（如 `Read` / `Bash` / `Edit`）。**审批、权限规则、持久化规则、错误与结果渲染都以叶子为单位**，与是否经 `ToolInvoke` 调用无关。
- **defer 标注（逐工具）**：每个工具的延迟加载标注 = 参与延迟加载 / 不参与（`alwaysLoad`）。粒度是**单个工具**，不是「整类工具」或「整台服务器」。
- **可 defer 工具数**：当前工具池中所有参与延迟加载的已注册工具数量（MCP 工具 + 标注了 defer 的内置工具），是阈值门控的判定输入。
- **首次成功率（P1 准入指标）**：模型**第一次**经 `ToolInvoke` 调用某叶子时，参数就被该叶子接受的比例。它是目录保真度的唯一验收指标（不能用「最终成功率」：叶子错误足够详细，模型重试后总能补齐，最终成功率无区分力）。可验收阈值 = 转发组 ≥ 90%、与逐条声明组差值 ≤ 5pp、缺必填类失败 ≤ 5%。
- **显式退化**：**目录条目**不试图表达完整参数结构、而是明确标注「参数以完整 schema 为准」的形态（与 `args` **承载形态**退化是两件事，见「边界情况」）。

## 边界情况

- **工具池状态变化**：服务器在会话中途断开或被连接、内置工具的 defer 标注变化、`--tools` 变更、子代理派生时，目录必须随之更新；同一工具池下目录文本逐字节稳定，工具池变化则允许变化。
- **目录即权限边界**：目录的输入必须是**当前 agent 的工具池**（子代理、受限会话各有自己的集合），不得使用全局工具表；`ToolInvoke` 只对目录内的叶子生效，否则它就是权限提升通道。
- **不存在「既不在目录里、又能被调用」的叶子**：模型能经 `ToolInvoke` 调用的叶子集合 ≡ 该 agent 目录（含常驻与仅可搜索）所覆盖的集合。
- **保真度不足的归属**：目录写法导致的参数错误由叶子返回的错误暴露（作为工具结果回给模型），不引入客户端静默重试或参数猜测。
- **热工具不做 defer**：热工具（`Read` / `Edit` / `Write` / `Bash` / `Grep` / `Glob` 等）默认不 defer——内置工具的 defer 收益只是「完整 schema → 紧凑签名」（约 3.6×），抵不过多一层调用形态的成本；defer 一旦按类别施加，就会把这些工具一起卷进来，属于净亏。
- **首批 defer 名单待定**：默认不 defer（未标注即不 defer）；名单评估维度 = schema 体积 + 使用频率；本 spec 不锁定具体名单。
- **任何更粗的粒度都必须等价于逐工具语义**：如将来提供「整台服务器」「整类内置工具」的批量写法，其语义必须**定义为**「对其全部工具逐个标注」的等价形式，不得引入独立于逐工具标注的第二套语义。
- **`alwaysLoad` 与阈值并存**：`alwaysLoad` 的工具不计入「可 defer 工具数」，也不进入常驻目录、不占用目录预算；若某 `namespace` 的全部工具都 `alwaysLoad`，则它对阈值判定不贡献数量。
- **显式列出的工具**：通过 `--tools` 等入口显式列出的工具必须逐条扁平声明（被白名单吸收的工具不得只存在于目录中），详见 [`ui/tools-selection.md`](../ui/tools-selection.md)。
- **未声明工具的上游行为**：上游对「不在本轮工具声明中的工具名」可能以非 function 形状返回（`type:"custom"`，含名称与输入），客户端当前不解析该形状的调用；因此本机制**不得**依赖「模型能调用未声明工具」这一假设——能力必须经由已声明的 `ToolInvoke` 暴露（`ToolInvoke` 自身是已声明工具，其调用不受这条边界影响，见「转发工具声明契约」）。
- **声明恒定 vs 说明可变**：随工具池变化的是 `ToolInvoke` 的**说明文本**（目录），不是它的**参数声明**（`namespace` / `tool` / `args` 三字段的名字、类型与必填性）。工具池变化后应能观察到：说明变了、声明没变。
- **`args` 承载形态与退化顺序**：默认以开放对象承载；仅当 P1 准入验证不达标时退化为 JSON 字符串承载（host 解析），并保持目录条目、叶子审批语义与调用链路不变。退化顺序不得跳过该顺位直接引入「按需获取完整 schema」的第二跳。
- **两条退化互不替代**：**目录条目的显式退化**（超复杂 schema 的参数结构不进目录，标注以完整 schema 为准）与 **`args` 承载形态退化**（参数进得去、但换记法）解决不同问题，可同时存在，不得以其中之一代替另一个。
- **权限检查的归属**：权限判定发生在**叶子**上（MCP 叶子 = `mcp__server__tool`；内置叶子 = 工具名本身），入口是 `ToolInvoke`；规则评估使用叶子的名字与**叶子自己的参数**，禁止用 `ToolInvoke` / `ToolSearch` 的名字或它的 `namespace` / `tool` 字段参与匹配（`namespace` 只是寻址用的命名空间）；针对 `ToolInvoke` 本身的拒绝规则会整体阻止转发，其允许规则不构成对叶子的放行。
- **目录规模**：单条目录必须紧凑（工具名 + 参数摘要），过长的工具描述必须被裁剪，且裁剪**按 token**（与预算同口径）而不是按字符数；常驻目录整体体积必须受预算约束（默认 6000 tokens，以 `estimateTokens` 计价），不得随工具数与描述长度无界增长。
- **截断必须显式**：任何一次截断都必须在目录首行以固定文案 `PARTIAL — <X> of <Y> tools shown` 标注并给出一行指向 `ToolSearch` 的指引；未截断时为 `COMPLETE — all <Y> tools shown`。文案里不带预算数值（预算只进 host 侧日志，不参与模型决策）。不得静默丢弃条目——静默截断会使模型把「未常驻」当作「不存在」，直接与「目录外能力必须拒绝」冲突（该故事以**完整目录**为判据，而非常驻目录）。
- **每个 `namespace` 至少一行**：每个已连接的 `namespace` 必须至少保留一行代表行（`namespace` 名 + 该 `namespace` 的工具总数，如 `github: 24 tools`），即使其工具全部被截断；预算按 `namespace` 轮转摊平，避免靠前的 `namespace` 独占。截断的触发条件 = 完整目录的全部条目渲染后超出预算。
- **搜索返回形状**：结果必须是文本、逐行与常驻目录同记法，并带总数 `X of Y` 与下一页入口（`offset`）；无命中时必须给可操作的回落提示；结果有界（默认 10 条）。
- **描述来源固定为静态 description**：动态说明结果（如 `prompt()` 的输出）不进目录；只有动态说明的工具仍进目录，但**描述留空**（不取动态说明的任何部分），不得因此从目录中消失。描述来源必须固定——目录文本只依赖工具池与预算配置，来源若随上下文漂移，逐字节稳定性与请求前缀缓存（见 [`core/prompt-cache-control.md`](./prompt-cache-control.md)）会同时失效。
- **保留名 `builtin` 冲突 = 退化，不是失败**：MCP 服务器名等于保留命名空间 `builtin` 时，连接**照常建立**、工具**照常可调用**（以 `mcp__builtin__tool` 全名逐条声明），只把该服务器的工具**全部排除出延迟加载**（等价逐工具 `alwaysLoad` 的强制版），并给出一条可操作的日志/提示。三条理由：①不静默改名——叶子的 `namespace` 一变，目录里的名字就与该叶子的权限全名、与用户的 `.mcp.json` 配置不一致；②不引入新失败模式——今天这份配置是能正常工作的，硬失败会把「能用」变成「整个 server 不可用」；③歧义自然消失——这些工具根本不进目录，寻址歧义不存在。该退化只影响延迟加载的纳入范围，不改变叶子的名字、权限归属与调用路径。
- **目录必须随 agent 重新生成**：目录的输入始终是**当前 agent 的工具池**，必须按 agent 重新生成（不得由根容器一次性生成后复用、不得跨 agent 缓存）。工具池如何构成沿用现状（含 MCP 工具池经根容器单例共享的现状）——本机制**不改变既有可见性**，只把「池里有工具」映射为「目录里有条目」。若为所有 agent 共用一份全量目录，`ToolInvoke` 立即成为权限提升路径。
- **`--tools` 对 MCP 工具的已知偏差（正交缺口，不在本 spec 范围内）**：今天 `--tools` 只约束**内置工具**的注册，不过滤 MCP 工具；而 [`ui/tools-selection.md`](../ui/tools-selection.md) 要求白名单同时限制 MCP 工具。本机制不改变这一现状——目录来自**当前 agent 的有效工具池**，该池今天就是「`--tools` 只管内置工具注册」的结果，因此转发既不引入新行为，也不构成对白名单承诺的兑现。该偏差的修复属独立 issue，不因此扩大本机制的范围。
- **搜索无匹配**：必须显式说明「无匹配」并给可操作的回落提示（换更短/更通用的关键词、注意搜索范围仅限当前工具池），不得返回空响应或编造工具名；搜索结果必须有界（默认 10 条）。
- **搜索不改变能力清单**：搜索只在已有工具池内翻找，既不加载目录外的工具，也不改变可调用集合（不产生可调用声明、不改 `tools[]`）；找到工具后的调用仍走 `ToolInvoke`。
- **搜索工具的声明条件**：与延迟加载同进同退——延迟加载未生效时不得声明 `ToolSearch`（无目录可搜）。

## 假设

- 叶子工具的参数校验由其自身负责（MCP 工具由 MCP 服务器，内置工具由其既有校验路径）；客户端不因延迟加载而新增或减少参数校验能力。
- 工具池在一次会话内的变化来自连接/断开 MCP 服务器、修改配置、改 defer 标注或派生子代理，而非模型行为。
- 内置工具是否参与延迟加载由逐个标注决定（默认不 defer）；本 spec 不锁定首批名单。
- 延迟加载不改变叶子侧的协议与执行行为，只改变工具「如何被声明给模型」以及调用「如何被寻址」。
- 每个 agent 的工具池如何构成沿用现状（含 MCP 工具池经根容器单例共享的现状）；本机制只负责把该池映射为目录，不重新定义可见性，也不把某 agent 的池扩大到另一个 agent。
- 目录条目的描述取自工具的静态 description；工具说明的动态生成（`prompt()`）不参与目录，其在本机制内的用途与边界见 [`core/prompt-engineering.md`](./prompt-engineering.md)。
