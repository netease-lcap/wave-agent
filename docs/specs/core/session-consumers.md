# 功能规格说明：会话消费者（实时）

**创建日期**：2026-11-23

> 有些能力只在「有人能把结果渲染出来」时才有意义：交付文件（卡片）、推送通知、面板类产物。判断依据不能是「这个会话是从哪个入口建的」——同一个 daemon 会话可能先被终端建、再被手机接管，也可能反过来被手机建、再被桌面端打开。
>
> **对齐 Claude Code 的做法**（`@anthropic-ai/claude-code@2.1.325`）：它的 `SendUserFile.isEnabled()` 最后一道是 `(replBridgeActive() || remoteEnv…) && !briefMode`。所谓 `replBridgeActive()` 是 remote-control 桥的**实时连接状态**（桥 `connected|ready` 置真、`failed` 置假），`remoteEnv` 是 `CLAUDE_CODE_REMOTE*` / 桌面端入口那类静态兜底。**入口不参与这个判断**。wave 照这个模型做，但把结论收成一份可复用的公开信号。

## 术语

- **消费者（consumer）**：此刻能接收并渲染这条会话输出的一方。
- **基础消费者**：由会话创建入口静态推导出的那一部分，进程活多久就存在多久（桌面端子进程、插件端、交互 CLI）。
- **附加消费者**：运行期挂上来、也会走掉的，本期只有 `remote-page`（远控页）。

## 用户场景与测试 _（必填）_

### 用户故事：手机接管终端会话后，模型立刻能交付文件（优先级：P1）

作为用户，我在终端里开了一条会话，后来用手机打开远控页接着聊。我希望接下来模型交付的文件在手机上显示成卡片——也就是说，**接管之后**模型才拿到交付能力。

**为什么是这个优先级**：这是"实时"两个字的全部理由。静态按入口判断会在这里判错：会话的入口是 `cli`，但此刻看着它的是手机。

**独立测试**：起一条 `entrypoint: "cli"` 的会话，断言初始消费者只有 `terminal`、工具清单里没有 `SendUserFile`；再模拟远控页对该会话发一次请求，断言消费者变成 `["terminal", "remote-page"]` 且工具清单里出现 `SendUserFile`。

**验收场景**：

1. **假设** 一条会话的入口是 `cli`、没有远控页跟随，**当** 组装本轮工具清单时，**则** 不声明 `SendUserFile`（终端渲不出卡片，声明它只会让模型做一次无效调用）。
2. **假设** 远控页正跟随这条会话，**当** 远控页对该会话发出任意一个带 `sessionId` 的页请求，**则** 该会话的消费者追加 `remote-page`；**且从下一次组装工具清单起**声明 `SendUserFile`（同一轮内已发出的请求不回溯）。
3. **假设** 消费者里出现了 `remote-page`，**当** 模型调用 `SendUserFile` 时，**则** 工具照常执行、结果照常落进消息（卡片渲染在远控页）——信号只决定"能不能调"，不参与执行。
4. **假设** 远控页发了一个不带 `sessionId` 的 `initialize`（新建会话，或带 `restoreSessionId` 恢复一条），**当** 宿主把回执里的 `sessionId` 交回去，**则** 该会话立刻带 `remote-page`——它是这个页建出来的，从出生起就有人在看。少了这一条，手机新建的会话在页发出下一个请求之前既没有基础消费者也没有附加消费者，第一轮就交付不了。

### 用户故事：链路断开后，工具从模型视野消失（优先级：P1）

作为用户，我在手机上聊完就关掉了会话（或者链路断了、被策略关闭了）。我希望模型不再往一条没人看的会话里"交付文件"，因为它以为有人会点。

**为什么是这个优先级**：信号只增不减会退化成"永远可调"，等于没做。

**为什么"走掉"只能按链路判**：中继没有"某个订阅者退订"的上行帧——`peer_disconnected` 是发给**订阅端**的（随后一个 4001 把它放掉），不是发给持有会话的这一侧；手机静默关掉浏览器更是一个字都不会传来（见边界情况）。CC 也是同一条口径：它的 `replBridgeActive()` 读的是**桥的连接状态**，不是一份观众名册。所以"走掉"的唯一证据是**链路本身不在 `online` 了**；给它配一个"多久没请求算走了"的超时就是猜，本规格明确不做。

**独立测试**：在上一故事的会话上把 relay 状态从 `online` 翻到 `connecting`（或 `off`），断言消费者回到 `["terminal"]`，工具清单里 `SendUserFile` 消失。

**验收场景**：

1. **假设** 某条会话有 `remote-page` 消费者，**当** relay 连接离开 `online`（掉线重试、被拒绝、用户关掉远程控制），**则** 该机器上所有会话的 `remote-page` 消费者被清空——中继帧不带 page 标识，只能按机器全清。
2. **假设** 链路重新回到 `online`，**当** 还没有任何页请求到达，**则** 消费者仍是 `["terminal"]`：重新上线不等于有人看着，页要自己开口（它重连后走 `getMessages` / `getSessionInfo` 的补齐路径，届时自动挂回）。
3. **假设** 手机退出后模型再也没调用过交付工具，**当** 用户下次打开远控页，**则** 历史消息里已有的交付卡片照常渲染——卡片数据在消息里，不依赖这个信号。

### 用户故事：本机宿主不需要任何实时判定（优先级：P1）

作为桌面端 / 插件端用户，我的会话由一个跟会话同寿命的子进程驱动，不存在"宿主走了会话还在"的情况。这条规格不该给我引入新的状态机。

**独立测试**：以 `entrypoint: "desktop"` 创建会话，断言消费者恒为 `["desktop"]`，全程不调用任何附加消费者接口，工具清单里 `SendUserFile` 恒在。

**验收场景**：

1. **假设** 会话入口是 `desktop`，**当** 读取消费者时，**则** 返回 `["desktop"]`，与 relay 是否在线无关。
2. **假设** 会话入口是 `vscode` 或 `jetbrains`，**当** 读取消费者时，**则** 返回 `["vscode"]`（沿用面板那条"两端同一份 webview"的合并口径）。
3. **假设** 会话入口是 `desktop` 且远控页也挂上来，**当** 读取消费者时，**则** 返回 `["desktop", "remote-page"]`——基础与附加是并集，不互相覆盖。

### 用户故事：没有界面的会话不声明交付能力（优先级：P2）

作为在 CI 里用 `wave -p` 的用户，我不希望模型调用一个结果只存在于 JSON 流里的交付工具。

**独立测试**：以 `entrypoint: "cli"` + 无渲染面（`-p`）创建会话，断言消费者为 `[]`、工具清单里没有 `SendUserFile`。

**验收场景**：

1. **假设** 会话声明了 `renderSurfaces: []`（`-p` 的形态），**当** 读取消费者时，**则** 返回 `[]`。
2. **假设** 消费者为空，**当** 模型想做交付时，**则** 它在看不到这个工具的情况下用具描述里要求的替代方式（正文里写路径）——不引入"工具存在但静默失败"的路径。

### 用户故事：后续能力复用同一个信号（优先级：P2）

作为后续做推送、附件预览、面板能力判断的人，我希望读的是同一份"此刻谁在看"的事实，而不是各自再判一遍入口。

**独立测试**：新增的读取点只依赖 `sessionConsumers()`，不读 `Entrypoint`。

**验收场景**：

1. **假设** 某处要判断"要不要把结果推给手机"，**当** 它读取消费者时，**则** 只看 `remote-page` 在不在，不需要自己连 relay。
2. **假设** 将来新增一种附加消费者（例如某个客户端通道），**当** 它接入时，**则** 只需上报附加项，基础推导与读者都不用改。

## 非功能需求

- **一份实现**：消费者的合成（入口推导 ∪ 附加）只有一处实现，"终端算不算能渲染"这个判断也只有一个谓词（`能渲染 = 消费者里存在非 terminal 项`），工具注册、推送、面板都调它。
- **入口推导复用既有口径**：`cli` 交互式 → `terminal`；`-p`（声明了空渲染面）→ `[]`；`desktop` → `desktop`；`vscode` / `jetbrains` → `vscode`。这套映射与面板的 `renderSurfaces` 同源，不另造一份 entrypoint 表。
- **同进程，不跨进程**：relay 向来建在**持有会话的那个进程**里（daemon / 每个 GUI 宿主的 `--stdio` 子进程 / 交互 CLI），所以附加消费者的上报是进程内调用，不新增 RPC 方法、不新增跨进程状态同步。
- **注册常驻、声明过滤**：`SendUserFile` 始终在工具注册表里，只有"声明给模型的清单"按消费者过滤。理由：历史转录里可能已有这个工具的调用（会话恢复、重放、续跑），注册表里拿掉会让那些调用变成 `Tool not found`。
- **读是同步的**：消费者状态缓存在内存里，组装工具清单时同步读取；不得在组装路径上 await 任何网络或文件 IO。
- **变化要有通知**：消费者变化时向宿主发一次变更回调，供 UI 与日志使用；不轮询。
- **不猜**：附加消费者只由持有 relay 的那一层上报，不从 `WAVE_REMOTE*` 环境变量、连接 id 或 URI 反推。

## 边界情况

- **同一个 page 看着两条会话？** 支持：附加消费者按会话记账，两条会话各自持有 `remote-page`。
- **两个 page 看着不同的两条会话，其中一个关掉了？** 什么也不会发生：中继对订阅者的离开没有上行帧，两条会话都保持 `remote-page`，直到链路整体离开 `online` 才一起清空。代价是最多多交付一次，而卡片留在历史里，下次打开仍能看到。
- **手机浏览器直接关掉、链路还活着？** 保持"在线"（与上一条同一个原因）。代价同上，比"会话还在被看着却交付不了"轻。
- **远控页只是打开会话列表、没进会话？** 不算跟随：只有带 `sessionId` 的页请求才算。
- **page 跟着一条 `-p` 起来的会话？** 消费者从 `[]` 变成 `["remote-page"]`，工具出现——这正是实时信号要覆盖的形态。
- **会话在终端里，但终端已被 `ctrl+z` 挂起 / 窗口不可见？** `terminal` 消费者照常存在，本规格不做可见性判断（终端渲不出卡片，本来就不够格）。
- **子代理会话？** 子代理没有独立入口，沿用父会话的消费者；不为它单独记账。
- **消息层渲染交付卡片需要这个信号吗？** 不需要。卡片数据在 `ToolBlock.metadata` 里，老消息、离线、消费者为空时都照常渲染；信号只管"模型还能不能调"。
