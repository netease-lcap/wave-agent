# 功能规格说明：支持 AskUserQuestion 工具

**创建日期**：2026-01-19

## 用户场景与测试 _（必填）_

### 用户故事：澄清模糊指令（优先级：P1）

作为 AI agent，当我收到用户的模糊指令时，我希望使用结构化的多选界面提出澄清问题，以便我可以在正确理解用户意图的情况下继续。

**为什么是这个优先级**：这是工具的核心价值。它防止 agent 做出错误假设并提高交互质量。

**独立测试**：可以通过给 agent 一个模糊任务（如"重构这个函数"）并验证它使用 `AskUserQuestion` 工具询问期望的重构模式而不是猜测来测试。

**验收场景**：

1. **假设** agent 正在处理任务，**当**遇到模糊性时，**则**它必须调用 `AskUserQuestion` 工具并提供相关选项。
2. **假设**用户看到问题，**当**用户选择选项时，**则** agent 必须收到答案并基于该选择继续任务。

---

### 用户故事：在实现方案之间选择（优先级：P2）

作为 AI agent，当有多种有效方式实现功能时，我希望向用户展示这些选项，以便他们可以决定哪种方案最适合其需求。

**为什么是这个优先级**：使用户能够在不必自己编写代码的情况下做出架构或设计决策。

**独立测试**：可以通过要求 agent "添加认证" 并验证它询问是使用 JWT、OAuth2 还是基于 Session 的认证来测试。

**验收场景**：

1. **假设** agent 处于规划或实施阶段，**当**识别出多种方案时，**则**它应该使用 `AskUserQuestion` 让用户选择。
2. **假设**选项中包含推荐项，**则** agent 应该在标签中标记为 "(Recommended)"。

---

### 用户故事：在计划模式中收集需求（优先级：P2）

作为计划模式中的 AI agent，我希望在最终确定计划之前向用户询问缺失的需求，确保计划准确并获得批准。

**为什么是这个优先级**：确保规划阶段是交互式的并产生高质量计划。

**独立测试**：可以通过带着模糊请求进入计划模式并验证 agent 在调用 `ExitPlanMode` 之前提出问题来测试。

**验收场景**：

1. **假设** agent 处于计划模式，**当**需求缺失时，**则**它必须使用 `AskUserQuestion` 来收集。
2. **假设** agent 准备最终确定计划，**则**它不得将 `AskUserQuestion` 用于计划批准（必须使用 `ExitPlanMode` 代替）。

### 用户故事：选项组键盘焦点圈（优先级：P1）

作为用户，当回答 agent 的提问时，我希望选项组（单选/多选）只提供一个 Tab stop，选项之间用方向键移动、空格键选中，以便键盘操作无需在全部选项间逐个 Tab。

**为什么是这个优先级**：单选是 radio group 语义，ARIA APG 的标准做法就是 roving tabindex（组内仅当前项一个 Tab stop，方向键移动）；当前实现中每个选项 label 都是 `tabIndex={0}`（4 个选项 + 「其他」= 5 个 Tab stop），加上输入框/导航/提交按钮后一页 Tab 循环约 10 步。改后一页选项区只剩 1 个 Tab stop，且配合已有的 Enter 提交快捷键可做到全程不碰 Tab：方向键选 → 空格确认 → Enter 提交。

**独立测试**：触发 AskUserQuestion 弹窗，用 Tab 进入选项组（一步）、方向键遍历全部选项（含「其他」）、空格选中、Enter 提交；验证焦点离开选项组再回来时回到上次位置，方向键移动不改变已选答案。

**验收场景**：

1. **假设** 选项组渲染（单选或多选），**当** Tab 焦点进入选项组时，**则** 组内只有一个 Tab stop（当前项 `tabIndex={0}`，其余选项 `tabIndex={-1}`），不再逐项经过每个选项。
2. **假设** 焦点在选项组内，**当** 用户按 ↑/↓（及 ←/→）时，**则** 焦点在当前组内选项之间移动，移动不改变已选答案（选中/取消只来自空格或点击）。
3. **假设** 焦点在某个选项上，**当** 用户按空格时，**则** 单选=替换为该选项；多选=切换该选项的勾选状态。
4. **假设** 「其他」作为组内选项之一，**当** 方向键移动到「其他」并空格选中时，**则** 输入框自动聚焦可直接输入（保留现有自动聚焦行为）；未选中时提示「输入自定义回答...」照常显示。
5. **假设** 焦点在选项组内，**当** 用户按 Tab 时，**则** 焦点离开选项组直接到达下一可聚焦元素（textarea / 上一题 / 下一题 / 提交按钮），不经过其余选项。
6. **假设** 焦点曾离开选项组，**当** 再次 Tab 回到选项组时，**则** 焦点回到上次离开时的选项（roving 记录最后位置）。
7. **假设** 焦点在选项组或自定义输入框上，**当** 用户按 Enter 时，**则** 保留现有快捷键行为（非最后一题进入下一题，最后一题提交）。
8. **假设** 用户回答完当前问题后切换到下一题（点击或键盘触发「下一个」/「下一题」），**当** 题目切换完成时，**则** 焦点落在新题目选项组的当前 Tab stop 上（roving 记录位置或默认选项），焦点不会因「下一个」按钮变为禁用而丢失到弹窗外。

### 用户故事：多问题向导式逐步提交（优先级：P1）

作为用户，当 agent 在一次 AskUserQuestion 中提出多个问题时，我希望弹窗以向导形式引导：第一题只有「下一个」、中间题有「上一个/下一个」可回退修改、最后一题才出现「提交回答」，以便我清楚还剩多少问题要回答，不会因未答完而困惑为什么无法提交。

**为什么是这个优先级**：当前实现底部始终显示「提交回答」按钮（全部问题未答完时禁用），用户答完当前题后容易误以为可以直接提交，点击无反应才意识到还有题未答，交互混乱。向导式按钮把「逐题答完才能提交」的路径显式化。

**独立测试**：触发包含 3 个问题的 AskUserQuestion，逐题观察底部按钮组合与启用状态；「提交回答」只在最后一题出现，点击后一次性返回全部答案。

**验收场景**：

1. **假设** 弹窗包含多个问题，**当** 展示第一题时，**则** 底部导航只显示「下一个」，不显示「提交回答」；第一题作答前「下一个」禁用。
2. **假设** 用户作答第一题，**当** 「下一个」启用后点击时，**则** 进入第二题，第一题答案保留。
3. **假设** 弹窗包含至少 3 题，**当** 展示中间题（非第一题、非最后一题）时，**则** 底部导航同时显示「上一个」与「下一个」，不显示「提交回答」；本题未作答时「下一个」禁用。
4. **假设** 用户在中间题，**当** 点击「上一个」时，**则** 回到前序问题且其已填答案保留，可自由修改（「上一个」始终可用，不要求当前题已作答）。
5. **假设** 用户走到最后一题，**当** 查看底部导航时，**则** 显示「上一个」与「提交回答」，不再显示「下一个」。
6. **假设** 用户回到前序问题修改后再次「下一个」走到最后一题，**当** 全部问题均有有效答案时，**则** 「提交回答」可用，点击后一次性提交所有问题的答案。
7. **假设** 弹窗只有一个问题，**当** 查看底部导航时，**则** 直接显示「提交回答」（与现状一致，无「下一个」）。
8. **假设** 用户按 Enter 快捷键，**当** 处于非最后一题时，**则** 进入下一题；处于最后一题时提交（保留现有快捷键行为）。

### 边界情况

- **用户提供自定义输入**："Other" 选项的自定义输入框在用户**选中 "Other" 后才出现**；未选中时不显示输入框。
  - 用户选中 "Other" 后，输入框出现，输入的文本作为该问题的答案返回。
  - 用户**选中 "Other"（键盘空格或鼠标点击）后，输入框自动聚焦**，可直接开始输入；切换题目时，若新题目此前已选中 "Other"，不抢占输入框焦点（焦点落回选项组的当前 Tab stop，用户需要时再 Tab/方向键进入输入框）。
  - **未选中 "Other" 时**，选项下方以灰色显示「输入自定义回答...」提示（复用普通选项的 description 样式），说明该选项可输入自定义内容；选中后提示由输入框替代。
  - 用户取消选择 "Other"（单选改选其他选项 / 多选取消勾选）时，输入框隐藏，但**已输入的内容保留**；再次选中 "Other" 时内容恢复，不丢失。
  - 选中 "Other" 但未输入任何内容时，不算有效答案，提交/下一步仍被禁用。
  - 多选模式行为相同：勾选 "Other" 显示输入框，取消勾选隐藏输入框（内容保留）。
- **多个问题**：一次最多 4 个问题。弹窗一次只显示一个问题，按向导式逐步导航（第一题「下一个」→ 中间题「上一个/下一个」→ 最后一题「上一个/提交回答」），顶部显示当前进度（如 "1 / 3"）；所有问题都有有效答案后「提交回答」才可用，一次性提交全部答案。
- **键盘导航不改变答案**：Tab 聚焦弹窗内任意元素（包括自定义输入框）只应移动焦点，不得改变已选答案；选中/取消选项必须来自明确的用户操作（点击或空格键）。
- **多选答案**：多个选中选项如何返回？应该以逗号分隔的字符串或类似的结构化格式返回。
- **工具拒绝**：如果用户拒绝回答怎么办？agent 应该被通知并决定是使用假设继续还是再次询问。
- **选项与内容的关系**：选项列表固定在确认 UI 底部始终可见，↑↓ 只用于选项导航，与上方内容区的滚动完全无关（内容区超高时的 PgUp/PgDn 滚动见 `confirm-ui.md`「确认详情超高时滚动」）。
- **选项组 roving 与选中状态**：方向键移动焦点不改变已选答案；「其他」参与组内移动，选中后输入框自动聚焦；焦点离开选项组后再回来回到上次位置。

## 假设

- 渲染这些问题的 UI 组件已存在或将作为 `code` 包的一部分实现。
- `AskUserQuestion` 工具将被视为需要用户交互的"受限"工具，类似于 `Bash` 或 `Write`。
- "Other" 选项由 UI 自动处理，agent 不需要在工具的输入模式中明确定义。
