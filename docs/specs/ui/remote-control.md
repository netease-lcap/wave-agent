# 功能规格说明：远程控制（手机控制面）

**创建日期**：2026-10-13

## 概述

远程控制把「本机正在跑的会话」开放给手机：手机只当**控制面**——看会话列表与消息流、审批等待确认的工具调用、派发消息与中断；agent 与工具执行始终留在用户自己的电脑上，手机上不跑任何代码。手机不做原生 App，客户端是一张网页（可「添加到主屏幕」）。

连接方向的根因是**手机连不到电脑**（电脑没有公网地址、也不做端口转发）⇒ 由**持有会话的那个 wave 进程主动向中继服务拨出一条出站 WebSocket**，订阅自己这台机器的通道；手机经中继说话。因此通道是**设备级**（一条长连承载该进程上的全部会话，`sessionId` 只作信封字段），不是每会话一条。通道键（hostId）**由中继分配**：本机首次启用时向中继登记（`POST /api/relay/hosts`），把响应里的 `host.id` 与长期令牌一起持久化到 `~/.wave/remote-control.json`，此后每次启动只读本地、不再登记（该接口不幂等）。它不取主机名、也不由本机自铸：中继的通道归属以登记行为唯一权威，库里没有行的 id 会让两端握手直接 4003。

**谁在服务、谁在开关**：服务能力只由**持有会话的进程**提供——常驻的 `wave --daemon`、某个 GUI 宿主（desktop / VS Code / JetBrains）自己拉起的 `wave --stdio` 子进程，或**用户正坐在前面的那个交互式 CLI（TUI）进程本身**（前台会话只活在这个进程里，没有任何别的进程能替它服务）。所以同一个用户可能同时有多条出站连接，手机看到的是**被指着的那一个进程**的会话集合；这一点是刻意的，不跨进程汇聚。该能力默认关闭，由设置键 `enableRemoteControl` 控制（见「开关语义」故事）。开启是**两层**的：开关说「本机**可以**服务」，`wave remote-control on` / GUI 弹窗里的开启动作才是**真的拨号**。开关只在该进程启动时读一次，改设置后要重启进程（`wave daemon restart`）才生效。

**跨仓库分工**：中继服务（会话中继 + 设备登记 + Web Push）不在本仓库，实现在内部 GitLab 的 codechat 仓库（跟踪单 `vusion/codechat#40`）。本规格只约定本机侧与它交互的那一小块契约，**不复制中继自己的 schema**：

- **登记**（一次性 REST）：`POST /api/relay/hosts`（企业成员令牌）→ `host.id` / `hostToken`（`rch_` 前缀，长期、可吊销）。**没有配对码**：页面地址由本机按自己的通道键拼出来（见「没有配对码」那条边界情况）。
- **订阅**：`wss://<中继>/v1/hosts/ws/{hostId}/subscribe`。
- **控制帧**：本机上行 `{type:"auth"|"ping"|"host_state"}`，中继下行 `{type:"auth_ok"|"auth_error"|"peer_disconnected"|"resync_required"|"pong"}`。判定是结构性的——「合法 JSON 对象 + 有顶层 `type` + **不带 `jsonrpc`**」；控制帧永不被转发。
- **业务信封**：其余一切（含带 `jsonrpc` 的 JSON-RPC 信封）逐字透传，中继不解析、不落内容。

**覆盖范围**：这是**跨宿主**规格。CLI 侧有两个入口：`wave remote-control [on|off|status] [name]` 子命令组（作用于 daemon 上常驻的会话，可脚本化、可无人值守），以及交互式 TUI 内的 `/remote-control` 斜杠命令（作用于**你手上这条前台会话**，见「用户故事：前台 CLI 会话也能被手机接管」）；desktop / VS Code / JetBrains 侧的入口是聊天输入框里的 `/remote-control` 弹窗（三端共用同一份 webview UI，各自路由到自己的子进程）；Web 页是本仓库产出的**第五种宿主**（同一份 webview 产物 + 浏览器 shim）。

## 用户场景与测试 _（必填）_

### 用户故事：在本机开启远程控制并连接手机（优先级：P0）

作为在电脑前工作的用户，我希望一条命令就把本机连上中继并拿到一个可扫的页面地址，以便用手机接管这台机器上的会话。

**为什么是这个优先级**：这是手机唯一的入场券——没有地址，手机不知道去哪台机器；没有登录态，它也不知道自己凭什么说话（页面复用企业端登录态，没有第二套账号）。开关打开但没人拨号时，本机什么也不做（开关只是「可以服务」，不是「已在服务」）。

**独立测试**：在已登录且开关打开的本机运行 `wave remote-control on`，能打印页面地址与可扫的二维码；再次运行得到同一个地址（幂等）；把开关关掉后运行同一命令，得到退出码 1 与指向设置键的提示。

**验收场景**：

1. **假设** 开关已打开且本机已登录、daemon 在运行，**当** 用户运行 `wave remote-control on` 时，**则** 本机向中继发起出站连接，并打印**页面地址与可扫的二维码**，退出码 0。页面地址是**本机按自己的通道键拼出来的**（`<服务端地址>/remote/?host=<hostId>`），不依赖中继在响应里带回什么——通道键是这台机器自己的身份，地址也就该由它自己拼。
2. **假设** daemon 尚未运行，**当** 用户运行 `wave remote-control on` 时，**则** 命令按需拉起 daemon 再执行（语义与 `wave daemon` 子命令组一致），而不是报「连不上」。
3. **假设** 本机已经处于已连接状态，**当** 用户再次运行 `wave remote-control on` 时，**则** 命令是幂等的——不建立第二条连接、也不重新登记（登记不幂等，重复调用会在中继上多出一行），而是重新读回本机自己的通道键并打印同一个页面地址。
4. **假设** 连接因未登录、中继地址无法解析、登记失败（超时 / 无企业上下文 / 非已激活成员）或被中继拒绝凭证（4003）而失败，**当** 用户运行 `on` 时，**则** 命令打印失败原因、以及指向 `enableRemoteControl` 的修复提示（含「已运行的 daemon 要重启才换设置」），退出码 1；其中「不是企业成员」与「不是已激活成员」要给出不同措辞的下一步动作。登记超时**就是失败**——拿不到通道键就没有可连的东西，不再有「连接已建立、只是码没拿到」这种半成功。
5. **假设** 用户运行 `wave remote-control on my-laptop`，**当** 手机侧列出这台账户下的机器时，**则** `my-laptop` 作为本机的标签随**登记**请求（`POST /api/relay/hosts`）上报并存进中继的机器行里，用于区分同账户下的多台电脑。

### 用户故事：关闭与查询远程控制（优先级：P0）

作为用户，我希望随时能查当前状态、也能一句话收回手机的访问权，以便确认手机还能不能看，并且不必相信「我记得我开过」。

**为什么是这个优先级**：开得起来就必须收得回去——「关」是安全底线，而「查」是用户判断自己是否暴露在外的唯一手段。「关」的实现口径是不撒谎也不制造副作用：没有东西可关时不拉起 daemon、也不假装关过。

**独立测试**：对已连接的机器运行 `wave remote-control status` 能看到连接状态与地址，运行 `off` 后状态变为未开启；在 daemon 未运行时运行 `off`/`status` 不拉起 daemon 且退出码 0；开关关闭时的读状态失败要给出退出码 1 与修复提示。

**验收场景**：

1. **假设** 本机已连接，**当** 用户运行 `wave remote-control off` 时，**则** 本机断开中继连接、打印「远程控制已断开」，退出码 0。
2. **假设** daemon 根本没有运行，**当** 用户运行 `off` 时，**则** 命令打印「远程控制未开启（wave daemon 未运行）」并以退出码 0 结束，且**不**借此拉起 daemon（与 `wave daemon stop` 同一口径）。
3. **假设** 本机进程里压根没有中继（开关是关的），**当** 用户运行 `off` 时，**则** 命令按「用户要的终态已经达成」处理：打印已关闭并附上原因、把开关提示写到 stderr，退出码 0。
4. **假设** 本机已连接，**当** 用户运行 `wave remote-control status` 时，**则** 命令打印当前状态（`off` / `connecting` / `online` / `error`），有页面地址时一并打印。
5. **假设** daemon 未运行，**当** 用户运行 `status` 时，**则** 命令打印「状态：未开启（wave daemon 未运行）」，退出码 0。
6. **假设** 状态读不出来（例如 daemon 是更旧的构建、不认识这个 RPC），**当** 用户运行 `status` 时，**则** 命令打印失败原因与开关提示、退出码 1——「读不到」不等于「已关闭」。
7. **假设** 用户不带任何参数运行 `wave remote-control`，**当** 命令解析参数时，**则** 它等价于 `status`；给出未知 action 时打印用法并以退出码 1 结束，不落到交互式 TUI。

### 用户故事：GUI 三端的 `/remote-control` 弹窗（优先级：P0）

作为 desktop / VS Code / JetBrains 的用户，我希望在聊天输入框里输入 `/remote-control` 就能开关并看到页面地址，以便不必切到终端敲另一条命令。

**为什么是这个优先级**：GUI 用户本来就在聊天界面里工作，把开启入口放到他们眼前的那个界面上，是「默认关闭」这个保守取值能成立的前提——否则关掉的开关等于没有入口。

**独立测试**：在任一 GUI 宿主输入 `/remote-control`（不被发给模型）弹出弹窗，弹窗能显示未开启状态、能点击开启并回显状态、能显示页面地址与可扫的二维码；开关关闭时弹窗显示明确的读取失败原因而不是一个假的默认状态。

**验收场景**：

1. **假设** 用户在任一 GUI 宿主的输入框里输入 `/remote-control` 并回车，**则** 这条文本不被发给模型、不进入会话历史，而是打开远程控制弹窗；该命令也出现在斜杠命令列表的「系统指令」分组里，可直接点选。
2. **假设** 弹窗打开，**则** 它立即向本端进程查询一次状态，并在此后每秒重查一次（宿主到 CLI 只有请求/应答这一个通道，没有状态推送），状态按「未开启 / 连接中… / 已连接 / 出错」呈现。
3. **假设** 当前状态是未开启或出错，**则** 主按钮是「开启远程控制」；其余状态主按钮是「断开」；点击后对应的连接/断开结果在同一弹窗内回显。
4. **假设** 已连接，**则** 弹窗显示页面地址（可点「在浏览器中打开」交给系统浏览器），并**画出一个可扫的二维码**——内容就是那个页面地址本身（地址里带着本机的通道键）。地址由**持有会话的那个进程**拼出来（它手上有通道键，也知道服务端地址）随状态一起交给弹窗，弹窗只负责显示；二维码与终端命令打印的是同一个地址。因此 GUI 这边**总是画得出**二维码——没有「等中继带回地址」这一说，也就没有「没带回所以不画」的回退。**Web 页自己不显示二维码**——它是被扫码打开的那一方，不是扫码的一方（PC 浏览器直接打开同一个地址也一样，不需要再扫一次）。
5. **假设** 弹窗开着、每秒一次的轮询让多个请求同时在飞，**则** 只有**最新一次请求**的回执会被渲染——迟到的旧回执（例如晚一秒到达的「未开启」）不得把用户刚建立的连接改回去。
6. **假设** 宿主侧读取失败（开关关闭 / 会话尚未就绪 / 对端不认识该 RPC），**则** 弹窗显示「无法读取状态」与原因原文，并给出开关提示；**不得** 伪造一个默认快照充数。
7. **假设** 用户在弹窗里按 Escape，**则** 只关闭弹窗，不触发「中断生成」——该按键不得溢出到输入框的中断快捷键上。
8. **假设** 桌面端同时开着多个 pane，**则** 弹窗作用于**当前 pane 自己的** `wave --stdio` 子进程（每端各自持有一条出站连接），不影响其它 pane 或其它进程。

### 用户故事：开关语义——默认关闭、显式开启、进程启动时定型（优先级：P0）

作为用户与管理员，我希望「本机能不能被手机接管」默认是不行的、且只有显式打开才可能联网，以便这条件事永远是有意为之，而不是默认后果。

**为什么是这个优先级**：打开它意味着把「正在等待确认的工具调用」暴露到本机之外，并与一个外部服务保持长连；这类能力的默认值只能是关，且判定必须可被企业侧统一收口。

**独立测试**：在不配置任何开关的机器上运行 `wave remote-control status`（或 GUI 弹窗），得到「未开启 / 需设置 `enableRemoteControl`」的明确结果，且本机不做任何出站连接；写 `~/.wave/settings.json` 打开后重启进程，能力可用但仍需显式拨号。

**验收场景**：

1. **假设** `enableRemoteControl` 在用户级设置、项目级设置与远端托管设置里都没有配置，**则** 本机不具备服务能力：不建立任何中继连接，`remoteControlStatus` / `remoteControlConnect` / `remoteControlDisconnect` 三个 RPC 一律失败，错误信息指出要打开哪个设置键。
2. **假设** 用户在 `~/.wave/settings.json` 里写入 `"enableRemoteControl": true` 并重启进程，**则** 本机**具备**服务能力，但仍不自动联网——要等用户执行 `wave remote-control on` 或在弹窗里点「开启远程控制」才拨号。
3. **假设** 企业侧经远端托管设置（`GET /api/wave/settings`）显式下发了该键，**则** 它优先于本地设置与代码默认值。
4. **假设** 进程启动时开关是关的、之后用户改了设置文件，**则** 已在运行的进程保持旧答案（开关只在进程启动时读一次），失败提示必须引导用户重启 daemon 而不是让用户反复改文件。
5. **假设** 设置文件损坏或读不到，**则** 判定按「关」处理——既不按开、也不让读设置这件事把进程带崩（判定发生在准备开网络监听的位置，坏设置必须读成「关」）。
6. **假设** GUI 宿主（desktop / VS Code / JetBrains）拉起自己的 `--stdio` 子进程，**则** 该子进程以**它自己的工作目录**判定开关：用户级 `~/.wave/settings.json` 总是被读到，项目级 `.wave/settings.json` 只在子进程恰好从该项目目录启动时才参与合并。

### 用户故事：远端通道只开一个白名单、且不把全量内容推给手机（优先级：P1）

作为用户与管理员，我希望手机只能问聊天与审批相关的那几个方法，并且长会话不会因为「手机在旁边」而把 MB 级全量帧推给中继，以便同时控制暴露面与流量成本。

**为什么是 P1**：本地传输一直是什么都能调——那是用户自己的机器跟自己说话；手机是一张持有令牌的网页，暴露面必须显式收窄。这条不改也能跑通审批闭环，但它决定这个功能能不能长期开着。

**独立测试**：对已连接的中继路径发一个白名单外的方法，得到明确的「Method not available over remote control」拒绝；对一个≥1000 条消息的会话，远端路径看不到 MB 级全量帧，只有「列表变了」的信号 + 按 `since` 的增量拉取。

**验收场景**：

1. **假设** 手机发来白名单内的方法（`listSessions` / `listDaemonSessions` / `getSessionInfo` / `getMessages` / `listPendingPermissions` / `permissionResponse` / `sendMessage` / `abortMessage` / `setPermissionMode`），**则** 请求照常经 bridge 执行并把结果回执给手机。其中 `listDaemonSessions` 是手机列会话的主数据源：它报的是**该进程内存里的活会话**（`sessionId` / `workingDirectory` / `isLoading` / 消息数），而 `listSessions` 读的是磁盘上的 jsonl、会把早已结束或本进程从未载入的会话也列出来 —— 那些条目在手机上打不开（见边界情况），所以它只留作兼容、不做手机列表的数据源。回执是**带 `method` 的 JSON-RPC 信封**——成功 `{id, method:"result", params:{result}}`、失败 `{id, method:"error", params:{code, message}}`，**不是**裸的 `{id, result}`：页面侧必须按这个形状取结果与错误（把结果读成顶层 `result` 字段会让每一份回执都变成 `undefined`，于是会话列表恒为空、「没有更早的消息」恒为真，而失败一声不吭）。
2. **假设** 手机发来白名单外的方法，**则** 回明确错误（`-32601`「Method not available over remote control: &lt;method&gt;」），不执行、不静默丢弃。
3. **假设** 某会话产生了 `messagesChange`（全量显示列表，长会话可达 MB 级），**则** 发往中继的那一路只发一条**不含内容**的「列表变了」信号，内容由手机按 `since` 自己拉；本地桌面 / IDE 客户端照旧收到原来的全量数组。
4. **假设** 流式输出以每秒几十到上百帧的速率产生增量，**则** 只有**发往中继**的那一路按 150ms 窗口合并累积型增量，合并是**延迟而非抽样**（不丢任何一帧，合并后的帧携带的字节与逐帧发出的一样多）；本地进程内的客户端完全不走这条路径。
5. **假设** 发生离散事件（权限请求、工具块结束、状态信号），**则** 它立即写出，并先冲刷已合并的增量，手机不会看到乱序的流。
6. **假设** 某会话正卡在等待审批，**则** 本机上报 `requires_action`；`running` 表示仍有事情在飞（含后台任务，手机没有终端可以瞄一眼，所以「忙」的判据取宽），`idle` 表示空闲。该信号每会话**一个词**、不含任何消息内容，按 250ms 去抖推送，且只在真的变化时才发。上报走**两条**：业务通知 `sessionStatus`（不带顶层 `type`，中继逐字转发给手机，手机 UI 照旧消费）**再加**一条控制帧 `{"type":"host_state","sessionId":"…","state":"…"}`——中继只消费后者来判断「有人正在等审批」并触发 Web Push，因为从业务信封里取状态等于要它解析 body 语义，与「不解析」的前提冲突。
7. **假设** 手机用 `getMessages` 只带 `since`（增量）或只带 `limit`（尾页），**则** 按锚点/分页返回并标注是否还有更早的消息；`since` 指向的消息已被 rewind / clear 截断时返回「锚点已消失」标志，让手机重拉尾页而不是猜；不传任何新参数时，既有调用方的返回与行为逐字节不变。
8. **假设** 手机请求的一页在序列化后超过**单帧字节预算**（默认 512 KiB），**则** 宿主把这页按预算截短（从最早的条目开始丢，保证留下的是**最新**的一段）、仍带 `hasMore` 标志返回，而**不是**把超预算的帧发出去。`limit` 因此只是**条数起点**：条数够小是常态，但**保证一律来自字节预算** —— 因为「一页多少字节」随会话内容（工具输出、diff）而变化，只有字节数是能兑现的承诺。

### 用户故事：连接生命周期——重连、背压与断连恢复（优先级：P1）

作为用户，我希望网络抖动、电脑休眠、中继重启之后连接能自己回来，也接受「电脑联系不上时手机不展示历史」，以便不必盯着状态、也不必担心电脑这边被拖垮。

**为什么是 P1**：首版能连上就能跑通闭环，但这些规则决定它能不能长时间挂着——重试策略写错会变成断线后永不回来或无限重试，背压写错会让一台电脑被一个读到一半的手机吃掉内存。

**独立测试**：断开中继后连接能按固定间隔自动重试并恢复；把中继回成 4003 后本机永久停止重连并把原因呈现为错误状态；让手机停止读取，本机在未发送数据超过阈值时断开连接而不是无上限排队。

**验收场景**：

1. **假设** 连接因普通原因断开（中继重启、网络抖动），**则** 本机以 2 秒固定间隔重试、最多 5 次（固定而非指数退避：中继是知名主机而非抖动对端，退避只会拖慢一台刚休眠醒来的笔记本）；期间状态如实呈现为断开/重连中，不静默假死。
2. **假设** 中继以 4001 告知「本机暂不可用」（瞬态），**则** 本机用**独立的、更小的**预算重试 3 次——真实的不可用重试五次也买不到什么。
3. **假设** 中继以 4003 拒绝凭证（永久），**则** 本机立即永久停止重连，并把原因作为错误状态交给上层呈现，不无限重试。
4. **假设** 手机停止读取，导致未发送数据超过 4MB，**则** 本机断开这条连接并告知手机不必重发已缓冲的内容，**不做无上限排队**；手机重连后按 `since` 追赶（与冷启动同一条路径）。
5. **假设** 链路当时是断的，**则** 新产生的通知直接丢弃而不缓冲：手机重连时会用 `since` 补齐，缓冲只会换来一串它马上要丢掉的重放帧。
6. **假设** 连接已建立，**则** 本机每 30 秒发一个**应用层**心跳控制帧 `{"type":"ping"}`（浏览器不能发 WebSocket 控制帧，中继面向的又是手机，所以保活必须长在应用层），中继回 `{"type":"pong"}`，且**两端都不把它转发**——改之前的心跳长得像 JSON-RPC，会被广播给该电脑下全部订阅端。链路层的活性另有一层：中继每 30 秒发 WS 协议层 ping，浏览器与 `ws` 库自动回 pong。
7. **假设** 中继发来回程控制帧（`auth_ok` / `auth_error` / `peer_disconnected` / `resync_required` / `pong`），**则** 本机的中继控制层必须**逐种消化**：`auth_ok` 标记握手完成、`peer_disconnected` 呈现为「电脑已断开」（随后是 4001）、`resync_required` 触发重拉一次快照、`pong` 只是心跳回执；**一个都不许进 agent 桥**——它既不能让手机看到一条凭空多出来的方法调用，也不能被本机当成对端发来的请求去执行。判定是结构性的：「无 `method` 且有顶层 `type`」⇒ 控制层，其余 ⇒ JSON-RPC 层。
8. **假设** 中继以 `auth_error` + `host_version_unsupported` 拒绝本机（`minVersion` 随帧带回），**则** 本机把它当作**永久**失败：状态置为错误并明示「请升级电脑侧 wave（最低 X.Y.Z）」，**不再自动重连**——重试改变不了本机版本。这条也是 `minVersion` 必须从**帧**里读而不是从关闭码里猜的原因：关闭码只分得出瞬态/永久，说不出要升到哪一版。
9. **假设** `--stdio` 子进程的宿主消失了（stdin EOF）或服务器停止，**则** 本机主动断开中继连接，不让中继替一个已经不存在的进程保留订阅。
10. **假设** 本机要发往中继的某帧在序列化后超过**单帧字节预算**（默认 512 KiB），**则** 处置按类别分两种，但都不许把这一帧发出去：读接口返回**按预算截短的页**（见白名单故事的场景 8），通知类降级为**不含内容的「有更新」信号**（`messagesChange` 早已是这条形状）。理由是中继侧两道闸都不站在我们这边：`maxPayload` 默认 4 MiB **越界即 `1009` 关闭连接**，而**订阅者缓冲默认 1 MiB，判定是把 `bufferedAmount + 本帧字节` 与 1 MiB 比较、超了就丢弃该帧并下发 `resync_required`** —— 这条判定的形态意味着**任何超过 1 MiB 的单帧必然被丢，跟手机读得多快无关**。因此有效单帧上限 = 三者的最小值（本机 4 MiB 累积缓冲 / 中继 4 MiB `maxPayload` / **中继 1 MiB 订阅缓冲**），而**预算必须按最小的那个来定**；本机那个 4 MiB 只作最后兜底，不该有机会被用到。
11. **假设** 一条超过一页的长会话在手机上打开，**则** 首屏那一页本身也必须满足上面那条预算（默认页大小按此选取，而不是按「条数看起来够用」选取）——否则首屏帧在中继被丢弃，`since` 补差又因缺少基准而失败，于是每次重连都重演同一个循环。

### 用户故事：Web 页作为第五种宿主（页面产物，优先级：P1）

作为离开电脑的用户，我希望用手机扫一下二维码（或在任意一台设备的浏览器里直接打开这个地址）就能看到正在跑的会话并完成审批，以便不必回到电脑前推进任务。

**为什么是 P1**：页面本身不是目标，审批闭环才是；但它决定了 Web 页能不能用——页面产物是「同一份 webview + 一层浏览器 shim」这一复用策略的交付物，其边界（单会话、只拉尾页、不支持的命令要明说）需要在规格里钉住。

**独立测试**：从企业端部署的页面用带通道键的地址打开，能列出本机会话并显示最后一段消息与待审批请求；在页面上批准后本机继续执行；关掉页面再打开，待审批请求仍在。另在手机上打开一次：顶栏与输入区同屏可见、页面本身不产生纵向滚动，两端都不被系统 UI 遮挡；聚焦任一输入框时整页不放大。

**验收场景**：

1. **假设** 用带通道键的地址打开 Web 页，**则** 页面先把「去哪、用什么说」两件补全：中继地址由页面**同源**推导（页面就部署在中继同一个域下的 `/remote/`，`?ws=` 只留给本地调试覆盖），通道键直接取地址里的 `host=`；然后连上订阅地址、以 `{"type":"auth","credential":{"type":"sso","token":"<登录 JWT>"},"version":"…"}` 完成握手（拿到 `role:"subscriber"`）。**这一份 JWT 就是企业端登录态本身**（页面与登录页同源，读的是同一份已存下的令牌），页面不引入第二套账号、也没有单独的登录步骤。**地址里那个通道键不是凭证**：中继在订阅握手时校验「这行 host 属于当前账号、且账号是该企业的活跃成员」，别人的通道键换不来任何东西——所以它可以坦然印在二维码上。
2. **假设** 页面已连上，**则** 首屏先列**本进程内此刻持有的活会话**（主数据源是 `listDaemonSessions`，每条给 `sessionId` / `workingDirectory` / `title` / `lastActiveAt` / `isLoading`，按 `lastActiveAt` 倒序；title 与 lastActiveAt 由机器侧从该会话的显示消息派生），未指定就选**最近活跃**的一条；然后只拉它的**最后一页**（默认 100 条，且整页序列化后不超过单帧字节预算）与待审批请求，以一份完整初始状态回答 webview 的就绪消息（用户、会话、消息、待确认请求一次给全）。磁盘上的历史会话不进这个列表，见边界情况。页大小按**预算**定而不是按「条数看起来够用」定：均值 5.7 KB/条时 100 条 ≈ 0.57 MB 已贴着 512 KiB 预算，再往上就跨过中继的订阅缓冲（见连接生命周期故事的场景 10 / 11）。
3. **假设** 中继发来「列表变了」的信号、或页面重新连上，**则** 页面只按本地最后一条消息 id 走 `since` 补差；补不上时（锚点已消失）回落为重拉最后一页。
4. **假设** 本机触发了一次需要审批的工具调用，**则** 页面弹出审批卡（工具名、参数、计划内容等）；用户批准或拒绝后以 `permissionResponse` 回执给本机；关掉页面再打开，该待审批请求仍在。
5. **假设** 页面渲染的是与桌面 / IDE 相同的那份聊天 UI，**则** 它是**一次看一条**的单会话视图（没有 pane、没有工作目录管理），会话之间用顶栏的「会话」入口切换（见第 10 条）；顶栏**不提供**「新建对话（原地清空）」与「历史对话」这两个入口——与桌面端同口径（桌面端也是把会话的新建与历史收进侧栏，顶栏 `hideSessionButtons`）。并且**不支持**的命令（打开本地文件、打开外链、预览本地图片、上传文件、单独登录/登出等）必须给出明确原因或显式提示，绝不能静默无响应把用户晾在一个灰着的界面上。
6. **假设** 用户点弹窗里的「在浏览器中打开」，**则** Web 页把它列为不支持（页面自己就运行在浏览器里），不产生未处理的动作。
7. **假设** 用户在 Web 页上看或改权限模式，**则** 口径是钉死的：**Web 端默认就提供四档**（含「跳过权限确认」），不设「会话创建时是否已授权」那道门；**默认模式保守** —— 会话初始仍是 `default`，**连接这个动作本身不改模式**；**「不自动继承」指的是连接动作不改模式**，不是「Web 页看不到当前模式」（同一个会话只有一份模式状态）。
8. **假设** 页面手上的**访问令牌**不可用——本地读不到 `token`（这台设备没登录过）、本地令牌已过期（同源存储的 `expiresAt` 已到）、或中继在握手时回了 `invalid_token`——**但**企业端的刷新令牌（同源存储的 `refreshToken`）仍在，**则** 页面**先就地静默续期**：对同源的 `POST /api/auth/refresh` 发一次请求，成功后把新凭证写回存储、用**新令牌**继续原来的连接流程（握手与后续请求都用新的那一个），**全程不发生任何导航**。续期在页内**单飞**（同一时刻只发一个请求，其余调用复用同一份结果）且**每次会话只自动尝试一次**；本地没有 `expiresAt` 时按「令牌仍可用」处理、直接连接，过期与否交给握手说话。这是「每小时被赶去登录一次」与「一个用户看不见的请求」之间的取舍，见边界情况那条耦合清单。
9. **假设** 静默续期没拿到可用凭证——没有刷新令牌、刷新令牌也已失效、响应不合形状（缺 `token`），或请求本身发不出去（网络异常、存储不可用）——**则** 页面才走原来那条路：**自动导航到企业端登录页**，并把**当前页面地址（原样带着 `host=` 等参数）**作为回跳目标一并带上；用户在企业端完成登录（密码与 SSO 两条路都算）后**自动回到这个地址**，页面重新读一次登录态、继续原来的连接流程。回跳目标**只接受同源站内路径**，跨站地址一律拒绝——这是这条路上唯一真实的攻击面（开放重定向）；页面只负责带参数，不解析登录结果，也不接管登录表单。这条路的其余硬约束不变：每次会话只自动跳一次、只在企业端域名上跳（本地调试页照旧只提示）。
10. **假设** 用户点开顶栏的「会话」入口，**则** 页面列出**本进程内此刻持有的活会话**（跨工作目录：每条带自己的 `workingDirectory`，它就是这条会话的身份），当前正在看的那条有选中态；选中另一条后，页面只切**自己**的视图 —— 改本地 `sessionId`、清空消息列表、重拉该会话的尾页与它的待审批请求 —— 并且**不调用 `restoreSession`**：电脑端那条会话本身、以及电脑端用户正看着的界面都不受任何影响。**切换只改手机视图，这是「控制面」的含义**。
11. **假设** 页面收到一条通知，其信封 `sessionId` 与页面当前会话不同（设备级通道下这是常态：同一进程里别的会话也在产出），**则** 直接丢弃、不落进当前视图；只有信封 `sessionId` 与当前会话一致（或该通知不带 `sessionId`，如状态信号与机器信息）才处理。否则多个会话的消息与流式增量会混进同一个列表。
12. **假设** 用户把消息列表滚到顶部并继续上拉，**则** 页面以当前最早一条消息的 id 作 `before`、按同一个字节预算取**更早的一页**并 prepend 到列表前面：视口**停在用户原来看到的那条消息**上（不是被新插入的内容顶走），也**不能被判成「来了新消息」而强制贴底**——列表从此不再只从尾部增长，任何「长度变长了就是新消息」的判据在这里都不成立。取不到更早的消息（`hasMore` 为假）时，页面明确说明「没有更早的消息」并停止继续请求，而不是无声地把上拉变成什么都没发生。
13. **假设** 上拉期间链路断开或 `before` 锚点已被 rewind / clear 截断，**则** 本次加载放弃并保持用户当前视口不动（可选提示），**不**回落成「重拉尾页」——那是冷启动与补差路径的动作，用来回答「上拉更早」会把用户看到的位置整段换掉。
14. **假设** 页面在手机上打开（浏览器标签页里，或「添加到主屏幕」之后的独立窗口里），**则** 它必须**整屏装得下**：顶栏与输入区在同一屏内同时可见、页面自身不产生纵向滚动，两端也都不被系统 UI 压住——浏览器工具栏的伸缩（地址栏与底部工具栏的收起 / 展开）与全面屏的安全区（状态栏、Home 指示条、横屏时的圆角区）都不得把这两个区域推出可视范围或盖在它们上面。**依据**：这是唯一跑在浏览器里的宿主，它的高度由**浏览器的可视区**决定，而不是由承载它的窗口决定；本地四端嵌在没有动态工具栏、也没有安全区的窗口里，这条约束在它们身上恒成立（页面高度与窗口高度逐像素相等）。因此这是 Web 页独有的要求，按宿主收口，不改动其余四端的布局。

14. **假设** 用户在 iPhone 的浏览器里（含「添加到主屏幕」后打开的窗口）聚焦页面上的任一文本类输入控件，**则** 页面**不得被浏览器自动放大**：聚焦前后整页的视觉缩放比不变（`visualViewport.scale` 保持 1），用户不必手动缩回去。**依据**：iOS Safari 对 computed `font-size` 小于 16px 的文本控件，会在聚焦时把整页缩放到等效 16px 且此后不自动还原（15px 仍触发，16px 起才不触发），而页面上每个输入框都在线下（消息输入区 12px、设置项 14px）——所以页面对此必须显式表态。两条路都走得通：**把文本控件抬到 16px**，或**不让页面被缩放**；他 2026-10-14 在真机上看过前者，判「确实大了（比设计稿大一档）」，因此取后者，并接受随之而来的「页面不能再手动双指缩放」（一张已响应式的控制面板用不到它）。该要求**只作用于远控页**：其余四端不跑在移动端浏览器里，不受这条约束，也不该为它改动共享样式。

### 用户故事：前台 CLI 会话也能被手机接管（优先级：P1）

作为正坐在终端前对话的用户，我希望离开工位时把**手上这条**会话交给手机，而不是另开一条再重述一遍上下文，以便走出工位还能接着推进。

**为什么是这个优先级**：前面几条故事覆盖的都是「常驻着、可以被指着的会话」（daemon、GUI 子进程）。前台 TUI 会话是唯一一种**只活在用户眼前那个进程里**的会话——它的寿命跟着用户敲的那一下退出走。能不能接管，取决于这条会话所在的进程自己愿不愿意拨号，没有第二个进程能替它做（「谁持有会话谁服务」在这条故事里是极端情形）。它不改安全模型（同一个开关、同一份白名单、同一条设备级通道），所以既可以独立落地，也可以独立不落地；缺了它，既有闭环一条都不少。

**独立测试**：在交互式 TUI 里执行开启动作，拿到页面地址与二维码；手机连上后看到的**就是终端里这条会话**（消息逐条一致，不是空会话）；两端各发一句对方都能看到；构造一次等待确认的工具调用，两端同时出现审批卡，任意一端作答后另一端那张卡消失、会话继续；退出 TUI 后页面显示「电脑已断开」。

**验收场景**：

1. **假设** 开关已打开且用户已登录，**当** 用户在交互式 TUI 里执行开启远程控制的动作时，**则** 拨号的是**这个前台进程自己**——不经 daemon 代理、也不为了完成这个动作去拉起 daemon——并在 TUI 里回显与 `wave remote-control on` 同形的页面地址与可扫二维码；失败时的提示同样指向 `enableRemoteControl`（并说明前台进程也要重启才换设置）。
2. **假设** 手机连上了前台 CLI 会话，**则** 它看到的是这条会话**本身**（与终端同一份消息序列、同一个模型与权限模式），不是新会话、也不是空会话。
3. **假设** 用户在手机上发出一条消息，**则** 它进入这条会话的历史并驱动同一条生成循环，终端的消息列表随之更新；反过来，在终端发出的消息同样出现在手机上。
4. **假设** 会话正在生成、用户在手机上触发中断，**则** 中断的是这条会话当前这一轮，与在终端按中断键等价。
5. **假设** 这条会话有等待确认的工具调用，**则** **两端都能作答**（终端沿用既有审批 UI，手机用审批卡），**先作答的一端生效**、另一端同一张卡随即消失；两端看到的待确认集合一致。这不是新增权限：同一个请求本来就要用户点一次，区别只在点在哪一端。
6. **假设** 用户正常退出 TUI、或前台进程被结束，**则** 本机**主动断开这条中继连接**（不替一个已经不存在的进程保留订阅），页面呈现为「电脑已断开」并停止展示内容（与「服务端不落内容」这条既有口径一致）；该会话按 CLI 既有语义落盘，将来恢复出来的是一条**新会话**，不会自动接回手机原来那条连接。
7. **假设** 用户想在 TUI 里关掉，**则** 关闭断开的正是**这个进程**这条连接（关的入口必须和开的入口在同一个进程里，理由同第 1 条）；此时本机别的进程若在服务（daemon / GUI 子进程），它不受影响。
8. **假设** 同一台机器上已经有另一个进程在用同一个通道键服务（daemon 在跑、或某个 GUI 子进程已连），**当** 前台 TUI 尝试开启时，**则** 结果必须唯一且如实呈现——要么新进程接管、要么明确拒绝并告知先关掉哪一个；**不允许**两个进程都以为自己在线（通道键是设备级的，见边界情况）。

### 边界情况

- **没有配对码：通道键不是凭证，页面靠登录态说话**。不发码的两条理由：① 短期票据只有能被**重复签发**才有意义，而本机的登记是一次性且不幂等的——把码塞进登记响应，等于让它的寿命跟着那次登记一起结束，过期即无解；② 码换来的东西本来就不需要保护——中继在订阅握手时校验「这行 host 属于当前账号、且账号是该企业的活跃成员」，**通道键本身没有权限**，印在二维码上不泄露任何东西。对齐参照是同类的 Claude Code：它也没有配对码，二维码只是会话 URL 的快捷入口。因此页面地址就是 `<服务端地址>/remote/?host=<hostId>`，与中继给推送用的落地页模板**同一个形状**——扫码进来和点推送进来是同一条路。
- **一条连接承载全部会话**：通道键是设备（本机）而不是会话——会话级通道在这里根本不成立：手机要先从本机学到会话列表，会话级通道会让「列表页」无处可问。因此 `sessionId` 只是信封字段，中继逐字转发不需要理解内容。
- **一台机器只有一个服务方**：通道键既然是设备级的，同一台机器上的多个 wave 进程就只能**共用同一个通道键**（本机只有一份 `~/.wave/remote-control.json`）。于是「谁持有会话谁服务」在多进程并存时必须收敛成一个答案——手机指向的那台机器，同一时刻只由其中一个进程提供服务，不允许两个进程都以为自己在线（前台 CLI 故事第 8 条）。
- **手机能看、能切的，只限「服务进程内活着的那批会话」**：这不是 UI 取舍而是可达性事实——① 手机列会话只能靠 `listDaemonSessions`（进程内存注册表，跨工作目录都在里面）；② 读消息与发消息都要求信封 `sessionId` 在本进程注册表里（`getMessages` 走 `requireSessionForRead`），磁盘 jsonl 里没被载入本进程的历史会话会回 `Session not found`；③ 唯一能把历史会话载入进程的 `restoreSession` **不进白名单** —— 它是「原地载入」语义，用它等于把服务进程里该条会话换掉（在桌面端就是换掉用户正在看的那个 pane），与「手机只当控制面」相冲。所以手机侧的会话列表与切换都只看进程内活会话，历史会话留给电脑端。切换只改手机自己那份 `sessionId` 与视图，**不发起任何写向电脑端的会话操作**。
- **中继订阅地址不上界面**：`wss://<中继>/v1/hosts/<hostId>/subscribe` 是本机到中继的**出站订阅端点**——用户既打不开它也无处输入它，而它携带的 `hostId` 已经原样出现在页面地址的 `?host=` 里，唯一的信息增量是中继域名（即「这台机器连的是哪个环境」），那条信息属于排查场景，排查走状态输出与日志更直接。因此 CLI（`on` / `status`）、前台 TUI 与 GUI 弹窗都不渲染它；快照里的 `url` 字段保留（连接与日志仍需要），去掉的只是呈现。
- **顶栏没有「新建 / 清空」是刻意的**：`clearChat` 在 Web 端从未实现（点了只会留一条 console 警告），而「新建会话」也不属于控制面（会话该在电脑侧创建）。桌面端同样把会话的新建与历史收进侧栏、顶栏不渲染那两个按钮（`hideSessionButtons`），手机页沿用同一口径，改为顶栏一个「会话」入口用于在进程内已活着的会话之间切换。
- **「开关打开」≠「已连接」**：开关只授权**能力**，连接是用户的动作。两者分开的结果是：一台开着开关但没人拨号的机器不会建立任何出站连接，而一个失败连接会停在 `error` 状态（带原因），不是 `off`。
- **`off` / `error` 两种失败必须分开呈现**：宿主侧根本读不到状态（开关关闭、会话未就绪、对端不认识该 RPC）与「中继连上了但自报出错」是两件事，界面文案与 CLI 退出码都不同——把前者伪装成 `state: "error"` 会让用户去修一个不存在的网络问题。
- **Web 页的高度与安全区由浏览器说了算**：本地四端（IDE / 桌面的宿主）都被嵌在一个自己就是整屏的窗口里——页面高度与窗口高度逐像素相等，没有会伸缩的浏览器工具栏，也没有被系统 UI 盖住的边缘。Web 页不是：它跑在浏览器里，可视区随工具栏收起 / 展开而变，页面若按「工具栏收起后」的高度铺满，贴底的输入区就会落到折叠线以下（用户看不到输入框 = 交互失效）；页面又刻意画到屏幕边缘以吃满全面屏，于是状态栏 / 灵动岛、Home 指示条、横屏圆角区都压在内容之上，让开它们同样是页面自己的责任。这两条只对这一个宿主成立 ⇒ 按宿主收口，不落在共享布局上（见 Web 页故事场景 14）。
- **服务端不落内容，断连不展示历史**：中继是无状态转发，不缓存会话内容。因此本机离线时手机只应显示离线状态并停止展示内容，而不是继续渲染本地旧列表「假装还在」。
- **`messagesChange` 的两种形态**：同一个通知既是全量数组（本机侧快照）又是远端那条路的信号（无 `messages` 字段）。手机侧两种都要接住——拿到数组就用它，拿到信号就问 `since`。
- **`since` 是位置不是版本号**：消息 id 稳定，所以调用方可以只报「我最后看到的那条」；唯一致命的失败是锚点被截断（rewind / clear），此时必须回「重拉尾页」的信号，因为存储里没有版本号能发现这件事。同一个 id 可能在显示列表里出现多次（压缩后的消息会被重新加回），锚点按**最后一次**出现解析。
- **远端路径的异常不外溢**：远端扇出被就地兜住（try/catch），一个手机、一条坏帧不能让本地桌面 / IDE 的客户端掉线；本地路径（unix socket / 子进程管道）的逐帧行为完全不变。
- **`--stdio` 子进程与 daemon 都可能是服务方**：同一台机器上「谁持有会话谁服务」，手机看到的就是那个进程的会话集合；GUI 三端各自拉子进程 ⇒ 各自可能同时持有一条出站连接，这是设计而不是重复。
- **版本在握手帧的顶层，不在 `params` 里**：`{"type":"auth","credential":{…},"version":"1.2.3"}`——中继只读顶层 `frame.version`；写进 `params.version` 是**静默失效**（它「无从判断 ⇒ 放行」，两侧都不报错，只是版本过低的机器照样连上）。这是「页面永远是最新的、版本不匹配时请升级电脑侧」这条策略能不能生效的唯一开关（页面侧提示尚未实现，见下节）。该机标签（`name`，≤100 字符）则是在**登记**时上报的，只用于让手机区分同账号下的多台电脑。
- **两种凭证角色靠 `credential.type` 显式区分**：电脑侧 `{"type":"host","token":"rch_…"}`（登记时取到、持久化在本地，长期可吊销，撑得住几小时长连与重连）；手机侧 `{"type":"sso","token":"<登录 JWT>"}`。**两边是同一个人，身份区分不出角色**，所以角色只能显式声明——漏了它最隐蔽的后果是电脑侧走成订阅者分支：**能连上、两侧都不报错**（拿到的是 `role:"subscriber"`），但没人占 host 位，于是**它自己**先被中继按 4001 `host_offline` 关掉（订阅者必须挂在一台在线的主机上），随后真正的手机连上时也是 `auth_ok` → `peer_disconnected` → 4001。看到 4001 先查「电脑侧是不是走了 sso 分支」。电脑侧的长期令牌免掉了「常驻 daemon 的寿命长于 1 小时 JWT」这个矛盾，而端点解析仍在**连接时**做（用户也可能在进程跑了几小时后才想起开远程控制）；手机侧沿用已有登录态，没有第二套账号体系。登录态不可用时的错误不是笼统的「连接失败」，而是先就地续期、续不上再跳到企业端登录页并跳回来（见「登录态缺失先就地续期，续期不成才是一次重定向」那条）。
- **页面「去哪、用什么说」都取自同源，不靠页面配置**：中继地址不做成构建期常量——页面本身就部署在中继同一个域下的 `/remote/`，因此地址由 `location` 同源推导（`http(s)` → `ws(s)`，路径用中继公布的通道形态 `/v1/hosts/ws/{hostId}/subscribe`），`?ws=` 只留作本地调试；通道键就取地址里的 `host=`（地址由本机自己拼，形状与推送落地页模板 `/remote/?host={hostId}&session={sessionId}` 一致）。凭证同理：**握手用的就是企业端那一份登录令牌**（同源存储的同一个键），页面既不要求单独登录、也不注册第二套账号。代价是页面对企业端**会话存储与续期接口的完整形状**形成了耦合，键名、过期时机与接口形状都归对方前端定——这条耦合要显式记一笔，别指望将来有人能从我们的代码里推出来：**四个存储键**（`token` / `refreshToken` / `expiresAt` / `user`，后三个只服务于续期——`user` 是「登录地改过邮箱后别在页面上显示旧信息」这一条）加**一个端点**（`POST /api/auth/refresh`，请求体 `{refreshToken}`，响应 `{token, refreshToken, expiresInSeconds, user}`，与登录响应同形；少一个键就少一条退路）。**为什么值得**：页面的寿命是「一直挂着、或随时打开」，而访问令牌只有 1 小时、刷新令牌是 30 天滑动——不续期就等于用户每过一小时被赶去登录一次，续期把那个每小时一次的打断换成一个用户看不见的请求。**代价是失败模式而不是能力损失**：企业端改了键名、换了端点路径、或改了响应形状，页面**不会硬失败**，而是静默退化成下面那条「跳登录页」的路——有意的选择，宁可退化成「多点一次登录」，也不要留一个只在对方改键名那天才炸的硬依赖。登录态不可用时的处置见下一条——续期在先，跳转在后。
- **登录态缺失先就地续期，续期不成才是一次重定向**：页面没有自己的登录步骤（它只是企业端登录态的消费者），所以「登录态不可用」有三种来源——本地读不到令牌、本地令牌已过期、或中继握手回 `invalid_token`（令牌过期或被吊销）。三者都**先试续期**（刷新令牌还在时；耦合清单见上一条），续不上才把**当前地址**（原样带着 `host=`）当回跳目标、跳到企业端登录页（见「Web 页作为第五种宿主」故事场景 8 / 9）。三条硬约束：① **回跳目标只接受同源站内路径**（以 `/` 开头的相对路径；`//evil.com` 与绝对跨站 URL 一律拒绝）——开放重定向是这条路上唯一真实的攻击面；② **每次会话只自动跳一次**（`sessionStorage` 记标记），跳回后仍没有有效登录态就停在明确提示上，不与登录页来回弹跳——续期同理只自动试一次，否则「续期失败 → 跳登录 → 回来 → 再续期失败」只是把同一场弹跳换了个形式；③ **只在企业端域名上跳**——本地调试（`file:`、`localhost`）没有登录页可跳，那里照旧只提示。收端要给的配合是登录页与 SSO 回调支持这个站内回跳参数，且**不复用 CLI 的 `callback_url`**：那个参数的语义是「把授权码回调到本机 localhost 的 HTTP 服务」（服务端也只放行 localhost，见 `POST /api/auth/code` 的白名单），与「登录完回到哪个站内页面」是两件事，混用只会让白名单变成两种语义的叠加。
- **握手完成前一个业务帧都不能发**：中继把「未认证连接发来的任何帧」一律当 `auth` 帧解析，解析不过即 4003 永久关闭（不重连）。而页面挂载、会话就绪这类事件随时可能早于握手完成，因此出站队列必须闸在 `auth_ok` 之后——抢跑一帧就再也连不上。回程那五个控制帧（`auth_ok` / `auth_error` / `peer_disconnected` / `resync_required` / `pong`）同理一个都不许进 agent 桥，这条纪律与中继控制层那条用户故事完全一致。
- **有效单帧上限取三者最小值**：本机未发送**累积**缓冲 4 MiB、中继 `maxPayload` 4 MiB、**中继每订阅者缓冲 1 MiB**。我们的单帧预算（512 KiB）按**最小的那个**定，并留出余量给同时在途的其它帧。⚠️ 这两条中继侧的闸语义不同、别混：`maxPayload` 越界是**关连接**（1009），订阅缓冲越界只是**丢这一帧 + 要求重同步**——后者不会报错，只会让手机静默少一页，因此**不能指望「中继会拦住」来替代本机自己守预算**。把中继的阈值调大也不解决问题（弱网手机照样撞），只会把丢弃点往后推。

## 未落地与待决

以下部分**尚未实现或尚未验证**，本节只记录状态，不代表已交付的能力：

- **中继服务本身**：会话中继、设备登记表、Web Push 的触发都在另一个仓库（内部 GitLab codechat 的 `#40`），本仓库不含其实现；本规格只约束本机侧与它交互的最小契约（登记 REST、订阅 URL 形态、控制帧与回程控制帧、信封逐字透传），跨仓细节以对方仓库为准，这里不复制其 schema。
- **Web Push 推送**：Web 端订阅/注销与「添加到主屏幕」引导均未实现（页面产物里没有任何 push 代码）。本机已上报的 `requires_action` 状态信号正是为它准备的输入，但目前没有消费者。
- **Web 端到端**：**电脑侧与真中继的联调已实测通过**（登记拿 hostId/hostToken → 订阅 → `auth_ok` → 会话列表 → 审批往返 → 状态信号 → 重连与版本门槛）；**页面侧也已改到本规格描述的形状**（地址同源推导、企业端登录态作凭证、`auth` 帧带顶层 `version`、回程五个控制帧逐种消化、应用层心跳、出站队列闸在 `auth_ok` 之后），并在对着桩 WebSocket 的用例里逐条断言过（地址推导、第一帧必须是 `auth`、握手前的出站闸门、登录态缺失的跳转与不跳转、登录态过期时的静默续期——续期成功不导航、失败才跳、每次会话只试一次、令牌仍有效时不发多余请求、跨会话帧过滤、进程内会话列表与本地切换）。**仍未做的是「真中继 + 真浏览器」那一次**：两端各自都对着契约对齐了，但页面还没对着真中继跑过完整链路（会话列表 → 审批往返），这一步留到测试环境的人工验证里一并覆盖（页面侧的静默续期同样只对着桩 `fetch` 断言过，还没打过企业端真的 `POST /api/auth/refresh`）。页面侧已有「CLI 版本过旧」的明确提示（中继在 `host_version_unsupported` 回执里带上 `minVersion`，页面渲染为「请升级电脑侧 wave」）；但**中继侧的版本地板要覆盖本规格这一轮的新依赖**——页面现在要 `listDaemonSessions`，而老机器的远端白名单只放行 `listSessions`，地板没跟上时老机器会落到「读不到电脑侧的会话列表」的横幅上（不是静默空白，但仍应被版本门提前挡住）。此外，**收端仍在返回并保留** `pairingCode` / `pairingUrl` / `pairingExpiresAt` 与 `POST /api/relay/pairings/{code}/claim` —— 本机改成自造页面地址后不再读它们（本规格已无配对码），这套字段与接口可以下线，要在收端另行处理。**手机视口适配（Web 页故事场景 14）在本机也无法验证**：无头浏览器里既没有会伸缩的工具栏、也没有安全区，「页面比可视区高」这一条在本机复现不出来——只有在 iPhone Safari（标签页）与「添加到主屏幕」两种形态下打开才能确认它的实际效果。
- **企业端登录页的站内回跳**：需要收端（codechat `frontend-enterprise`）在登录页与 SSO 回调上支持一个**站内回跳参数**——密码登录与 SSO 两条路都要，且 SSO 要跨一次外部 IdP 往返，所以回跳目标得先落 `sessionStorage` 扛过那一次跳转（现有 `callback_url` 已经这么做，可照搬形状）。本仓库侧只负责在登录态不可用时带上这个参数；参数名与校验逻辑归收端，本规格只约定「只接受同源站内路径」这一条。
- **页面产物的打包与分发**：本仓库侧已就绪——`pnpm -F wave-webview pack:remote` 构建页面并把 `remote/dist` 里的产物（`index.html` + `chat`/`shim` 两个哈希命名的 JS 与 `chat` 哈希命名的 CSS，加上按需拉取的 `mermaid` 哈希 JS，共五个文件）打成 `remote/dist/remote-page.zip`，**根含 `index.html`**，即运营平台上传接口（`POST /api/ops/remote-page/upload`，管理员权限）吃的形状。入口 HTML 只留骨架（约 1 KB），样式与脚本全部走哈希命名：这样入口重校验时不必捎带没变过的 CSS，而未变的资源可长期缓存（入口 `index.html` 走 `no-cache`，哈希资源可走 `immutable`）。**另一半（上传 + 托管）也已接通**：zip 由运营平台上传接口收下、由企业端在 `<服务端地址>/remote/` 托管并配好缓存策略——上传本身是运营平台侧的管理员动作、落的是线上对象，不在本仓库。托管就位之后，页面**不再需要任何地址配置**：它部署在中继同源，地址自行推导（见边界情况），此前「本机/中继地址经页面配置或 URL 参数指定」的说法随之作废。
- **状态行展示**：把连接状态与「待审批数」显示在状态行（第二行）未实现。
- **Web 端的会话列表与切换**：**已按本规格落地**（机器侧：白名单加 `listDaemonSessions`，并给它补 `customTitle` / `firstMessage` / `lastActiveAt`；shim：改用进程内活会话列表并按 `lastActiveAt` 倒序、切换只在本地改 `sessionId` 与视图、按信封 `sessionId` 过滤通知、同时认 `messagesChange` 与 `messagesChanged` 两种写法、列表拉不到时给出横幅；webview：手机页隐藏「新建对话 / 历史对话」并给出顶栏「会话」入口）。用例见 `packages/webview/tests/remote/shim.test.ts` 与 `packages/webview/tests/webview/remotePageSessionSwitch.test.tsx`。**未做的**：真机（真中继 + 真浏览器）联调，以及让电脑侧生成的页面地址带上 `?session=` —— 该参数目前只在地址里手工带上时生效（pin 一条活会话），电脑侧拼地址时还没有「默认选中我正看着的那条」这个语义。
- **「上滑翻更早」**：**口径已于 2026-10-14 改为要做**（原来是「首期不做」，见 Web 页故事场景 12 / 13）。宿主侧的「取更早一页」参数（`before`）早已就绪，缺的是**调用方与页面 UI**。**本机侧已于 2026-10-14 实现**：四端共享的 `MessageList` 补上了上滑分页（四个接触点——新消息判据改尾锚定、视口锚定、登记程序化滚动、窗口外跳转受限），并加了一条上行命令 `loadOlderMessages`——它只登记在页面产物 shim 这第五个面上（本机 IDE / 桌面客户端永远不会发它），由 `audit:commands` 校验。**仍未做过的是「真中继 + 真浏览器」那一次**：本机侧的单测与 jsdom 测试都对着桩跑，真链路要留到测试环境的人工验证里覆盖。
- **同一台机器两个服务方**：通道键是设备级的（本机只有一份 `~/.wave/remote-control.json`），所以「daemon / GUI 子进程」与「前台 TUI」同时开启时，会出现同一个 hostId 的两条出站连接。中继对这种互斥的实际行为（谁掉线、是否真的互斥、能否并存）**尚未核对**，因此本规格只钉一条不变量：不得有两个进程同时以为自己在线（见前台 CLI 故事第 8 条）。具体取舍——后开的接管、还是明确拒绝并要求先关掉先开的那一个——留到与该契约核对之后再定。
