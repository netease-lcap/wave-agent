# 功能规格说明：远程控制（手机控制面）

**创建日期**：2026-10-13

## 概述

远程控制把「本机正在跑的会话」开放给手机：手机只当**控制面**——看会话列表与消息流、审批等待确认的工具调用、派发消息与中断，也能在这台机器上**发起新会话**（选定目录、分支、是否用 worktree，见「Web 端也能发起新会话」故事）；agent 与工具执行始终留在用户自己的电脑上，手机上不跑任何代码。手机不做原生 App，客户端是一张网页（可「添加到主屏幕」）。

连接方向的根因是**手机连不到电脑**（电脑没有公网地址、也不做端口转发）⇒ 由**持有会话的那个 wave 进程主动向中继服务拨出一条出站 WebSocket**，订阅自己这台机器的通道；手机经中继说话。因此通道是**设备级**（一条长连承载该进程上的全部会话，`sessionId` 只作信封字段），不是每会话一条。通道键（hostId）**由本机按机器级稳定标识派生、随登记请求提交**：本机首次启用时向中继登记（`POST /api/relay/hosts`，请求体带上这个 id），把响应里的 `host.id` 与长期令牌一起持久化到 `~/.wave/remote-control.json`，此后每次启动只读本地、不再登记。中继按「本账号 + 该 id」**幂等**处理这条登记：命中已有行就复用它并重新签发令牌，于是本地状态丢失后重新登记也只是把同一行认回来、不再多出一行（见「机器身份稳定」故事）。它不取主机名——机器标识与主机名是两回事；中继的通道归属仍以登记行为唯一权威，库里没有行的 id 会让两端握手直接 4003。

**谁在服务、谁在开关**：服务能力只由**持有会话的进程**提供——常驻的 `wave --daemon`、某个 GUI 宿主（desktop / VS Code / JetBrains）自己拉起的 `wave --stdio` 子进程，或**用户正坐在前面的那个交互式 CLI（TUI）进程本身**（前台会话只活在这个进程里，没有任何别的进程能替它服务）。所以同一个用户可能同时有多条出站连接，手机看到的是**被指着的那一个进程**的会话集合；这一点是刻意的，不跨进程汇聚。该能力默认关闭，由设置键 `enableRemoteControl` 控制（见「开关语义」故事）。开启是**两层**的：开关说「本机**可以**服务」，`wave remote-control on` / GUI 设置页「远程控制」项里的开启动作才是**真的拨号**。开关只在该进程启动时读一次，改设置后要重启进程（`wave daemon restart`）才生效。

**跨仓库分工**：中继服务（会话中继 + 设备登记 + Web Push）不在本仓库，实现在内部 GitLab 的 codechat 仓库（跟踪单 `vusion/codechat#40`）。本规格只约定本机侧与它交互的那一小块契约，**不复制中继自己的 schema**：

- **登记**（一次性 REST）：`POST /api/relay/hosts`（企业成员令牌，请求体带本机派生的 `id`）→ `host.id` / `hostToken`（`rch_` 前缀，长期、可吊销）。中继按「本账号 + `id`」幂等复用同一行；请求不带 `id` 时维持今天的行为（中继生成随机 id、每次调用新增一行），响应里的 `host.id` 就是最终身份（见「机器身份稳定」故事）。**没有配对码**：页面地址由本机按自己的通道键拼出来（见「没有配对码」那条边界情况）。
- **订阅**：`wss://<中继>/v1/hosts/ws/{hostId}/subscribe`。
- **控制帧**：本机上行 `{type:"auth"|"ping"|"host_state"}`，中继下行 `{type:"auth_ok"|"auth_error"|"peer_disconnected"|"resync_required"|"pong"}`。判定是结构性的——「合法 JSON 对象 + 有顶层 `type` + **不带 `jsonrpc`**」；控制帧永不被转发。
- **业务信封**：其余一切（含带 `jsonrpc` 的 JSON-RPC 信封）逐字透传，中继不解析、不落内容。

**覆盖范围**：这是**跨宿主**规格。CLI 侧有两个入口：`wave remote-control [on|off|status] [name]` 子命令组（作用于 daemon 上常驻的会话，可脚本化、可无人值守），以及交互式 TUI 内的 `/remote-control` 斜杠命令（作用于**你手上这条前台会话**，见「用户故事：前台 CLI 会话也能被手机接管」）；desktop / VS Code / JetBrains 侧的入口是聊天输入框里的 `/remote-control`（打开设置页的「远程控制」项，三端共用同一份 webview UI，各自路由到自己的子进程）；Web 页是本仓库产出的**第五种宿主**（同一份 webview 产物 + 浏览器 shim）。

## 用户场景与测试 _（必填）_

### 用户故事：在本机开启远程控制并连接手机（优先级：P0）

作为在电脑前工作的用户，我希望一条命令就把本机连上中继并拿到一个可扫的页面地址，以便用手机接管这台机器上的会话。

**为什么是这个优先级**：这是手机唯一的入场券——没有地址，手机不知道去哪台机器；没有登录态，它也不知道自己凭什么说话（页面复用企业端登录态，没有第二套账号）。开关打开但没人拨号时，本机什么也不做（开关只是「可以服务」，不是「已在服务」）。

**独立测试**：在已登录且开关打开的本机运行 `wave remote-control on`，能打印页面地址与可扫的二维码；再次运行得到同一个地址（幂等）；把开关关掉后运行同一命令，得到退出码 1 与指向设置键的提示。

**验收场景**：

1. **假设** 开关已打开且本机已登录、daemon 在运行，**当** 用户运行 `wave remote-control on` 时，**则** 本机向中继发起出站连接，并打印**页面地址与可扫的二维码**，退出码 0。页面地址是**本机按自己的通道键拼出来的**（`<服务端地址>/remote/?host=<hostId>`），不依赖中继在响应里带回什么——通道键是这台机器自己的身份，地址也就该由它自己拼。
2. **假设** daemon 尚未运行，**当** 用户运行 `wave remote-control on` 时，**则** 命令按需拉起 daemon 再执行（语义与 `wave daemon` 子命令组一致），而不是报「连不上」。
3. **假设** 本机已经处于已连接状态，**当** 用户再次运行 `wave remote-control on` 时，**则** 命令是幂等的——不建立第二条连接、也不重新登记（登记是「本地没有身份时才发生」的一次性动作，本地状态在就一直复用），而是重新读回本机自己的通道键并打印同一个页面地址。
4. **假设** 连接因未登录、中继地址无法解析、登记失败（超时 / 无企业上下文 / 非已激活成员）或被中继拒绝凭证（4003）而失败，**当** 用户运行 `on` 时，**则** 命令打印失败原因、以及指向 `enableRemoteControl` 的修复提示（含「已运行的 daemon 要重启才换设置」），退出码 1；其中「不是企业成员」与「不是已激活成员」要给出不同措辞的下一步动作。登记超时**就是失败**——拿不到通道键就没有可连的东西，不再有「连接已建立、只是码没拿到」这种半成功。
5. **假设** 用户运行 `wave remote-control on my-laptop`，**当** 手机侧列出这台账户下的机器时，**则** `my-laptop` 作为本机的标签随**登记**请求（`POST /api/relay/hosts`）上报并存进中继的机器行里，用于区分同账户下的多台电脑。

### 用户故事：关闭与查询远程控制（优先级：P0）

作为用户，我希望随时能查当前状态、也能一句话收回手机的访问权，以便确认手机还能不能看，并且不必相信「我记得我开过」。

**为什么是这个优先级**：开得起来就必须收得回去——「关」是安全底线，而「查」是用户判断自己是否暴露在外的唯一手段。「关」的实现口径是不撒谎也不制造副作用：没有东西可关时不拉起 daemon、也不假装关过。

**独立测试**：对已连接的机器运行 `wave remote-control status` 能看到连接状态与地址，运行 `off` 后状态变为未开启；在 daemon 未运行时运行 `off`/`status` 不拉起 daemon 且退出码 0；开关关闭时的读状态失败要给出退出码 1 与修复提示。

**验收场景**：

1. **假设** 本机已连接，**当** 用户运行 `wave remote-control off` 时，**则** 本机断开中继连接、打印「远程控制已断开」，退出码 0。
2. **假设** daemon 根本没有运行，**当** 用户运行 `off` 时，**则** 命令打印「远程控制未开启（wave daemon 未运行）」并以退出码 0 结束，且**不**借此拉起 daemon（与 `wave daemon stop` 同一口径）。
3. **假设** 本机进程里压根没有中继（开关是关的），**当** 用户运行 `off` 时，**则** 命令按「用户要的终态已经达成」处理：打印已关闭并附上原因、把开关提示写到 stderr，退出码 0。
4. **假设** 本机已连接，**当** 用户运行 `wave remote-control status` 时，**则** 命令打印当前状态（`off` / `connecting` / `online` / `error`），有页面地址时一并打印。
5. **假设** daemon 未运行，**当** 用户运行 `status` 时，**则** 命令打印「状态：未开启（wave daemon 未运行）」，退出码 0。
6. **假设** 状态读不出来（例如 daemon 是更旧的构建、不认识这个 RPC），**当** 用户运行 `status` 时，**则** 命令打印失败原因与开关提示、退出码 1——「读不到」不等于「已关闭」。
7. **假设** 用户不带任何参数运行 `wave remote-control`，**当** 命令解析参数时，**则** 它等价于 `status`；给出未知 action 时打印用法并以退出码 1 结束，不落到交互式 TUI。

### 用户故事：`/remote-control` 打开设置页的远程控制选项卡（优先级：P0）

作为 desktop / VS Code / JetBrains 的用户，我希望在聊天输入框里输入 `/remote-control` 就能开关并看到页面地址，以便不必切到终端敲另一条命令；这一项和 MCP 服务一样住在设置页里，不另开一个弹窗。

**为什么是这个优先级**：GUI 用户本来就在聊天界面里工作，把开启入口放到他们眼前的那个界面上，是「默认关闭」这个保守取值能成立的前提——否则关掉的开关等于没有入口。**为什么是设置页里的一项而不是弹窗**（2026-10-17 拍板）：它和「MCP 服务」「项目设置」同属「这台机器上的一项能力」，一个自己管自己的浮层要多带一套关闭语义（点外面关、Escape 关、与其它弹窗互斥），而设置页已经有返回按钮、有导航、有聚焦管理。搬进去之后**只有承载位置变了**：查询/轮询节奏、回执过滤、二维码与地址、失败文案全部逐条不变（见下面场景 2–7），入口仍是同一条命令。

**独立测试**：在任一 GUI 宿主输入 `/remote-control`（不被发给模型）→ 设置页打开并选中「远程控制」→ 能显示未开启状态、能点击开启并回显状态、能显示页面地址与可扫的二维码；手动从导航点进同一项得到同一页；开关关闭时显示明确的读取失败原因而不是一个假的默认状态；切到别的导航项后不再每秒查询。

**验收场景**：

1. **假设** 用户在任一 GUI 宿主的输入框里输入 `/remote-control` 并回车，**则** 这条文本不被发给模型、不进入会话历史，而是**打开设置页并选中「远程控制」项**（desktop 为整页替换会话区，IDE 宿主为宿主另开的设置标签页）；该命令也出现在斜杠命令列表的「系统指令」分组里，可直接点选。该项位于左导航「通用」组的第三位（全局设置 / 个性化 / **远程控制**），手动点击进的是同一页、同一份视图。
2. **假设** 该选项卡被选中，**则** 它立即向本端进程查询一次状态，并在此后每秒重查一次（宿主到 CLI 只有请求/应答这一个通道，没有状态推送），状态按「未开启 / 连接中… / 已连接 / 出错」呈现。**只在这一项被选中时轮询**：切到别的导航项即卸载、即停止（与弹窗时代「关掉就停」等价）。
3. **假设** 当前状态是未开启或出错，**则** 主按钮是「开启远程控制」；其余状态主按钮是「断开」；点击后对应的连接/断开结果在同一视图内回显。
4. **假设** 已连接，**则** 视图显示页面地址（可点「在浏览器中打开」交给系统浏览器），并**画出一个可扫的二维码**——内容就是那个页面地址本身（地址里带着本机的通道键）。地址由**持有会话的那个进程**拼出来（它手上有通道键，也知道服务端地址）随状态一起交给视图，视图只负责显示；二维码与终端命令打印的是同一个地址。因此 GUI 这边**总是画得出**二维码——没有「等中继带回地址」这一说，也就没有「没带回所以不画」的回退。**二维码必须保持库自己的白底**（深色主题下换成主题色就是反相码，扫不出来——实测 `jsQR` 的常规通道在反相版本上失败）。**Web 页自己不显示二维码**——它是被扫码打开的那一方，不是扫码的一方（PC 浏览器直接打开同一个地址也一样，不需要再扫一次）；页面上这一项也**不出现**（场景 24）。
5. **假设** 视图开着、每秒一次的轮询让多个请求同时在飞，**则** 只有**最新一次请求**的回执会被渲染——迟到的旧回执（例如晚一秒到达的「未开启」）不得把用户刚建立的连接改回去。
6. **假设** 宿主侧读取失败（开关关闭 / 会话尚未就绪 / 对端不认识该 RPC），**则** 视图显示「无法读取状态」与原因原文，并给出开关提示；**不得** 伪造一个默认快照充数。
7. **假设** 用户切换到别的导航项或按返回离开设置页，**则** 停掉这条每秒一次的状态查询、不触发「中断生成」——切走与弹窗时代的「关掉弹窗」同义。（搬进设置页后不再有「按 Escape 只关弹窗」这条：Escape 不属于这一项，它是设置页整体的键位。）
8. **假设** 桌面端同时开着多个 pane，**则** 这一项作用于**当前 pane 自己的** `wave --stdio` 子进程（每端各自持有一条出站连接），不影响其它 pane 或其它进程。设置页本身按 pane 布局挂在根实例上（pane 内的斜杠命令经 `onOpenSettingsFromPane` 委派，与 `/config` 同一条路）。**IDE 宿主那条路不一样但结论相同**：设置 tab 是**独立于任何会话**的（不能靠「本 tab 的会话」去问），而远程控制本来就是**进程级**的（`remoteControl*` 在 CLI 里由进程的控制器应答、不看 sessionId），设置 tab 又与聊天会话共用**同一个** `wave --stdio` 子进程——所以这里问到的就是本窗口那个进程，它正是「你在这台电脑的这个窗口里能看到的会话」的持有者；与聊天路由同一份实现，差别只在回包发给设置面板本身。**判据**：只要进程没开 `enableRemoteControl`，两条路给出的是同一句原因原文（场景 6）。

### 用户故事：开关语义——默认关闭、显式开启、进程启动时定型（优先级：P0）

作为用户与管理员，我希望「本机能不能被手机接管」默认是不行的、且只有显式打开才可能联网，以便这条件事永远是有意为之，而不是默认后果。

**为什么是这个优先级**：打开它意味着把「正在等待确认的工具调用」暴露到本机之外，并与一个外部服务保持长连；这类能力的默认值只能是关，且判定必须可被企业侧统一收口。

**独立测试**：在不配置任何开关的机器上运行 `wave remote-control status`（或 GUI 设置页的「远程控制」项），得到「未开启 / 需设置 `enableRemoteControl`」的明确结果，且本机不做任何出站连接；写 `~/.wave/settings.json` 打开后重启进程，能力可用但仍需显式拨号。

**验收场景**：

1. **假设** `enableRemoteControl` 在用户级设置、项目级设置与远端托管设置里都没有配置，**则** 本机不具备服务能力：不建立任何中继连接，`remoteControlStatus` / `remoteControlConnect` / `remoteControlDisconnect` 三个 RPC 一律失败，错误信息指出要打开哪个设置键。
2. **假设** 用户在 `~/.wave/settings.json` 里写入 `"enableRemoteControl": true` 并重启进程，**则** 本机**具备**服务能力，但仍不自动联网——要等用户执行 `wave remote-control on` 或在设置页的「远程控制」项里点「开启远程控制」才拨号。
3. **假设** 企业侧经远端托管设置（`GET /api/wave/settings`）显式下发了该键，**则** 它优先于本地设置与代码默认值。
4. **假设** 进程启动时开关是关的、之后用户改了设置文件，**则** 已在运行的进程保持旧答案（开关只在进程启动时读一次），失败提示必须引导用户重启 daemon 而不是让用户反复改文件。
5. **假设** 设置文件损坏或读不到，**则** 判定按「关」处理——既不按开、也不让读设置这件事把进程带崩（判定发生在准备开网络监听的位置，坏设置必须读成「关」）。
6. **假设** GUI 宿主（desktop / VS Code / JetBrains）拉起自己的 `--stdio` 子进程，**则** 该子进程以**它自己的工作目录**判定开关：用户级 `~/.wave/settings.json` 总是被读到，项目级 `.wave/settings.json` 只在子进程恰好从该项目目录启动时才参与合并。

### 用户故事：远端通道只开一个白名单、且不把全量内容推给手机（优先级：P1）

作为用户与管理员，我希望手机只能问聊天与审批相关的那几个方法，并且长会话不会因为「手机在旁边」而把 MB 级全量帧推给中继，以便同时控制暴露面与流量成本。

**为什么是 P1**：本地传输一直是什么都能调——那是用户自己的机器跟自己说话；手机是一张持有令牌的网页，暴露面必须显式收窄。这条不改也能跑通审批闭环，但它决定这个功能能不能长期开着。

**独立测试**：对已连接的中继路径发一个白名单外的方法，得到明确的「Method not available over remote control」拒绝；对一个≥1000 条消息的会话，远端路径看不到 MB 级全量帧，只有「列表变了」的信号 + 按 `since` 的增量拉取。

**验收场景**：

1. **假设** 手机发来白名单内的方法（`listSessions` / `listDaemonSessions` / `getSessionInfo` / `getMessages` / `listPendingPermissions` / `permissionResponse` / `sendMessage` / `abortMessage` / `setPermissionMode`，以及后续两条故事放行的会话维护、建新会话与第二批方法——**完整名单以 `remoteControlService.ts` 的 `REMOTE_ALLOWED_METHODS` 为准**），**则** 请求照常经 bridge 执行并把结果回执给手机。其中 `listDaemonSessions` 是手机列会话的主数据源：它报的是**该进程内存里的活会话**（`sessionId` / `workingDirectory` / `isLoading` / 消息数），而 `listSessions` 读的是磁盘上的 jsonl、会把早已结束或本进程从未载入的会话也列出来 —— 那些条目在手机上打不开（见边界情况），所以它只留作兼容、不做手机列表的数据源。回执是**带 `method` 的 JSON-RPC 信封**——成功 `{id, method:"result", params:{result}}`、失败 `{id, method:"error", params:{code, message}}`，**不是**裸的 `{id, result}`：页面侧必须按这个形状取结果与错误（把结果读成顶层 `result` 字段会让每一份回执都变成 `undefined`，于是会话列表恒为空、「没有更早的消息」恒为真，而失败一声不吭）。
2. **假设** 手机发来白名单外的方法，**则** 回明确错误（`-32601`「Method not available over remote control: &lt;method&gt;」），不执行、不静默丢弃。
3. **假设** 某会话发生结构变化（新消息、消息被丢弃、清空 / rewind、会话 re-attach），**则** 发往中继的那一路只发一条**不含内容**的「列表变了」信号，内容由手机按 `since` 自己拉；本机侧的桌面 / IDE 客户端收到的也是**同一个不含内容的信号**——它们不消费它的载荷，restore 后用自己的 `getMessages` 兜底（2026-10-18 收成一种形态：本机侧原发全量数组，但零消费者，且长会话可达 MB 级的构造与序列化是中继路径上的纯成本）。
4. **假设** 流式输出以每秒几十到上百帧的速率产生增量，**则** 只有**发往中继**的那一路按 150ms 窗口合并累积型增量，合并是**延迟而非抽样**（不丢任何一帧，合并后的帧携带的字节与逐帧发出的一样多）；本地进程内的客户端完全不走这条路径。这个窗口属于**远端通道**而不是某个宿主：窗口挂在「通知扇出 → 中继」这条缝上，因此**每一个**持有会话并拨号的服务方（常驻 daemon / GUI 宿主的 `--stdio` 子进程 / 前台 CLI 进程）都按同一条 150ms 走，手机在哪个宿主上看到的帧率上界都一样（约 1000/150 ≈ 6.7 帧/秒，且窗口是一个进程一个定时器，正文/推理/工具参数三路一起冲刷，不按路数翻倍）。
5. **假设** 发生离散事件（权限请求、工具块结束、状态信号），**则** 它立即写出，并先冲刷已合并的增量，手机不会看到乱序的流。
6. **假设** 某会话正卡在等待审批，**则** 本机上报 `requires_action`；`running` 表示仍有事情在飞（含后台任务，手机没有终端可以瞄一眼，所以「忙」的判据取宽），`idle` 表示空闲。该信号每会话**一个词**、不含任何消息内容，按 250ms 去抖推送，且只在真的变化时才发。上报走**两条**：业务通知 `sessionStatus`（不带顶层 `type`，中继逐字转发给手机，手机 UI 照旧消费）**再加**一条控制帧 `{"type":"host_state","sessionId":"…","state":"…"}`——中继只消费后者来判断「有人正在等审批」并触发 Web Push，因为从业务信封里取状态等于要它解析 body 语义，与「不解析」的前提冲突。
7. **假设** 手机用 `getMessages` 只带 `since`（增量）或只带 `limit`（尾页），**则** 按锚点/分页返回并标注是否还有更早的消息；`since` 指向的消息已被 rewind / clear 截断时返回「锚点已消失」标志，让手机重拉尾页而不是猜；不传任何新参数时，既有调用方的返回与行为逐字节不变。
8. **假设** 手机请求的一页在序列化后超过**单帧字节预算**（默认 512 KiB），**则** 宿主把这页按预算截短（从最早的条目开始丢，保证留下的是**最新**的一段）、仍带 `hasMore` 标志返回，而**不是**把超预算的帧发出去。`limit` 因此只是**条数起点**：条数够小是常态，但**保证一律来自字节预算** —— 因为「一页多少字节」随会话内容（工具输出、diff）而变化，只有字节数是能兑现的承诺。
9. **假设** 手机上的这条会话是由**前台 CLI 进程**（而不是 daemon / GUI 子进程）服务的，**则** 它收到的推送面与另一个宿主**同形**：同方法名、同载荷、同触发点——流式正文 / 推理 / 工具参数走 `assistantContentUpdated` / `assistantReasoningUpdated` / `toolBlockUpdated` 的 `streaming` 增量帧（因此同样落进场景 4 那个 150ms 窗口），结构变化才走不含内容的 `messagesChange` 信号。**不允许**用「监视本机 UI 状态、变一次就推一条信号」来充当这条通道（见「前台 CLI 会话也能被手机接管」场景 10 的实测依据）：那样推送速率不受任何窗口约束，而且因为信号不带内容、手机只能按 `since` 回拉，而同一条流式消息正是手机列表里的最后一条（`since` 是**排他**锚点），页面只能拿到拉取那一刻的片段、之后的增长永远补不回来。

### 用户故事：连接生命周期——重连、背压与断连恢复（优先级：P1）

作为用户，我希望网络抖动、电脑休眠、中继重启之后连接能自己回来，也接受「电脑联系不上时手机不展示历史」，以便不必盯着状态、也不必担心电脑这边被拖垮。

**为什么是 P1**：首版能连上就能跑通闭环，但这些规则决定它能不能长时间挂着——重试策略写错会变成断线后永不回来或无限重试，背压写错会让一台电脑被一个读到一半的手机吃掉内存。

**独立测试**：断开中继后连接能按固定间隔自动重试并恢复；把中继回成 4003 后本机永久停止重连并把原因呈现为错误状态；让手机停止读取，本机在未发送数据超过阈值时断开连接而不是无上限排队。

**验收场景**：

1. **假设** 连接因普通原因断开（中继重启、网络抖动），**则** 本机以 2 秒固定间隔重试、最多 5 次（固定而非指数退避：中继是知名主机而非抖动对端，退避只会拖慢一台刚休眠醒来的笔记本）；期间状态如实呈现为断开/重连中，不静默假死。
2. **假设** 中继以 4001 告知「本机暂不可用」（瞬态），**则** 本机用**独立的、更小的**预算重试 3 次——真实的不可用重试五次也买不到什么。
3. **假设** 中继以 4003 拒绝凭证（永久），**则** 本机立即永久停止重连，并把原因作为错误状态交给上层呈现，不无限重试。
4. **假设** 手机停止读取，导致未发送数据超过 4MB，**则** 本机断开这条连接并告知手机不必重发已缓冲的内容，**不做无上限排队**；手机重连后按 `since` 追赶（与冷启动同一条路径）。
5. **假设** 链路当时是断的，**则** 新产生的通知直接丢弃而不缓冲：手机重连时会用 `since` 补齐，缓冲只会换来一串它马上要丢掉的重放帧。
6. **假设** 连接已建立，**则** 本机每 30 秒发一个**应用层**心跳控制帧 `{"type":"ping"}`（浏览器不能发 WebSocket 控制帧，中继面向的又是手机，所以保活必须长在应用层），中继回 `{"type":"pong"}`，且**两端都不把它转发**——改之前的心跳长得像 JSON-RPC，会被广播给该电脑下全部订阅端。链路层的活性另有一层：中继每 30 秒发 WS 协议层 ping，浏览器与 `ws` 库自动回 pong。
7. **假设** 中继发来回程控制帧（`auth_ok` / `auth_error` / `peer_disconnected` / `resync_required` / `pong`），**则** 本机的中继控制层必须**逐种消化**：`auth_ok` 标记握手完成、`peer_disconnected` 呈现为「电脑已断开」（随后是 4001）、`resync_required` 触发重拉一次快照、`pong` 只是心跳回执；**一个都不许进 agent 桥**——它既不能让手机看到一条凭空多出来的方法调用，也不能被本机当成对端发来的请求去执行。判定是结构性的：「无 `method` 且有顶层 `type`」⇒ 控制层，其余 ⇒ JSON-RPC 层。
8. **假设** 中继以 `auth_error` + `host_version_unsupported` 拒绝本机（`minVersion` 随帧带回），**则** 本机把它当作**永久**失败：状态置为错误并明示「请升级电脑侧 wave（最低 X.Y.Z）」，**不再自动重连**——重试改变不了本机版本。这条也是 `minVersion` 必须从**帧**里读而不是从关闭码里猜的原因：关闭码只分得出瞬态/永久，说不出要升到哪一版。
9. **假设** `--stdio` 子进程的宿主消失了（stdin EOF）或服务器停止，**则** 本机主动断开中继连接，不让中继替一个已经不存在的进程保留订阅。
10. **假设** 本机要发往中继的某帧在序列化后超过**单帧字节预算**（默认 512 KiB），**则** 处置按类别分两种，但都不许把这一帧发出去：读接口返回**按预算截短的页**（见白名单故事的场景 8），通知类降级为**不含内容的「有更新」信号**（`messagesChange` 早已是这条形状）。理由是中继侧两道闸都不站在我们这边：`maxPayload` 默认 4 MiB **越界即 `1009` 关闭连接**，而**订阅者缓冲默认 1 MiB，判定是把 `bufferedAmount + 本帧字节` 与 1 MiB 比较、超了就丢弃该帧并下发 `resync_required`** —— 这条判定的形态意味着**任何超过 1 MiB 的单帧必然被丢，跟手机读得多快无关**。因此有效单帧上限 = 三者的最小值（本机 4 MiB 累积缓冲 / 中继 4 MiB `maxPayload` / **中继 1 MiB 订阅缓冲**），而**预算必须按最小的那个来定**；本机那个 4 MiB 只作最后兜底，不该有机会被用到。
11. **假设** 一条超过一页的长会话在手机上打开，**则** 首屏那一页本身也必须满足上面那条预算（默认页大小按此选取，而不是按「条数看起来够用」选取）——否则首屏帧在中继被丢弃，`since` 补差又因缺少基准而失败，于是每次重连都重演同一个循环。

### 用户故事：Web 页作为第五种宿主（页面产物，优先级：P1）

作为离开电脑的用户，我希望用手机扫一下二维码（或在任意一台设备的浏览器里直接打开这个地址）就能看到正在跑的会话并完成审批，以便不必回到电脑前推进任务。

**为什么是 P1**：页面本身不是目标，审批闭环才是；但它决定了 Web 页能不能用——页面产物是「同一份 webview + 一层浏览器 shim」这一复用策略的交付物，其边界（单会话、只拉尾页、不支持的命令要明说）需要在规格里钉住。

**独立测试**：从企业端部署的页面用带通道键的地址打开，能列出本机会话并显示最后一段消息与待审批请求；在页面上批准后本机继续执行；关掉页面再打开，待审批请求仍在；断开链路之后让本机进入一次待审批，重连时该审批卡（带选项）出现在页面上；页面上 `ExitPlanMode` 的卡片里能读到**计划全文**；消息里的文件路径不再是可点入口（纯文本，Write 块的内容预览仍在）；页面上不出现「看着能点、点了没反应」的入口；**重命名会话 / 压缩上下文 / 斜杠命令菜单**在页面上真的能用；电脑端会话处在非 `default` 档位时，页面上显示的权限档与它一致（不是「修改前询问」）；电脑端这条会话挂着待办清单、正在自动压缩、或有排队未发的消息时，页面（冷启动或重连后）看到的是这些状态的**当前值**——待办清单不为空、「正在压缩对话」指示在场、待发清单不缺条目；电脑端构建比页面旧（`getSessionInfo` 回包缺新字段）时，页面保持现值、不把清单写空。另在手机上打开一次：顶栏与输入区同屏可见、页面本身不产生纵向滚动，两端都不被系统 UI 遮挡；聚焦任一输入框时整页不放大、且页面仍可双指缩放；正文与辅助信息不必捏合即可读；顶栏右侧与输入区左下角的图标按钮不必瞄准即可点中，且相邻两个不会互相误触；同一地址在 PC 浏览器里打开时字号与设计稿一致（文本类控件也不例外）、图标按钮也仍是设计稿尺寸，且本机 IDE 与桌面端的同一份 UI 视觉不变。

**验收场景**：

1. **假设** 用带通道键的地址打开 Web 页，**则** 页面先把「去哪、用什么说」两件补全：中继地址由页面**同源**推导（页面就部署在中继同一个域下的 `/remote/`，`?ws=` 只留给本地调试覆盖），通道键直接取地址里的 `host=`；然后连上订阅地址、以 `{"type":"auth","credential":{"type":"sso","token":"<登录 JWT>"},"version":"…"}` 完成握手（拿到 `role:"subscriber"`）。**这一份 JWT 就是企业端登录态本身**（页面与登录页同源，读的是同一份已存下的令牌），页面不引入第二套账号、也没有单独的登录步骤。**地址里那个通道键不是凭证**：中继在订阅握手时校验「这行 host 属于当前账号、且账号是该企业的活跃成员」，别人的通道键换不来任何东西——所以它可以坦然印在二维码上。
2. **假设** 页面已连上，**则** 首屏先列**本进程内此刻持有的活会话**（主数据源是 `listDaemonSessions`，每条给 `sessionId` / `workingDirectory` / `title` / `lastActiveAt` / `isLoading`，按 `lastActiveAt` 倒序；title 与 lastActiveAt 由机器侧从该会话的显示消息派生），未指定就选**最近活跃**的一条；然后只拉它的**最后一页**（默认 100 条，且整页序列化后不超过单帧字节预算）与待审批请求，并重读一次会话状态（场景 26），以一份完整初始状态回答 webview 的就绪消息（用户、会话、消息、待确认请求、会话状态一次给全）。磁盘上的历史会话不进这个列表，见边界情况。页大小按**预算**定而不是按「条数看起来够用」定：均值 5.7 KB/条时 100 条 ≈ 0.57 MB 已贴着 512 KiB 预算，再往上就跨过中继的订阅缓冲（见连接生命周期故事的场景 10 / 11）。
3. **假设** 中继发来「列表变了」的信号、或页面重新连上，**则** 页面只按本地最后一条消息 id 走 `since` 补差；补不上时（锚点已消失）回落为重拉最后一页。
4. **假设** 本机触发了一次需要审批的工具调用，**则** 页面弹出审批卡（工具名、参数等）；**`ExitPlanMode` 的完整计划内容就渲染在这张卡里**（markdown、独立滚动区、不截断）—— 桌面端把它放在右栏计划面板、IDE 端由宿主另开一个计划标签页，**页面这两处都没有**，所以页面这一处**刻意**用卡片承载（这是与其余各端不同的例外，见 `core/plan-mode.md` 的同名故事与其场景 11）；用户批准或拒绝后以 `permissionResponse` 回执给本机；关掉页面再打开，该待审批请求仍在（**含计划正文**：正文随权限请求的 context 一起来到页面，冷启动快照与断线补读两条路都带）。
5. **假设** 页面渲染的是与桌面 / IDE 相同的那份聊天 UI，**则** 它是**一次看一条**的单会话视图（没有 pane、没有工作目录管理），会话之间用顶栏的「会话」入口切换（见第 10 条）；顶栏**不提供**「历史对话」入口（切换收在「会话」面板），顶栏的「新建对话」图标则**重绑**为「发起新会话」的入口（IDE 端同位同图标，见「Web 端也能发起新会话」故事场景 1；IDE 端那个 `clearChat`——开一条继承旧目录的新会话、不回传新 id——语义不在页面上提供）。并且**不支持**的命令（打开本地文件、打开外链、预览本地图片、上传文件、单独登录/登出等）必须给出明确原因或显式提示，绝不能静默无响应把用户晾在一个灰着的界面上。
6. **假设** 用户点「远程控制」项里的「在浏览器中打开」，**则** Web 页把它列为不支持（页面自己就运行在浏览器里），不产生未处理的动作。
7. **假设** 用户在 Web 页上看或改权限模式，**则** 口径是钉死的：**Web 端默认就提供四档**（含「跳过权限确认」），不设「会话创建时是否已授权」那道门；**默认模式保守** —— 会话初始仍是 `default`，**连接这个动作本身不改模式**；**「不自动继承」指的是连接动作不改模式**，不是「Web 页看不到当前模式」（同一个会话只有一份模式状态）。**模式是状态、不是过渡**：页面必须显示这条会话**当前**的模式，所以冷启动 / 页面重挂（刷新）/ 从列表切到这条会话 / 断线重连 / 回前台这几条路都要把它**重读一次**（`getSessionInfo` 是载体，与适配器推的 `permissionModeChange` 同源；同一次读还带待办清单 / 压缩中 / 命令运行 / 待发队列，见场景 26）。宿主推的 `permissionModeChange` 是**转换通知**——只在页面挂着的那段时间里发生的那次切换才会到——所以只听它的页面会停在自己 reducer 的初始值 `default`：那是这条会话**并没有**的一个权限，用户看到的是一个比实际更保守、却不是实际生效的档位（场景 17 的忙闲、场景 20 的待审批、场景 26 的其余会话状态是同一类缺口）。
8. **假设** 页面手上的**访问令牌**不可用——本地读不到 `token`（这台设备没登录过）、本地令牌已过期（同源存储的 `expiresAt` 已到）、或中继在握手时回了 `invalid_token`——**但**企业端的刷新令牌（同源存储的 `refreshToken`）仍在，**则** 页面**先就地静默续期**：对同源的 `POST /api/auth/refresh` 发一次请求，成功后把新凭证写回存储、用**新令牌**继续原来的连接流程（握手与后续请求都用新的那一个），**全程不发生任何导航**。续期在页内**单飞**（同一时刻只发一个请求，其余调用复用同一份结果）且**每次会话只自动尝试一次**；本地没有 `expiresAt` 时按「令牌仍可用」处理、直接连接，过期与否交给握手说话。这是「每小时被赶去登录一次」与「一个用户看不见的请求」之间的取舍，见边界情况那条耦合清单。
9. **假设** 静默续期没拿到可用凭证——没有刷新令牌、刷新令牌也已失效、响应不合形状（缺 `token`），或请求本身发不出去（网络异常、存储不可用）——**则** 页面才走原来那条路：**自动导航到企业端登录页**，并把**当前页面地址（原样带着 `host=` 等参数）**作为回跳目标一并带上；用户在企业端完成登录（密码与 SSO 两条路都算）后**自动回到这个地址**，页面重新读一次登录态、继续原来的连接流程。回跳目标**只接受同源站内路径**，跨站地址一律拒绝——这是这条路上唯一真实的攻击面（开放重定向）；页面只负责带参数，不解析登录结果，也不接管登录表单。这条路的其余硬约束不变：每次会话只自动跳一次、只在企业端域名上跳（本地调试页照旧只提示）。
10. **假设** 用户点开顶栏的「会话」入口，**则** 页面列出**本进程内此刻持有的活会话**（跨工作目录：每条带自己的 `workingDirectory`，它就是这条会话的身份），当前正在看的那条有选中态；选中另一条后，页面只切**自己**的视图 —— 改本地 `sessionId`、清空消息列表、重拉该会话的尾页、它的待审批请求与会话状态（场景 7 / 26）—— 并且**不调用 `restoreSession`**：电脑端那条会话本身、以及电脑端用户正看着的界面都不受任何影响。**切换只改手机视图，这是「控制面」的含义**。这条切换也**不套用 IDE 那条忙闲守卫**（当前会话正在生成 / 压缩中 / 有正在运行的后台任务）：守卫防的是「**原地**恢复替换当前会话」，而页面上的「恢复」只改自己这份 `sessionId` 与视图，电脑侧那条会话照旧跑着——所以页面上选中另一条会话**始终有效**，不得在忙时被静默忽略（依据与同一口径的「新建对话」入口见「Web 端也能发起新会话」故事场景 10）。
11. **假设** 页面收到一条通知，其信封 `sessionId` 与页面当前会话不同（设备级通道下这是常态：同一进程里别的会话也在产出），**则** 直接丢弃、不落进当前视图；只有信封 `sessionId` 与当前会话一致（或该通知不带 `sessionId`，如状态信号与机器信息）才处理。否则多个会话的消息与流式增量会混进同一个列表。**审批与提问没有例外**：跨会话的 `permissionRequest` 同样丢弃——2026-10-15 收严的一处（此前把它当「进程级事实、用户最不能漏」放行，代价是页面会在当前对话里弹别条对话的卡，见「待确认只在它自己的对话里弹，对话状态在会话列表标出来」故事场景 1；别处等在确认这件事改由会话列表的标记承接）。
12. **假设** 用户把消息列表滚到顶部并继续上拉，**则** 页面以当前最早一条消息的 id 作 `before`、按同一个字节预算取**更早的一页**并 prepend 到列表前面：视口**停在用户原来看到的那条消息**上（不是被新插入的内容顶走），也**不能被判成「来了新消息」而强制贴底**——列表从此不再只从尾部增长，任何「长度变长了就是新消息」的判据在这里都不成立。取不到更早的消息（`hasMore` 为假）时，页面明确说明「没有更早的消息」并停止继续请求，而不是无声地把上拉变成什么都没发生。
13. **假设** 上拉期间链路断开或 `before` 锚点已被 rewind / clear 截断，**则** 本次加载放弃并保持用户当前视口不动（可选提示），**不**回落成「重拉尾页」——那是冷启动与补差路径的动作，用来回答「上拉更早」会把用户看到的位置整段换掉。
14. **假设** 页面在手机上打开（浏览器标签页里，或「添加到主屏幕」之后的独立窗口里），**则** 它必须**整屏装得下**：顶栏与输入区在同一屏内同时可见、页面自身不产生纵向滚动，**顶部与横屏两端**也都不被系统 UI 压住——浏览器工具栏的伸缩（地址栏与底部工具栏的收起 / 展开）与全面屏的安全区（状态栏、灵动岛、横屏时的圆角区）都不得把这两个区域推出可视范围或盖在它们上面；**底部则不再额外让位**：输入区底边就落在可视区底边上（只留输入区自身的常规内边距），不按底部安全区再往上抬一条。**依据**：这是唯一跑在浏览器里的宿主，它的高度由**浏览器的可视区**决定，而不是由承载它的窗口决定；本地四端嵌在没有动态工具栏、也没有安全区的窗口里，这条约束在它们身上恒成立（页面高度与窗口高度逐像素相等）。因此这是 Web 页独有的要求，按宿主收口，不改动其余四端的布局。顶部与底部之所以**不对称**：页面声明了 `black-translucent`，内容画到状态栏底下，顶部不让位就是「顶栏按钮被系统图标压住、点不动」（真机实测）；底部反过来——独立窗口形态下浏览器给出的视口高度本身已经扣掉了底部安全区，再让一条会在输入区下方多出一倍宽的同色空带（真机实测「底部有空白」），而最下面那一条是系统手势保留区、页面本来就画不进去，输入区贴到可视区底边已经在它之上。

15. **假设** 用户在 iPhone 的浏览器里（含「添加到主屏幕」后打开的窗口）聚焦页面上的任一文本类输入控件，**则** 页面**不得被浏览器自动放大**（聚焦前后整页的视觉缩放比不变，`visualViewport.scale` 保持 1），**且**用户仍然可以自行双指缩放页面——**不得以关掉用户缩放为代价**换来前一条。**依据**：iOS Safari 对 computed `font-size` 小于 16px 的文本控件，会在聚焦时把整页缩放到等效 16px 且此后不自动还原（15px 仍触发，16px 起才不触发）。两条路并不等价：**不让页面被缩放**（`maximum-scale=1`）确实能挡住自动放大，但会把用户的手动缩放一并关掉；**把文本控件抬到 16px** 才能两条都要到。他 2026-10-14 先按前者上过真机，用下来判「这一页的字本来就偏小、现在连放大都没得用」不可接受，于是改回后者——**页面上的每一个文本类控件都必须在线（≥16px），不止消息输入区**。这条下限**与上一条同一条判据（触控设备）**：触控设备上文本类控件一律 16px 起，PC 浏览器保持设计稿密度（输入框回落各组件自己的基线）。**依据（2026-10-16 改）**：触发这条的机制是 iOS 的**字号阈值**（15px 仍触发，16px 起才不触发）；Android 的同族机制并不相同——Chrome 聚焦输入框时的放大是**视野补偿**（页面被缩到 zoom < 1 时才把输入框放到约 1.5x 并居中），它的文本膨胀（text inflation）只作用于**未按设备宽度布局**的页面，而本页声明 `width=device-width, initial-scale=1.0`，两条都不成立。也就是说 16px 只对「触控 + iOS」是必需的、理论上可以只给 iOS，但样式里**没有可靠的 iOS 判据**（能区分 Safari 的写法随版本失效，无公认解法），而「主输入是手指」是稳定判据、本页档位组已经在用；反过来「只给 iOS」会让 Android 上的控件掉回组件基线（12/14px），与已抬到 15px 的正文并排比现状更不协调。初版写的是「不按设备开关、宁可一律给足」，他 2026-10-16 在 PC 上打开这一页时报「所有输入控件都是 16px、看着偏大」——同一屏正文只有 13px——据此收进触控媒体查询。该要求**只作用于远控页**：其余四端不跑在移动端浏览器里，不受这条约束，也不该为它改动共享样式。

16. **假设** 用户用**触控设备**（手机或平板）打开远控页，**则** 页面上的文字按**手机档**渲染，而不是沿用插件（IDE）那一档：消息正文与输入区一类阅读主体抬到移动端可读的尺寸，工具与代码块、辅助信息、弹窗与审批卡随之**整体抬一档**（不是只把某一个控件调大——只调一处会让它在整页里显得孤立地大）。**判据是设备能力，不是页面身份**：同一张远控页在 PC 浏览器里也会被打开（它本就能，也常被这么用），那里要保持设计稿的密度；而「主输入是手指、没有悬停」（`pointer: coarse` / `hover: none`）正好是手机与平板的共同点，把两端分开——这也是业界的判据（claude.ai 的共享样式里就有多处 `@media (pointer:coarse), (hover:none)`）。**不用宽度断点代替**：宽度是连续量——手机 320–430、小平板 600–1024、PC 窗口什么宽度都有——「多大算手机」没有自然分界，必须任选一个阈值，而阈值两侧都是误判：PC 上把窗口拉窄会被判成手机（那里原本是设计稿的密度），平板又会被判成桌面。横屏手机是宽度方案会漏掉的又一种，但他 2026-10-14 判「这一页竖着才装得下更多信息，横屏概率很低」，所以这条只作补充、不是选触控的主因。**依据**：同一份 webview 服务五端，字号此前是全站硬编码 px、只有两档（插件高密度 13px / 桌面中密度 14px，后者是 `host-desktop.css` 里 60 余处 `[data-host="desktop"]` 覆写）；远控页落在插件那一档，在手机上正文 12–13px、辅助信息 10–12px，既偏小，又因为上一条不能再靠捏合弥补。业界对「一套代码、两端字号不同」的主流解法是把同一套组件**按宿主/设备选一个密度档**（另一个极端是给移动端另写一套 UI 或原生客户端，Claude Code 手机端走的是那条路）；本页是前者的特例——五端里只有它**一种宿主对应两种设备**，所以它在自己这一档里还要再按设备分一层。具体取值归设计与本档的样式文件（本规格只钉住「触控设备上的文本类控件 ≥16px」这条下限，见上一条，以及下一条边界情况里那条范围）。

17. **假设** 电脑侧这条会话**此刻正在生成**（之后任何时刻，只要不重启就成立），**则** 页面打开后输入区必须呈现**停止**入口，而不是「发送」——**不论页面是什么时候到位的**：冷启动 / 刷新、从列表切到这条会话、断线重连、中继丢帧后的重拉，都算。**依据**：手机上**没有 ESC 键**，页面上的这枚按钮是中断唯一可达的入口（「前台 CLI 会话也能被手机接管」场景 4 已把「手机上能中断」写成硬要求，缺的只是它可达）。宿主推的 `loadingChange` 是**转换通知**——只在页面挂着的那段时间里发生的那次开始/结束才会到——所以「只听通知」的页面必然漏掉它到位之前就已开始的那一轮：**那一整轮都没有停止入口**，用户只能等它跑完。真值在机器的会话注册表里（`listDaemonSessions` 的 `isLoading`，与 `loadingChange` 同源）：页面应在每次重新读取注册表后按它对齐自己呈现的忙闲，而**不是把快照里的忙闲写死成「空闲」**；重连那条路只补消息增量、不带状态，所以它也要单独重读一次注册表。

18. **假设** 用户在手机上发出一条消息（`sendMessage`），**则** 页面**不把「回执有没有按时回来」当成发送是否成功的判据**：这条请求的回执是**整个回合结束时**才回的（桥接层要 `await agent.sendMessage()` 到生成循环走完，而循环会停在一次等人作答的审批上——在手机上作答的往往正是刚发出这条消息的人），而**回合长度没有上界**。因此：(a) **回合级方法单独一档时限**（`sendMessage` 与同样以一次回合级 LLM 调用作答的 `compact`，远长于普通请求的 20 秒）；(b) `sendMessage` 超时且页面已知这条会话**正在生成**（上一条的忙闲口径）时**不呈现为错误**——消息流本身就在证明消息已送达，此时在对话里插一条红字只会让用户以为「没发出去」而重发，机器就多收一条一样的消息；(c) 超时文案不得写成「中继或电脑侧没有响应」——两端都响应了，只是回合还没结束。**依据**：桌面 / IDE 宿主是同进程调用、没有这层超时，所以这条按 Web 页收口，不改共享聊天 UI。
19. **假设** 用户在本页触发**控制指令**（暂停本轮生成 / 切换权限档 / 压缩上下文），**则** 指令的失败**必须有回显**：这三件事的结果都会从消息流自己长出来（忙闲、模式、压缩后的列表），所以成功不需要额外提示，但失败此前被空 `catch` 吞掉——屏幕上什么都没有，而「点了暂停但没反应」在这台设备上无处追问（没有 ESC 键，也没有终端可看）。失败时页面给出可见状态（例如「暂停指令没有回执：…」），不静默。

20. **假设** 链路断过一段（手机锁屏 / 切走、信号抖动，或「电脑侧不在线」的 4001 重试期间）**且** 断开期间本机有工具调用进入待审批，**则** 页面重连成功时必须**重新读取待审批请求**（`listPendingPermissions`）并把页面上还没有的审批卡补上——只补消息增量不够。**依据**：链路断开时本机**主动丢弃**通知（`RemoteControlService` 在无订阅端时不缓冲，理由正是「手机重连会用 `getMessages({ since })` 补齐」），而那句话只对**消息**成立：待审批是一次**进程级事实**（`listPendingPermissions` 报告全部会话的请求，不限于页面正在看的那条——页面只把**属于当前会话**的那些补成卡，其余喂会话列表的「待确认」标记，见「待确认只在它自己的对话里弹，对话状态在会话列表标出来」故事），它不在消息流里，所以断线期间到达的审批在页面上**永远不出现**——列表里只剩那个工具块（工具名与图标），选项一个都渲染不出来（选项只由审批卡渲染），页面看起来像卡住了。**冷启动是另一条路**：首屏快照本就带待审批（场景 2），所以「杀掉 App 重开就有选项」——这正是用户 2026-10-14 报的现象，也是它区别于「页面卡住」的判据。补读与场景 17 同源（重连只补增量、状态要单独重读），并必须**按请求 id 去重**：同一条审批可能先由通知送达、又在这次重读里出现，而页面的 reducer 是**追加**——不去重就会为一次审批出两张卡。用户在页面上作答过的那条若在机器侧**仍待审批**（作答那一帧在断线时丢了，`permissionResponse` 是无回执的通知），下一次重读应当**再次出现**：它确实还没有被处理。

21. **假设** 页面从后台回到前台（`visibilitychange` 变成 visible，或从 bfcache 恢复时的 `pageshow`），**则** 页面必须**重新对齐一次**：补消息增量、重读忙闲（场景 17）、重读待审批（场景 20）、重读权限模式（场景 7）与待办清单 / 压缩中 / 命令运行 / 待发队列（场景 26）——即把「重连成功」那几件事再做一遍。**依据**：页面在后台被冻结期间不会收到任何通知（iOS 直接挂起整个页面，帧也不排队），所以睡过去的那段时间与断线等价：醒来时消息停在旧位置、忙闲可能早已翻转、睡着的过程中到达的审批一张都没有；而这一页此前**没有任何回前台动作**（`visibilitychange` 与 `pageshow` 都不监听），从后台回来是一张静止的旧画面。这四处重读只在链路可用（已完成握手且 socket 是 OPEN）时发起：链路不可用时这些请求只会压在发件箱里、最后以一条**误报**的超时收场，而重连成功那条路（场景 20）本来就会补做同样的事。（场景 26 的状态同走这几处重读，回前台对它们同样生效。）

22. **假设** 本机在计划模式下请求退出（`ExitPlanMode` 待审批），**则** 页面这张审批卡里渲染**计划全文**（markdown、可滚动的独立区域、不截断），并且**两条到达路径都带正文**——实时通知与冷启动/断线补读取回的卡片没有区别（正文随权限请求的 context 一起来，页面不额外去取）；用户只看到卡片就能决定批准还是拒绝。**依据**：计划内容是批准流程的核心信息，而页面**没有**桌面端右栏面板、也**没有** IDE 端那个由宿主另开的计划标签页——不放进卡片，手机上就只能盲批准。
23. **假设** 用户在页面上遇到**文件路径**（消息正文里的路径、工具块头部的路径、Write 工具块里的「打开预览」），**则** 页面**不把它渲染成可点入口**：正文里的路径**退化为纯文本**，工具块头不再可点，Write 块的「打开预览」按钮不渲染——因为页面上没有编辑器可以打开它，留着只会是「点了没反应」。**Write 块的内容预览仍然保留**：那是手机上唯一能读到写入内容的路径。**依据**：同一份 webview 在 IDE 端把这些路径点成 `openFile`（宿主开编辑器），页面点了则只会落进未实现分支、连回执都没有。
24. **假设** 用户浏览页面上的各入口，**则** 凡在页面上**必然无效**的入口都**不渲染**（不出现「看着能点、点了没反应」）。2026-10-17 的第三批解禁之后，**仍属此列**的是：**设置页里的五个管理视图**（插件市场、技能、子代理、钩子、MCP 服务）与插件的安装/卸载流程、**登录与退出登录**、**上传文件**、**点路径打开本地文件**（消息正文里的路径退化为纯文本、工具块头不可点、Write 块的「打开预览」不渲染）、**磁盘历史会话**（`/resume` 与顶栏「历史对话」）、`/plan`、`/btw`、`/reload-plugins`、`/remote-control`（在控制页上是自我指涉），以及 `/status` 弹窗里的「检查更新」（该按钮本就只在桌面端渲染）。**已解禁、不再是「不渲染」**：回滚（`/rewind` 与消息上的回滚按钮）、`/clear`、`/model`、`/tasks` 与 `/workflows`、排队消息的三个动作、`@` 文件建议、历史提示词（见下面的「页面能执行的那批宿主命令」故事），以及**设置页本身**（`/config` 与「更多」菜单的「设置」）的三块视图——全局设置 / 个性化 / 项目设置（见下面的「Web 端也能改设置」故事；那五块管理视图仍不在其中，它们要的是宿主的**界面**能力）。**页面内的 toast 不是宿主转发来的**：宿主那条 `showToast` 仍然不转发，但 shim 会为设置页的保存结果**自己发一条**（成功/失败都要有可见回执，见「Web 端也能改设置」故事场景 6）——所以「页面收不到 toast」这句话只说对了宿主那半边。**企业控制台与帮助文档例外**：它们改成**真链接**（浏览器原生打开，不经宿主），所以保留且可用。**依据**：页面渲染的是 IDE 那份 UI，不做守卫就会把一批宿主专属入口带出来；留在清单里的这些，背后要么是宿主的**界面**能力（开编辑器、装插件、登录流程、管理视图里的目录与配置文件路径），要么只有宿主侧才有意义（磁盘上的历史会话、更新检查），而不是「方法还没接」——那条分界正是第二批与第三批解禁的共同判据。
25. **假设** 用户在页面上**重命名会话**、触发**压缩上下文**、或打开**斜杠命令菜单**，**则** 这三件事在页面上**真的能用**（远端的白名单放行 `renameSession` / `compact` / `getSlashCommands`，宿主侧各自实现），而不是留一条「未实现」的提示。**依据**：这三条与页面已有能力同源（都作用于当前会话、不需要编辑器或文件系统），是「先按隐藏处理」还是「补成能用」的分界；后台任务与工作流不在此列（它们要的是宿主的进程与输出流，本轮仍按场景 24 隐藏）。

26. **假设** 页面在五条重新对齐路径中的任何一条上到位——冷启动 / 从列表切到这条会话 / 断线重连 / 页面重挂（刷新）/ 回前台，**则** 页面上由**会话状态**驱动的呈现都按**当前值**对齐，而不是停在 reducer 初值或只等下一次过渡：**待办清单**（`TaskCreate` / `TaskUpdate` 的任务列表，`TaskList` 挂在输入区上方——它与场景 24 隐藏的 `/tasks` **后台任务弹窗**不是一回事，后者是 `backgroundTasks`）、**压缩中**（「正在压缩对话」指示；压缩不只会由页面自己发起——自动压缩在每次 API 请求前由机器侧触发，页面根本不在场）、**命令运行中**、**待发队列**（场景 24 已把它定为只读清单——只读不等于可以显示成空）与**上下文占用**（输入区的百分比环）。**依据**：与场景 7 / 17 / 20 同一族——首屏快照是唯一一次无过渡的初始化，没写进它的字段就只能靠后续过渡补；「页面到位之前就是那个值」「断线期间变了」「重挂后回到初值」三种情况全都照不到。载体是 `getSessionInfo` 扩的四个字段（`tasks` / `isCompacting` / `isCommandRunning` / `queuedMessages`）：该方法已过远端白名单、两个宿主都已实现，扩字段是增量改动，不动白名单；上下文占用**不新增读路径**——`getMessages` 回包本就带 `contextUsagePercent`，每次（重）拉消息顺手对齐。**版本错配的容忍**：页面比机器新是常态（机器在跑哪份构建，页面管不到）——回包里缺哪个字段就**不写**哪个字段（保持现值），绝不把 `undefined` 落成空清单或「空闲」。

27. **假设** 用户用**触控设备**（手机或平板）打开远控页，**则** 页面上**图标按钮**的点击目标与间距按手指给足，不沿用插件（IDE）那一档按鼠标指针定的尺寸：顶栏右侧的图标按钮族（新建对话 / 会话 / 切换电脑 / 更多）与输入区左下角的图标按钮族（「+」添加、「/」快捷指令）——页面上相邻图标最密、最容易被误触的两处——每个按钮的**点击热区不小于 40×40px**、相邻两个之间的**间距不小于 8px**，图标字形随之抬到 20px（仍然是「按钮带内边距、字形居中」的原有关系，只是两个数各放大一档）。**热区与间距必须同时给足**：只把热区撑大而不动间距，相邻两个按钮的可点区域就会相贴甚至重叠，误触**更**容易发生——用户 2026-10-15 报的正是这一点（「图标有点小，手指点起来很容易碰到其他图标」）。**判据与第 16 条同源**：`pointer: coarse` / `hover: none`（主输入是手指、没有悬停），不是页面身份、也不用宽度断点——同一张远控页在 PC 浏览器里打开时保持设计稿密度，其余四端（IDE 与桌面）的同一份 UI 一个像素都不动。**范围就按这两个族划**（`[data-remote-page]` 作用域内的 `.header-button` 与 `.toolbar-icon-button` 及其按钮容器）：输入区右下角的权限档与发送按钮不在本场景内，它们的目标本就更大、也不与谁紧挨着。**依据**：现状是按钮 22×22、图标 16×16、间距 4px（中心距 26px），这套数是按鼠标指针定的；手指的接触面远大于指针热区，Apple HIG 的最小可点目标是 44pt、Material 是 48dp，26px 的中心距在手指下必然误触。**代价照实说**：顶栏与输入区因此各高一些（顶栏约 45 → 56px），整屏约束（第 14 条）仍须成立——长高的量不能把消息区挤到「顶栏与输入区无法同屏」。

### 用户故事：待确认只在它自己的对话里弹，对话状态在会话列表标出来（优先级：P1）

作为用手机盯着好几条对话的用户，我希望屏幕上弹出的提问 / 审批卡**一定属于我正在看的这条对话**，而「谁在等我确认」「谁还在跑」这两件事在「会话」列表里一眼可见，以便不会在别人的上下文里替它作答、也不会漏掉真正在等我的那条、更不必逐条点进去才知道哪条在跑。

**为什么是这个优先级**：这不是性能或观感问题，而是**归属错误**。现状里 `permissionRequest` 是通知过滤唯一的例外（shim 按信封 `sessionId` 丢掉别的会话的帧，唯独放行审批，依据是「审批是进程级事实、用户最不能漏」），而 `AskUserQuestion` 走的正是这条链路——于是别条对话的提问会落到当前对话里；卡片本身又不带来源（`confirmationOf` 只映射工具名与参数，丢掉请求自带的 `sessionId`），客户端只有「这是本对话在问」这一个解释；再叠加「弹窗只渲染队列第一条」与「`listPendingPermissions` 返回全部会话」，当前对话自己的待确认还可能被别条更早的请求挤到队列后面（用户 2026-10-15 报的就是这个：「有多个对话，非当前对话的 ask user question 弹窗有时候会出现在当前对话里」）。它本来与场景 11「跨会话通知一律丢弃」是同一条口径，开口子的理由（审批不能漏）成立，但**承接方式不该是「混进当前视图」**：标记是「哪里在等我」的正确载体，回答则必须发生在那条对话里。后半（状态标记）是同一件事的另一半——待确认一旦不再进当前视图，**列表就必须接得住**，否则「不会误答」会变成「会漏答」；而列表既然要承载状态，运行中（正在生成）是同性质、同数据源的一条，一并给出才有意义（用户 2026-10-15 追加：「把运行中也标记上，类似桌面端左侧对话列表的效果」）。

**独立测试**：两条对话同时挂着待确认（A 一条工具审批、B 一个 `AskUserQuestion`），另有一条正在生成，页面停在 A——A 弹自己的卡、B 一张都不弹；「会话」列表里 B 带「待确认」标记（A 不重复标：它本来就弹着卡）、正在生成的那条带「运行中」标记（哪怕它就是 A 也照样标）；切到 B 才弹 B 的提问卡；在电脑侧把 B 的请求作答掉，页面（无论停在哪条）下次对齐后该标记消失。

**验收场景**：

1. **假设** 页面正在看会话 A，另一条会话 B 进入待确认（`AskUserQuestion` 或工具审批），**则** B 的卡**不进当前视图**——不弹、也不进待确认队列；A 自己的待确认照旧弹。B 的等待在「会话」列表里以「待确认」标记呈现，**当前正在看的那条不标**（它本来就弹着卡，重复提醒没有增量；与桌面端侧栏「打开后消失」同款取舍）。
2. **假设** 用户从列表切到会话 B，或冷启动就落在 B，**则** 这次重读把 B **自己**的待确认带进来并弹卡——切会话是「这条对话的待确认第一次进入视图」的时刻，与冷启动同一条路，且**不新增读路径**：`listPendingPermissions` 本就报告全部会话、每条带 `sessionId`，页面按该字段筛出属于当前会话的那些弹卡，其余留着喂列表标记。
3. **假设** 同一条对话有多个待确认，**则** 卡按到达顺序弹；队列里不再混进别的对话的请求，于是「弹窗只渲染第一条」这个既有约束不再意味着「当前对话的卡可能被别条挤在看不见的位置」。
4. **假设** 某条对话的待确认在电脑侧（终端 / 桌面端）被作答、或随会话结束消失，**则** 该标记在下一次重读后消失——标记是 `listPendingPermissions` 的**当前事实**、不是历史累积，与场景 20 的补卡共用同一次读。
5. **假设** 某条对话正在生成（进程内这条会话有活 turn / 正在压缩），**则** 它在列表里带「**运行中**」标记，**含当前正在看的那条**——与桌面端「选中的对话也应显示 loading」同款（那里是拍板过的例外），因为「我正在看的这条还在不在跑」同样是列表要回答的问题（页面输入区另有一份忙闲呈现，见场景 17；两者同源、不冲突）。判据是会话注册表 `listDaemonSessions` 的 `isLoading`：与场景 17 的重读同一次，零新增读路径。
6. **假设** 一条对话同时满足「待确认」与「运行中」，**则** 只呈现**一个**标记，优先级 **待确认 > 运行中**（被审批卡住的对话不算「在跑」，它更需要被看见）——与桌面端侧栏的优先级同款。**「已完成未读」（桌面端绿点）不做**：那是宿主的本地已读跟踪（打开即清），页面每次切视图都重读消息，没有「未读」这个语义，照搬只会给出一个永远亮着或永远不亮的点。
7. **假设** 用户看到某条对话带标记，**则** 标记只**指路**：它不替用户切视图、也不自动跳到那条对话（切视图只改手机自己，进那条对话才弹卡，见场景 10 / 场景 2）。**标记本身不发系统通知**——页面内的标记不弹横幅、也不申请通知权限；「别处有东西等你」在锁屏 / 后台时的那条通道是 **Web Push**（见「锁屏也能知道」故事，那里同时规定页面可见时不弹横幅），与桌面端 SSH 后台会话同款口径（见 `desktop-app.md` 的「SSH 远程后台会话」故事）。
8. **假设** 页面在任何一条重对齐路径上到位（冷启动 / 切会话 / 断线重连 / 页面重挂 / 回前台），**则** 两类标记都按**当前值**对齐，与场景 7 / 17 / 20 / 26 同族——待确认与忙闲都是**状态**（进程级事实），不是只发生一次的过渡。数据源就是既有那两次重读（`listPendingPermissions` 与会话注册表 `listDaemonSessions`）：本故事**不加读路径、也不加通知**。

**代价照实说**：手机不再在**页面内**主动把「别处有东西在等你」推到眼前（页面不跳、标记不弹横幅），用户若既不看着页面、也不看会话列表，就等同于不知道那条对话卡着；**锁屏 / 后台那一段由 Web Push 承接**（见「锁屏也能知道」故事），但推送是进程级的、只按「哪个会话在等」送达，不含内容、也不替用户切视图。换来的是**每一次作答都发生在正确的上下文里**。这正是把「不能漏」交给列表标记 + 推送，而不是交给「跨会话也弹一张卡」的原因。

**依据（与场景 11 / 20 的关系）**：本故事把场景 11 那条口径收严到「审批与提问没有例外」，同时保留场景 20 那条**读**的口径（重连 / 回前台要重读待审批，因为它不在消息流里）——读是进程级的，弹是会话级的，两者不矛盾。

### 用户故事：Web 端也能发起新会话（优先级：P2）

作为离开电脑的用户，我希望在 Web 页上直接开一条新会话——选定电脑上的工作目录、（在仓库里时）分支，以及是否放进 worktree——以便「想起新任务」时不必等回到电脑前先在电脑侧把会话建好。

**为什么是这个优先级**：审批闭环与既有故事一条都不依赖它；而它把远端通道的能力面从「接管已存在的会话」扩到「在那台机器的任意目录发起会话并驱动 agent」，是一次真实的扩权。收益真实（发起即不必回电脑），代价也真实（暴露面扩大），所以单独成篇、可以独立不落地。

**为什么服务端几乎现成**：Web 页背后就是它所连的那个 wave 进程的 `AgentBridge`——桌面端在远程主机上新建对话用的那几个 RPC（带 `workdir` 的 `initialize`、`listGitBranches`、`createWorktree`）都在同一个 bridge 上，远端白名单是唯一闸门；主机不可选是天然的（`?host=` 定死设备级通道，页面没有主机维度——这是它与桌面端远程主机唯一的不同，而它不需要任何设计）。真正的新东西只有三样：白名单放行、一个列目录 RPC、页面 UI。

**独立测试**：点顶栏「新建对话」图标打开「新建会话」流程，「浏览…」给出与桌面端远端同形的目录浏览器（面包屑 + 子目录 + 手输），输入 `~` 或相对路径能解析成该机器上的绝对路径并列出其子目录；选定目录创建后，页面切到新会话，电脑端（CLI / 桌面端）能看到这条会话出现在服务进程的会话列表里；在 git 仓库目录下列出分支、可用 worktree 创建；构造带 `apiKey` 的请求被忽略而非生效。

**验收场景**：

1. **假设** 用户想新建会话，**则** 入口就是顶栏的「新建对话」图标——与 IDE 端**同一个按钮位、同一个图标**（远控页复用 IDE 那份 ChatApp，这个按钮此前因语义未定而随「历史对话」一起隐藏）；在 Web 页上它的语义**重绑**为「打开新建会话流程」（下一条）。IDE 端这个图标的底层是 `clearChat` → `clearMessages`——在 agent 内部**换绑一个新 sessionId**（旧会话归档、标题随旧会话丢弃），效果是「开一条**同目录**的新会话」；Web 页上底层换成 `initialize`，原因见第 9 条。「历史对话」仍不提供，切换走「会话」面板。
2. **假设** 用户打开「新建会话」，**则** 目录选择与桌面端**同一套形状**：**最近目录**（去重，来自会话列表既有数据）与**「浏览…」**；「浏览…」打开的目录浏览器与桌面端**远端主机**那个同形——面包屑、单层子目录列表（点击进入）、底部路径输入 + 「选择此目录」（手输住在这里，不是独立入口），数据源从桌面端的宿主命令换成 `listDirectories`（下一条），浏览器组件与桌面端同源可复用。桌面端**本机**的「浏览…」是 OS 目录对话框，浏览器里没有这个能力——远端那套浏览器面板就是 Web 页的对应物，二者不要求同形。无论哪条路，最终都落成**显式的绝对 `workdir`**——不存在「不选目录直接创建」（隐式落到服务进程的工作目录，是桌面端 cwd 漂移的同款老坑）。
3. **假设** 页面要列出某个目录下的子目录，**则** 调用 bridge 的 `listDirectories`（随本故事进白名单）：**这个方法没有主机概念——你连着哪个 wave 进程，就列哪个进程所在机器的目录**（与 `listGitBranches` 完全同形：同一方法名，本机 stdio 与 daemon socket 各自吃自己的 bridge）。`~` 按该机器上服务进程用户的家目录展开，返回 realpath 化的绝对路径与排序后的子目录名；目录不存在或不可读时返回明确错误而不是空列表。桌面端远程主机的目录浏览随之切到同一个 RPC（那条 ssh shell 路径退役），两端吃同一份实现。
4. **假设** 用户提交创建，**则** 页面经远端通道调用 `initialize`（带 `workdir`）拿到新 `sessionId`，随后做的是与「会话」切换**同一套本地动作**：改自己的 `sessionId`、清空列表、重拉尾页与待审批——不引入第二条切换机制。新会话**真实落进当前服务进程的会话注册表**：服务方是 daemon 时电脑端 CLI / 桌面端都能看到它（「Web 端发起、机器落地」）；服务方是某个 GUI 子进程时它出现在那一端的侧栏里——页面指向哪个进程，会话就落在哪个进程，与设备级通道一致。
5. **假设** `initialize` 从远端通道进来，**则** 它的入参在远控入口**收敛**：只放行 `workdir` 与 `permissionMode`（不传即 `default`），其余参数面（`apiKey` / `baseURL` / `model` / `tools` / `plugins` / `mcpServers`…）一律忽略——白名单放行的是「在选定目录建一条会话」这个能力，不是 `initialize` 的整张参数表。
6. **假设** 选定的是一个 git 仓库，**则** 页面给出分支选择（`listGitBranches`）与「在 worktree 中打开」；勾选后按桌面端同形的两步走——`createWorktree` 拿到 worktree 路径，再 `initialize(workdir=该路径)`。非仓库目录下这两个控件不出现（能力不可达），而不是渲染出来再报错。
7. **假设** 新会话的生成触发一次需要审批的工具调用，**则** 审批卡走既有链路到达页面——新会话初始 `default` 档，执行侧的兜底与既有会话无差别。
8. **假设** 有人持有企业端登录态与本机通道键，**则** 本故事意味着他能在这台机器的**任意目录**发起会话并驱动 agent 跑工具——远端通道「只碰已存在会话」的既有语义被**显式**扩大，这份扩大必须随本故事一起被接受（执行侧兜底不变：`default` 档 + 审批链）。
9. **假设** 有人问「底层为什么不直接放行 `clearMessages`——IDE 端的『新建对话』本来就是它」，**则** 答案钉在这里：`clear` 在 agent 内部确实是**换绑新 sessionId**（旧会话归档），效果上就是开一条新会话，但它开的是**继承旧会话工作目录**的新会话（agent 的 `workdir` 在 `initialize` 时定死，`clear` 不碰它）——本故事的核心（选目录 / 分支 / worktree）它一样都给不了；而且它的回执**不携带新 sessionId**（bridge 返回 `null`，IDE 宿主清完也只推空列表），页面要发现新 id 只能靠信封漂移；同进程里电脑端正在看的那个视图随 agent 换绑而漂移，活会话列表里旧 id 原地变成新 id、切换语义跟着乱。`initialize` 四条全无——这就是按钮位可以复用、底层不能复用的完整论证。
10. **假设** 电脑侧这条会话此刻**正在生成**、**正在压缩上下文**，或**存在正在运行的后台任务**（即 IDE 端把「新建对话」置灰的那三种忙闲状态），**当** 用户在页面上点顶栏的「新建对话」时，**则** 这个入口**照常可用**——它打开的「新建会话」流程与创建本身都不受这三种状态影响（不置灰，也不在提交时被忽略）。**依据**：页面上这个按钮不是 IDE 那个 `clearChat`——它是在机器上**另起一条会话**（`initialize`），页面随后只把自己的视图挪过去（场景 4，与「会话」切换同一套本地动作）。那条守卫（`session-management.md` 场景 2 / 6 / 7 与边界情况）防的是「**原地**清空或替换当前会话」——把正在跑的这一轮生成、或正在跑的后台任务中断掉、或让它与 UI 脱离；而页面上这个动作**没有对象可破坏**：电脑侧那条会话继续按自己的节奏跑，新会话与它**并行**（与桌面端多会话并行模型同形，`session-management.md` 边界情况已把那个模型排除在本守卫之外，页面属同一理由）。反过来，按忙闲置灰的代价是实打实的：手机用户在电脑侧一个长回合跑着的时候**完全无法**发起新会话，而「想起新任务时不必等回到电脑前」正是本故事存在的理由。同一口径也适用于顶栏「会话」切换（「Web 页作为第五种宿主」场景 10）。

### 用户故事：页面能执行的那批宿主命令——回滚、清空、模型、后台任务与队列动作（优先级：P1）

作为用手机接管会话的用户，我希望页面上的**回滚、清空、切模型、看后台任务/工作流、改排队消息、`@` 文件搜索、历史提示词**都**真的能用**，而不是被藏起来或者点了没反应；其中**会动电脑侧文件**的那几个（回滚、清空）在手机上执行前必须先问一次，并且说清它到底动了什么。

**为什么是这个优先级**：第一批把「页面能承载的」与「只有宿主才有的」混成了一张清单——回滚、`/clear`、`/model`、`/tasks`、`/workflows`、队列三动作、`@` 建议、历史提示词被一起判成「宿主才持有」，理由是「宿主才持有的数据」。逐条查过之后，这个理由只对其中的**界面**类成立（设置页、插件市场、编辑器、磁盘历史会话）：上面这些的能力都在 `AgentBridge` 上早就实现了，缺的只是**白名单一行 + shim 一个 case + 页面一道远端守卫**。把它们留成「不渲染」，代价是手机上**能看不能改**：回滚要回电脑前按、模型要回电脑前切、后台任务跑了什么要回电脑前看。它不改安全模型（同一个开关、同一份白名单、同一条设备级通道），但确实把远端通道的**写**面从「发消息 / 审批 / 权限档 / 重命名 / 压缩」扩到「按快照还原文件、清空会话、写用户级设置、停后台任务」——所以每条写操作都带明确回执，代价最大的两条（回滚、清空）在页面上各加一次确认。

**独立测试**：在页面上点一条消息的回滚按钮 → 出现确认框（文案写明会撤销**电脑侧工作区**的文件改动）→ 确认后对话截断到那条消息，且电脑侧被后续回合改过的文件回到回滚点的内容；敲 `/rewind` 打开检查点列表并选中一条，走同一个确认；敲 `/clear` 出现确认框，确认后对话清空（电脑侧那条会话换绑新 sessionId）；敲 `/model` 打开模型列表，选中另一个模型 → 确认后电脑侧 `~/.wave/settings.json` 的 `model` 变了；敲 `/tasks` 与 `/workflows` 能打开并看到任务与运行、能停止其中一个；排队消息出现编辑 / 立即发送 / 删除三个动作且都生效；在输入框打 `@` 出现文件建议且能选中；「+ → 历史提示词」能列出历史且能搜索。同一批操作在 IDE 端与桌面端**行为不变**（桌面端仍不拦截 `/clear`，回滚仍不多一次确认）。

**验收场景**：

1. **假设** 页面要执行本批解禁的任一动作，**则** 它背后是**已在 `AgentBridge` 上实现**的方法，白名单只放行这些：`rewindToMessage` / `listRewindCheckpoints`（回滚）、`clearMessages`（清空）、`getConfiguredModels` / `setModel`（模型）、`updateQueuedMessage` / `deleteQueuedMessageById`（队列）、`getBackgroundTaskOutput` / `stopBackgroundTask` / `getWorkflowRuns` / `stopWorkflowRun`（后台任务与工作流）、`searchFiles`（`@` 建议）、`getPromptHistory` / `searchPromptHistory`（历史提示词）。**不新增任何一个协议方法**：本批全部是「已实现但远端不放」，所以放行即生效。**依据**：白名单只该回答「页面能不能承载」，不该回答「宿主有没有实现」；第二批之前这两个问题被混成了一条。

2. **假设** 用户在页面上点某条消息的**回滚按钮**，或敲 `/rewind` 选中一个检查点，**则** 执行前**必须有一次确认**（消息按钮与 `/rewind` 走的是**同一个**确认框，页面不为这两条入口各造一套），且确认文案必须写明**这会同时撤销电脑侧工作区的文件改动**——不是「只删对话」。确认后页面发 `rewindToMessage`，宿主执行完回 `rewindResult {requestId, messageId, ok}`，页面只在 `ok === true` 时**切自己的列表**（回执不携带消息列表）。**语义与桌面 / IDE 完全一致**：`agent.truncateHistory` → `messageManager.truncateHistory` → `reversionManager.revertTo`，即除了截断对话，还会按每条消息携带的 `file_history` 快照**逆序**把本机工作区文件还原（`create` 的删掉、有快照的写回、快照内容为空的删除）——所以「回滚到这条消息之前」在电脑上是一次**文件操作**，这是手机误触代价最高的一个动作，也是它必须确认的理由。

3. **假设** 用户在页面上敲 `/clear`，**则** 执行前同样有一次确认（清空会换绑新 sessionId、跑 SessionEnd/SessionStart hooks，电脑侧那条会话随之换新），确认后发 `clearMessages`。**桌面端行为不变**：桌面端 `/clear` 仍整端不拦截（当普通消息发给模型），本场景只作用于远控页与 IDE 端的既有拦截。

4. **假设** 用户在页面上敲 `/model`，**则** 打开与 IDE / 桌面同一份模型选择 UI（`getConfiguredModels` 拉列表、`setModel` 切换）。**确认文案必须说清作用范围**：`setModel` 落盘的是**用户级全局配置**（`~/.wave/settings.json` 的 `model` 键，写失败时退化为仅当前会话生效），不是这条会话的临时覆盖——在手机上换一次模型，**这台机器上所有会话、以及此后新开的会话**都会跟着换。因此远端切换前给一次确认；桌面 / IDE 不加。

5. **假设** 队列里有待发消息，**则** 三个动作在页面上都可用了：**编辑**（纯本地，把内容装回输入框，提交时才发 `updateQueuedMessage {id, text, images}`，宿主回 `{ok}`，`ok === false` 时页面提示「这条已不存在」）、**删除**（`deleteQueuedMessageById {id}`）、**立即发送**（**没有专门的宿主方法**：就是 `sendMessage {force: true}` + `deleteQueuedMessageById` 两条既有方法，与 IDE / 桌面实现同形——先以 `force` 打断并立即发出这条，再把队列里那条删掉，否则它会再发一遍）。

6. **假设** 用户在页面上敲 `/tasks` 或 `/workflows`，**则** 两个弹窗照常打开并**有真实内容**：任务列表来自会话状态（宿主通知 `backgroundTasksChange` → 页面 `updateBackgroundTasks`，冷启动 / 切会话 / 重连 / 重挂 / 回前台各重读一次 `getSessionInfo`——该回包为此扩一个 `backgroundTasks` 字段，与 `tasks` / `queuedMessages` 同族），工作流运行来自 `getWorkflowRuns`（同一批对齐路径各读一次，与桌面端 `refreshWorkflowRuns` 同源）；`getBackgroundTaskOutput` 按任务读取输出（运行中由弹窗按既有节奏轮询），`stopBackgroundTask` / `stopWorkflowRun` 停止并回执。**停止不要求二次确认**：它杀的是任务进程、不删文件也不动会话，回执（`backgroundTaskStopped` / `workflowRunStopped`）+ 列表随之更新就够。

7. **假设** 用户在输入框里打 `@`，**则** 远端也启用文件建议：`requestFileSuggestions` → `searchFiles {query, maxResults}`，**工作目录由宿主按信封 `sessionId` 取该会话的 workdir**（页面不猜目录，也不用自己那份 `workdir`），回包映射成与桌面端同一个建议形状（`path` / `relativePath` / `name` / `extension` / `isDirectory`）。**依据**：这条此前被关掉的唯一理由是「会发出一个没人应答的请求，下拉永远停在『正在搜索文件…』」——现在有人应答了，那条理由随之消失。

8. **假设** 用户打开「+ → 历史提示词」，**则** 弹窗**真的能列出历史**并能搜索：`requestHistory` → `getPromptHistory`、`searchHistory` → `searchPromptHistory`，回包 `historyResponse {requestId, history}` / `historyError`，页面的过期回执按 `requestId` 丢弃。**这是一条现成 bug 的修复**：入口与请求早就写好了，shim 却没有这两个 case ⇒ 点了以后永远停在加载中，且连告警都没有（`default:` 分支只 `warnOnce`、不回执）。同族的「未实现即无回执」在本批一并收口：shim 对未映射命令的兜底改为**回一条错误给页面**，而不是让界面停在那一步。

9. **假设** 用户碰到的是本批**仍然不做**的项，**则** 它们**照旧不渲染**（清单见「Web 页作为第五种宿主」场景 24）：设置页里的五个管理视图（插件市场 / 技能 / 子代理 / 钩子 / MCP）与插件安装、登录/退出、上传文件、点路径打开本地文件、磁盘历史会话（`/resume`）、`/plan`。（**设置页本身**已由第三批解禁，见「Web 端也能改设置」故事。）**`getWorkspaceDiff` / `getWorktreeChanges` / `getPlanFile` / `getFullMessageThread` 也仍在白名单外**：页面上**没有** diff 面板、计划面板、工作树面板可承载它们——`DiffPane` / `PlanPane` 挂在桌面端的 pane 体系里（`isDesktop` 分支），页面既没有 pane 也没有侧栏，计划正文本来就渲染在 `ExitPlanMode` 的审批卡内（`core/plan-mode.md` 场景 13）。放行它们只会扩大暴露面而没有调用方。**`removeWorktree` 同理不放行**：页面上没有删除会话 / 删除工作树的入口（那是桌面端侧栏的动作，`desktopDeleteSession` 是桌面专有命令），所以「能建不能删」不是白名单漏了一条，而是白名单**跟页面能力一致**。

10. **假设** 手机发的这批方法在**当前宿主上没有实现**（前台 CLI 只接了会话内那一批），**则** 宿主回一个**结构化的「该宿主不支持」**错误（固定错误码，区别于 `-32601` 的「通道不放行」与 `-32603` 的内部错误），页面据此收尾这条请求并给**一句可见文案**（「这台电脑上的会话不支持这个操作：<能力>」）。**依据**：白名单是通道级的（daemon / GUI 子进程 / 前台 CLI 共用一份），三个宿主的实现面不同；把「通道不放行」和「这个宿主没实现」压成同一个错误，页面就分不清该升级、该换个电脑、还是该等实现——而静默不回执会让界面停在那一步。

### 用户故事：Web 端也能改设置——配置、个性化与项目设置（优先级：P1）

作为用手机接管会话的用户，我希望**设置页在页面上真的能开、能改**：AI 回复语言、上下文长度、服务端地址，两份 AGENTS.md（用户级 / 项目级），以及项目内置插件（如 SDD）的开关；被组织配置管理的键显示「由组织配置管理」并置灰，而不是让我以为改了会生效。并且这一页在 **390px 的手机屏幕上真的能用**——不是把桌面那套「240px 左导航 + 右内容」硬塞进手机。插件市场、技能、子代理、钩子、MCP 这些要宿主**界面**能力的视图，以及桌面端本机偏好（主题、接收 Beta 版更新），在这一页上**整项不出现**，而不是渲染出来再置灰。

**为什么是这个优先级**：第二批解禁之后，手机上仍然「能看不能改」的最后一处就是配置——换个回复语言、改个上下文长度、把项目里的 SDD 关掉，都得回电脑前操作。这些能力在 `AgentBridge` 上**早就实现了**（桌面端与 IDE 端都跑同一份 `SettingsPage`、同一对读写方法），缺的只是白名单的一行、shim 的一段合成、页面的一道远端守卫；与第二批同一判据，也与第二批同一张账单：它把远端通道的**写**面从「会话内容」扩到「用户级配置与项目设置」。反过来，那五块管理视图要的是宿主的**界面**能力（目录树、配置文件路径、安装流程），页面上没有承载面——所以是**整项不出现**，而不是「先渲染再置灰」：置灰回答的是「现在不能用」，缺席回答的是「这里没有这件事」，两者的真假不同。

**独立测试**：在页面上敲 `/config`（或从顶栏「更多」菜单点「设置」）→ 设置页整页替换会话区，左导航只有 全局设置 / 个性化 / 项目设置 三项；改「AI 回复语言」→ 点保存 → 页面提示「保存成功」，电脑侧 `~/.wave/settings.json` 的 `language` 确实变了；把该项在远端托管设置里钉住后再打开，该行显示「由组织配置管理」且下拉置灰；切到个性化改 AGENTS.md 并保存，电脑侧文件跟着变；切到项目设置关掉 SDD，电脑侧该项目的插件开关跟着变；把浏览器窗口压到 390px 宽，导航变成一行可横向滑动的胶囊、输入框与按钮占满一行；点「返回」回到会话区。同一页在桌面端与 IDE 端**一个像素都没变**。

**验收场景**：

1. **假设** 用户在页面上敲 `/config` 或从「更多」菜单点「设置」，**则** 设置页**整页替换会话区**（与桌面端同形、就地渲染），左导航只留**全局设置 / 个性化 / 项目设置**三项；`/plugin` `/mcp` `/agents` `/skills` `/hooks` 在页面上**仍按普通消息发给模型**（不拦截、也不打开设置页）——它们要的那五块视图不在页面上。**依据**：IDE 宿主的「宿主另开一个设置标签页」那条命令（`openSettings`）在页面上不存在，请求发给宿主只会落进未实现分支；所以这一页必须自己承载，且只承载它真能用的那三块。

2. **假设** 设置页要读配置，**则** **不新增任何协议方法**：页面发的 `getConfiguration` 由 shim 折成 `getUserSettings`，回包按桌面端 `getConfiguration` 的**同一形状**合成 `configurationResponse`——`configurationData` 里既是**生效值**、也带**每键来源层** `preferenceSources`（`user` / `remote` / `env` / `default`）。来源层是「由组织配置管理」「来自系统环境变量」这两句置灰文案的唯一依据：少了它，被组织配置覆盖的键在手机上看起来可以随便改。模型候选（`getConfiguredModels`）第二批已放行，但补全模型那两行**不在页面上渲染**（见场景 4），所以不新增调用方。

3. **假设** 用户在设置页点保存，**则** 页面发的 `updateConfiguration` 由 shim 折成 `updateUserSettings`，载荷按桌面端 `updateUserPreferences` **逐键对应**（`language` / `contextLength` / `autoMemoryEnabled` / `autoMemoryFrequency` / `serverUrl` / `completionModel`（去首尾空白，空串不写）/ `completionEnabled`）——**不自创键名、也不给页面没发的键补默认值**：省略的键就是「这次不改」，补默认值会把一次「只改了语言」翻译成一次全量写入（例如把系统环境里的 `WAVE_MAX_INPUT_TOKENS` 钉成 200000）。**不改用 `updateConfig`**：那条设置页自 2026-09-10 起就不再使用，页面上能存的每一个键都是用户偏好，`updateUserSettings` 就是全部写路径；放行一个没有调用方的方法只会扩大暴露面。保存成功后 shim **重读一次** `getUserSettings` 再回 `configurationResponse`——回给页面的是**生效视图**而不是乐观值（被组织配置管理的键保存后仍须显示那个事实）。

4. **假设** 用户在页面上浏览设置页，**则** 两类东西**不渲染**：**桌面端本机偏好**（主题、接收 Beta 版更新、检查更新——它们改的是那台电脑的显示与更新通道，从手机上调既看不出效果，也和「页面能改什么」不是一回事）与**补全模型 / 代码补全两行**（它们要一个代码编辑器，页面上补全从不触发）。同理，五块管理视图（插件市场 / 技能 / 子代理 / 钩子 / MCP）在导航里**整项缺席**，对应方法也**不进白名单**（`getMcpServers` / `getSkillConfigurations` / `getSubagentConfigurations` / 钩子读写 / 插件安装卸载等），登录与登出同样不放行。判据与场景 24 同源：**宿主实现了但页面没有承载面 = 不进白名单**。

5. **假设** 用户在**手机上**打开这一页（触控设备、视口宽度 ≤760px），**则** 布局换成**单列**：返回按钮在最上，左导航压成**一行可横向滑动的胶囊**（分组标题收起，所有导航项平铺成一行），内容在下并占满宽度；`.settings-view` 的边距从 40/24 收到 20/16，输入框 / 下拉 / 按钮一律占满一行、点击目标抬到 40px。**760px 以上一个像素都不变**（桌面端、IDE 宿主、以及平板浏览器里打开的远控页仍是「240px 左导航 + 右内容」的两列）——本断点只服务手机。**验收档位：390px（手机竖屏）与 768px（平板 / 横屏折叠）**：前者必须是单列且所有控件可点可填，后者必须还是两列。**依据**：两列布局在 390px 下只剩不到 150px 给内容，任何控件都放不下；而设置页是这五种宿主里唯一会跑在手机浏览器里的一页，桌面与 IDE 的布局不该为它让路。

6. **假设** 保存成功或失败，**则** 页面必须有**可见回执**：成功提示「保存成功」，失败给一句人话（并**复位**「保存中」态，否则保存按钮会一直灰着）。**这条回执由 shim 自己发**：宿主那条 `showToast` 并不转发给页面（场景 24），设置页在页面上也收不到宿主的 toast 通道，所以 shim 在写成功/失败时自己合成一条 toast；AGENTS.md 的保存则无论成败都回一条 `agentsContentSaved` 来复位编辑器的保存态。**写操作不加确认弹窗**：桌面端也没有，保存按钮本身就是那个动作（与回滚 / 清空不同——那两个动的是电脑侧文件与会话本体）。

7. **假设** 本机这个宿主**根本没有实现**这批设置方法（前台 CLI 会话常常只接会话内那一批），**则** 宿主回**结构化的「该宿主不支持」**（`-32011`，见「前台 CLI 会话也能被手机接管」场景 12），页面把它翻成**一句常驻文案**（「这台电脑上的会话不支持读写设置（它没有常驻的 daemon）。换一台运行 daemon 的机器再试。」）并**把可编辑控件整体置灰**——而不是让用户对着一个必然失败的保存按钮反复按，也不是 `-32601` 那句「去升级电脑侧」（那会让用户去升级一台本来就最新的机器）。重新进入设置页时先清掉这个判断，重试一次再说。

8. **假设** 用户从设置页点「返回」，**则** 回到会话区（页面自己的视图，含当前会话、待审批、输入区状态），**不改**电脑侧任何东西；设置页里改过并保存的项已在电脑侧生效（用户级 `settings.json` / 项目 AGENTS.md / 项目插件开关），未保存的编辑不落盘。

### 用户故事：手机端的会话列表与删除（优先级：P1）

作为用手机盯着好几条对话的用户，我希望「会话」是一张**整页的列表**——每条带项目与最近活跃时间、带「谁在跑 / 谁在等我」，还能就地重命名、删除，以便在手机上把这几条对话管理完整，而不是只能在一份挤在顶栏下面的窄下拉里点一行切过去。

**为什么是这个优先级**：列表是手机上**唯一**的会话管理面——这一页没有侧栏、没有右键、没有终端，桌面端侧栏里那些行级动作在这里无处安放。当前那份下拉是**借来的**：它本来是 IDE 端「历史对话」的弹窗（`SessionListPopup`，标题换成了「会话」），只有搜索与点击切换，行级动作一个都没有；删一条会话、或者给一条会话改个名，手机上彻底做不到（改名只能借用顶栏标题的就地编辑，且只对**当前那条**有效）。所以这一篇补的不是「更好看」，而是把「能切」补成「能管」。

**独立测试**：打开远控页点顶栏「会话」→ 出现整页列表（顶部「返回」+ 标题「会话」），最上一个搜索框，每行两行字与右侧「⋯」；输入关键词能筛到对应行；点一行切到该会话并**自动返回对话页**；点「⋯」从底部升起动作面板（重命名 / 删除会话）；选「重命名」后该行标题变成输入框，回车生效、Esc 回滚、清空后回车什么都不发生；选「删除会话」→ 全屏确认卡片，第一句固定是「对话记录仍保留在这台电脑上，可以从桌面端恢复。」；普通会话直接可删；建在 worktree 里的会话先显示「正在检查该 worktree 的改动…」且确认键禁用，计数回来后显示「…将一并删除：N 个未提交文件、M 个未合并提交，删除后不可恢复」，确认键文案变成「删除会话与工作树」；让检查超时（或宿主报错）则降级成泛警告、确认键恢复可用；会话正在回答时卡片上多一行红字「会终止这条会话正在进行的回答」，且不勾选「我知道了」就点不动；删完回到列表、顶部出现一条「已删除」，页面**不**自动跳进别的会话；同一张列表在 IDE 端与桌面端**一个字都没变**（IDE 顶栏「历史对话」仍是那个下拉，桌面侧栏仍是它自己的行菜单）。

**验收场景**：

1. **假设** 用户在远控页点顶栏的「会话」按钮，**则** 打开的是**整页**的「会话」列表（顶部一行「返回」+ 标题「会话」），不再是原先那份从顶栏右上方弹出的下拉。**这一条只对远控页成立**：IDE 端的「历史对话」与桌面端的会话入口/侧栏一个字都不改（同一个 `SessionListPopup` 在 IDE 端照旧以 `variant="dropdown"` 渲染），因为「下拉」在指针设备上是好形态、在手机上才不够用（行级动作、触控热区、整屏滚动都是它给不了的）。

2. **假设** 列表已打开，**则** 最上一个**搜索框**（沿用原下拉的搜索逻辑：按显示标题做大小写不敏感的子串匹配），下面每行**两行字 + 右侧一个「⋯」**：第一行是标题（`customTitle` ?? `firstMessage` ?? id 前缀，与其余四端同一个 `formatSessionLabel`），第二行是「项目目录名 · 最近活跃时间」，第二行前面一个**状态点**——正在生成转圈、有待确认（琥珀点）、有后台任务在跑（蓝点）。**一条只出一个点**，优先级 **待确认 > 运行中 > 有后台任务在跑**（被审批卡住的对话不算「在跑」；后台任务在跑但前台回合已结束的对话仍要标出来，那正是「它还在动」的唯一信号）。排序沿用下拉的口径（`lastActiveAt` 倒序）。

3. **假设** 用户点列表里的某一行，**则** 切到那条会话并**自动返回对话页**——与原先下拉点一行完全同一套本地动作（只改页面自己的 `sessionId` 与视图、不调用 `restoreSession`、不套用 IDE 那条忙闲守卫），见「Web 页作为第五种宿主」场景 10。行内的「⋯」**不触发切换**（它有自己的可点区，点它只开动作面板）。

4. **假设** 用户点某一行的「⋯」，**则** 从底部升起一个**动作面板**（action sheet），两项：`重命名` 与 `删除会话`（红字）。**不做左右滑删除、不做长按菜单**：移动网页里横向滑动与纵向滚动、系统返回手势互相打架，长按与选词冲突；「⋯」稳定、可测、不依赖手势冲突的裁决。

5. **假设** 用户选「重命名」，**则** 该行标题**就地**变成输入框（与桌面侧栏、顶栏标题同一套口令：Enter 或失焦保存、Esc 回滚、trim 后为空则什么都不做），走既有的 `renameSession`（乐观更新 → 按 `requestId` 关联回复 → 失败回滚并给出可见提示）。**不新增任何协议**：shim 早就有这个 case，白名单也早就放行了它。

6. **假设** 用户选「删除会话」，**则** 进入删除流程的第三/第四步：一个**全屏确认卡片**，内容按下面的顺序给全——① 固定一句「**对话记录仍保留在这台电脑上，可以从桌面端恢复。**」（这句话是删除语义的核心：删的是**这台机器上正在跑的这条会话**，不是磁盘上的对话记录）；② **worktree 警告**（复用桌面端 `utils/worktreeDeleteWarning.ts` 的**同一份**文案与流程，见场景 7）；③ 会话**正在回答**（`isLoading` 或 `hasRunningBackgroundWork`）时一行红字「会终止这条会话正在进行的回答」，且**必须勾选「我知道了」确认键才可点**；④ 按钮 `取消` / `删除会话`（这条会话的工作目录是 linked worktree 时改成 `删除会话与工作树`，红色）。

7. **假设** 被删会话的工作目录是一个 **linked git worktree**，**则** 确认卡片上的 worktree 警告走桌面端那条**逐字相同**的流程：先显示「正在检查该 worktree 的改动…」并**禁用确认键**；计数回来后显示「该会话的 worktree 目录与临时分支将一并删除：N 个未提交文件、M 个未合并提交，删除后不可恢复。」（干净工作树按那份文案的既有规则不显示警告，但确认键照常可点）；计数**查不到**（超时 / 宿主失败 / 工作树已经不在）时**降级成泛警告**再放行确认——**不许静默删**（未知不等于干净）。working tree 干净或不是 worktree 时，卡片只有场景 6 那句固定文案。

8. **假设** 用户确认删除，**则** 页面发两条请求的一条：`destroy`（带 `removeWorktree: <这条是否是 worktree>`，按信封 `sessionId` 指向被删的那条）。**不新增协议方法、也不放行裸 `removeWorktree`**——后者收 `path` / `branch` / `repoRoot`，放给手机等于把「删这台机器上任意工作树目录」开出去；改成让 daemon **自己**从该会话的 `createdWorkdir` 定位工作树（与 `wave daemon destroy --remove-worktree` 同一条推导），且**必须排在 `agent.destroy()` 之后**（agent 的 cwd 就在工作树里，先删目录会让保存 transcript 报 ENOENT、丢尾消息——桌面端同一条顺序注释照抄）。**定位不到工作树时**：会话照删、回 `worktreeRemoved: false`，不整体失败。`destroy` 的返回值从 `null` 扩成 `{worktreeRemoved: boolean}`；**不传参数时行为逐字不变**（CLI `wave daemon destroy` 就是那条路）。改动计数走一条**会话作用域**的只读方法（`getSessionWorktreeChanges`，路径由 daemon 从该会话的 `createdWorkdir` 推导、**不接受调用方给路径**）——与「不放行裸 `removeWorktree`」同一条理由：页面不该能指名这台机器上的任意目录。

9. **假设** 用户问「列表里那行的 `worktree` 从哪来」，**则** 它由 daemon 从该会话的 `createdWorkdir` **推导**（`listDaemonSessions` 每行追加可选字段 `worktree?: {path, branch, repoRoot, hookBased}`），**不新增「worktree ↔ 会话」的持久状态**——daemon 重启就没了，而桌面端那套索引是它自己的（`entry.worktree`），两边各自持有各自的事实。**计数绝不逐行跑 git**（那会让每次列表刷新都变成 N 次 git 调用）：列表只回 `worktree` 本身，计数走场景 8 那条按需读。**推导不出来或失败一律降级为「没有这个字段」**（= 不是工作树或不确定），绝不让整个列表报错。

10. **假设** 某条会话是由**别的宿主**托管的（桌面端 / IDE 的 `--stdio` 子进程），**则** 它照样能在这张列表里被删——**不按托管方做任何区分或限制**（能列出来的就是能删的，它们都活在同一个服务进程里）。**已知残留（明确接受）**：手机删掉一条由桌面端 / IDE 托管的会话后，**电脑侧那个面板不会自动关闭**，它会留一个点进去就报错的口子，需要用户手动关；本轮**不做**「会话被远端删除」的跨进程通知（那要一条新的宿主内广播，收益只覆盖一个残留，代价是又一条状态同步链路）。

11. **假设** 删除成功，**则** 页面**回到列表**并在顶部给一条「**已删除**」（短暂显示），**不自动跳进别的会话**。被删的若是**当前正在看的那条**，页面按既有 `chooseSession` 规则重新挑一条活会话绑定（否则每次读都会落到 `Session not found`），但**视图仍停在列表上**——「挑一条绑上」与「替用户跳进去」是两件事，后者会把用户刚做完的动作变成一次意外导航。

12. **假设** 有人把这条故事读成「手机能翻磁盘历史会话了」，**则** 不是：本篇把「**删活会话**」补齐，**不等于**「读磁盘上的历史会话」。`/resume` 与顶栏「历史对话」**仍然不渲染**（「Web 页作为第五种宿主」场景 24 的清单不变），`listAllSessions` / `restoreSession` **仍不放行**；删掉一条活会话**不删它的磁盘 transcript**（因此场景 6 那句「对话记录仍保留在这台电脑上」是字面意思）。

13. **假设** 有人问「桌面端那条删除规格要不要跟着改」，**则** **不改**：`desktop-sessions.md`「删除 worktree 会话前提示将丢失的改动」的语义与文案归桌面端，手机端**复用同一份文案**（`utils/worktreeDeleteWarning.ts` 是两端共用的唯一来源，本故事不改它的一个字），差别只在**承载物**——桌面端是侧栏行菜单 + 居中确认框，手机端是整页列表的行「⋯」+ 底部动作面板 + 全屏确认卡片。

### 用户故事：前台 CLI 会话也能被手机接管（优先级：P1）

作为正坐在终端前对话的用户，我希望离开工位时把**手上这条**会话交给手机，而不是另开一条再重述一遍上下文，以便走出工位还能接着推进。

**为什么是这个优先级**：前面几条故事覆盖的都是「常驻着、可以被指着的会话」（daemon、GUI 子进程）。前台 TUI 会话是唯一一种**只活在用户眼前那个进程里**的会话——它的寿命跟着用户敲的那一下退出走。能不能接管，取决于这条会话所在的进程自己愿不愿意拨号，没有第二个进程能替它做（「谁持有会话谁服务」在这条故事里是极端情形）。它不改安全模型（同一个开关、同一份白名单、同一条设备级通道），所以既可以独立落地，也可以独立不落地；缺了它，既有闭环一条都不少。

**独立测试**：在交互式 TUI 里执行开启动作，拿到页面地址与二维码；手机连上后看到的**就是终端里这条会话**（消息逐条一致，不是空会话）；两端各发一句对方都能看到；构造一次等待确认的工具调用，两端同时出现审批卡，任意一端作答后另一端那张卡消失、会话继续；退出 TUI 后页面显示「电脑已断开」；让会话流式生成一段长正文，手机端正文**逐段增长**（不是停在某一瞬的片段），且这期间推给手机的增量帧数远少于模型增量数、结构变化信号只在结构变化时出现；再让一次工具调用失败，手机端那条回复下出现**同一条错误块**（不必手动刷新）。

**验收场景**：

1. **假设** 开关已打开且用户已登录，**当** 用户在交互式 TUI 里执行开启远程控制的动作时，**则** 拨号的是**这个前台进程自己**——不经 daemon 代理、也不为了完成这个动作去拉起 daemon——并在 TUI 里回显与 `wave remote-control on` 同形的页面地址与可扫二维码；失败时的提示同样指向 `enableRemoteControl`（并说明前台进程也要重启才换设置）。
2. **假设** 手机连上了前台 CLI 会话，**则** 它看到的是这条会话**本身**（与终端同一份消息序列、同一个模型与权限模式），不是新会话、也不是空会话。
3. **假设** 用户在手机上发出一条消息，**则** 它进入这条会话的历史并驱动同一条生成循环，终端的消息列表随之更新；反过来，在终端发出的消息同样出现在手机上。
4. **假设** 会话正在生成、用户在手机上触发中断，**则** 中断的是这条会话当前这一轮，与在终端按中断键等价。
5. **假设** 这条会话有等待确认的工具调用，**则** **两端都能作答**（终端沿用既有审批 UI，手机用审批卡），**先作答的一端生效**、另一端同一张卡随即消失；两端看到的待确认集合一致。这不是新增权限：同一个请求本来就要用户点一次，区别只在点在哪一端。
6. **假设** 用户正常退出 TUI、或前台进程被结束，**则** 本机**主动断开这条中继连接**（不替一个已经不存在的进程保留订阅），页面呈现为「电脑已断开」并停止展示内容（与「服务端不落内容」这条既有口径一致）；该会话按 CLI 既有语义落盘，将来恢复出来的是一条**新会话**，不会自动接回手机原来那条连接。
7. **假设** 用户想在 TUI 里关掉，**则** 关闭断开的正是**这个进程**这条连接（关的入口必须和开的入口在同一个进程里，理由同第 1 条）；此时本机别的进程若在服务（daemon / GUI 子进程），它不受影响。
8. **假设** 同一台机器上已经有另一个进程在用同一个通道键服务（daemon 在跑、或某个 GUI 子进程已连），**当** 前台 TUI 开启时，**则** 由前台进程接管、那个进程的连接被中继关掉并如实呈现（见「一个通道一个服务方」故事）——**不允许**两个进程都以为自己在线（通道键是设备级的，见边界情况）。
9. **假设** 手机打开顶栏的「会话」列表，**则** 前台 CLI 这个宿主**有且只有一条**可列：它自己手上这条会话（`listDaemonSessions` 报的就是它，一条，带 `sessionId` / `workingDirectory` / 标题材料 / `lastActiveAt` / 忙闲，全部取自进程内这条会话），**不读磁盘 jsonl、也不列这台机器上的历史会话**；手机点进去只能是这条，「切换」在这个宿主上没有第二个目标。**依据**：页面列会话的唯一数据源是 `listDaemonSessions`（见「边界情况」——手机只能看进程内活着的会话），而前台 CLI 的「进程内注册表」就是它这一条；宿主漏答这个方法时页面落到「读不到电脑侧的会话列表」横幅上（就是这条把「前台 CLI 也必须答它」钉成契约，而不是留给实现去发现）。
10. **假设** 这条会话正在流式生成，**则** 推给手机的通知与 `AgentBridge` 为 daemon / `--stdio` 会话发出的**是同一张映射表**（同一个 agent 回调 → 同一条通知、同方法名同载荷），于是「白名单与增量拉取」故事场景 4 那个 150ms 合并窗口在两条路上照常生效：正文 / 推理 / 工具参数的增量帧各按 key 累积拼接，离散事件（审批请求、工具块 `start`/`end`、忙闲与其它状态）立即写出并先冲刷缓冲；手机端正文**由这些增量帧驱动增长**，`messagesChange` 只在真的结构变化（新消息、消息被丢弃、清空 / rewind、会话切换）时发一条。**这张表必须是代码里的同一处，而不是两份约定**：方法名与载荷字段集中在 `packages/code/src/remote/remoteNotifications.ts` 的 `remoteWire`，两个宿主都从它取帧（含上下文占用百分比的取整规则 `percentOf`）——宿主各写各的「谁发哪条」，但**形状只有一处**，所以将来改一个字段不会只在一条路上生效。**只由 bridge 发的那些族不进这张表**（会话注册表、`tasksChange` / `queuedMessagesChange` / `commandRunningChange` / 压缩与计划等），因为它们没有第二份实现要对齐，前台宿主也不为此补一条（判据见场景 11）。**依据（2026-10-16 实测）**：改之前这条通道只有「监视本机 UI 状态、变一次推一条粗信号」一条路，而 CLI 的数据层节流已于 2026-10-15 移除 ⇒ 每个模型增量都改一次消息状态，手机侧真实速率是「每个增量一条信号 + 一次 `getMessages` 回拉」，不受任何窗口约束；更糟的是信号不带内容、`since` 又是**排他**锚点，而流式中那条消息正是手机列表的最后一条 ⇒ 页面正文停在拉取那一瞬的片段（实测停在 `He`），同一个增量以增量帧发出却能长到 `Hello`。即「这条路上没有节流」与「手机看不到流式增长」是同一个根因，本场景一次收掉。
11. **假设** 这一轮在**尾部那条消息内部原地**多出一个块（最典型：工具失败 / 生成失败的错误块——前台宿主把它追加到正在流式的最后一条 assistant 消息上，只有当最后一条是 user 消息时才另起一条），**则** 宿主必须用**带载荷的通知**（`errorBlockAdded`，与 `AgentBridge` 同方法名、同载荷）把它送出去，页面按既有的 `updateErrorBlock` → `APPEND_ERROR_BLOCK` 落到那条消息里，**两端看到同一条错误块**。**不允许**只发「列表变了」信号了事：`since` 是**排他**锚点、而锚点正是这条消息本身 ⇒ 回拉返回空 `messages`，错误在手机上永远不出现（与场景 10 的 `He` 是同一个坑，只是方向相反：那边是帧太少，这边是没有帧）。**明确允许的降级**：以「读」为准的状态族——待办清单 / 待发队列 / 命令运行中 / 压缩中——**不要求**在这个宿主上实时推送，页面在冷启动、切会话、重连、重挂、回前台时各读一次 `getSessionInfo` 即对齐（与「Web 页作为第五种宿主」故事里那条既有口径同形：读出来的事实等下一次对齐，页面不为它新增轮询）。判据是**内容能不能被回拉补回**：一手内容（模型增量、工具参数、错误块）必须由通知携带；只作指示用的状态可以只靠读。

12. **假设** 手机请求了一个**这个宿主没有实现**的方法（白名单是通道级的，daemon / GUI 子进程 / 前台 CLI 共用同一份，而三个宿主的实现面不同——前台 CLI 只接了会话内那一批），**则** 宿主回一个**结构化的「该宿主不支持」**错误：固定错误码 + 带方法名的消息，语义上明确是「这个宿主没接」，而不是 `-32601 Method not found`（那是「通道不放行」的意思，页面会据此以为该升级电脑侧）、也不是 `-32602`（参数错）、更不是静默不回。**依据**：把「通道不放行」「这个宿主没实现」「内部报错」压成同一个错误，页面就分不清该升级、该换一台电脑、还是该等实现；而静默不回执会让界面停在那个动作上（没有回执、也没有告警）。该错误由页面翻成一句可见文案并收尾这条请求（见「页面能执行的那批宿主命令」故事场景 10）。

### 用户故事：机器身份稳定——同一台机器只有一行登记（优先级：P1）

作为在同一台电脑上反复开关远程控制（CLI / 插件端 / 桌面端任一入口）的用户，我希望这台机器在中继上始终是同一行、同一个 hostId，而不是每丢一次本地状态就多出一条同名记录，并连带换掉页面地址与主屏图标。

**为什么是这个优先级**：首次使用感受不到它（首次登记本来就要建一行）。它决定的是**长期整洁与地址稳定**：hostId 今天是中继在建行那一刻随机生成的，本机只是把结果记在 `~/.wave/remote-control.json` 里——那个文件一丢（重装、清 home、只读 home、换 OS 用户），下次开启就会在同一个账号下再建一行，手机上机器列表里出现多条同名记录，页面地址与主屏图标也一起失效。把 id 的**来源**从「中继随机」换成「本机按机器标识派生」之后，同一台机器算出的 id 恒定，登记因此变成幂等：本地状态丢了也只是把同一行认回来。**跨仓**：这需要中继支持「按本机提交的 id 幂等登记」，本机侧只是换 id 的来源。

**独立测试**：在同一台机器上删掉 `~/.wave/remote-control.json` 后重新运行 `wave remote-control on`，中继的机器列表**行数不变**、hostId 与删除前相同；CLI 与桌面端分别开启得到同一个 hostId；屏蔽机器标识读取后开启仍成功（回退到中继生成的 id）。

**验收场景**：

1. **假设** 本机没有身份（`~/.wave/remote-control.json` 里没有 hostId），**当** 开启远程控制时，**则** 登记请求带上按机器标识派生的 id（「固定命名空间 + 机器标识 + 本机登录账号 id」派生出的 UUID，v5 / RFC 4122），中继按「本账号 + 该 id」查行——命中则复用那一行（不新增行）并重新签发 `hostToken`，未命中则以这个 id 建行；响应里的 `host.id` 与 `hostToken` 一起写进本地状态。
2. **假设** 本地状态文件被删除、损坏或写不进去（重装、清 home、半写），**当** 用户在同一台机器、同一账号下再次开启时，**则** 中继上**不新增行**：派生出的 id 与删除前相同，登记认回原来那一行，页面地址与主屏图标不变。
3. **假设** 同一台机器上先后从 CLI（含 TUI 斜杠命令）、插件端、桌面端开启，**则** 三个入口共用同一份本地状态与同一个 hostId（入口不同不产生额外行）——这一点与今天一致，本故事改的是「本地状态是唯一载体」这件事本身。
4. **假设** 本机已经有一行（老机器：本地存着历史上由中继随机生成的 hostId），**则** 继续用它、**不做迁移**：本地状态在就一直复用，而迁移会让每台老机器多出一行垃圾。派生只在本地没有身份时才参与。
5. **假设** 本机读不到机器标识（平台不支持、权限不足、取值失败），**当** 首次登记时，**则** 登记照常进行：请求不带 id，由中继生成随机 id（今天的行为），响应里的 id 写进本地状态；读不到标识不导致开启失败。
6. **假设** 同一台机器上换成另一个账号登录（另一个 OS 用户、或登出后再登入别的账号），**则** 派生的输入不同 ⇒ 另一个 hostId、中继上另一行——行的归属本来就是「某个账号的一台机器」，与中继 `relay_hosts.user_id` 的口径一致。
7. **假设** 派生出的 id 在中继上已经被**另一个账号**占用（同一份机器标识被两台机器共享：克隆的虚拟机、镜像还原），**则** 中继不覆盖他人的行，改为生成一个随机 id 建行并把实际 id 返回；本机以响应里的 id 为准。**已知代价**：这类机器每次丢本地状态都会再建一行（幂等在这条路径上不成立）——根因是它们本就自称同一台机器。
8. **假设** 机器标识要送往中继，**则** 送的是**不可逆的派生值**（派生摘要）而不是原文：标识只在本机读取、只参与派生，中继与手机上看到的永远只是 id。
9. **假设** 用户在中继侧吊销了这台机器的行（`DELETE /api/relay/hosts/:id`），**当** 本机丢失本地状态后带着同一个派生 id 重新登记时，**则** 中继复用那一行、把它翻回 active 并重新签发令牌——吊销的语义是「立刻失效、断开连接、从列表消失」，不是「永久拉黑这台机器」；本地状态还在时本机根本不会重新登记，所以吊销在正常路径上依然成立。永久拒绝一台机器属于中继侧的拉黑能力，本规格不做。
10. **假设** 本地状态丢失的同时有多个入口并发首次开启，**则** 它们提交同一个 id、都命中同一行，但**各自拿到一份新令牌**，后到的那份让先到的失效（一台机器一份令牌）——表现是先开的那个可能连不上，重新开启即恢复。**已知取舍**：中继只存令牌摘要，而「本地状态丢失后要能拿回令牌」只能靠重新签发，这个窄窗口不额外加锁。

### 用户故事：一个通道一个服务方——后开的入口接管，先开的自动停（优先级：P1）

作为在同一台机器上从不同入口（CLI / 插件端 / 桌面端，甚至桌面端的不同分屏）开远程控制的用户，我希望**最后开启的那一个**成为手机看到的那一个、先前那个自动退下来，而不是两个进程每两秒互相顶一次、手机跟着反复断流。

**为什么是这个优先级**：通道键是设备级的（一台机器一个 hostId），而「谁持有会话谁服务」意味着同一时刻只能有一个进程在服务。**中继侧已经就是这样**：同一通道上后到的主机上线时按「换代接管」处理——先把登记换成新的，再以 `4001` 关闭旧连接（跨中继实例经总线广播同样的接管），并且**不惊动订阅者**（不给手机推 `peer_disconnected`、不清在线键），所以手机侧看到的是一次无缝替换。缺的是本机侧的另一半：被顶掉的那个进程把 `4001` 当成瞬态错误、两秒后重连就又把对方顶掉，于是两个进程**每两秒互踢一次**、永不收敛（每次都能连上，而每次连上都会清空重试预算，谁都用不完预算）。本故事只补这一半：**被接管 = 这个进程不再服务**，不再抢回来。

**独立测试**：在同一台机器上先从一个入口开启远控、再从另一个入口开启；第二个的页面地址能连上；第一个的状态里出现「已被另一个入口接管」的说明、且不再拨号（观察两分钟无重连）；把第一个关掉再开启，它能重新接管回来。

**验收场景**：

1. **假设** 同一台机器上已经有一个进程在服务（daemon / GUI 子进程 / 前台 TUI），**当** 用户在另一个入口开启远程控制时，**则** 由**后开的那个**接管：中继把登记换成它、并以 `4001`（`reason: "replaced"`）关闭旧连接，手机侧不出现断开提示（不推 `peer_disconnected`、在线状态不翻）。
2. **假设** 一个进程的连接是被「换代接管」关掉的，**当** 本机收到那次关闭时，**则** 它按**被接管**处理：不再重连，状态明确写出「已被这台机器上的另一个入口接管」，不留一句笼统的「中继连接断开」。**依据**：中继用的是同一个 `4001`，光靠关闭码分不出「我被顶替了」与「这台机器没上线」；区分靠 close 帧的 `reason`（中继在接管时下发 `replaced`）。
3. **假设** 用户在被接管的那个入口里重新开启，**则** 它重新拨号并**接管回来**（后开启者为准）——接管关系不粘在进程上，`off` / `on` 始终是各入口自己的动作，谁最后连上谁服务。
4. **假设** 用户在某个入口里关闭（`off` / 弹窗断开），**则** 关掉的只是**那个进程**那条连接（既有口径不变）：别的进程若在服务，手机不受影响；没有任何进程在服务时，手机侧按 `4001` 重连（页面走既有的「等待上线」自愈路径）。
5. **假设** 桌面端的两个分屏各自开启远程控制，**则** 规则同上——后开的那个成为手机读到的会话集合，先开的那条连接停止（每个分屏一个 `--stdio` 子进程，各自都是一次「开启」）。
6. **假设** 一台远端机器上的 daemon 正开着远程控制（无人值守场景），**当** 有人在那台机器上跑一次前台 TUI 并开启时，**则** 前台进程接管、daemon 那条连接停止并如实显示被接管。**这是刻意的取舍**：接管只看「谁最后开启」，不按入口类型分优先级——无人值守要守的是「别在那台机器上再开一次」，而不是给 daemon 特权。
7. **假设** 先开的进程后来被重启（`wave daemon restart` 等），**则** 它启动后按自己的开关状态重新拨号——那是一次新的「开启」，于是它又接管回来（同场景 3 的规则）。

### 用户故事：机器列表与切换——一个页面管所有机器（优先级：P1）

作为有不止一台电脑的用户，我希望加到主屏幕的那**一个**图标就能列出并切换我账号下开启了远程控制的所有机器，而不是每台机器一个图标、各自登录一次、各自扫一次码。

**为什么是这个优先级**：单机器用户感受不到它（带 `host=` 的地址行为不变）；它是多机器用户「N 个图标 N 次登录」痛点的解药，也是「新机器开启远程控制后不必重新扫码」的前提——机器自己登记即出现在列表里，页面刷新即可见。收端的列表接口（`GET /api/relay/hosts`）已就绪，本故事是**纯页面侧**的活，收端零配合。本故事只做「选择与切换」：重命名 / 吊销 / 删除等机器管理不做（收端有接口，页面不接）。

**独立测试**：打开不带 `host=` 的页面地址（已登录），页面列出账号下的机器（名称 / 平台 / 在线状态）；选中一台进入会话视图且地址被改写成带 `host=`；再次打开直接重连上次选中的那台；「换机器」入口能回到列表切换另一台，且列表读取中 / 取不到的提示只出现在弹窗里，关掉弹窗后页面与点击前一致。

**验收场景**：

1. **假设** 地址里带 `host=`，**则** 页面行为与今天**逐字节一致**：直接连那台机器，不请求机器列表——这是既有链接与二维码的兼容面，也是单机器用户的主路径。
2. **假设** 地址不带 `host=` 且本地记住了上次选中的机器、那台仍在列表里，**则** 页面直接重连它（不展示列表），并把选择写回地址（`history.replaceState` 补上 `host=`）——主屏图标点开仍是同一台；同一账号下新增一台机器不改变这一点。
3. **假设** 地址不带 `host=` 且没有本地记录、或记录的那台已不在列表里，**当** 页面取到机器列表时，**则** 展示机器列表（每台给名称、平台、在线状态），选中即写地址并连接。在线状态来自接口的 `online` 字段（心跳续期，断连后 ≤60 秒翻为 false），只作**展示**判据——选中一台离线机器是允许的，交给「等待上线」的自愈路径（见断线自愈故事），不让离线状态把入口关死。
4. **假设** 列表为空，**则** 页面给明确状态（还没有机器开启远程控制 + 在电脑侧开启的指引），不留白屏。
5. **假设** 用户想换一台机器，**则** 「换机器」入口在两个时刻都可达：电脑连不上或断开时的横幅上，以及连接正常时的一个页面侧常驻入口（形态归页面侧壳，不改共享聊天 UI 的交互语义）。切换 = 改通道键 + 丢弃地址里的 `session=`（那是上一台机器的会话）+ 重走完整连接（快照、忙闲、待审批、权限档全部按冷启动口径重读）。
6. **假设** 页面要取机器列表，**则** 它对**同源**的 `GET /api/relay/hosts` 发起请求（凭证就是页面已在用的企业端登录令牌，接口按「登录用户 == 主机属主」返回该账号的机器，无服务端配对步骤），因此 CSP 的 `connect-src` 必须从 `wss:` 放宽到 `wss: 'self'`。**依据**：这张 CSP 是页面初版定的，当时页面没有任何同源出站请求；后来加的登录态静默续期（`POST /api/auth/refresh`）同样是同源 fetch，却没放宽 CSP——线上那一步会被**静默拦掉**、退化成跳登录页，而 jsdom 不执行 CSP，测试咬不到。机器列表是第二个同源 fetch，本故事把这张网一起补上。
7. **假设** 列表请求失败（网络不可达、接口异常），**则** 页面给明确状态与重试入口，不白屏、也不静默渲染成空列表。
8. **假设** 用户点「换机器」入口（连接正常时的顶栏图标，或断开横幅上的那个按钮），**则** 这次读取的两种中间状态都由**弹窗自己**承载：读取期间弹窗里显示「正在读取机器列表…」，取不到时弹窗里显示原因与「重试」（重试就地重取、刷新同一个弹窗）——而页面顶部那条横幅在弹窗开合前后**逐字不变**，关闭弹窗（取消）后页面与点击前一致。**依据**：那条横幅是连接层的**状态**面（「电脑侧不在线，等待上线…」+「重新连接 / 换机器」两个动作），列表读取则是**过渡**；把过渡写进状态面有两个后果——① 用错误色的横幅呈现「正在读取」，用户读到的是「出事了」（2026-10-15 实测反馈）；② 覆盖之后再无恢复路径，用户在等待上线时点一次「换机器」再取消，连「正在重连」和那两个入口一起丢掉。冷启动那次取列表（地址不带 `host=`、页面此刻还没有别的东西可说）仍用横幅占位，但取**中性**色：它说的是「正在做一件事」，不是「某件事失败了」。

### 用户故事：PWA 主屏元信息——真实图标与具名（优先级：P1）

作为把页面「添加到主屏幕」的用户，我希望主屏上出现的是一个**可辨识的图标和名字**，而不是灰色默认图标加一段截断的域名。

**为什么是这个优先级**：主屏入口是这个功能在手机上的主要形态；没有元信息，「添加到主屏幕」这个动作产出的东西既认不出也不愿点。图标只有**一份**、不分机器——机器的区分是页面内机器列表的事（上一故事），这正是「一个图标管所有机器」的字面义。

**独立测试**：在 iPhone Safari 打开页面地址 → 分享 → 「添加到主屏幕」，得到具名图标（非灰默认）与名字；点开以 standalone（无浏览器工具栏）形态打开；构建产物里含 manifest 与真实 PNG 图标（内容哈希命名，随 zip 走既有上传通道）。

**验收场景**：

1. **假设** 页面被加到主屏幕，**则** 产物提供全部元信息：manifest（`name` / `short_name`、`display: standalone`、`start_url` 指页面根——**不带查询参数**，机器的选择属于页面内的状态而不是入口的身份；主题色取页面深色主题）、真实 PNG 图标（以品牌应用图标为源，一份内容哈希文件同时充当 favicon 与 `apple-touch-icon`，替换掉现在的空图标 `data:,`）、`apple-mobile-web-app-title`（短名，主屏宽度内不截断，取品牌名）。iOS 用 `apple-touch-icon` 与这个短名渲染主屏条目；standalone 用 manifest 与 meta 两条路都声明——各代 iOS 各取其一。
2. **假设** 浏览器要取 manifest 与图标，**则** CSP 必须放行：`manifest-src` 缺省回落到 `default-src 'none'`，必须显式加 `'self'`；图标走 `img-src 'self'`（已有）。
3. **假设** 产物走既有上传通道，**则** 不需要收端配合：`.png` 与 `.json`（manifest 以 `manifest.json` 命名，`application/json` 浏览器接受）都已在运营平台上传接口的扩展名白名单与 MIME 表里（2026-10-15 对收端源码核实）。
4. **假设** 用户在电脑侧开启了远程控制、或在页面上看到机器列表，**则** 两处各有一句引导：**用相机扫码或在 Safari 里打开，再「添加到主屏幕」；不要用控制中心的扫码器**——它把链接开在沙箱容器里，没有 Safari 的会话存储，既不保留页面也加不了主屏（2026-10-14 真机实测）。iOS 没有 `beforeinstallprompt`，引导只能是文案。

### 用户故事：锁屏也能知道——会话等着我、或者跑完了（优先级：P1）

作为把页面加到主屏、然后锁屏揣兜里的人，我希望「某条对话在等我确认」和「某条对话已经跑完」这两件事能作为系统通知推到我手机上，点开直达那条对话，以便不必一直盯着页面。

**为什么是这个优先级**：页面在后台会被 iOS 冻结、长连必断（断线自愈故事已把接回做掉），没有推送就只剩「主动打开页面才知道」。而「人不在电脑前也能把卡住的会话推下去」正是远程控制不可替代的那一半——中继侧的推送基建（VAPID 密钥、订阅登记、`requires_action` 触发与限流）已经就绪，缺的只是页面这半。**跨仓依赖**：两条都已在中继侧落地——待确认那条本来就有；「已完成」那条 2026-10-16 放行（判据＝真正的 `running → idle` 跳变，文案与载荷见 codechat `!193`，已按该分支构建部署到测试环境、MR 未合），属 codechat 仓库的改动。

**独立测试**：手机把页面添加到主屏并授权通知 → 电脑侧触发一次工具审批 → 锁屏收到「有会话等待确认」，点开直达该对话的审批卡；批准后这一轮跑完，再收到「有会话已完成」，点开仍直达该对话；页面在前台且正显示该对话时，同样两件事都**不弹横幅**（页面内的卡片与会话列表标记照常）。

**验收场景**：

1. **假设** 某会话进入待确认——工具审批、`AskUserQuestion` 提问、或 `ExitPlanMode` 计划待批准，**则** 手机收到一条推送「`<机器名>` · 有会话等待确认」，点开直达该对话。**载荷不含会话标题、也不含命令或消息内容**：中继只拿得到「哪个会话、什么状态」这两个非内容字段（见边界情况「不解析内容」）。这三类共用同一条信号——`requires_action` 的判据就是该会话有待确认请求（`listSessionStatuses`），而提问与计划批准即使在 `bypassPermissions` 下也照样提示（`permissionManager` 的 `USER_INTERACTION_REQUIRED_TOOLS`）。
2. **假设** 某会话从「运行中」变为「空闲」（一轮生成结束、后台任务收尾——`running` 本就含后台任务），**则** 收到一条推送「`<机器名>` · 有会话已完成」，点开直达该对话。**依据**：桌面端把「已完成」交给侧栏绿点（2026-09-10 拍板移除「已完成」toast），但那条理由在这里不成立——页面没有已读跟踪（「待确认只在它自己的对话里弹」故事场景 6 已明确不做绿点），且页面不可见时用户眼前什么都没有，「跑完了」与「等着我」一样是只有推送能送达的信息。**这是与桌面端的刻意不一致，理由在此。**
3. **假设** 同一会话重复上报同一状态（仍是 `requires_action`、或仍是空闲），**则** 不重复推送——只在「进入」该状态的那一次推。**假设** 同一台机器 60 秒内推送超过 30 次，**则** 超出部分只更新状态、不投递（中继既有兜底：`PUSH_RATE_MAX = 30` / `PUSH_RATE_WINDOW_SECONDS = 60`；机器级天花板不变，只是「已完成」另有一层更严的子限＝一半预算，免得一轮一条的它把「待确认」挤掉——判据在被挡掉时不消耗共用桶）。
4. **假设** 页面此刻**可见**（Service Worker 的 `clients` 里有可见页面），**则** 不弹系统横幅，只在页面内呈现（该弹的卡照弹、会话列表标记照标）；页面不可见（后台、锁屏、已关闭）时才弹。**依据**：与桌面端「会话已显示在某个分屏就不弹 toast」同款口径（`desktop-sessions.md`「后台会话确认提醒」场景 2）——用户正看着那一页时，横幅是重复打扰。
5. **假设** 用户点开推送，**则** 打开 `/remote/?host=<hostId>&session=<sessionId>` 并落在该对话上（与扫码入口、中继落地页模板同一个形状）；该会话若已不存在，**则** 落在会话列表并给出明确状态，不白屏。
6. **假设** 用户在页面上订阅或注销通知，**则** 浏览器订阅经中继登记（`POST /api/relay/push/subscriptions`）与删除（`DELETE /api/relay/push/subscriptions/:id`），VAPID 公钥取自 `GET /api/relay/push/public-key`。页面同时自己注册那个接收推送的 Service Worker（与其余资源一样哈希命名、由构建把名字填进去，scope 落在页面自己的目录），因此 CSP 要显式写 `worker-src 'self'`——缺省时它回落到 `script-src 'self'`，这一行是把那条回落写明白而不是放宽；注册不依赖通知权限、也不依赖中继或登录态，所以它在页面启动时完成，不带任何请求。
7. **假设** 运行在 iOS 且页面**尚未添加到主屏**，**则** 页面给出「添加到主屏幕后才能开启通知」的引导——iOS 16.4 起 Web Push 只对主屏 web app 可用，普通 Safari 标签页拿不到 `PushManager`，不静默失败；**假设** 浏览器不支持推送、或用户拒绝通知权限，**则** 同样明确呈现，页面其余功能不受影响。

**边界**：不做 APNs、不做原生 App（形状已定）。推送里只有机器名、会话 id 与状态词这些**非内容**信息——会话标题**不**进推送：要带标题就得让本机把内容上报给中继，与「中继不落内容」的隐私边界冲突（2026-10-16 拍板）。

### 用户故事：断线自愈——等待上线、永久即停、手动重连（优先级：P1）

作为把页面一直挂着的用户，我希望电脑侧「关掉远程控制再打开」、休眠醒来、或中继重启之后，页面能**自己接回来**，而不是重试十秒就永久罢工、只能杀掉页面重进。

**为什么是这个优先级**：主屏 web app 从后台恢复**不会重新加载**，页面寿命以天计——重试预算一旦耗尽就是永久假死，而这正是远控场景最常规的波动（电脑重启、网络抖动、机器侧开关一次）。

**独立测试**：断开电脑侧远程控制，页面进入「等待上线」并按退避持续重试；重新开启后页面自动接回（快照与状态重读齐全）；把中继回成 4003，页面立即停止并给出明确文案；等待/断开状态下点「重新连接」能立即重试。

**验收场景**：

1. **假设** 订阅被中继以 4001 关闭（电脑侧不在线，瞬态），**则** 页面**不落入固定 5 次的重试预算**，而是无限退避重试（指数、有上限），期间状态如实呈现「电脑侧不在线，等待上线」；电脑重新开启远程控制后，下一次重试自动接回，接回路径与既有重连一致（增量补差 + 忙闲 / 待审批 / 权限档重读）。**依据**：现页面 4001 与其余瞬态断开共用 `MAX_ATTEMPTS = 5`、2 秒一次的预算（约 10 秒耗尽），耗尽后停在「已停止重试」不再尝试——机器侧一次「关掉再打开」就够触发；iOS 主屏形态不会自己重载，用户看到的是一张再也连不上的页面。
2. **假设** 连接因其余瞬态原因断开（网络抖动、中继重启、链路层关闭码），**则** 走同一条退避路径——页面寿命内的瞬态波动都值得等，不再出现「已停止重试」的终态。
3. **假设** 失败是**永久**的（4003、`auth_error` 的永久类错误、`host_version_unsupported`），**则** 页面立即停止并给出明确文案，不进入退避——重试改变不了这些原因，只会掩盖它们。
4. **假设** 页面处于等待上线或断开状态，**则** 提供「重新连接」入口：手动重置退避并立即重建订阅、重拉快照，不必杀页面。
5. **假设** 页面从后台回到前台（`visibilitychange` / `pageshow`）时正在退避等待，**则** 立即试连一次并把退避基数归零——回前台的既有一组重读（消息增量、忙闲、待审批、权限档）只在链路可用时发起，等待态这条路是它的补全：用户掏出手机的瞬间就是最好的重试时机。
6. **假设** 任何一次连接成功，**则** 退避基数归零，回到最快响应。

### 边界情况

- **没有配对码：通道键不是凭证，页面靠登录态说话**。不发码的两条理由：① 短期票据只有能被**重复签发**才有意义，而本机的登记是一次性的（本地有身份就不再登记，也没有第二处会重发码）——把码塞进登记响应，等于让它的寿命跟着那次登记一起结束，过期即无解；② 码换来的东西本来就不需要保护——中继在订阅握手时校验「这行 host 属于当前账号、且账号是该企业的活跃成员」，**通道键本身没有权限**，印在二维码上不泄露任何东西。对齐参照是同类的 Claude Code：它也没有配对码，二维码只是会话 URL 的快捷入口。因此页面地址就是 `<服务端地址>/remote/?host=<hostId>`，与中继给推送用的落地页模板**同一个形状**——扫码进来和点推送进来是同一条路。
- **一条连接承载全部会话**：通道键是设备（本机）而不是会话——会话级通道在这里根本不成立：手机要先从本机学到会话列表，会话级通道会让「列表页」无处可问。因此 `sessionId` 只是信封字段，中继逐字转发不需要理解内容。
- **一台机器只有一个服务方**：通道键既然是设备级的，同一台机器上的多个 wave 进程就只能**共用同一个通道键**（本机只有一份 `~/.wave/remote-control.json`）。于是「谁持有会话谁服务」在多进程并存时必须收敛成一个答案——手机指向的那台机器，同一时刻只由其中一个进程提供服务，不允许两个进程都以为自己在线（前台 CLI 故事第 8 条）。
- **机器身份取自机器标识，不取自本地文件、也不取自主机名**：id 由本机按「机器标识 + 本机登录账号」派生（见「机器身份稳定」故事），同一台机器上的多个入口、多个进程、多个工作目录在任何时刻都算出同一个 id；`~/.wave/remote-control.json` 不再是身份本身，只是「已知身份 + 令牌」的缓存。机器标识按平台取系统自带的那个（Linux `/etc/machine-id`、macOS `IOPlatformUUID`、Windows `MachineGuid`），拿不到就回退到今天的行为（中继生成随机 id）；**不取主机名**——主机名可改、可重复，把它当身份只会制造「改个名就多一行」的假象，而它作为展示标签（`name`）已经够用。派生值一旦定型就不再改：换命名空间或换派生输入等于换身份、会让所有机器重新登记一行，所以它只在本机没有已存身份时才参与（故事场景 4），既有的行不追着算法迁移。
- **手机能看、能切的，只限「服务进程内活着的那批会话」**：这不是 UI 取舍而是可达性事实——① 手机列会话只能靠 `listDaemonSessions`（进程内存注册表，跨工作目录都在里面）；② 读消息与发消息都要求信封 `sessionId` 在本进程注册表里（`getMessages` 走 `requireSessionForRead`），磁盘 jsonl 里没被载入本进程的历史会话会回 `Session not found`；③ 唯一能把历史会话载入进程的 `restoreSession` **不进白名单** —— 它是「原地载入」语义，用它等于把服务进程里该条会话换掉（在桌面端就是换掉用户正在看的那个 pane），与「手机只当控制面」相冲。所以手机侧的会话列表与切换都只看进程内活会话，历史会话留给电脑端。切换只改手机自己那份 `sessionId` 与视图，**不发起任何写向电脑端的会话操作**（发起新会话是另一条**显式设计**的写路径，见「Web 端也能发起新会话」故事，不在此列）。
- **中继订阅地址不上界面**：`wss://<中继>/v1/hosts/<hostId>/subscribe` 是本机到中继的**出站订阅端点**——用户既打不开它也无处输入它，而它携带的 `hostId` 已经原样出现在页面地址的 `?host=` 里，唯一的信息增量是中继域名（即「这台机器连的是哪个环境」），那条信息属于排查场景，排查走状态输出与日志更直接。因此 CLI（`on` / `status`）、前台 TUI 与 GUI 设置页的「远程控制」项都不渲染它；快照里的 `url` 字段保留（连接与日志仍需要），去掉的只是呈现。
- **顶栏那两个按钮的分工**：「历史对话」仍不提供（切换收在「会话」面板）；「新建对话」图标恢复渲染但**重绑语义**——IDE 端它发 `clearChat` → `clearMessages`（agent 内部换绑新 sessionId = 开一条**同目录**的新会话；在 Web 页从未被实现过、点了只会留一条 console 警告），Web 页上它打开「发起新会话」流程（见「Web 端也能发起新会话」故事）——`clear` 那条路给不了选目录，也不回传新 id，为什么不能直接放行见该故事场景 9。桌面端同样把会话的新建与历史收进侧栏、顶栏不渲染那两个按钮（`hideSessionButtons`）——桌面端口径不变，页面是唯一恢复图标的一端：它是唯一没有侧栏、又需要发起入口的宿主。
- **「开关打开」≠「已连接」**：开关只授权**能力**，连接是用户的动作。两者分开的结果是：一台开着开关但没人拨号的机器不会建立任何出站连接，而一个失败连接会停在 `error` 状态（带原因），不是 `off`。
- **`off` / `error` 两种失败必须分开呈现**：宿主侧根本读不到状态（开关关闭、会话未就绪、对端不认识该 RPC）与「中继连上了但自报出错」是两件事，界面文案与 CLI 退出码都不同——把前者伪装成 `state: "error"` 会让用户去修一个不存在的网络问题。
- **Web 页的高度与安全区由浏览器说了算**：本地四端（IDE / 桌面的宿主）都被嵌在一个自己就是整屏的窗口里——页面高度与窗口高度逐像素相等，没有会伸缩的浏览器工具栏，也没有被系统 UI 盖住的边缘。Web 页不是：它跑在浏览器里，可视区随工具栏收起 / 展开而变，页面若按「工具栏收起后」的高度铺满，贴底的输入区就会落到折叠线以下（用户看不到输入框 = 交互失效）；页面又刻意画到屏幕边缘以吃满全面屏，于是状态栏 / 灵动岛、Home 指示条、横屏圆角区都压在内容之上，让开它们同样是页面自己的责任——**但只让顶部与横屏两端**：独立窗口形态下视口高度已经把底部安全区扣过一次，再让一条只是多出一条同色空带（2026-10-15 真机定性，见 Web 页故事场景 14）。这两条只对这一个宿主成立 ⇒ 按宿主收口，不落在共享布局上。
- **字号档的判据是设备能力，不是页面身份**：远控页是五端里唯一会被**两种形态**打开的一页——手机浏览器与 PC 浏览器打开的是同一张 `/remote/`，所以「这是哪一页」不足以决定字号（这既是它的特点，也是它必须两端都好用的原因）。判据取**输入能力**：`pointer: coarse` / `hover: none` 表示「主输入是手指、没有悬停」，正是手机与平板的共同点，也是业界（claude.ai 共享样式里多处 `@media (pointer:coarse), (hover:none)`）的做法。宽度断点做不到这件事：宽度是连续量，「多大算手机」没有自然分界点，只能任选一个阈值，而两侧都会误判——PC 上把窗口拉窄会被判成手机、平板（768–1024）又会被判成桌面；横屏手机同样是它漏掉的一种，但那属于补充（他 2026-10-14 判这一页横屏概率很低，见场景 16），不是选触控的主因。它同时也说明为什么这条差异不该写进共享样式：共享样式被五端同时加载，判据必须收在远控页这一层作用域里（`[data-remote-page]`，见上一条）。**16px 那条下限也归这一档**（2026-10-16 改，见 Web 页故事场景 15）：它防的 iOS 自动放大是**字号阈值**型的，而 Android 的同族机制（聚焦时的视野补偿、未按设备宽度布局的页面上的文本膨胀）在本页都不成立 ⇒ 16px 严格说只对 iOS 必需；但样式里**没有可靠的 iOS 判据**（能区分 Safari 的写法随版本失效），而「主输入是手指」正是本档已在用的稳定判据，且在触控设备上 16px 与已抬到 15px 的正文同档。初版按「无条件给足」写，代价是 PC 上输入框比 13px 正文明显偏大（他 2026-10-16 报）。
- **服务端不落内容，断连不展示历史**：中继是无状态转发，不缓存会话内容。因此本机离线时手机只应显示离线状态并停止展示内容，而不是继续渲染本地旧列表「假装还在」。
- **`messagesChange` 只有一种形态（不含内容的信号）**：所有产出方——bridge 的 re-attach 推送、前台 CLI 的结构变化通知、转发到远端的扇出——都只发不带 `messages` 字段的空载荷，内容一律由消费方按 `since` 自己拉。历史上本机侧曾发全量数组、由远端扇出丢弃，2026-10-18 收成一种形态（零消费者 + MB 级帧的构造与序列化是纯成本）；中继侧仍保留剥离动作，兼容还在发数组的旧机器。
- **`since` 是位置不是版本号**：消息 id 稳定，所以调用方可以只报「我最后看到的那条」；唯一致命的失败是锚点被截断（rewind / clear），此时必须回「重拉尾页」的信号，因为存储里没有版本号能发现这件事。同一个 id 可能在显示列表里出现多次（压缩后的消息会被重新加回），锚点按**最后一次**出现解析。
- **远端路径的异常不外溢**：远端扇出被就地兜住（try/catch），一个手机、一条坏帧不能让本地桌面 / IDE 的客户端掉线；本地路径（unix socket / 子进程管道）的逐帧行为完全不变。
- **`--stdio` 子进程与 daemon 都可能是服务方**：同一台机器上「谁持有会话谁服务」，手机看到的就是那个进程的会话集合；GUI 三端各自拉子进程 ⇒ 各自可能同时持有一条出站连接，这是设计而不是重复。
- **版本在握手帧的顶层，不在 `params` 里**：`{"type":"auth","credential":{…},"version":"1.2.3"}`——中继只读顶层 `frame.version`；写进 `params.version` 是**静默失效**（它「无从判断 ⇒ 放行」，两侧都不报错，只是版本过低的机器照样连上）。这是「页面永远是最新的、版本不匹配时请升级电脑侧」这条策略能不能生效的唯一开关（页面侧提示尚未实现，见下节）。该机标签（`name`，≤100 字符）则是在**登记**时上报的，只用于让手机区分同账号下的多台电脑。
- **两种凭证角色靠 `credential.type` 显式区分**：电脑侧 `{"type":"host","token":"rch_…"}`（登记时取到、持久化在本地，长期可吊销，撑得住几小时长连与重连）；手机侧 `{"type":"sso","token":"<登录 JWT>"}`。**两边是同一个人，身份区分不出角色**，所以角色只能显式声明——漏了它最隐蔽的后果是电脑侧走成订阅者分支：**能连上、两侧都不报错**（拿到的是 `role:"subscriber"`），但没人占 host 位，于是**它自己**先被中继按 4001 `host_offline` 关掉（订阅者必须挂在一台在线的主机上），随后真正的手机连上时也是 `auth_ok` → `peer_disconnected` → 4001。看到 4001 先查「电脑侧是不是走了 sso 分支」。电脑侧的长期令牌免掉了「常驻 daemon 的寿命长于 1 小时 JWT」这个矛盾，而端点解析仍在**连接时**做（用户也可能在进程跑了几小时后才想起开远程控制）；手机侧沿用已有登录态，没有第二套账号体系。登录态不可用时的错误不是笼统的「连接失败」，而是先就地续期、续不上再跳到企业端登录页并跳回来（见「登录态缺失先就地续期，续期不成才是一次重定向」那条）。
- **页面「去哪、用什么说」都取自同源，不靠页面配置**：中继地址不做成构建期常量——页面本身就部署在中继同一个域下的 `/remote/`，因此地址由 `location` 同源推导（`http(s)` → `ws(s)`，路径用中继公布的通道形态 `/v1/hosts/ws/{hostId}/subscribe`），`?ws=` 只留作本地调试；通道键就取地址里的 `host=`（地址由本机自己拼，形状与推送落地页模板 `/remote/?host={hostId}&session={sessionId}` 一致）。凭证同理：**握手用的就是企业端那一份登录令牌**（同源存储的同一个键），页面既不要求单独登录、也不注册第二套账号。代价是页面对企业端**会话存储与续期接口的完整形状**形成了耦合，键名、过期时机与接口形状都归对方前端定——这条耦合要显式记一笔，别指望将来有人能从我们的代码里推出来：**四个存储键**（`token` / `refreshToken` / `expiresAt` / `user`，后三个只服务于续期——`user` 是「登录地改过邮箱后别在页面上显示旧信息」这一条）加**一个端点**（`POST /api/auth/refresh`，请求体 `{refreshToken}`，响应 `{token, refreshToken, expiresInSeconds, user}`，与登录响应同形；少一个键就少一条退路）。**为什么值得**：页面的寿命是「一直挂着、或随时打开」，而访问令牌只有 1 小时、刷新令牌是 30 天滑动——不续期就等于用户每过一小时被赶去登录一次，续期把那个每小时一次的打断换成一个用户看不见的请求。**代价是失败模式而不是能力损失**：企业端改了键名、换了端点路径、或改了响应形状，页面**不会硬失败**，而是静默退化成下面那条「跳登录页」的路——有意的选择，宁可退化成「多点一次登录」，也不要留一个只在对方改键名那天才炸的硬依赖。登录态不可用时的处置见下一条——续期在先，跳转在后。
- **登录态缺失先就地续期，续期不成才是一次重定向**：页面没有自己的登录步骤（它只是企业端登录态的消费者），所以「登录态不可用」有三种来源——本地读不到令牌、本地令牌已过期、或中继握手回 `invalid_token`（令牌过期或被吊销）。三者都**先试续期**（刷新令牌还在时；耦合清单见上一条），续不上才把**当前地址**（原样带着 `host=`）当回跳目标、跳到企业端登录页（见「Web 页作为第五种宿主」故事场景 8 / 9）。三条硬约束：① **回跳目标只接受同源站内路径**（以 `/` 开头的相对路径；`//evil.com` 与绝对跨站 URL 一律拒绝）——开放重定向是这条路上唯一真实的攻击面；② **每次会话只自动跳一次**（`sessionStorage` 记标记），跳回后仍没有有效登录态就停在明确提示上，不与登录页来回弹跳——续期同理只自动试一次，否则「续期失败 → 跳登录 → 回来 → 再续期失败」只是把同一场弹跳换了个形式；③ **只在企业端域名上跳**——本地调试（`file:`、`localhost`）没有登录页可跳，那里照旧只提示。收端要给的配合是登录页与 SSO 回调支持这个站内回跳参数，且**不复用 CLI 的 `callback_url`**：那个参数的语义是「把授权码回调到本机 localhost 的 HTTP 服务」（服务端也只放行 localhost，见 `POST /api/auth/code` 的白名单），与「登录完回到哪个站内页面」是两件事，混用只会让白名单变成两种语义的叠加。
- **握手完成前一个业务帧都不能发**：中继把「未认证连接发来的任何帧」一律当 `auth` 帧解析，解析不过即 4003 永久关闭（不重连）。而页面挂载、会话就绪这类事件随时可能早于握手完成，因此出站队列必须闸在 `auth_ok` 之后——抢跑一帧就再也连不上。回程那五个控制帧（`auth_ok` / `auth_error` / `peer_disconnected` / `resync_required` / `pong`）同理一个都不许进 agent 桥，这条纪律与中继控制层那条用户故事完全一致。
- **有效单帧上限取三者最小值**：本机未发送**累积**缓冲 4 MiB、中继 `maxPayload` 4 MiB、**中继每订阅者缓冲 1 MiB**。我们的单帧预算（512 KiB）按**最小的那个**定，并留出余量给同时在途的其它帧。⚠️ 这两条中继侧的闸语义不同、别混：`maxPayload` 越界是**关连接**（1009），订阅缓冲越界只是**丢这一帧 + 要求重同步**——后者不会报错，只会让手机静默少一页，因此**不能指望「中继会拦住」来替代本机自己守预算**。把中继的阈值调大也不解决问题（弱网手机照样撞），只会把丢弃点往后推。
