# 功能规格说明：Webview 链接与文件路径解析

**创建日期**：2026-08-21

> 本规格覆盖 VS Code / JetBrains / Desktop 共享 webview（`packages/webview`）中消息 markdown 渲染的链接与文件路径点击行为。宿主路由（desktop 的 localhost 预览面板分流、文件面板）见 [桌面应用](desktop-app.md)，此处不重复。

## 用户场景与测试 _（必填）_

### 用户故事：行内代码中的链接可点击（优先级：P1）

作为用户，我希望助手文本 markdown 中位于行内代码（反引号）里的 http(s) 链接也能像普通链接一样被解析并点击打开，以便 agent 用代码样式展示 URL 时仍可直接访问，无需手动复制。

**为什么是这个优先级**：agent 输出 URL 时常以反引号包裹（避免被 markdown 误处理），当前这类 URL 渲染为纯文本代码、不可点击，是高频打断阅读的场景。

**独立测试**：渲染包含 `` `https://example.com/a/b` `` 的助手 markdown 文本，验证其保留代码样式（等宽字体 + 底色）同时渲染为可点击链接，点击行为与普通链接一致。

**验收场景**：

1. **假设**助手文本含行内代码 `` `https://example.com/a/b` ``，**当**渲染时，**则**保留代码样式（等宽字体 + 底色），同时渲染为可点击链接；点击行为与普通链接一致——desktop 上 localhost 链接在预览面板打开、其余链接用系统浏览器，IDE 上按原生链接处理。
2. **假设**行内代码内容不是合法 http(s) 链接（如 `` `var x = 1` ``、`` `www.example.com` ``（无协议）、相对路径 `` `/foo` ``），**当**渲染时，**则**保持纯代码样式，不可点击。
3. **假设**行内代码内是 `[text](url)` 形式的 markdown 链接语法原文，**当**渲染时，**则**保持代码原文展示，不按链接语法解析——仅提升裸 URL。
4. **假设**行内代码 URL 首尾带常见标点（如 `` `https://example.com.` `` 或 `` `（https://example.com）` ``），**当**渲染时，**则**链接可点击，且首尾标点不进入链接目标。
5. **假设**行内代码内容为 `javascript:` 等非 http(s) 协议，**当**渲染时，**则**不得生成链接。

### 用户故事：行内代码中的文件路径可点击打开（优先级：P1）

作为用户，我希望助手文本 markdown 中位于行内代码（反引号）里的文件路径可以点击打开——desktop 端在文件面板中预览文件内容，IDE 插件直接在 IDE 中打开该文件——以便快速查看 agent 提到的文件，无需手动复制路径。

**为什么是这个优先级**：agent 输出文件路径时几乎总是用反引号包裹，查看/定位这些文件是高频操作；write/read 工具块已支持打开，消息正文是同一能力的自然延伸，复用既有宿主链路（desktop `openFile` → 文件面板、IDE `openFile` RPC），实现成本低。

**独立测试**：渲染包含 `` `src/main.ts` `` 的助手 markdown 文本，验证其保留代码样式同时渲染为可点击；点击后 desktop 打开文件面板显示该文件内容，VSCE/JetBrains 在 IDE 中打开该文件。

**验收场景**：

1. **假设**助手文本含行内代码 `` `src/main.ts` ``，**当**渲染时，**则**保留代码样式（等宽字体 + 底色）同时渲染为可点击路径；点击后 desktop 在文件面板打开并显示内容、IDE 在编辑器中打开该文件。
2. **假设**路径带行号后缀（`` `src/main.ts:42` ``），**当**渲染并点击时，**则**解析出行号并随打开请求传递；desktop 文件面板与 IDE 均定位到第 42 行。
3. **假设**行内代码是绝对路径（`` `/Users/me/proj/src/main.ts` `` 或 `` `C:\Users\me\proj\src\main.ts` ``），**当**渲染时，**则**同样可点击，点击按绝对路径直接打开。
4. **假设**行内代码是相对路径（`` `./src/utils/parse.ts` `` 或 `` `../lib/index.ts` ``），**当**渲染时，**则**可点击，打开时以当前会话工作目录为基准解析。
5. **假设**行内代码不是文件路径——普通代码表达式（`` `var x = 1` ``）、含空白文本、无已知扩展名的裸文件名（`` `main` ``）、版本号（`` `1.2` ``），**当**渲染时，**则**保持纯代码样式，不可点击。
6. **假设**行内代码是 URL（`` `https://example.com/a/b` ``），**当**渲染时，**则**仍按行内代码 URL 规则渲染为可点击链接（浏览器/预览面板打开），不被当作文件路径。
7. **假设**点击的路径对应文件不存在、已被删除或无法读取（如 desktop 远程会话路径不可达），**当**打开时，**则**遵循宿主既有打开失败行为（IDE 显示错误通知、文件面板显示错误态），不崩溃、不静默。
8. **假设**行内代码含文件名但扩展名不在已知扩展名白名单（`` `report.final` ``），**当**渲染时，**则**不判定为文件路径（避免误判）；但若内容含路径分隔符（`` `docs/report.final` ``），**则**仍判定为路径。

## 边界情况

- **行内代码内含多个 URL（如 `` `https://a.com https://b.com` ``）怎么办？** 内容整体不是单个 URL，保持代码原文、不生成链接，避免歧义。
- **围栏代码块中的 URL 怎么办？** 不处理，保持代码块原文，用户仅期望行内代码场景。
- **推理（reasoning）文本块中的行内代码怎么办？** 与助手文本一致——共用同一 markdown 渲染路径，行为自然对齐。
- **安全如何保证？** 仅 http(s) 协议被提升为链接，`javascript:` 等危险协议不生成链接；渲染结果仍经 DOMPurify 过滤。
- **文件路径如何判定（避免误判）？** 采用启发式白名单：含路径分隔符（`/`、`\`）、以 `./` 或 `../` 开头、扩展名命中已知代码/配置文件扩展名表、或命中常见点文件/知名文件名（`.gitignore`、`Makefile`、`package.json` 等）→ 判定为路径；含空白、含 `()` `[]` `{}` `*` `+` `=` `<` `>` `|` `&` `^` `"` `'` `;` 等特殊字符、纯数字后缀（`1.2`）→ 不判定。判定不做文件存在性预检查（纯文本启发式），文件是否存在由宿主在打开时处理。
- **行号后缀如何解析？** 仅识别形如 `path:行号`（行号为纯数字）的后缀并拆出行号；无法解析的数字后缀（如冒号后非数字）不拆分，按整体路径处理。
- **点击后的视觉反馈？** 路径保持代码样式并附加链接感（悬停手型、下划线），与行内代码 URL 的提升一致；无已知扩展名的裸文件名不误标。
